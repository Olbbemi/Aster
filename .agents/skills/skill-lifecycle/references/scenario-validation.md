# 시나리오 준비와 검증 절차

이 문서는 `skill-lifecycle`에서 시나리오 초안을 준비하고 사용자와 확정한 뒤 실행하고 판정하는 절차를 정의한다.
구조 설계부터 동작 검증까지 적용하며, 호환성 검증에도 범위 선정, 확정, 변경, 결과 대조와 시험 정리 기준을 적용한다.

단계의 진입과 완료는 각 단계 문서를, 도구의 호출 방법과 실행 제한은 해당 도구의 사용 계약을 따른다.

## 초안 작성과 보완

요건 정의에서 검증할 동작과 판정 기준을 정하고, 구조 설계가 정리되면 구현을 시작하기 전에 시나리오 초안을 작성한다.
구현과 기계 검사에서 요건, 구조 또는 변경 영향이 달라지면 초안도 보완한다.

- 작업 유형에 따른 범위와 사례 선정은 [검증 원칙](../../../../standards/skills/skill-validation.md#검증-원칙)을 따른다.
- 통합과 폐기는 작업 유형에 따른 기대 상태와 영향을 받는 기존 사용 사례를 반영한다.
- 사례의 종류와 선정 기준은 [동작 검증](../../../../standards/skills/skill-validation.md#동작-검증) 또는
  [호환성 사례 선정](../../../../standards/skills/skill-validation.md#호환성-사례-선정) 중 해당 검증의 기준을 따른다.
- 사례가 연결되지 않은 검증 대상 요건은 미정 사항으로 표시한다.
  초안의 세부 입력과 환경에 남은 미정 사항은 사용자 검토에서 보완하며, 미정을 적용 제외로 처리하지 않는다.

| 초안 항목 | 작성 내용 |
| --- | --- |
| 식별자와 목적 | 무엇을 확인하는 사례인지 |
| 대응 요건과 선정 근거 | 검증할 요건, 해당 사례가 필요한 이유와 필수 여부 |
| 사전 조건과 입력 | 준비할 상태와 대표 요청 |
| 실행 흐름 | 진행 순서와 확인할 지점 |
| 기대 결과와 판정 기준 | 실제 동작과 산출물에서 관찰할 결과 및 충족 기준 |
| 실행 환경과 미정 사항 | 대상 CLI, 필요한 환경과 아직 결정하지 못한 조건 |

계획은 대상 스킬 명세서의 "확정한 시나리오와 실행 조건" 항목 또는 그 항목에서 연결한 작업 자료 한 곳에 둔다.
구조 설계의 "동작 검증 시나리오 초안"에는 해당 위치와 준비 상태를 연결한다.

저장 위치는 [공유 작업 데이터 접근](../../../../AGENTS.md#공유-작업-데이터-접근)을 따른다.
초안이나 선행 기록이 있다는 사실은 동작 검증 단계의 진입, 사용자 확정 또는 실행 완료를 뜻하지 않는다.

새로 작성하거나 현재 작업 범위에서 보완하는 요건/계획/결과 표는
[시나리오 기록 대조 형식](../../../../standards/skills/scenario-records.md)을 따른다.
상세 입력과 환경은 해당 표에서 기존 정본을 연결한다.

## 시험 환경

동작 검증에서 내부용 스킬은 저장소 사용 구조를 기준으로 하고, 쓰기가 필요한 시험은 격리한다.
플러그인은 설치 전에 변경한 스킬과 필요한 참조 문서, 템플릿 및 공용 자료를 실제 배치 구조에 맞춰 격리된 시험용 위치에 복사한다.

시험용 사본의 출처와 변경 상태, 배치 및 호출 조건을 확인하고 실제 설치본의 인식 결과와 구분한다.

호환성 검증은 [해당 단계](stages/compatibility-validation.md)에 따라 실제 사용 환경을 준비한다.
전체 사례 실행 전에 필요한 실제 로드 위치, 자료 접근과 권한을 대표 호출로 확인한다.
그 관찰로 충족한 항목은 본 검증의 근거로 사용하고 같은 확인을 반복하지 않는다.

두 검증 모두 준비할 때부터 아래 [시험 생성물과 임시 기록 정리](#시험-생성물과-임시-기록-정리)의
사전 상태 및 생성 경로 추적을 적용한다.

## 사용자 검토와 확정

기계 검사 완료 후 실제 동작 검증을 시작하기 전에, 변경 영향을 반영한 시나리오 묶음을 사용자에게 제시하고 확정한다.
검증할 요건과 사례의 대응, 입력과 기대 결과, 판정 기준, 실행 범위와 환경, 종료 조건을 함께 확인한다.
제외하거나 확인하지 못하는 항목과 그 이유도 제시한다.

호환성 검증도 같은 방식으로 호환성 목적에 맞는 사례 묶음을 실행 전에 확정한다.
[모델 제안과 승인](lifecycle.md#모델-제안과-승인)에 따라 필요한 모델 선택을 이 실행 승인과 함께 제시한다.

위 기록 형식을 적용한 묶음은 사용자 확정 전에
[검사 스크립트 사용 가이드라인](../../../../tools/guidelines.md)과
[시나리오 기록 대조 안내](../../../../tools/references/check-scenario-records.md)에 따라 `plan` 모드로 확인한다.
기록 대조 통과와 실제 사용자 확정을 구분한다.

실행 부담과 정리 범위는 다음 내용으로 설명한다.

- 사용할 CLI와 사례별 호출 수, 한 번의 요청으로 끝나는지 또는 후속 대화가 필요한지.
- 사본 준비, 설치나 업데이트, 필요한 권한과 사용자 작업.
- 오래 걸리거나 모델 사용량이 커질 것으로 예상되는 부분과 추정의 불확실성.
- 재시도 범위, 중단 조건과 시험 후 삭제할 범위.

정확한 토큰 수의 사전 계산을 요구하지 않으며 시간과 사용량의 추정을 확정 수치로 제시하지 않는다.

- 모의 승인을 사용하는 시험은 허용 범위를 함께 확인한다.
- 사용자와 확정한 사례, 조건과 합의 근거를 명세서에 반영한 뒤 시험을 실행한다.
  실행에 필요한 미정 조건이 남아 있으면 해당 시험을 시작하지 않는다.
- 확정 단위는 시나리오 묶음이다.
  같은 실행 승인으로 진행할 수 있는 개별 입력마다 현재 사용자에게 승인을 반복 요청하지 않는다.
  시험 대상 스킬의 승인 조건과 합의한 모의 승인 범위는 유지한다.
- 시나리오의 사용자 확정 여부와 실행 환경의 준비 상태는 동작 검증의 진입 조건에서 확인한다.
  기계 검사 통과만으로 실제 시험 실행이 승인되었다고 판단하지 않는다.

## 실행과 역할

Codex에서 동작 검증을 진행할 때는 현재 세션이
[시나리오 공통 실행기](../../../../tools/references/scenario-runner.md)로 별도 Codex 세션을 실행하는 방식을 기본으로 한다.
기본 방식으로 수행할 수 없으면 이유와 필요한 실행 방법을 사용자와 별도로 논의한다.

1. 현재 세션이 확정한 시나리오에 따라 시험 환경과 입력을 준비한다.
2. 공통 실행기로 입력을 전달한다.
   첫 요청은 새 Codex 세션을 시작하고, 후속 요청은 같은 시험 세션을 재개한다.
3. 현재 세션이 수집한 응답, 로그와 실제 파일을 기대 결과에 대조한다.
4. 합의한 범위와 종료 조건에 따라 다음 입력을 전달하거나 시험을 종료한다.

- 실행기는 전달과 근거 수집을 담당하며, 시나리오 통과 여부는 현재 세션이 판단한다.
  실행기의 정상 종료만으로 시나리오를 통과 처리하지 않는다.
- 시나리오 누락과 사용자 확정 여부도 실행기가 자동 검사하는 항목이 아니므로 현재 세션이 확인한다.
- Claude를 이용한 교차 검증은 [교차 검증 단계](stages/cross-validation.md)의 별도 절차로 유지한다.
- 기본 실행 방식이 [지원 CLI별 호환성 검증](stages/compatibility-validation.md)을 대신하지 않는다.
  해당 검증의 실행 방법에 제약이 있으면 사용자와 논의하며, Codex 결과를 다른 CLI의 통과 근거로 사용하지 않는다.

## 결과 대조와 완료 판단

확정한 시나리오 목록과 실제 실행 내역을 사례 식별자 및 대응 요건으로 대조한다.
각 사례에 기대 결과, 실제 결과, 판정과 근거를 연결하고, 실행하지 않은 사례도 목록에 남긴다.
검증할 요건이나 확정한 사례가 결과에서 빠지지 않았는지 확인한다.

위 기록 형식을 적용한 묶음은 [시나리오 기록 대조 안내](../../../../tools/references/check-scenario-records.md)의
`results` 모드로 표의 대응과 누락을 확인한다.
기록 대조 결과와 실제 사례별 상태를 구분하고 아래 기준으로 완료 여부를 판단한다.

| 상태 | 의미 |
| --- | --- |
| 통과 | 실제 동작과 산출물이 판정 기준을 충족함 |
| 실패 | 실제 결과가 판정 기준을 위반함 |
| 미실행 | 시험을 실행하지 못함 |
| 미판정 | 실행했지만 근거 부족 등으로 판단하지 못함 |

- 실패 원인은 스킬 결함, 시험 설계 문제와 환경 제약을 구분하고, 확인하지 못한 원인은 미확정으로 기록한다.
- 미실행과 미판정은 사용자와 원인 및 후속 처리를 논의한다.
- 환경이나 시험 설계 문제는 원인을 해결한 뒤 미확인 부분과 확인에 필요한 선행 절차만 재시험한다.
  한 사례의 여러 요건은 관찰 결과를 구분하고 이미 충족한 항목의 근거를 재개에 활용한다.
- 스킬 수정이 필요하면 변경 영향에 따라 동작 검증과 필요한 교차 검토를 수행한 뒤,
  플러그인은 재배포하고 내부용은 실제 사용 환경에 변경을 반영하여 호환성을 확인한다.
- 제외나 보류할 근거가 있으면 사용자와 합의하고
  [검증 범위 변경과 완료 판단](lifecycle.md#검증-범위-변경과-완료-판단)에 따라 요건, 검증 범위와 완료 기준을 갱신한다.
  미검증 사실, 처리 근거와 남은 영향을 기록하며, 기존 결과를 통과로 바꾸지 않는다.
- 변경 후 범위에 남은 필수 요건과 필수 사례가 모두 통과해야 해당 시나리오 검증을 완료한다.
  필수 항목의 실패, 미실행과 미판정은 완료를 막는다.
  시나리오 결과 대조와 별도로 해당 단계의 나머지 완료 조건도 충족해야 한다.

## 확정 후 변경과 재실행

| 변경 | 처리 |
| --- | --- |
| 검증할 요건이나 사례의 추가, 제외, 보류 | 변경 이유와 영향을 제시하고 다시 확인받는다. |
| 기대 결과, 판정 기준, 실행 범위나 환경, 모의 승인 또는 종료 조건의 의미 있는 변경 | 변경된 조건을 적용하기 전에 사용자에게 다시 확인받는다. |
| 같은 검증 목적과 기준을 유지하는 오탈자, 잘못된 경로와 실행 명령 오류 수정 | 별도 재확인 없이 수정하고 이유를 기록한다. |
| 같은 조건의 재실행 | 합의한 실행 범위 안에서 원인을 확인하고 필요한 조치를 마친 뒤 진행한다. |

같은 목적을 유지하는 세부 수정과 실행 조건 자체가 달라지는 변경을 구분한다.
변경된 계획과 합의 근거는 적용 전에 명세서에 반영하고, 재실행 결과와 현재 유효한 판정을 갱신한다.

이전 실패나 미판정의 관찰과 근거는 재개와 판정에 필요한 동안 유지하며, 원인이나 조건의 변화 없이 반복하지 않는다.
스킬의 요건이나 구현을 보완해야 하면 [단계 전이](lifecycle.md#단계-전이)에 따라 필요한 단계로 돌아간다.

## 시험 생성물과 임시 기록 정리

동작 검증과 호환성 검증의 시험용 사본, 입력, 로그와 시험 산출물은 판정, 필요한 후속 검토와 재시험에서 사용을 마치면 정리한다.
생성 경로와 삭제 상태를 별도 임시 작업 기록으로 추적하고 이 기록은 마지막에 삭제한다.

독립 교차 검토 문서와 생명 주기 명세서/history는 시험별 임시 기록으로 취급하지 않는다.

1. 시험 준비 전 기존 상태를 확인하고, 해당 시험에서 생성한 파일의 경로를 임시 작업 기록에 모아 반영한다.
2. 시험 종료 후 필요한 결과 대조와 보고를 마치고, 후속 검토나 재시험에 사용할 자료가 남아 있는지 확인한다.
   필요한 동안은 자료와 임시 기록을 유지한다.
   자료를 삭제했다는 이유로 미실행이나 미판정을 통과로 바꾸지 않는다.
3. 삭제 전에 판정/재현에 필요한 내용이 명세서 또는 결과 기록에 보존되었는지 확인한다.
   - 완료 단계의 최종 선별/이관은 [완료 산출물 정리와 보존](completion-records.md)을 따른다.
   - 용도가 끝난 파일은 기록과 실제 파일을 대조해 해당 시험에서 만든 파일만 삭제한다.
   - 다른 파일의 보존과 정리 대상의 삭제 완료를 확인한다.
4. 정리가 모두 끝나면 명세서의 판정, 이유와 남은 사항을 갱신하고 정리 결과를 기록한다.
   삭제된 자료의 참조를 제거한다.
   원시 입력이나 로그 전체를 명세서나 다른 파일로 복사해 영구 보관하지 않는다.
   임시 작업 기록도 마지막에 삭제한다.

시험 파일이 들어 있다는 이유로 상위 디렉토리 전체를 삭제하지 않는다.
디렉토리 전체 삭제는 해당 시험에서 만든 항목만 있음을 확인한 경우에만 수행한다.

기존 파일과 다른 작업의 파일은 보존하고, 기존 파일의 수정은 생성과 구분하여 삭제 대상으로 취급하지 않는다.
소유가 불명확하거나 삭제에 실패한 항목은 임의로 지우지 않고 임시 기록에 남겨 해결한 뒤 정리한다.

단계별 입력 및 상세 실행 근거의 기록 요구는 이 보관 기간 안에서 적용한다.
정리 후에는 명세서의 판정과 이유로 완료를 판단하며 삭제된 원시 파일의 계속 존재를 요구하지 않는다.
