# 완료 산출물 정리와 보존

`completed` 단계에서 완료 판단에 앞서 수행한다.
현재 lifecycle 작업에서 만든 명세서와 관련 산출물 전체를 검토하여 필요한 기록만 정리하고 [전용 작업 자료 배치](work-data.md#완료-기록의-배치)의 Git 관리 경로로 이관한다.

작업 대상 스킬 소스, todo와 다른 작업의 자료는 선별 및 이관 대상에서 제외한다.
이미 완료된 다른 작업도 일괄 이관하지 않는다.

## 선별 기준

최종 명세서는 반드시 보존한다.

### 명세서를 최종 보고서로 정리

완료 시에는 명세서 전체를 새 세션에서 처음 읽는 독자를 기준으로 다시 검토한다.
각 항목에는 작업의 목적, 최종 결정, 실제 변경과 검증 결과를 이해하는 데 필요한 내용만 남긴다.

문장의 표현만 고치는 것으로 정리를 마치지 않는다.
필수 단계와 기록 제목은 유지하며 각 항목을 아래 기준으로 다시 작성하거나 정본에 연결한다.

| 기록 항목의 성격 | 최종적으로 남길 내용 |
| --- | --- |
| 문제/범위/요건 | 해결한 문제, 확정된 대상과 요건, 범위 및 중요한 제외 사유 |
| 설계/구현 | 채택한 구조와 계약, 실제 변경한 동작/파일, 결정에 필요한 이유와 상세 정본 링크 |
| 검증/실패/보완 | 검증 대상과 환경, 실제 수행 범위와 관찰 결과, 판정, 주요 실패 원인과 보완 결과 및 한계 |
| 사용자 승인 | [승인 기록 정리](#승인-기록-정리)에 따른 체크리스트와 적용 범위, 조건/예외 및 근거 |
| 조건 확인/단계 이동 | 실제 판단과 근거 위치. 반복되는 설명은 해당 결과의 정본을 참조하고, 중요한 복귀/재작업 이유는 보존 |
| 후속 확인/미확인 사항 | 해결된 사항은 결과나 근거 링크로 갱신하고, 남은 사항은 사유와 완료 판단에 미치는 영향 및 필요한 조치를 기록 |

- 같은 사실이나 결정은 한 곳에서 정의하고 다른 항목에서는 참조한다.
  표, 체크리스트나 설계 정의를 다시 긴 문장으로 풀어 쓰지 않는다.
- 발언 순서, 짧은 승인 응답 인용, 반복된 진행 보고와 중복 요약을 제거한다.
  폐기한 초안은 현재 결정이나 중요한 실패를 설명하는 데 필요한 이유만 남긴다.
- 효력이 끝난 계획과 해결된 대기 상태는 실제 결과로 바꾼다.
  검증 당시의 사실과 이후 Git 반영 등 별도 절차의 상태를 구분하여 시점이 다른 기록을 모순되게 만들지 않는다.
- 판단 근거 없이 반복한 "확인했다"나 "완료했다"는 구체적인 결과와 근거로 통합한다.
  작성 안내와 자리표시자는 제거하며, 적용 제외와 내용 없음은 해당 항목의 기록 규칙에 따라 구분한다.
- 승인 범위, 적용 조건과 예외, 주요 실패/보완 및 미검증 범위를 보존한다.
  미승인을 승인으로, 미실행이나 실패를 통과로 바꾸지 않는다.

### 승인 기록 정리

최종 보고서로 정리할 때 진행 중의 승인 기록을 실제 근거와 대조하고 체크리스트로 변환한다.
각 승인을 담당하는 항목에서 정리하며 같은 승인 목록을 여러 곳에 만들지 않는다.

- `[x]`는 실제 확인한 승인에만 사용하며 승인 대상, 확정된 범위와 조건/예외 및 근거를 함께 적는다.
- `[ ]`는 필요한 승인이 아직 없거나 확인되지 않은 상태에 사용하며 미승인 사유나 남은 판단을 적는다.
- 적용되지 않는 승인은 체크하지 않고 `해당 없음`과 사유를 적는다.
- 짧은 승인 응답이나 대화 순서를 나열한 기록은 승인 사실과 범위로 정리한다.
  원문이 판단에 꼭 필요하면 필요한 근거만 보존하고 연결한다.
- 체크 표시는 실제 사용자 승인, 단계 진입/완료 조건 확인이나 검증을 대신하지 않는다.
  기계 검사 통과나 이전 단계의 승인만으로 새 승인 항목을 체크하지 않는다.

### 보조 자료의 선별

다음 자료는 명세서에 없는 유용한 정보가 있을 때만 별도 파일로 남긴다.
파일명이나 형식만으로 보존 여부를 정하지 않는다.

| 후보 | 보존할 정보 |
| --- | --- |
| 검증 결과 | 대상 버전/상태, 환경, 기준, 실제 관찰, 판정과 한계 |
| 실패와 보완 근거 | 주요 실패 원인, 수정 이유와 재시험 결과 |
| 핵심 시험 시나리오 | 향후 회귀 확인에 필요한 사전 조건, 입력과 기대 결과 |
| 설계 결정 자료 | 선택한 방식, 중요한 대안과 기각 이유, 적용 조건 |
| 교차 검증 자료 | 최종 판단에 영향을 준 지적, 수용/반박 근거와 후속 검증 |
| history | 명세서나 Git 이력에 없는 변경 경위와 재작업 이유 |

원시 대화/실행 로그, 임시 프로젝트/설치 사본, 중간 초안, 반복 출력,
일회성 전체 해시 목록과 변경 패치는 기본 보존 대상에서 제외한다.

특정 결함의 재현 등에 꼭 필요한 입력이나 발췌는 목적을 설명하고 필요한 범위만 보존한다.
원시 자료 전체를 다른 파일로 복사하여 정리를 대신하지 않는다.

history의 유용한 내용을 명세서나 보존 문서에 통합했다면 완료 묶음에 history를 별도로 요구하지 않는다.
진행 중 history 기록 의무는 유지한다.
교차 검증을 수행했다면 재개에 필요한 검증 대상과 마지막 회차 번호도 보존 문서에 유지한다.

다른 작성자의 검토 원문과 이전 review는 임의로 다듬지 않는다.
필요한 판단을 출처/작성자/검증 대상과 함께 별도 요약하거나 원문 자체를 보존한다.
요약에서 원래 지적의 뜻, 처리 근거와 미해결 여부를 유지한다.

## 정리와 이관

1. 현재 작업 루트와 명세서가 참조하는 산출물을 확인한다.

   - 자료별로 별도 보존, 다른 기록에 통합, 정리, 로컬 유지 중 어떻게 처리할지 정한다.
   - 공유 자료와 다른 작업의 원본은 참조 관계만 확인하고 임의로 이동/삭제하지 않는다.

2. [명세서를 최종 보고서로 정리](#명세서를-최종-보고서로-정리)하고 필요한 파일만 남긴다.

   - 명세서만으로 충분하면 별도 결과/이력 파일을 만들지 않는다.
   - 상세 근거가 필요하면 관련 기록에서 그 정본을 참조한다.

3. 대상 스킬과 작업명에 맞는 보존 경로를 확인하고 정리한 파일을 옮긴다.

   - 목적지가 다른 작업과 충돌하면 덮어쓰지 않는다.
   - 같은 작업의 부분 이관이면 양쪽 내용을 대조하여 누락/중복 없이 이어간다.

4. 보존본을 직접 읽어 [최종 보고서 확인](#최종-보고서-확인)을 수행한다.

   - [검사 스크립트 사용 가이드라인](../../../../tools/guidelines.md)과
     [완료 보고서 모드](../../../../tools/references/check-references.md#완료-보고서-모드)에 따라
     현재 보존 묶음의 로컬 참조를 검사한다.
     - 미추적 파일의 커밋 필요 목록은 [완료와 Git 반영](#완료와-git-반영)에 따라 커밋 대상 확인에 사용한다.
   - 파일 간 링크와 재현 명령의 경로를 새 위치에 맞추고,
     개인 절대 경로, data의 원본 또는 삭제할 자료 없이도 완료 판단을 이해할 수 있는지 확인한다.
   - 검증 대상은 확인한 커밋이나 버전으로 식별한다.
     - 미커밋 상태를 검증했다면 기준 커밋과 변경 범위를 구분한다.
     - 아직 생성하지 않은 결과 커밋을 근거로 적지 않는다.

5. 대조를 통과하면 보존 명세서를 정본으로 전환하고 기존 참조를 갱신한다.

   - 이동한 파일의 중복 사본과 용도가 끝난 자료만 정리한다.
     - history를 통합했다면 재개에 필요한 내용이 보존되었는지 확인한 뒤 중복 원본을 정리한다.
   - 계속 필요한 로컬 자료는 기존 보관 기준에 따라 유지하되 보존본의 이해에 필수인 근거를 로컬 자료에만 두지 않는다.

6. [시험 정리](scenario-validation.md#시험-생성물과-임시-기록-정리)를 마치고,
   명세서의 기존 완료 판단 근거 항목에 보존 위치와 선별/통합/정리 결과를 간결하게 적는다.

   - 이관 실패, 누락이나 필수 참조 문제가 있으면 미완료로 기록하고 해결한 뒤 완료를 판단한다.

복사 후 검증하는 방식으로 이관할 때는 검증을 마치기 전에 원본을 삭제하지 않는다.
부분 실패 시 확인된 원본과 이관본을 유지하며 어느 위치가 정본인지 기록한다.
보존 파일을 확인하지 않고 디렉토리 이동만으로 완료 처리하지 않는다.
이관 도중의 복사본을 각각 수정하는 이중 관리는 하지 않는다.

## 최종 보고서 확인

완료를 판단하는 에이전트는 새 세션의 독자가 보존 명세서와 연결된 보존 자료만 읽는 상황을 기준으로 대조한다.
형식 검사 통과와 별개로 아래 내용을 실제 본문과 근거에서 확인한다.

- 어떤 문제를 어떤 범위에서 해결했고 무엇을 변경했는지 식별할 수 있다.
- 최종 설계와 구현, 요건별 검증 결과가 연결되며 계획과 실제 수행 결과가 구분된다.
- 승인 기록이 [승인 기록 정리](#승인-기록-정리)에 따른 형식이며 범위, 조건/예외 및 근거를 확인할 수 있다.
- 미해결 사항, 중요한 실패/보완과 미검증 범위가 남아 있으며 완료 판단과 모순되지 않는다.
- 필수 항목과 의미를 유지하면서 대화 나열, 중복 정의, 효력이 끝난 계획 및 작성 안내를 제거했다.
- 개인 절대 경로, 삭제할 자료나 Git에서 제외한 원본 없이 목적, 결정과 결과를 이해할 수 있다.

확인 결과와 중요한 정리 내용은 명세서의 기존 완료 판단 근거 항목에 한 번만 기록한다.
답을 찾을 수 없거나 근거가 모순되면 관련 항목을 보완하고 다시 대조한 뒤 완료를 판단한다.

## 완료와 Git 반영

- 보존 위치와 실제 커밋 여부를 구분하여 보고한다.
  - 이관만 마친 상태를 Git 이력에 보존한 것으로 표현하지 않는다.
- 커밋, 푸시와 PR은 이관과 별도로 [Git 운영 규칙](../../../../.github/git-workflow.md)의 승인 절차를 따른다.
- 완료 기록과 그 기록에서 연결한 새 로컬 자료는 함께 커밋 대상에 포함한다.
  - 미추적 파일(`git status --short`의 `??`)도 포함하며 이미 커밋된 자료는 기존 파일을 참조한다.

- 커밋 준비 시 참조 검사의 미추적 파일 목록과 실제 변경 파일을 대조하여 필요한 자료가 빠지지 않았는지 확인한다.
  - 이 목록만으로 작업 전체의 커밋 대상을 결정하지 않으며, 승인 후 실제 스테이징된 변경에도 누락이 없는지 확인한다.

- 완료 후 같은 작업을 보완하는 경우의 정본과 중간 자료 위치는
  [완료 기록의 배치](work-data.md#완료-기록의-배치)를 따른다.
