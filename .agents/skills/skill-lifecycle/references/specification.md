# 단일 명세서 형식

## 목적과 적용 범위

- 대상 스킬의 작업 내용과 판단 근거를 하나의 명세서에 일관된 형식으로 기록하도록 한다.
- 명세서는 대상 스킬의 생성, 변경, 통합, 폐기 중 선택한 작업 유형을 기준으로 작성한다.
- 명세서의 프론트매터, 본문 구조와 각 단계에 공통으로 적용할 기록 기준을 정의한다.
- 단계별로 수행할 작업이나 검증의 상세 절차는 이 문서에서 다시 정의하지 않는다.

## 관련 문서와 역할

- [lifecycle.md](lifecycle.md)는 단계의 순서와 진행, 복귀 및 완료에 관한 공통 운영 규칙을 정의한다.
- 각 단계 문서는 `lifecycle.md`에 나열된 단계 식별자를 파일명으로 사용하며, 스킬 디렉토리의 `references/stages/`에 둔다.
- 각 단계 문서의 "단계 운영 규칙"은 해당 단계에서 수행하고 판단할 기준을 정의한다.
- 각 단계 문서의 "명세서 기록 항목"은 해당 단계의 명세서 본문에 무엇을 어떻게 적을지 정의한다.
- 템플릿의 위치와 사용 방법은 [명세서 템플릿](#명세서-템플릿)을 따른다.
- 단계별 작성 지침은 각 단계 문서를 참조하며, `specification.md`와 명세서 템플릿 파일에 반복해서 정의하지 않는다.

## 명세서의 저장 위치와 식별

- 작업 대상 스킬의 실제 파일이 놓이는 경로와 해당 작업의 명세서를 저장하는 경로를 구분한다.
- 새 명세서는 [경로 확정](work-data.md#경로-확정)을 마친 뒤
  확정한 `records/` 작업 루트에서 처음 작성하고 완료 후에도 같은 정본을 사용한다.
- 기존 로컬 명세서는 [기존 작업의 경로](work-data.md#기존-작업의-경로)에 따라 재개한다.
- 공용 규격은 [Aster 작업 규칙의 공유 작업 데이터 접근](../../../../AGENTS.md#공유-작업-데이터-접근)에서 확인한다.
  명세서와 단계별 근거의 위치는 [전용 작업 자료 배치](work-data.md)를 따른다.
- 같은 스킬의 기존 작업 명세서가 있으면 이번 작업을 이어가는 것인지 별도 작업을 시작하는 것인지 확인한다.
- 여러 명세서가 후보이고 요청과 기록만으로 대상을 구분할 수 없으면 사용자에게 확인한다.
- 진행 중인 생명 주기를 이어가는 경우 기존 명세서를 사용한다.
- 별도 작업을 시작하는 경우 기존 명세서를 덮어쓰지 않고 새 명세서의 경로를 정한다.
- 별도 history나 인계 기록이 있으면 이번 명세서의 정본 경로를 연결한다.
  명세서 위치를 기록하기 위한 별도 파일은 만들지 않는다.
- 신규 작업의 이름이나 대상 경로가 미정이면 파일 작성 전에 사용 형태와 이름 및 경로를 함께 정한다.
  기존 미정 명세서를 재개할 때는 같은 작업의 이름이나 경로가 확정되었다는 이유로 새 명세서를 만들지 않는다.
  필요한 경로 전환은 전용 작업 자료 규격에 따라 정본과 참조를 대조하여 수행한다.

### 작업명과 제목

파일명은 `specification.md`로 유지한다.
작업 디렉토리명은 해결할 문제나 변경 결과를 짧고 직관적인 이름으로 표현한다.
상위 경로에서 식별되는 프로젝트나 플러그인 이름을 반복하거나 `update`, `work`만으로 작업을 구분하지 않는다.
예를 들어 `fixed-paths-and-final-format/specification.md`처럼 작업 목적을 나타낸다.
문서 제목도 "스킬 산출물 경로 확정과 커밋 전 문서 검토"처럼 내용을 드러내고,
대상 스킬은 프론트매터와 목적/범위에서 식별한다.
이미 확정한 경로는 표현 개선만을 이유로 일괄 변경하지 않는다.

## 명세서 템플릿

- 템플릿은 `skill-lifecycle` 스킬 디렉토리의 `assets/lifecycle-template.md`에 두며,
  이 문서에서는 [lifecycle-template.md](../assets/lifecycle-template.md)로 참조한다.
- 템플릿에는 `specification.md`에서 정한 프론트매터와 본문 기본 구조를 둔다.
- 단계별 본문 제목은 각 단계 문서의 "명세서 기록 항목"에 맞춘다.
- 템플릿은 새 명세서를 만드는 데 사용하며, 작업 결과는 생성된 명세서에 기록한다.
- [프론트매터](#프론트매터) 절의 정의에 따라 `name`, `target_path`, `operation`을 채우고, 문서 제목의 자리표시자를 실제 작업에 맞게 바꾼다.
- 최초 `current_stage`는 [생명 주기 운영 규칙의 최초 기록의 단계 판단](lifecycle.md#최초-기록의-단계-판단)에 따라 정한다.
  템플릿의 초기값 자체를 완료 판단의 근거로 사용하지 않는다.
- 신규 작업은 이름과 대상 경로를 확정한 뒤 템플릿으로 기록을 시작한다.
  작업 유형이나 관리 대상을 구분할 정보가 부족하면 요청과 기존 자료를 먼저 확인하고, 필요한 사용자 판단을 질문한다.
- 템플릿의 예시 값이나 안내 문구를 실제 작업의 확인 결과나 판단 근거로 사용하지 않는다.

## 명세서의 전체 구성

명세서는 다음 순서로 구성한다.

1. YAML 프론트매터
2. 작업의 목적과 변경 결과를 식별할 수 있는 문서 제목
3. 생명 주기 단계별 본문

- 단계별 본문은 [lifecycle.md](lifecycle.md)의 "생명 주기 순서"에 따라 배치한다.
- 각 단계의 제목에는 단계 식별자와 한글 이름을 함께 적는다.
- 각 단계 아래에는 해당 단계 문서의 "명세서 기록 항목"에 대응하는 내용을 둔다.
- 공통 기록 항목인 "진입 조건 확인", "완료 조건 확인", "단계 이동 기록"은 템플릿의 배치를 따른다.
- 현재 단계는 프론트매터의 `current_stage`로 확인하고, 각 단계의 판단 결과와 근거는 본문에서 확인한다.

## 프론트매터

프론트매터에는 `name`, `target_path`, `operation`, `current_stage`, `in_review` 다섯 필드만 사용한다.

아래는 `skill-lifecycle` 스킬을 새로 만드는 작업의 프론트매터 예시다.
각 필드의 값은 아래 정의에 따라 실제 작업에 맞게 작성한다.

```yaml
---
name: skill-lifecycle
target_path: .agents/skills/skill-lifecycle
operation: create
current_stage: problem-definition
in_review: false
---
```

### `name` (스킬 이름)

- 명세서가 관리하는 대상 스킬의 공식 이름을 적는다.
  새 명세서는 [경로 확정](work-data.md#경로-확정)에서 정한 이름을 사용한다.
  기존 초기 명세서의 YAML `null`은 미정값으로 읽고 문서 제목과 작업 목적 및 명세서 경로로 대상을 식별한다.
- 공식 이름을 확정하면 이 필드를 갱신하고, 실제 스킬 디렉토리명과 `SKILL.md`의 `name`도 같은 값을 사용한다.
  기존 스킬의 이름이 정해져 있다면 미정으로 바꾸지 않는다.
- `null`은 기존 초기 작업 명세서를 읽기 위한 미정값이다.
  실제 `SKILL.md`의 필수 이름 규칙에는 적용하지 않는다.
  이름은 요건 정의를 완료하기 전까지 확정한다.

### `target_path` (대상 경로)

- 실제 스킬 파일이 존재하거나 생성될 디렉토리를 적는다.
- 경로는 Aster 저장소 루트를 기준으로 한 상대 경로를 사용한다.
- 신규 스킬은 [저장소 배치 규격](../../../../standards/repository-layout.md)의 "스킬 배치"에 따라 앞으로 생성할 위치를 정하고,
  아직 디렉토리가 없어도 해당 경로를 적는다.
- 새 명세서는 사용 형태와 이름을 논의할 때 확정한 경로를 사용한다.
  기존 초기 명세서의 YAML `null`은 경로 미정으로 읽고, 요건 정의를 완료하기 전까지 확정한다.
  이미 식별된 대상 경로를 초기화하지 않으며 경로 확정 자체를 디렉토리 생성 지시로 취급하지 않는다.

### `operation` (작업 유형)

- 이번 생명 주기에서 수행할 작업 유형 하나를 적는다.
- 허용값은 다음과 같다.
  - `create`: 스킬 생성
  - `update`: 기존 스킬 변경
  - `integrate`: 스킬 또는 관련 구성 통합
  - `deprecate`: 스킬 폐기
- 문제 정의 본문의 필요성 판단은 `operation`에 지정된 작업 유형을 기준으로 작성한다.

### `current_stage` (현재 단계)

- 현재 진행 중인 생명 주기 단계의 식별자를 적는다.
- 값에는 영문 단계 식별자만 사용한다.
- 허용값과 진행 순서는 [lifecycle.md](lifecycle.md)의 "생명 주기 순서"를 따른다.
- 최초 상태의 판단은 [생명 주기 운영 규칙](lifecycle.md#최초-기록의-단계-판단)을 따른다.
  최초 상태 선정 또는 이후 단계 이동의 사유와 근거는 프론트매터에 중복하지 않고 해당 단계의 본문에 기록한다.

### `in_review` (커밋 전 검토 상태)

- YAML boolean `true` 또는 `false`를 사용한다.
  문자열, 숫자와 `null`은 허용하지 않는다.
- 최초 값은 `false`이며 [커밋 전 검토](commit-review.md)의 각 진입 시점에 `true`로 바꾼다.
  이미 검토 시점에 도달한 작업을 처음 기록하면 `true`로 시작한다.
- 현재 단계 식별자는 그대로 유지한다.
  `true`는 그룹별 정리, 검토와 커밋을 마쳐야 함을 뜻하며,
  `false` 자체가 검토 수행이나 생명 주기 완료의 증거는 아니다.
  검토 시점, 대상, 결과와 커밋 근거는 해당 단계 본문에 기록한다.
- 필드가 없는 기존 명세서는 미확인 상태로 읽는다.
  현재 작업을 재개할 때 실제 근거를 대조하여 필드를 추가하며,
  검토 관문에 도달했거나 검토가 미완료이면 `true`로 설정한다.
  아직 관문 전이면 `false`로 설정하고 후속 진입 때 검토한다.
  다른 작업이나 과거 완료 기록을 일괄 수정하지 않는다.
  표준 형식 검사는 갱신된 다섯 필드를 요구하며 누락을 자동 보정하지 않는다.

## 단계별 본문 기록 기준

### 작업 내용과 결과

- 각 단계 문서의 "명세서 기록 항목"을 읽고 대상 스킬과 이번 작업에 해당하는 내용을 적는다.
- 수행할 계획과 실제로 수행한 결과를 구분하여 적는다.
- 명세서와 해당 시점의 스킬을 함께 읽어 목적, 변경 동작과 기대 산출물을 파악할 수 있게 작성한다.
  요건별 입력/적용 조건, 수행할 동작, 산출물의 내용과 저장 위치 및 종료 조건을 명확히 한다.
  실제 스킬의 구현 위치와 검증 기준 및 결과를 연결하며 파일 목록만으로 설명을 대신하지 않는다.
  상세 정본이 있으면 해당 항목에서 연결하고 [대응 확인](commit-review.md#명세서와-스킬의-대응-확인)으로 대조한다.
- 각 단계 문서의 운영 규칙 전체를 복사하는 대신, 해당 규칙을 적용한 결과와 판단을 적는다.
- 같은 내용이 이미 명세서의 다른 항목에 있으면 해당 항목을 참조한다.
- 같은 주제의 추가 논의는 기존 항목에 통합하고 현재 유효한 내용으로 갱신한다.
  응답이나 날짜마다 새 이력 절을 추가하지 않는다.
  해결된 미정 사항은 확정 내용으로 대체하고, 준비/대기 등 지난 중간 상태는 누적하지 않는다.
  판단에 필요한 변경 경위는 Git 이력이나 생성 기준에 따라 유지하는 history를 참조한다.
- 목적, 범위, 확정 요건, 핵심 설계, 실제 변경과 요건별 최종 판정은 명세서에서 이해할 수 있어야 한다.
  상세 시험 결과는 [부가 문서 생성 기준](work-data.md#기록-루트-안의-배치)에 따라 필요할 때만 분리한다.
  명세서에는 핵심 결과, 판정, 남은 사항과 근거 링크를 유지하며 링크만으로 결과를 대신하지 않는다.
  상세 관찰이나 같은 정의를 여러 항목에 반복하지 않는다.
- 설계 정의는 [구조 설계 산출물](design-artifacts.md)에 따라 표/선언/도식으로 남긴다.
  상세가 길면 논의 그룹별 정본으로 연결하고 명세서에는 전체 구조, 설명과 링크를 둔다.
  필수 기록 제목은 유지하며 같은 정의를 각 항목에 다시 풀어 쓰지 않는다.
- 동작/호환성 시험 자료와 임시 기록의 보관 기간, 삭제 및 정리 후 기록과 참조 처리는
  [시험 정리](scenario-validation.md#시험-생성물과-임시-기록-정리)를 따른다.

#### 논의 내용의 배치

[명세서 기록 트리거](lifecycle.md#명세서-기록-트리거)에 해당할 때 여러 응답과 단계에 걸친 논의를 모아서 반영한다.
현재 단계와 관계없이 해당 내용을 담당하는 기록 항목을 기준으로 배치한다.
제목이 비슷하다는 이유만으로 관련 없는 항목에 넣지 않는다.

| 논의 내용과 기록 항목의 관계 | 기록 방법 |
| --- | --- |
| 대응하는 항목이 명확함 | 해당 항목에 내용과 합의 상태를 기록한다. 이미 정본이 있으면 그 위치를 참조한다. |
| 여러 항목에 걸침 | 내용을 담당할 정본 한 곳에 기록하고 관련 항목에서 참조한다. 같은 내용을 독립적으로 중복 관리하지 않는다. |
| 배치할 항목이 아직 불명확함 | 확정한 기록 루트의 작업 자료에 보존하고, 명세서의 현재 단계에서 미확인 사항을 다루는 항목에 위치, 배치가 불명확한 이유와 관련 단계 후보를 연결한다. 후보도 판단할 수 없으면 미확정으로 적는다. |

- 임시 기록에도 확인한 사실, 합의와 미확정 제안을 구분한다.
  임시 기록이 있다는 이유로 명세서 연결을 생략하지 않는다.
- 대화는 결정 내용, 적용 범위와 후속 판단에 필요한 이유로 압축한다.
  발언자, 대화 순서와 짧은 승인 응답을 서술하지 않는다.
  승인 원문이 증거로 필요하면 해당 근거 문서를 참조한다.
  이를 위해 history의 생성을 강제하지 않는다.
- 압축할 때 승인 범위, 조건, 예외와 미확정 상태를 보존한다.
  단순 질문이나 제안을 합의로 바꾸지 않으며, 결정이나 후속 작업에 영향을 주지 않는 설명은 기록하지 않는다.
- 실제 승인 상태는 [승인 기록](#승인-기록)을 따른다.
- 여러 기술 판단은 대상, 선택, 조건/예외와 근거 위치를 표로 정리한다.
  기술 정의는 정본을 연결하고, 승인 경위나 같은 결정의 설명을 줄줄이 나열하지 않는다.
  근거로 필요한 과거 판단은 이력 자료에서 찾을 수 있도록 보존한다.
- 배치가 정해진 내용은 기록 시점에 해당 항목에 정리하거나 정본을 참조하고 기존 임시 기록과 참조를 갱신한다.
  관련 단계에 진입하지 않았다는 이유로 배치가 명확한 내용을 이번 기록에서 제외하지 않는다.

#### 승인 기록

승인이 필요한 조건과 실제 승인 상태를 구분한다.
진행 중에는 승인 여부, 대상과 범위, 조건/예외 및 근거를 기록하되 체크리스트 등 특정 형식을 강제하지 않는다.

해당 승인을 담당하는 항목 한 곳에 기록하고 다른 항목에서는 참조한다.
조건부 승인은 조건이 붙은 범위로만 기록하며 후속 단계나 변경된 범위의 승인으로 확대하지 않는다.

체크리스트로의 변환은 완료 시 [승인 기록 정리](completion-records.md#승인-기록-정리)에서 수행한다.
명세서 전체의 재정리와 대조도 같은 문서를 따른다.

### 조건 확인과 판단 근거

- 해당 단계의 진입 조건과 완료 조건을 확인한 결과를 기록한다.
- 각 조건의 충족 여부와 판단 근거를 연결하여 적는다.
- 검증 범위나 필수 조건을 변경하기로 합의했다면 [검증 범위 변경과 완료 판단](lifecycle.md#검증-범위-변경과-완료-판단)에 따라
  갱신한 요건, 검증 범위와 완료 기준의 위치 및 합의 근거를 연결한다.
  해당 단계의 판단은 변경 후 기준을 참조하여 적는다.
- 조건을 충족하지 못하면 충족하지 못한 내용과 필요한 후속 작업을 적는다.
- 실제 파일, 명령 실행 결과 또는 외부 문서가 근거라면 해당 자료를 다시 확인할 수 있는 위치를 적는다.
- 근거 자료가 변경될 수 있으면 검토한 대상을 구분하는 데 필요한 버전, 커밋 또는 실행 시점 등을 적는다.
- 외부 검증 기록의 전체 내용을 복사하지 않고 판단에 필요한 결과와 원본 위치를 적는다.

### 미확인 사항과 적용하지 않는 항목

- 확인하지 못한 내용은 확인한 사실과 구분하고, 확인하지 못한 이유를 적는다.
- 단계에 진입하지 않은 상태, 해당 내용을 아직 논의하지 않은 상태, 논의했지만 배치가 미확정인 상태를 구분한다.
  단계의 진입/완료 조건을 판단하지 않았다면 그 항목에 미판정임을 적는다.
- 단계 미진입을 이유로 관련 내용이 있는 본문 항목까지 일괄 `미착수`로 두지 않는다.
  선행 논의나 초안이 있으면 내용 또는 참조와 검토 상태를 기록한다.
  배치 미확정 기록은 [논의 내용의 배치](#논의-내용의-배치)를 따른다.
- 아직 수행하지 않은 작업이나 검증은 수행하지 않았다는 사실을 적는다.
- 기록할 내용이 실제로 없는 경우에만 `없음`으로 적는다.
- 특정 기록 항목이 이번 작업에 적용되지 않는다고 판단하면 적용하지 않는 이유를 적는다.
- 확인하지 못했거나 수행하지 않은 내용을 `없음`으로 표시하지 않는다.
- 이후 단계에서 확인해야 하는 사항은 확인할 내용과 해당 단계를 적는다.

### 단계 이동과 재수행

- 최초 기록의 상태 산정은 선정한 단계의 "단계 이동 기록" 항목에 적고, 출발 단계는 `해당 없음(최초 기록)`으로 구분한다.
  선행 조건 확인 결과의 위치와 선정 근거를 연결하며 과거 전이를 추정하지 않는다.
- 이후 단계 이동 기록에는 출발 단계, 이동할 단계, 이동 사유와 판단 근거를 적는다.
- 이동 기록은 이동을 결정한 단계의 본문에 둔다.
- 프론트매터의 갱신 시점과 전이 가능 여부는 [lifecycle.md](lifecycle.md)와 해당 단계 문서의 "허용 전이"를 따른다.
- 이전 단계로 돌아가 수정했다면 이후 단계의 기존 결과에 미치는 영향과 재수행이 필요한 항목을 적는다.
- 재수행이 필요한 항목은 다시 확인하기 전까지 기존 결과를 현재 유효한 판단 근거로 사용할 수 없음을 표시한다.
- 재수행한 뒤에는 해당 항목의 결과와 근거를 갱신한다.
- 과거 수행 이력의 보관 방식은 [lifecycle.md](lifecycle.md)의 "단계 전이"를 따르며, 명세서 본문에 전체 이력을 누적하지 않는다.

## 명세서 작성 시 확인할 사항

아래 확인은 이번 변경 항목과 직접 연결된 참조, 요약 및 재개 안내를 대상으로 수행한다.
관련 부분만 읽고 정리하며, 다른 부분은 변경 영향이 확인된 경우에만 범위를 넓힌다.
전체 명세서의 재검토를 매 저장의 기본 절차로 삼지 않는다.

- 프론트매터가 본문과 구분되는 YAML 형식인지 확인한다.
- 필드의 값이 `specification.md`에서 정의한 의미와 허용값에 맞는지 확인한다.
- `name`과 `target_path`가 실제 작업 대상과 일치하는지 확인한다.
  기존 초기 명세서의 `null`은 위 필드별 허용 조건에 해당하며 작업 목적과 명세서 경로로 대상을 식별할 수 있는지 확인한다.
  새 명세서는 확정한 이름, 소스 경로와 기록 루트에 따라 작성되었는지 확인한다.
- `operation`이 이번 작업의 유형과 일치하는지 확인한다.
- `current_stage`가 진행 중인 단계와 일치하는지 확인한다.
- `in_review`가 실제 검토 상태와 일치하는지 확인하고,
  관문을 통과한 기록이면 그룹별 검토와 커밋 근거를 대조한다.
- 이번 저장에서 반영할 합의, 변경과 미정 사항을 식별하고, 각각의 실제 본문 또는 참조 위치와 대조한다.
  요약에 언급한 것만으로 관련 항목의 기록까지 완료했다고 판단하지 않는다.
- 이번 변경으로 기존 요약, 재개 안내와 남은 작업 안내가 현재 상태 및 판단과 어긋나지 않는지 확인하고 갱신한다.
  과거 경위를 설명하는 기록은 당시 사실을 유지하되, 현재 안내와 구분한다.
- 이번 기록 대상과 관련 기존 항목에서 중복, 불필요한 대화 경위, 해결된 미정 사항, 지난 중간 상태와 상세 근거 복사를 정리한다.
  필요한 이력과 증거는 작업 기록이나 원본 자료에서 찾을 수 있는지 확인한 뒤 본문을 줄인다.
  전체 문서를 매번 다시 요약하지 않는다.
- [논의 내용의 배치](#논의-내용의-배치)에 따라 대응이 명확한 내용, 여러 항목에 걸친 내용과 배치 미확정 내용을 각각 확인한다.
  임시 기록은 명세서에서 위치와 배치 검토 필요성을 찾을 수 있어야 한다.
- 실제 저장된 내용을 읽고 누락된 본문/참조를 보완한다.
  단계 미진입을 이유로 관련 항목이 `미착수`로 남아 있지 않은지 확인하며, 선행 기록을 단계 완료 근거로 바꾸지 않는다.
- 참조한 파일과 기록의 위치를 다시 찾을 수 있는지 확인한다.

## 최소 형식 검사

표준 템플릿을 사용하는 명세서의 형식을 확인하거나 단계 문서와 템플릿의 제목을 수정했을 때는
[검사 스크립트 사용 가이드라인](../../../../tools/guidelines.md)과
[명세서 형식 검사 안내](../../../../tools/references/check-lifecycle-specification.md)에 따라 필요한 검사를 선택한다.

매 저장마다 실행하거나 기존 명세서를 일괄 변환하는 절차는 아니다.
자체 수정에서 별도로 합의한 축약 기록에는 표준 명세서 본문 검사를 적용하지 않는다.

검사기는 프론트매터와 단계 구조 및 기록 제목의 형식만 확인한다.
기존 초기 명세서의 `null` 허용 조건, 실제 작업 대상, 내용과 참조의 적절성, 승인 및 단계 진입/완료 판단은
위 작성 시 확인 기준과 단계별 운영 규칙에 따라 별도로 대조한다.
검사 통과를 의미 검토나 사용자 승인으로 사용하지 않는다.
