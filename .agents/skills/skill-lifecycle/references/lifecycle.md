# 생명 주기 운영 규칙

이 문서는 `skill-lifecycle`의 단계 순서와 진행, 재개, 복귀 및 완료에 관한 공통 운영 규칙을 정의한다.

- 각 단계의 진입 조건, 수행 작업, 완료 조건, 허용 전이와 기록 지침은 해당 단계 문서에서 정의한다.
- 명세서의 프론트매터, 본문 형식과 공통 기록 기준은 [명세서 형식](specification.md)에서 정의한다.
- 이 문서는 단계별 상세 절차와 명세서 형식을 반복해서 정의하지 않고, 해당 문서를 참조하여 생명 주기를 진행할 공통 원칙을 정한다.

## 생명 주기 순서

스킬 생명 주기의 단계와 완료 조건을 확인하는 순서는 다음과 같다. 논의와 검토용 초안의 작성 순서는 아래 [논의와 기록](#논의와-기록)을 따른다.

1. `problem-definition` (문제 정의)
2. `requirements-definition` (요건 정의)
3. `existing-configuration-review` (기존 구성 확인)
4. `structure-design` (구조 설계)
5. `implementation` (구현)
6. `mechanical-validation` (기계 검사)
7. `behavioral-validation` (동작 검증)
8. `cross-validation` (교차 검증)
9. `compatibility-validation` (호환성 검증)
10. `completed` (완료)

## 단일 명세서

- 스킬의 각 생명 주기는 대상 스킬 명세서 하나를 기준으로 진행하며, 모든 단계에서 같은 명세서를 읽고 작업 결과와 판단 근거를 기록한다.
- 단계별로 별도 명세서를 만들거나, 단계가 바뀌었다는 이유로 명세서 파일을 다른 경로로 이동하지 않는다.
- 명세서의 생성과 저장 위치, 기존 명세서의 재사용 여부는 [명세서 형식의 저장 위치와 식별](specification.md#명세서의-저장-위치와-식별)을 따른다.

## 논의와 기록

- 논의 주제는 단계 순서에 제한하지 않는다. 대화에서 확인한 내용은 관련 단계의 명세서 항목에 정리하며, 기록을 위해 사용자에게 같은 내용을 단계별로 다시 질문하지 않는다.
- 요건을 구체화하기 위한 구조안이나 검토용 초안을 먼저 작성할 수 있다. 확정 내용과 미확정 제안, 초안의 위치와 후속 검토가 필요한 단계를 구분하여 기록한다.
- 선행 초안은 관련 단계에서 기준에 대조하여 재사용할 수 있다. 파일이 존재하거나 후속 주제를 논의했다는 사실만으로 그 단계를 완료하거나 현재 단계를 옮기지 않는다.
- 실제 구현에 적용할 목적, 동작과 검증 기준은 먼저 명세서에 반영한다. 선행 탐색을 명세 없이 확정된 결과물을 구현하는 근거로 사용하지 않는다.

## 명세서 기록 트리거

기록 시점은 논의한 내용을 실제 작업에 적용하기 전, 작업을 마치거나 중단할 때,
사용자가 저장을 요청할 때다. 해당 시점에 여러 응답에서 쌓인 내용을 모아서 반영한다.
논의 중 응답 종료, 주제 변경이나 합의 발생 자체는 저장 시점으로 삼지 않는다.

| 기록 시점 | 기록할 내용 | 처리 기준 |
| --- | --- | --- |
| 논의한 내용을 초안 작성, 구현, 검증 등 실제 작업에 적용하기 전 | 적용할 목적, 합의, 동작과 검증 기준 및 관련 미결정 사항 | 필요한 내용이 이미 반영되어 있으면 재저장하지 않는다. 적용 기준이 바뀌면 바뀐 내용을 적용하기 전에 반영한다. |
| 작업을 마치거나 중단할 때 | 미반영 합의와 미결정 사항, 수행 결과, 파일 위치, 검토 상태와 판단 근거 | 명세서의 현재 상태와 재개에 필요한 내용을 모아서 반영한다. |
| 사용자가 저장을 요청할 때 | 요청 범위에서 현재까지 확인된 내용 | 사용자가 지정한 시점에 반영하며, 시점 지정이 없으면 해당 응답을 마치기 전에 반영한다. |

- 명세서가 없으면 첫 기록 시점에 생성한다. 새 작업을 언급하거나 초기 질문을 주고받았다는 이유만으로 생성하지 않는다.
- 작업 종료나 중단은 수행 중인 작업 범위를 마무리하거나 사용자 요청 또는 진행 불가 사유로 실제 작업을 멈추는 경우다. 대화를 이어가기 위한 응답 종료나 질문 후 답변 대기 자체를 뜻하지 않는다.
- 같은 기준으로 이어지는 개별 파일 수정이나 검사마다 기록하지 않는다. 기록할 변경이 없으면 파일을 다시 저장하지 않는다.
- 기록할 항목의 형식과 내용은 [명세서 형식](specification.md)과 관련 단계의 기록 지침을 따른다. 반영 위치는 [논의 내용의 배치](specification.md#논의-내용의-배치)에 따라 정한다. 현재 단계 밖의 내용도 관련 항목에 기록하되, 단계의 진입이나 완료를 뜻하는 것으로 취급하지 않는다.
- 단계 전이나 완료 판단을 실제 작업에 적용할 때는 아래 [단계 전이](#단계-전이)와 [검증 범위 변경과 완료 판단](#검증-범위-변경과-완료-판단)의 선행 기록 조건을 충족한다. 논의가 여러 단계에 걸쳤다는 사실만으로 단계 전이나 추가 저장을 요구하지 않는다.
- 미확정 제안은 확정 내용과 구분하고, 항목을 채우기 위해 합의나 검증 결과를 추정하지 않는다.
- 갱신 후 [명세서 작성 시 확인할 사항](specification.md#명세서-작성-시-확인할-사항)에 따라 이번 기록 대상과 실제 본문/참조 위치를 대조하고 누락을 보완한다.
- 필요한 입력이나 권한 등으로 기록할 수 없으면 기록하지 못한 내용과 이유를 알린다. 기록한 것으로 보고하지 않으며, 명세 반영이 필요한 후속 구현은 해당 제약을 해결한 뒤 진행한다.
- 사용자가 기록을 보류하거나 금지한 경우 그 요청 범위를 따른다. 이를 명세서 없이 최종 산출물을 완성해도 된다는 승인으로 해석하지 않는다.

## 작업 기록 갱신

- history는 작업을 마치거나 중단할 때 수행 내용과 결과, 주요 변경 이유 및 재개에 필요한 사항을 묶어서 갱신한다. 사용자가 history 저장을 요청하면 요청한 시점과 범위를 따른다.
- 개별 응답, 파일 수정이나 검사마다 갱신하지 않으며, 기록할 변경이 없으면 다시 저장하지 않는다. 명세서 갱신이 history의 동시 갱신을 요구하지는 않는다.
- 작업 종료나 중단의 의미는 위 [명세서 기록 트리거](#명세서-기록-트리거)를 따른다. 작업 기록의 저장 위치, 형식과 상태 관리는 [Aster 작업 규칙의 공유 작업 데이터 접근](../../../../AGENTS.md#공유-작업-데이터-접근)에서 연결한 규격을 따른다.

## 최초 기록의 단계 판단

- 처음 명세서를 작성할 때는 현재까지 실제로 확인한 논의, 파일과 검증 근거를 단계별 항목에 정리한다. 명세서 생성 전에 이름이나 대상 경로가 미정인 경우의 표기는 [명세서 형식](specification.md#프론트매터)을 따른다.
- `problem-definition`부터 순서대로 각 단계의 실질적인 진입 조건, 완료 조건과 현재 유효한 근거를 대조한다. 최초 대조에서는 아직 부여하지 않은 `current_stage` 값이나 과거 전이 기록의 존재 자체를 선행 단계 충족 조건으로 요구하지 않는다.
- 선행 단계의 완료 조건과 근거가 모두 충족된 경우, 처음으로 완료 조건이 충족되지 않은 단계를 `current_stage`로 정한다. 선행 근거가 부족하면 해당 단계에 머물며 부족한 내용을 기록한다.
- 모든 단계의 완료 근거가 확인되었다면 [완료 단계](stages/completed.md)의 최종 판단까지 확인한 뒤 `completed`를 부여한다. 미수행 검증은 수행한 것으로 정리하지 않는다.
- 선정한 단계 본문에 최초 상태 산정이라는 사실, 선행 단계별 조건 확인 결과의 위치와 선정 근거를 기록한다. 실제로 수행하지 않은 전이 이력을 만들거나 상태값을 저장하기 위해 같은 작업을 다시 수행하지 않는다.
- 최초 기록 이후의 상태 변경과 재수행은 [단계 전이](#단계-전이)를 따른다. 기록을 갱신한다는 이유로 이전 완료 판단이나 변경 영향을 생략하지 않는다.

## 단계 표시

- 현재 단계는 명세서 프론트매터의 `current_stage`로 표현한다.
- 단계별 작업과 판정에는 해당 단계 문서의 운영 규칙과 대상 스킬 명세서의 해당 단계에 기록된 작업 내용 및 판단 근거를 함께 적용한다.
- 진입 조건과 완료 조건은 단계 문서에서 확인하고, 각 조건을 확인한 결과와 판단 근거는 대상 스킬 명세서에 기록한다.
- 다음 단계에 진입할 때는 `current_stage` 값뿐 아니라 이전 단계의 완료 조건과 근거도 확인한다.

## 작업 재개

- 작업을 재개할 때는 현재 단계 문서의 진입 조건과 운영 규칙을 확인하고, 대상 스킬 명세서에 기록된 조건 확인 결과, 작업 결과, 판단 근거 및 남은 사항을 확인한다.
- 명세서의 기록을 현재 파일과 검증 결과 등 필요한 실제 근거와 대조한다.
- 명세서에 연결된 배치 미확정 기록도 확인한다. 현재 정보로 배치할 수 있으면 [논의 내용의 배치](specification.md#논의-내용의-배치)에 따라 정리하고, 판단할 근거가 부족하면 그 이유와 참조를 유지한다.
- 단계 표시만으로 이전 작업의 완료를 인정하지 않고, 재개에 필요한 완료 조건과 근거를 확인한다.
- 기존 전제가 달라졌거나 재수행할 작업이 발견되면 현재 단계 문서의 "허용 전이"와 이 문서의 [단계 전이](#단계-전이)에 따라 복귀할 단계를 판단한다.

## 단계별 작업 수행

- 현재 단계의 판단에 이전 단계의 내용이 필요하면 명세서의 해당 항목과 필요한 단계 문서를 함께 확인한다.
- 도구와 검증 주체는 해당 작업에 필요한 기능과 실제 사용 가능 여부를 확인해 선택한다.

## 단계 전이

- 단계는 해당 단계 문서의 허용 전이에 따라 다음 단계 또는 이전 단계로 이동할 수 있다.
- 다음 단계로 이동하려면 현재 단계의 완료 조건과 확인 가능한 근거가 명세서에 있어야 한다.
- 이전 단계로 돌아가려면 다시 수행해야 할 작업이나 검증과 돌아가야 하는 이유가 명세서에 있어야 한다.
- 전이 사유와 근거를 기록한 뒤 명세서 프론트매터의 `current_stage`를 이동할 단계의 식별자로 변경한다.
- 이전 단계로 돌아가 작업 내용을 수정했다면, 그 수정이 이후 단계의 작업 결과와 완료 판단에 미치는 영향을 확인한다.
- 영향을 받는 작업이나 검증을 다시 수행하고, 그 결과를 근거로 해당 단계의 완료 조건을 충족하는지 다시 판단한다.
- 명세서에는 현재 단계에 이르게 된 전이 사유와 근거를 기록한다.
- 전체 수행 이력은 명세서에 누적하지 않고 작업 기록과 Git 이력에서 관리한다.

## 단계 생략

- 현재는 단계를 건너뛰는 상태나 전이를 정의하지 않는다.
- 각 단계에서 실제로 수행할 작업과 수행하지 않아도 되는 조건은 해당 단계 문서와 적용 규격에 따라 판단한다.
- 수행할 작업이 없거나 수행하지 않아도 되는 경우에는 그 이유와 근거를 대상 스킬 명세서에 기록한다. 이 경우에도 해당 단계의 진입 조건과 완료 조건은 확인한다.
- 교차 검증의 실제 수행 여부는 [교차 검증 단계](stages/cross-validation.md)에 따라 판단한다. 실제 외부 검토를 수행하지 않더라도, 해당 단계에서 요구하는 수행 여부 판단과 기록 및 완료 조건 확인은 진행한다.
- 완료 조건을 모두 충족했는지 확인하고, 확인 결과와 판단 근거를 기록한 뒤 해당 단계를 완료한다.
- 실제 사례에서 단계 생략이 필요하다고 확인되면 적용 조건과 근거를 별도로 설계한다.

## 검증 단계 순서

- 검증 단계는 [생명 주기 순서](#생명-주기-순서)에 따라 진행한다. 단계의 진행과 실제 검증 수행 여부의 구분은 [단계 생략](#단계-생략)을 따른다.
- 수정한 내용으로 인해 영향을 받는 검증 단계 중 진행 순서가 가장 빠른 단계부터 검증을 다시 진행한다.
- 각 검증 단계 안에서 서로 독립적인 검사 항목은 동시에 실행할 수 있다.
- 설계 중 다른 AI 에이전트에게 의견을 받는 조건부 협업은 최종 `교차 검증`과
  구분한다.

구조 설계에서 시나리오 초안을 준비할 때부터
[시나리오 준비와 검증 절차](scenario-validation.md)를 따른다.
초안의 작성과 보완, 기계 검사 후 사용자 확정, 실행과 결과 대조 및 확정 후 변경 기준은 해당 문서를 정본으로 관리한다.

각 단계에서 필요한 준비 상태와 완료 근거는 단계 문서에서 확인한다.
시나리오 확정을 위한 새 단계를 추가하지 않으며, 선행 초안과 사용자 확정 및 실제 실행 결과를 구분한다.

## 검증 범위 변경과 완료 판단

- 사용자와 검증 범위 또는 필수 조건을 변경하기로 명시적으로 합의하면, 유지, 제외 또는 보류할 요건과 사용 사례, 변경 이유 및 합의 근거를 기록한다. 실행 실패나 환경 제약만으로 범위 변경에 합의했다고 간주하지 않는다.
- 완료를 판단하기 전에 대상 스킬 명세서에서 해당 내용을 정의한 요건, 검증 범위와 완료 기준을 갱신한다. 변경 후 기준과 기존 기록이 어긋나지 않도록 관련 항목을 대조하고, 이전 단계의 보완이 필요하면 해당 단계의 허용 전이와 [단계 전이](#단계-전이)를 따른다.
- 변경 후 범위에 남은 필수 조건의 충족 여부와 제외 또는 보류한 항목이 완료 판단에 미치는 영향을 확인한다. 해당 단계의 완료 조건에 따라 판단하고, 충족하지 못한 필수 조건은 단순히 위험을 수용했다는 이유로 충족한 것으로 처리하지 않는다.
- 실제 검증 결과와 범위 조정에 따른 완료 판단을 구분한다. 기존 관찰과 당시 판정은 근거 자료에 보존하고, 제외 또는 보류한 항목을 통과로 바꾸지 않는다. 완료 기록과 보고에는 합의한 범위와 남은 미검증 사항을 명시한다.

## 완료

- `compatibility-validation` (호환성 검증)의 완료 조건과 근거가 확인되면 `completed` (완료) 단계로 이동한다.
- `current_stage`가 `completed`이면 [완료 단계](stages/completed.md)의 최종 확인 결과와 근거를 확인해 생명 주기의 완료 여부를 판단한다.
- 사용 형태와 배치에 관한 판단은 [요건 정의](stages/requirements-definition.md)와 [구조 설계](stages/structure-design.md)를, 해당 사용 형태에 맞는 검증 환경과 결과의 확인은 [동작 검증](stages/behavioral-validation.md)과 [호환성 검증](stages/compatibility-validation.md)을 참조한다.
- 실제 배포는 생명 주기의 필수 단계로 두지 않으며 사용자의 요청과 승인에 따라 별도로
  수행한다.
- 완료 판단 중이나 완료 후 보완 또는 변경이 필요하면, [완료 단계의 허용 전이](stages/completed.md#허용-전이)에 따라 기존 작업의 보완인지 별도 작업인지 구분한다.
- 기존 작업의 보완은 해당 생명 주기의 허용 전이에 따라 진행한다.
- 별도 작업이면 [명세서 형식](specification.md#명세서의-저장-위치와-식별)에 따라 새 명세서의 경로를 정한다.
  생성 시점은 [명세서 기록 트리거](#명세서-기록-트리거)를, 최초 단계는 [최초 기록의 단계 판단](#최초-기록의-단계-판단)을 따른다.

## 진행할 수 없는 경우

- 필요한 자료, 도구, 실행 환경 또는 권한이 없으면 수행하지 못한 내용과 그 이유를 명세서에 기록한다.
- 제약이 있을 때의 진행 가능 여부는 해당 단계 문서의 조건을 확인하고 판단한다.

## 작업 보고

- 작업을 마치거나 멈출 때는 [명세서 기록 트리거](#명세서-기록-트리거)와 [작업 기록 갱신](#작업-기록-갱신)에 따라 미반영 내용을 묶어서 기록한 뒤, 명세서 위치, 현재 단계, 수행한 결과, 미확인 사항과 다음에 필요한 작업을 보고한다.

## 단계 정의 공통 항목

각 단계 문서는 "단계 운영 규칙"과 "명세서 기록 항목"으로 구성한다.
"단계 운영 규칙"은 다음 순서로 배치한다.

- 진입 조건
- 수행 작업
- 완료 조건
- 허용 전이
- 산출물

"명세서 기록 항목"은 산출물에 대응하여 대상 스킬 명세서에 무엇을 어떻게 기록할지 안내한다.
실제 작업 결과는 단계 문서가 아니라 대상 스킬 명세서에 기록하며, 명세서의 구성과 공통 기록 기준은
[명세서 형식](specification.md)을 따른다.

실제 사용 중 불필요하거나 부족한 항목이 확인되면 단계 운영 규칙의 공통 항목 구성을 다시 검토한다.

## 공통 절차 적용

- 특정 스킬에서 사용한 작업 흐름은 공통 절차로 확정하기 전까지 다른 스킬에 일괄 적용하지 않는다.
