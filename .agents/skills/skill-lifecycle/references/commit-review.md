# 커밋 전 검토

현재 작업에서 생성하거나 수정한 파일을 목적별로 묶어 정리, 검토하고 커밋한다.
명세서와 해당 시점의 스킬을 함께 읽으면 작업 목적, 실제 변경과 기대 산출물을 파악할 수 있어야 한다.
문서의 가독성과 명세 대비 구현의 일치를 모두 확인한다.

## 적용 시점과 상태

| 대상 | 진입 시점 | 검토 후 진행 |
| --- | --- | --- |
| 플러그인 스킬 | `cross-validation`의 검증 판단을 마친 뒤, 호환성 검증용 커밋 전 | 검토한 커밋을 설치 또는 업데이트하여 `compatibility-validation` 수행 |
| 모든 스킬 | `completed`의 최종 정리와 완료 판단 시 | 최종 명세서와 남은 변경의 검토 및 커밋 후 생명 주기 완료 |

각 시점에 명세서의 `in_review`를 `true`로 설정하고 해당 단계 본문에 검토 목적과 그룹을 기록한다.
플러그인의 첫 검토는 당시 확정한 구현과 검증 준비를 다루며, 아직 수행하지 않은 호환성 검증을 완료로 기록하지 않는다.
최종 검토에는 이후 추가한 검증 결과와 최종 명세서도 포함한다.
내부용 스킬은 첫 관문을 적용하지 않고 완료 단계에서 소스와 기록을 함께 검토한다.

`true`인 동안 해당 관문을 넘어 호환성 검증에 진입하거나 생명 주기 완료를 선언하지 않는다.
보완에 필요한 이전 단계 복귀와 검증은 허용하며, 복귀 이유와 돌아올 검토 시점을 기록한다.
검토 대상이 달라지면 영향을 받는 검토와 검증을 다시 수행한다.
특히 플러그인의 설치 대상이 바뀌면 첫 관문을 다시 거쳐 새 커밋을 실제 반영한 뒤 호환성을 재검증한다.

## 그룹 구성과 승인

- 변경 파일과 미추적 파일을 확인하고 개선 목적별로 그룹과 처리 순서를 정한다.
  분리가 불분명하거나 서로 의존하여 독립적인 커밋이 성립하지 않으면 하나로 묶고 이유를 적는다.
- 각 그룹에 목적, 포함 파일 전체, 제외 파일과 이유, 검토 결과 및 커밋 근거를 기록한다.
  같은 파일이 여러 목적에 해당하면 각 그룹에 중복하여 나열한다.
- 명세서와 지원 문서, 코드와 검사 및 설정도 이번 변경에 포함되면 목록에서 빠뜨리지 않는다.
  [기록 루트에서 유지하는 모든 문서](work-data.md#기록의-커밋과-역할-유지)와 필요한 보존 자료를 포함한다.
  중복 파일을 통합했다면 삭제와 참조 갱신도 함께 검토하며 로컬 유지 자료는 제외한다.
  각 관문까지 확정하고 검토한 범위를 커밋하며 이후 단계의 계획은 미수행 상태로 구분한다.
  다른 작업의 변경은 포함하지 않는다.
- [Git 운영 규칙](../../../../.github/git-workflow.md#커밋과-원격-변경-권한)에 따라
  구체적인 그룹별 포함/제외 범위와 마지막 상태 기록의 커밋까지 함께 제시한다.
  기존 승인이 그 범위를 포함하면 재사용하고, 없으면 전체 묶음에 대해 한 번 승인받는다.
  승인 범위 내의 정리, 검토, 그룹별 커밋마다 승인을 반복하지 않는다.
  범위가 달라지는 경우에만 같은 규칙에 따라 다시 확인한다.

## 그룹별 처리

그룹 순서대로 아래 절차를 수행한다.

1. 목록의 각 파일을 현재 변경 내용과 대조한다.
   선행 그룹에서 검토하고 커밋한 파일은 해당 커밋 및 현재 내용과 파일 모드가 동일한 경우에만
   파일 검토를 생략하고 근거 커밋과 생략 이유를 남긴다.
   단순히 추적 중이거나 과거에 커밋된 적이 있다는 이유로 생략하지 않는다.
   이후 변경이 있으면 그 변경과 영향을 다시 검토한다.
   파일 검토를 재사용하더라도 해당 그룹의 요구사항 충족 여부는 확인한다.
2. 문서는 아래 가독성 기준으로 정리하고, 명세서와 구현의 대응을 확인한다.
   코드와 설정은 해당 형식의 규격과 검사를 적용한다.
   변경된 규칙과 직접 연결된 문맥을 확인하며 다른 작업이나 문서 전체의 무관한 재작성으로 범위를 넓히지 않는다.
3. 의미가 바뀌는 수정이 필요하면 먼저 명세를 갱신하고 영향을 받는 구현 및 검증으로 돌아간다.
   문서 정리를 이유로 합의한 동작이나 미검증 상태를 바꾸지 않는다.
4. 실제 스테이징한 변경이 승인 범위와 검토 결과에 일치하는지 대조하고 커밋한다.
   해당 그룹에 남은 변경이 없으면 빈 커밋을 만들지 않고 선행 커밋을 연결한다.
   실패하거나 승인이 없으면 미완료 사유를 기록하고 `in_review: true`를 유지한다.

모든 그룹의 커밋이 확인되면 결과와 근거 커밋을 기록하고 `in_review: false`로 바꾸는 마감 변경을 검토하여 커밋한다.
이 마감 변경도 처음 승인받은 범위에 포함한다.
마감 커밋 자신의 해시를 같은 파일에 다시 적는 순환 기록은 만들지 않고 Git 이력에서 확인한다.

마감 커밋이 실패하면 `true`로 복구하고 남은 작업을 기록한다.
재개할 때는 값과 본문 외에 실제 커밋 및 현재 작업 파일을 대조하여 미커밋 마감 기록을 통과로 인정하지 않는다.

관문 이후의 정상적인 단계 기록 갱신은 다음 검토 시점에서 정리하며, 새 구현 변경은 필요한 이전 관문으로 돌아간다.
푸시, PR과 설치 권한은 커밋 승인에 포함된 것으로 추정하지 않는다.

## 개행과 목록 구조 정리

명세서, `SKILL.md`와 지원 문서를 문맥에 맞게 정리하고 원문과 Markdown 렌더링의 가독성을 함께 확인한다.
문장의 길이나 외형만으로 계층을 바꾸지 않는다.

- 하나의 문단에는 하나의 논점을 두고 논점이 바뀌면 빈 줄로 나눈다.
  제목과 본문, 목록 앞뒤에도 빈 줄을 둔다.
- 원문은 문장 끝에서 개행하고 긴 문장은 의미가 끊기는 곳에서 나눈다.
  단어, 경로와 링크를 글자 수에 맞추려고 중간에서 끊지 않는다.
  일반 개행과 문단 구분을 구별하며, 개행을 위한 HTML 태그는 사용하지 않는다.
- 설명은 문단으로, 병렬 항목은 목록으로, 순서가 있는 절차는 번호 목록으로 정리한다.
  모든 문장을 일괄적으로 목록으로 만들지 않는다.
- 독립된 규칙은 같은 목록 단계에 둔다.
  상위 항목의 부가 설명, 조건이나 예외일 때만 하위 목록으로 묶는다.
  주제가 비슷하거나 보기 좋게 묶으려는 이유만으로 포함 관계를 만들지 않는다.
- 목록의 이어지는 설명은 새 목록 기호 없이 해당 항목의 본문 시작 위치에 맞춰 들여쓴다.
  일반 문단에 불필요한 공백을 넣어 코드 블록으로 해석되게 하지 않는다.
- 문장 축약, 중복 통합, 문단 또는 목록 구조 변경 전후의 의미를 대조한다.
  적용 범위, 조건, 예외와 의무 및 승인/검증 상태를 보존한다.
  의미가 달라지거나 내용이 빠질 우려가 있으면 해당 변경을 하지 않는다.
- 원문과 Markdown 렌더링에서 문단 구분, 목록의 포함 관계와 코드 블록이 의도대로 표시되는지 확인한다.
  형식 검사 통과만으로 문맥과 의미 검토를 대신하지 않는다.

## 명세서와 스킬의 대응 확인

[명세서의 작업 내용과 결과](specification.md#작업-내용과-결과)를 기준으로 다음을 대조한다.

- 작업 디렉토리명과 제목에서 해결한 문제와 변경 목적을 식별할 수 있다.
- 각 요건이 실제 스킬 본문과 지원 자료의 어느 지침으로 구현되었는지 연결된다.
  변경 파일 목록만으로 동작 설명을 대신하지 않는다.
- 스킬의 입력과 적용 조건을 따라가면 수행 절차, 기대 산출물의 내용과 위치 및 종료 조건이 명확하다.
  실행 결과가 항상 같다는 보장을 뜻하지 않으며, 충족 여부를 판단할 관찰 기준이 있어야 한다.
- 명세의 기대 결과와 실제 검증 결과가 구분되고, 차이와 미검증 범위가 드러난다.
  검증한 버전 또는 기준 커밋과 변경 범위를 통해 해당 시점의 스킬을 찾을 수 있다.
- 명세 없는 구현이나 구현되지 않은 요건이 발견되면 합의 범위를 확인하여 보완하고 다시 대조한다.

요건, 구현 위치, 기대 산출물과 검증 근거는 명세서의 담당 항목에서 관리한다.
그룹 검토 기록에는 그 정본과 대조 결과를 연결하며 동일한 정의를 다시 복사하지 않는다.
