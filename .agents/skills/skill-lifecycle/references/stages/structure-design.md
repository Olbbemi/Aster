# structure-design (구조 설계)

이 문서는 `skill-lifecycle` 생명 주기의 `structure-design` (구조 설계) 단계에 적용할 운영 규칙과 단일 명세서 기록 기준을 정의한다.

## 단계 운영 규칙

### 진입 조건

- 명세서 프론트매터의 `current_stage`가 `structure-design`이다.
- `existing-configuration-review` (기존 구성 확인)의 완료 조건과 근거가 확인되었다.
- 기존 구성의 재사용, 수정, 분리, 통합, 제거 또는 신규 생성에 대한 판단과 근거가 확인되었다.
- 구조에 반영할 요건, 스킬의 사용 형태(내부용 또는 플러그인 배포용), 지원 대상 CLI와 각 CLI에 적용할 호환성 요건 및 실행 환경이 확인되었다.

### 수행 작업

- [저장소 배치 규격](../../../../../standards/repository-layout.md)과 [스킬 내부 배치 규격](../../../../../standards/skills/skill-layout.md)을 확인하여 파일과 자료의 역할, 배치 및 생성 조건을 구조 설계에 적용한다.
- 정의된 요건과 기존 구성의 처리 방향을 기준으로 스킬 구현에 필요한 파일을 식별하고, 반드시 필요한 파일과 특정 조건에서만 필요한 파일을 구분한다.
- 새로 만들 파일과 기존 파일 중 유지, 이동, 수정 또는 제거할 파일을 구분하고, 각 파일의 처리 방법을 정한다.
- 핵심 지침, 조건부 상세 지침, 스크립트 및 결과물용 자료의 역할과 배치할 파일을 구분한다.
- 관리할 자료를 작업 대상 스킬 전용 자료, 내부 스킬 공용 자료와 플러그인 단위 자료로 구분한다.
- 같은 플러그인의 여러 스킬이 사용하는 플러그인 단위 자료는 플러그인 내부 공용 자료로 구분한다.
- 개발 과정에서만 사용하는 규격과 검사 자료를 작업 대상 스킬을 설치하거나 저장소에서 직접 사용하는 경우 필요한 파일과 자료와 구분한다.
- 명세서에 정의된 지원 대상 CLI와 각 CLI에 적용할 호환성 요건을 기준으로, 지원 CLI에서 함께 사용할 수 있는 공용 구성을 우선하여 설계한다.
- 지원 CLI 사이에서 실제로 호환되지 않는 사항이 확인되어 공용 구성만으로 요건을 충족할 수 없다면, 그 근거에 따라 해당 CLI에서만 필요한 전용 구성을 설계한다.
- 스킬을 구성하는 파일과 자료 사이의 참조 방향 및 의존 관계를 정의한다.
- 작업 대상 스킬을 플러그인으로 배포한다면 플러그인의 배포 경계와 그 안에 포함할 파일을 결정한다.
- 정의된 요건이나 파일별 역할을 담당하지 않는 디렉토리와 자리 표시용 파일은 구조에서 제외한다.
- 구조 설계에 영향을 주지만 확인하지 못한 사항을 식별하고, 현재 단계에서 확인할 사항과 후속 단계에서 확인할 사항을 구분한다.

### 완료 조건

- 작업 대상 스킬과 지원 파일 및 디렉토리의 전체 구조가 정의되었다.
- 설계한 파일과 자료의 역할, 배치 및 생성 조건이 [저장소 배치 규격](../../../../../standards/repository-layout.md)과 [스킬 내부 배치 규격](../../../../../standards/skills/skill-layout.md)의 해당 기준을 충족한다.
- 새로 만들 파일과 기존 파일 중 유지, 이동, 수정 또는 제거할 파일이 구분되었고, 각 파일의 처리 방법이 정의되었다.
- 정의된 모든 요건이 해당 요건을 담당할 파일 또는 구성 요소와 그 역할에 연결되었다.
- 같은 규칙이나 정보를 중복하여 관리하지 않고, 해당 내용을 변경할 기준 위치가 하나로 정해졌다.
- 각 파일과 자료가 담당할 역할이 구분되었고 서로 충돌하도록 겹치지 않는다.
- 스킬 사용에 필요한 파일과 자료의 관리 범위가 작업 대상 스킬 전용, 내부 스킬 공용 또는 플러그인 단위 중 하나로 구분되었다.
- 개발 과정에서만 사용하는 자료와 스킬을 저장소에서 직접 사용하거나 설치하여 사용하는 데 필요한 자료가 구분되었다.
- 작업 대상 스킬을 플러그인으로 배포한다면 설치 및 실행에 필요한 모든 파일이 플러그인 배포 경계 안에 배치되도록 설계되었다.
- 파일과 자료 사이의 참조가 저장소에서 직접 사용할 때 성립하며, 플러그인으로 배포한다면 설치 후 경로에서도 성립하도록 설계되었다.
- 파일과 자료 사이의 의존 관계가 정의되었으며 순환 참조가 없다.
- 명세서에 정의된 둘 이상의 지원 CLI에서 함께 사용하는 공용 구성이 있다면, 해당 CLI에서 같은 내용과 형식으로 사용할 수 있다는 근거에 따라 설계되었다.
- 특정 지원 CLI에서만 사용하는 전용 구성이 있다면, 실제로 호환되지 않는 사항과 공용 구성만으로 해당 CLI의 요건을 충족할 수 없는 근거에 따라 설계에 반영되었다.
- 정의된 요건이나 역할을 담당하지 않는 파일, 자리 표시용 파일 및 빈 디렉토리가 구조에 포함되지 않았다.
- 구조 설계의 완료를 막는 미확인 사항이 없다.
- 만약 구조 설계에 영향을 주지만 후속 단계에서 확인할 사항이 남아 있다면 그 내용, 현재 단계에서 확인하지 못한 이유와 확인할 단계가 명시되었다.

### 허용 전이

- 모든 완료 조건과 그 근거가 확인되면 `implementation` (구현)으로 이동한다.
- 이동할 때는 전이 사유와 근거를 기록한 뒤 명세서 프론트매터의 `current_stage`를 `implementation`로 변경한다.
- 기존 구성의 처리 방향과 근거를 다시 판단해야 하면 `existing-configuration-review` (기존 구성 확인)로 돌아간다.
- 구조 설계 과정에서 정의된 요건을 변경해야 한다고 판단되면 `requirements-definition` (요건 정의)으로 돌아간다.
- 해결할 문제나 스킬의 수행 범위 및 제외할 범위를 변경해야 하면 `problem-definition` (문제 정의)으로 돌아간다.
- 이전 단계로 돌아갈 사유가 없고 완료 조건을 충족하지 못하면 `structure-design` (구조 설계)에 머물며 부족한 내용을 확인하고 보완한다.
- 이전 단계로 돌아갈 때는 전이 사유와 근거를 기록한 뒤 명세서 프론트매터의 `current_stage`를 돌아갈 단계의 식별자로 변경한다.

### 산출물

- 작업 대상 스킬과 지원 파일 및 디렉토리의 구조
- 각 파일과 자료가 담당할 역할
- 스킬을 구성하는 파일과 자료 사이의 참조 방향 및 의존 관계
- 작업 대상 스킬 전용 자료
- 내부 스킬 공용 자료
- 플러그인 단위 자료와 플러그인 내부 공용 자료
- 개발 전용 자료와 스킬 사용 자료의 구분
- 지원 CLI에서 함께 사용하는 공용 구성
- 특정 지원 CLI에서만 사용하는 전용 구성
- 구조 설계에 영향을 주는 미확인 사항과 확인 단계

## 명세서 기록 항목

### 작업 대상 스킬과 지원 파일 및 디렉토리의 구조

- 작업 대상 스킬의 루트 경로와 전체 파일 및 디렉토리 구조를 적는다.
- 반드시 필요한 파일과 특정 조건에서만 필요한 파일을 구분한다.
- 특정 조건에서만 필요한 파일은 해당 파일이 필요한 조건과 이유를 함께 적는다.
- 새로 만들 파일과 생성할 경로 및 처리 방법을 적는다.
- 기존 파일 중 유지, 이동 또는 수정할 파일과 처리 방법을 적는다.
- 제거할 기존 파일과 제거하는 이유 및 처리 방법을 적는다.
- 설계한 구조에는 빈 디렉토리와 자리 표시용 파일을 포함하지 않는다.

### 각 파일과 자료가 담당할 역할

- 각 파일과 자료가 담당할 역할을 적는다.
- 각 파일에 포함할 지침, 설정, 스크립트 또는 결과물용 자료를 적는다.
- 각 규칙과 정보를 처음 정의하고 이후 변경할 때 기준으로 삼을 파일 또는 구성 요소의 위치를 적는다.
- SSOT 원칙에 따라 같은 규칙이나 정보를 여러 파일에 반복하여 정의하지 않고 기준 위치를 참조하도록 파일별 역할을 구분한다.
- 각 파일과 자료가 정의된 어떤 요건을 담당하는지 적고, 여러 요건을 담당한다면 각 요건을 구분하여 적는다.

### 스킬을 구성하는 파일과 자료 사이의 참조 방향 및 의존 관계

- 각 참조 관계에서 어느 파일이 참조하고 어느 파일 또는 자료가 참조되는지 적는다.
- 각 참조가 필요한 이유와 참조가 사용되는 조건을 적는다.
- 스크립트, 설정 또는 자료가 다른 파일에 의존한다면 의존 대상과 조건을 적는다.
- 작업 대상 스킬을 저장소에서 직접 사용할 때 스킬을 구성하는 파일과 자료 사이에서 성립해야 하는 참조 경로를 적는다.
- 작업 대상 스킬을 플러그인으로 배포한다면 설치 후 스킬을 구성하는 파일과 자료 사이에서 성립해야 하는 참조 경로를 적는다.
- 순환 참조가 있다면 해당 경로와 영향 및 해소 방법을 적고, 해소되기 전까지 구조 설계의 완료를 막는 사항으로 구분한다. 순환 참조가 없다면 `없음`이라고 적는다.

### 작업 대상 스킬 전용 자료

- 작업 대상 스킬에서만 사용하는 파일과 자료를 적는다.
- 각 파일과 자료를 작업 대상 스킬 내부의 어느 경로에 배치할지와 해당 위치에서 담당할 역할을 적는다.
- 각 파일과 자료를 작업 대상 스킬 내부에서만 관리해야 하는 이유를 적는다.
- 작업 대상 스킬 전용 자료가 없다면 `없음`이라고 적는다.

### 내부 스킬 공용 자료

- 여러 내부용 스킬이 함께 사용할 파일과 자료를 적는다.
- 각 파일과 자료의 배치 경로와 해당 자료를 사용하는 내부용 스킬을 적는다.
- 각 파일과 자료를 특정 내부용 스킬이 아닌 내부 스킬 공용 자료로 관리해야 하는 이유를 적는다.
- 기존 내부 스킬 공용 자료를 변경한다면, 이를 사용하는 스킬의 사용 방식과 참조 경로에 미치는 영향 및 필요한 수정과 검증 항목을 적는다.
- 내부 스킬 공용 자료가 없다면 `없음`이라고 적는다.

### 플러그인 단위 자료와 플러그인 내부 공용 자료

- 플러그인 단위로 관리할 파일과 자료를 적는다.
- 대상 플러그인의 이름과 자료의 배치 경로를 적는다.
- 플러그인 단위로 관리하는 각 파일과 자료를 사용하는 스킬, MCP, 훅 또는 그 밖의 플러그인 구성 요소를 적는다.
- 각 파일과 자료를 개별 스킬이 아닌 플러그인 단위로 관리해야 하는 이유를 적는다.
- 같은 플러그인의 여러 스킬이 사용하는 자료는 플러그인 내부 공용 자료로 구분하고, 이를 사용하는 스킬을 적는다.
- 기존 플러그인 내부 공용 자료를 변경한다면, 이를 사용하는 스킬의 사용 방식과 참조 경로에 미치는 영향 및 필요한 수정과 검증 항목을 적는다.
- 플러그인 배포 경계에 포함할 파일과 제외할 파일을 구분한다.
- 플러그인 단위 자료와 플러그인 내부 공용 자료가 없다면 `없음`이라고 적는다.

### 개발 전용 자료와 스킬 사용 자료의 구분

- 개발 과정에서만 사용하는 규격, 검사와 작업 자료를 적는다.
- 작업 대상 스킬을 저장소에서 직접 사용하는 경우 필요한 파일과 자료를 적는다.
- 작업 대상 스킬을 설치하여 사용하는 경우 필요한 파일과 자료를 적는다.
- 각 파일과 자료를 개발 전용 자료 또는 스킬 사용 자료로 구분한 근거를 적는다.
- 작업 대상 스킬을 플러그인으로 배포하는 경우, 해당 스킬 사용에 필요한 모든 파일과 자료가 배포 경계 안에 포함되도록 설계되었는지 적는다.

### 지원 CLI에서 함께 사용하는 공용 구성

- 명세서에 정의된 둘 이상의 지원 CLI에서 같은 내용과 형식으로 사용할 수 있는 파일, 설정과 자료를 적고, 각 구성을 함께 사용할 CLI를 명시한다.
- 각 공용 구성의 배치 경로, 역할과 대응하는 요건을 적는다.
- 각 구성을 해당 CLI에서 공용으로 사용할 수 있다고 판단한 근거를 적는다.
- 공용 구성에 포함한 각 규칙과 정보를 정의하고 변경할 기준 파일 또는 구성 요소의 경로를 적는다.
- 둘 이상의 지원 CLI에서 함께 사용하는 공용 구성이 없다면 `없음`이라고 적는다.

### 특정 지원 CLI에서만 사용하는 전용 구성

- 명세서에 정의된 지원 CLI별로 해당 CLI에서만 필요한 파일, 설정과 자료를 적고, 전용 구성이 없는 CLI는 `없음`으로 적는다.
- 전용으로 분류한 각 파일, 설정과 자료의 배치 경로, 담당할 역할 및 대응하는 요건을 적는다.
- 전용 구성이 필요한 경우 지원 CLI 사이에서 실제로 호환되지 않는 사항과 그 근거, 공용 구성만으로 해당 CLI의 요건을 충족할 수 없는 이유를 적는다.
- 전용 구성에는 공용 구성과 다른 내용만 적고, 같은 규칙이나 정보를 중복하여 정의하지 않는다.

### 구조 설계에 영향을 주는 미확인 사항과 확인 단계

- 현재까지 확인하지 못했지만 구조 설계에 영향을 주는 사항을 적는다.
- 구조 설계에 영향을 주는 각 사항을 현재까지 확인하지 못한 이유를 적는다.
- 구조 설계에 영향을 주는 각 미확인 사항이 현재 단계의 완료를 막는지 구분한다.
- 구조 설계에 영향을 주는 미확인 사항을 현재 단계에서 확인해야 한다면, 확인에 필요한 정보와 사용자에게 확인 또는 판단을 요청할 사항을 적는다.
- 구조 설계에 영향을 주는 미확인 사항을 후속 단계에서 확인할 수 있다면, 현재 단계의 완료를 막지 않는 이유와 확인할 단계를 구분하여 적는다.
- 구조 설계에 영향을 주는 미확인 사항에 관해 현재까지 확인한 사실과 근거가 있다면 함께 적는다.
- 구조 설계에 영향을 주는 미확인 사항이 없다면 `없음`이라고 적는다.
