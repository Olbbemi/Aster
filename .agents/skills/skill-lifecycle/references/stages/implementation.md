# implementation (구현)

이 문서는 `skill-lifecycle` 생명 주기의 `implementation` (구현) 단계에 적용할 운영 규칙과 단일 명세서 기록 기준을 정의한다.

## 단계 운영 규칙

### 진입 조건

- 명세서 프론트매터의 `current_stage`가 `implementation`이다.
- `structure-design` (구조 설계)의 완료 조건과 근거가 확인되었다.
- 새로 만들거나 수정, 이동 또는 제거할 파일과 디렉토리가 식별되었고, 각 대상이 담당할 역할이 정해졌다.
- 구현할 각 요건과 이를 담당할 파일 또는 구성 요소의 대응 관계가 확인되었다.
- 구현에 필요한 파일 변경이 사용자와 합의한 작업 범위에 포함된다.

### 수행 작업

- [스킬 내용 작성 규격](../../../../../standards/skills/skill-content.md)을 확인하여 `SKILL.md`와 지원 자료의 작성에 해당 기준을 적용한다.
- 명세에 기록된 요건과 구조 설계에 따라 `SKILL.md`와 지원 파일 및 디렉토리를 새로 만들거나 수정, 이동 또는 제거한다.
- 핵심 지침과 조건부 상세 지침을 구조 설계에서 정한 역할과 위치에 맞게 배치한다.
- 구조 설계에서 스크립트로 구현하기로 정한 작업은 해당 스크립트의 역할과 명세에 정의된 입력, 기대 결과 및 실패 시 대응에 맞게 구현한다.
- 내부 스킬 공용 자료와 플러그인 내부 공용 자료는 구조 설계에서 정한 관리 위치에 한 번만 정의하고, 이를 사용하는 스킬에서 참조한다.
- 파일과 자료를 변경하면서 영향을 받는 참조 경로와 의존 구성을 구조 설계에 따라 갱신한다. 공용 자료를 변경한다면 이를 사용하는 스킬에 필요한 수정도 함께 반영한다.
- 명세서에 정의된 지원 대상 CLI에 대해 구조 설계에서 정한 공용 구성을 구현한다.
- 특정 지원 CLI에서만 사용하는 전용 구성은 구조 설계에 기록된 실제로 호환되지 않는 사항과 판단 근거에 따라 작성한다.
- 스킬의 생성, 변경, 통합 또는 폐기에 따라 플러그인 매니페스트와 같은 스킬 외부 구성을 변경해야 한다면, 구조 설계에서 정한 대상과 처리 방법에 따라 필요한 범위만 변경한다.
- 구현 과정에서 명세 또는 구조 설계와 실제 구현이 맞지 않는 사항을 식별하고, 해당 문제를 보완해야 할 이전 단계를 구분한다.
- 구현 중 발견한 문제를 해결하기 위해 이전 단계에서 확정한 명세 내용을 임의로 변경하지 않는다.
- 변경이 필요하면 돌아갈 단계와 그 근거를 명세서에 기록한다.

### 완료 조건

- 명세에서 구현 대상으로 정한 모든 요건이 구현 결과에 반영되었다.
- `SKILL.md`와 지원 자료에 [스킬 내용 작성 규격](../../../../../standards/skills/skill-content.md)의 해당 기준이 반영되었다.
- 각 변경 대상이 구조 설계에서 정한 역할, 위치와 처리 방법에 따라 변경되었다.
- 파일과 자료의 변경으로 영향을 받는 참조 경로와 의존 구성이 구조 설계에 따라 갱신되었으며, 공용 자료를 사용하는 스킬에 필요한 수정이 반영되었다.
- 같은 규칙이나 정보가 여러 파일에 중복하여 정의되지 않았으며, 해당 내용을 변경할 기준 위치가 하나로 유지되었다.
- 미완성 자리 표시자, 사용되지 않는 파일 및 빈 디렉토리가 남아 있지 않다.
- 구조 설계에서 스크립트로 구현하기로 정한 작업이 해당 스크립트의 역할과 명세에 정의된 입력, 기대 결과 및 실패 시 대응에 맞게 구현되었다.
- 명세서에 정의된 지원 대상 CLI의 공용 구성이 구조 설계에 따라 구현되었다.
- 특정 지원 CLI에서만 사용하는 전용 구성이 있다면, 구조 설계에 기록된 실제로 호환되지 않는 사항과 판단 근거에 따라 작성되었다.
- 스킬 외부 구성의 변경은 스킬의 생성, 변경, 통합 또는 폐기에 따라 구조 설계에서 정한 대상과 처리 방법에 맞게 수행되었으며, 필요한 범위로 제한되었다.
- 구현 과정에서 새로 만들거나 수정, 이동 또는 제거한 파일과 디렉토리가 식별되었다.
- 각 파일 및 디렉토리의 변경 내용이 그 변경으로 구현한 명세 항목과 대응하는지 확인되었다.

### 허용 전이

- `implementation` (구현)의 모든 완료 조건과 근거가 확인되면 `mechanical-validation` (기계 검사)으로 이동한다.
- 이동할 때는 전이 사유와 근거를 기록한 뒤 명세서 프론트매터의 `current_stage`를 `mechanical-validation`로 변경한다.
- 파일이나 자료의 역할, 배치, 처리 방법, 참조 방향 또는 의존 관계를 다시 설계해야 하면 `structure-design` (구조 설계)으로 돌아간다.
- 정의된 요건을 변경하거나 보완해야 하면 `requirements-definition` (요건 정의)으로 돌아간다.
- 해결할 문제나 스킬이 수행할 범위와 제외 범위를 변경해야 하면 `problem-definition` (문제 정의)으로 돌아간다.
- 이전 단계로 돌아갈 사유가 없고, 필요한 변경 권한이나 입력이 없거나 다른 완료 조건을 충족하지 못하면 `implementation` (구현)에 머물며 부족한 내용을 확인하고 보완한다.
- 이전 단계로 돌아갈 때는 전이 사유와 근거를 기록한 뒤 명세서 프론트매터의 `current_stage`를 돌아갈 단계의 식별자로 변경한다.

### 산출물

- 새로 만들거나 수정, 이동 또는 제거한 파일과 디렉토리
- 구현하지 못한 요건과 구현하지 못한 이유 및 보완할 단계

## 명세서 기록 항목

### 새로 만들거나 수정, 이동 또는 제거한 파일과 디렉토리

- 새로 만들거나 수정, 이동 또는 제거한 파일과 디렉토리의 경로를 적는다.
- 각 파일과 디렉토리에 수행한 작업을 생성, 수정, 이동 또는 제거로 구분한다.
- 각 파일 및 디렉토리의 변경 내용이 어떤 명세 항목을 구현했는지 적는다.
- 각 변경 대상이 구조 설계에서 정한 어떤 자료 종류와 역할에 해당하는지 적는다.
- 스킬 사용 자료에 해당하는 변경 대상은 구조 설계에서 정한 작업 대상 스킬 전용, 내부 스킬 공용 또는 플러그인 단위의 관리 범위 중 어디에 해당하는지 적는다. 개발 전용 자료에 해당하는 변경 대상은 그 구분과 용도를 적는다.
- 각 변경 대상의 CLI 적용 범위를 구조 설계에 따라 적는다.
- 공용 구성은 함께 사용하는 지원 CLI를 명시하고, 전용 구성은 해당 지원 CLI를 명시한다. CLI에 따른 구분이 필요하지 않은 대상은 `구분 없음`으로 적는다.
- 스크립트를 새로 만들거나 수정했다면 구조 설계에서 정한 역할, 사용 조건과 수행 작업 및 명세에 정의된 입력, 기대 결과와 실패 시 대응에 맞게 작성되었는지 적는다.
- 결과물용 자료를 새로 만들거나 수정했다면 구조 설계에서 정한 사용 대상과 사용 방법에 맞게 작성되었는지 적는다.
- 파일과 자료의 변경으로 영향을 받은 참조 경로와 의존 구성 및 갱신한 내용을 적는다.
- 내부 스킬 공용 자료나 플러그인 내부 공용 자료를 새로 만들거나 수정, 이동 또는 제거했다면, 이를 사용하는 스킬과 해당 스킬에 필요한 수정의 반영 결과를 적는다.
- 유지하거나 새로 정의한 공용 내용은 해당 내용을 변경할 기준 위치가 구조 설계와 일치하는지 적는다.
- 특정 지원 CLI에서만 사용하는 전용 구성을 새로 만들거나 수정했다면, 구조 설계에 기록된 실제로 호환되지 않는 사항과 판단 근거에 따라 작성되었는지 적는다.
- 스킬 외부 구성을 변경했다면 변경 대상과 내용 및 스킬의 생성, 변경, 통합 또는 폐기에 따라 해당 변경이 필요한 이유를 적는다. 구조 설계에서 정한 대상과 처리 방법에 맞게 필요한 범위만 변경했는지 함께 적는다.
- 파일이나 디렉토리를 이동했다면 이동 전 경로와 이동 후 경로를 적는다.
- 파일이나 디렉토리를 제거했다면 제거한 이유를 적는다.

### 구현하지 못한 요건과 구현하지 못한 이유 및 보완할 단계

- 명세에서 구현 대상으로 정한 요건 중 구현하지 못한 요건을 적는다. 일부만 구현했다면 구현한 부분과 남은 부분을 구분한다.
- 각 요건을 구현하지 못한 이유를 적는다.
- 구현하지 못한 각 요건으로 인해 충족하지 못한 완료 조건을 적는다.
- 허용 전이를 기준으로 현재 단계에서 보완할지 이전 단계로 돌아갈지 판단하고, 보완할 단계와 그 판단 근거를 적는다.
- 해당 단계에서 필요한 작업과 보완에 필요한 입력, 권한 또는 사용자 판단이 있다면 함께 적는다.
- 구현하지 못한 요건이 없으면 `없음`으로 적는다.
