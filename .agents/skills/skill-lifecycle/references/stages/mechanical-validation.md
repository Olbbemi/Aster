# mechanical-validation (기계 검사)

이 문서는 `skill-lifecycle` 생명 주기의 `mechanical-validation` (기계 검사) 단계에 적용할 운영 규칙과 단일 명세서 기록 기준을 정의한다.

## 단계 운영 규칙

### 진입 조건

- 명세서 프론트매터의 `current_stage`가 `mechanical-validation`이다.
- `implementation` (구현)의 완료 조건과 근거가 확인되었다.
- 기계 검사 대상인 파일, 디렉토리 및 설정과 적용할 개발 규격이 식별되었다.
- 명세서에 정의된 검증 대상 요건과 각 요건의 검증 기준이 확인되었다.
- 사용할 검사 도구와 검사 명령을 실행하는 데 필요한 조건이 확인되었다.

### 수행 작업

- [스킬 검증 규격](../../../../../standards/skills/skill-validation.md)과 명세서의 검증 기준을 확인하여, 기계적으로 판정할 항목과 사람 또는 AI 에이전트의 판단이 필요한 항목을 구분한다.
- 각 기계 검사 항목의 적용 여부와 필수 여부, 판정 기준 및 근거가 되는 개발 규격의 항목을 확인한다.
- 구현 단계에 기록된 변경 대상과 영향 범위를 기준으로 검사 대상을 정한다. 공용 자료를 사용하는 스킬과 스킬 외부 구성에 영향을 주었다면 관련 검사 대상에 포함한다.
- 명세서의 작업 유형과 구조 설계를 기준으로 유지하거나 생성할 대상에는 해당 구조 검사를 적용하고, 제거할 대상에는 제거 여부와 남아 있으면 안 되는 참조 및 등록의 정리 여부를 검사한다.
- 파일과 디렉토리의 구조 및 이름, 프론트매터와 필수 파일의 존재 여부를 검사한다.
- 파일 간 참조 경로가 유효하고 참조 대상이 존재하는지 검사한다.
- 중복 정의, 미완성 자리 표시자 및 미사용 파일의 후보를 기계적으로 식별한다. 의미 판단이 필요한 후보는 확정된 위반과 구분하여 기록한다.
- 스크립트가 있으면 구문 오류를 검사하고, 지침에서 실행하도록 지정한 스크립트는 필요한 실행 조건을 확인한 뒤 대표 입력에서 정상 처리와 예상 가능한 오류 상황의 결과를 검사한다.
- 같은 입력에 일관된 결과가 요구되는 스크립트는 결과가 재현되는지도 검사한다.
- 명세서에 정의된 지원 대상 CLI가 공식 검사 도구를 제공하고 해당 도구가 검사 대상의 파일과 설정에 적용 가능하다면, 그 도구로 해당 항목을 검사한다.
- 검사 스크립트를 새로 작성하거나 수정했다면, 적용할 개발 규격과 판정 기준에 따라 의도한 대상을 검사하고 올바른 결과를 반환하는지 확인한다.
- 실행한 검사 명령, 검사 대상, 검사 결과 및 실패한 경우의 판정 근거를 기록한다.
- 실행하지 못한 검사와 실행했지만 결과를 판정하지 못한 항목을 구분하고, 그 이유와 해결에 필요한 사항을 기록한다.
- 사람 또는 AI 에이전트의 판단이 필요한 항목은 판단할 내용과 이를 확인할 후속 검증 단계를 기록한다.
- 사람 또는 AI 에이전트의 의미 판단이 필요한 항목은 기계 검사 결과만으로 통과하거나 실패했다고 판정하지 않는다.

### 완료 조건

- 명세서의 작업 유형과 구현 단계에 기록된 변경 대상 및 영향 범위에 따라 필요한 기계 검사 항목과 대상이 식별되었다.
- 각 기계 검사 항목의 적용 여부, 필수 여부와 판정 기준이 개발 규격 및 명세서에 근거하여 기록되었으며, 적용하지 않는 항목은 그 이유가 기록되었다.
- 작업 대상 스킬에 적용하기로 한 모든 기계 검사 항목이 실행되었다.
- 필수로 지정된 기계 검사가 모두 통과했다.
- 실행한 모든 검사 명령과 각 명령의 적용 대상 및 실행 조건이 기록되었다.
- 실행한 모든 기계 검사의 통과 또는 실패 결과와 판정 근거가 기록되었다.
- 검사 실패가 발생했다면 실패 위치와 위반한 개발 규격의 항목이 기록되었다.
- 발생한 검사 실패가 누락되지 않았으며, 적용할 개발 규격과 명세서의 판정 기준에 근거하지 않고 통과 또는 적용 제외로 처리되지 않았다.
- 각 검사 결과가 판정한 개발 규격의 항목을 추적할 수 있다.
- 사람 또는 AI 에이전트의 의미 판단이 필요한 항목은 기계 검사로 확정한 결과와 구분되었으며, 판단이 필요한 이유와 내용 및 이를 확인할 후속 검증 단계가 기록되었다.
- 검사 과정에서 검사 스크립트를 새로 작성하거나 수정했다면, 해당 스크립트가 의도한 대상을 검사하고 올바른 결과를 반환하는지 확인되었다.

### 허용 전이

- 모든 완료 조건과 그 근거가 확인되면 `behavioral-validation` (동작 검증)으로 이동한다.
- 이동할 때는 전이 사유와 근거를 기록한 뒤 명세서 프론트매터의 `current_stage`를 `behavioral-validation`로 변경한다.
- 명세서의 요건과 구조 설계를 변경할 필요 없이 구현 결과를 수정하여 해결할 수 있으면 `implementation` (구현)으로 돌아간다.
- 파일과 디렉토리의 구조, 각 구성 요소의 역할과 배치, 참조 방향 또는 의존 관계를 다시 설계해야 하면 `structure-design` (구조 설계)으로 돌아간다.
- 검사 대상인 요건이 불명확하거나 검증 가능한 완료 기준에 문제가 있으면 `requirements-definition` (요건 정의)으로 돌아간다.
- 이전 단계로 돌아갈 사유가 없고 완료 조건을 충족하지 못하면, 부족한 내용과 원인 및 해결에 필요한 사항을 기록하고 `mechanical-validation` (기계 검사)에 머문다.
- 이전 단계로 돌아갈 때는 전이 사유와 근거를 기록한 뒤 명세서 프론트매터의 `current_stage`를 돌아갈 단계의 식별자로 변경한다.

### 산출물

- 작업 대상 스킬의 기계 검사 항목과 적용 여부
- 기계 검사에 사용한 명령과 각 명령의 적용 대상
- 기계 검사별 통과 또는 실패 결과
- 검사 실패가 발생한 위치와 위반한 개발 규격
- 실행하지 못한 검사와 실행했지만 결과를 판정하지 못한 항목
- 의미 판단이 필요한 항목과 그 이유 및 확인할 후속 단계

## 명세서 기록 항목

### 작업 대상 스킬의 기계 검사 항목과 적용 여부

- 검토한 기계 검사 항목과 각 항목의 검사 대상, 적용 여부 및 판정 기준을 적는다.
- 명세서의 작업 유형과 구현 단계에 기록된 변경 대상 및 영향 범위를 기준으로 해당 검사 항목과 대상을 선정한 근거를 적는다.
- 각 기계 검사 항목의 판정 기준이 근거로 삼은 개발 규격의 항목과 위치 및 명세서의 관련 요건을 적는다.
- 각 검사 항목이 필수인지 선택인지 구분하고, 그 판단의 근거가 되는 개발 규격 또는 명세서의 내용을 적는다.
- 각 검사 항목을 적용하거나 적용하지 않는 이유를 적는다.
- 적용 대상으로 정했지만 도구나 실행 조건의 문제로 실행하지 못한 검사는 적용 제외와 구분한다.

### 기계 검사에 사용한 명령과 각 명령의 적용 대상

- 기계 검사에 실제로 사용한 명령을 변경하거나 생략하지 않고 적는다.
- 각 명령으로 수행한 기계 검사 항목과 해당 명령을 적용한 파일, 디렉토리 및 설정을 명령별로 적는다.
- 각 명령을 실행한 작업 디렉토리와 실제로 사용한 입력, 설정 및 실행 환경을 적는다. 결과에 영향을 주는 실행 조건이 있다면 함께 적는다.
- 명령에서 사용한 검사 도구의 이름을 적고, 버전을 확인할 수 있으면 함께 적는다.

### 기계 검사별 통과 또는 실패 결과

- 실제로 실행하여 결과를 판정할 수 있는 기계 검사 항목의 판정 결과를 `통과` 또는 `실패`로 적는다.
- 각 검사 항목에 사용한 명령을 연결하고, 해당 명령이 반환한 종료 코드와 주요 결과 내용을 적는다. 그 결과가 해당 항목의 판정 기준을 충족하거나 위반한다고 판단한 근거를 함께 적는다.
- 검사 과정에서 새로 작성하거나 수정한 검사 스크립트가 있으면 해당 스크립트의 동작을 확인한 방법과 결과를 적는다.
- 재검사를 수행했다면 재검사 대상과 이유 및 결과를 적고, 현재 유효한 판정 결과와 근거를 갱신한다.
- 검사 실패를 통과 또는 적용 제외로 변경했다면, 해당 검사와 변경 전후의 판단 및 개발 규격과 명세서의 판정 기준에 따른 변경 근거를 적는다.

### 검사 실패가 발생한 위치와 위반한 개발 규격

- 실패한 검사 항목과 해당 검사에서 실패가 확인된 파일, 디렉토리 또는 설정의 위치를 적는다.
- 실패 위치를 세부적으로 확인할 수 있으면 해당 줄 번호나 설정 항목을 적는다.
- 검사 실패가 위반한 개발 규격의 항목과 해당 항목의 위치를 적는다.
- 검사 실패의 원인과 필요한 보완 작업을 적고, 허용 전이를 기준으로 보완할 단계와 그 이유를 적는다.
- 기록할 검사 실패가 없으면 `없음`으로 적는다.

### 실행하지 못한 검사와 실행했지만 결과를 판정하지 못한 항목

- 기계 검사 대상으로 정한 항목 중 실행하지 못한 검사와 실행했지만 결과를 판정하지 못한 항목을 구분하고, 각 항목의 검사 대상을 적는다.
- 검사 도구의 부재, 실행 조건의 미충족 또는 판정에 필요한 결과와 근거의 부족 등 각 항목을 실행하거나 판정하지 못한 이유를 적는다.
- 실행했지만 결과를 판정하지 못한 경우에는 실제로 관찰한 결과와 판정에 부족한 정보를 구분하여 적는다. 판정하지 못한 결과를 임의로 `통과` 또는 `실패`로 표시하지 않는다.
- 해당 항목으로 인해 충족하지 못한 현재 단계의 완료 조건을 적는다.
- 실행 또는 판정에 필요한 작업, 입력, 도구, 실행 환경과 권한을 적고, 사용자 판단이 필요하면 해당 내용을 함께 적는다. 이전 단계에서 보완해야 한다면 허용 전이에 따라 돌아갈 단계와 그 근거를 적는다.
- 실행하지 못한 검사와 실행했지만 결과를 판정하지 못한 항목이 없으면 `없음`으로 적는다.

### 의미 판단이 필요한 항목과 그 이유 및 확인할 후속 단계

- 기계 검사만으로 통과 또는 실패를 확정할 수 없어 사람 또는 AI 에이전트의 의미 판단이 필요한 항목을 적는다.
- 각 항목에서 판단해야 할 내용과 기계 검사만으로 판단할 수 없는 이유를 적는다.
- 기계 검사에서 식별한 중복 정의, 미완성 자리 표시자 또는 미사용 파일 등의 후보가 있다면, 해당 위치와 관찰한 사실을 적고 확정된 위반과 구분한다.
- 각 항목을 확인할 후속 검증 단계와 해당 단계를 선택한 이유를 적고, 판단에 필요한 자료와 근거의 위치를 함께 적는다.
- 각 항목의 판단을 후속 단계에서 수행해도 현재 단계의 완료 조건을 충족할 수 있는 근거를 적는다. 검사 도구나 실행 조건의 문제로 실행 또는 판정하지 못한 기계 검사를 의미 판단 항목으로 바꾸어 넘기지 않는다.
- 의미 판단이 필요한 항목이 없으면 `없음`으로 적는다.
