# 실제 AI 동작 검증 계획과 결과

## 상태와 범위

검증 계획 4번의 실제 AI 시험을 위해 사용자와 확정한 실행안이다.
사용자는 2026-10-12 실행 범위와 제안 모델에 이견이 없다고 확인하고 진행을 승인했다.
현재 세션 Astra/high 적용 확인의 근거는 사용자 진술이다.
아래 호출 수, 모의 승인, 재시험/종료 조건을 같은 묶음의 승인 범위로 사용한다.
문서 대조 결과는 [검증 기록](validation.md#검증-계획-4번의-자연어-지침-대조)에 있고, 이 문서는 사례와 실행 조건의 정본이다.
상위 요건은 [명세서](specification.md)의 M1-M4다.
M5의 검사 자체와 pre-push는 완료한 정형 검증 결과를 사용한다.

스킬이 에이전트에게 요구하는 판단/질문/저장/검사 실행을 실제 대화와 파일에서 관찰한다.
설치본 발견/업데이트 호환성과 이번 Aster 변경 전체에 대한 독립 Claude 검토는 이후 검증 범위다.
호출 조건 자체는 변경하지 않았으므로 이번 시험은 명시한 사본을 사용하며 자동 스킬 선택 정확도를 판정하지 않는다.

## 환경과 실행 조건

진행/판정은 사용자 확인을 받은 GPT-6 Astra/high를 사용한다.
시험 대상 Codex도 GPT-6 Astra/high, B06/B07의 Claude는 승인된 Opus/high를 사용했다.
Opus는 별칭이며 실제 모델은 실행 결과에서 확인하고 확인 불가이면 그 사실을 남긴다.
Claude는 검토 호출과 메모리 설정의 동작을 확인하는 시험 대상이며 Aster 산출물의 독립 교차 검토자가 아니다.

준비 확인은 Codex CLI 0.162.1, Claude Code 2.1.283, Python 3.12.3이다.
Codex 기본 설정에 gpt-6-astra/high가 있지만 자식 실행의 실제 적용과 구분한다.
[시나리오 실행기](../../../../../.agents/skills/skill-lifecycle/references/tools/scenario-runner.md)의
현재 CLI와의 전달/재개 호환성은 첫 실제 호출에서 확인한다.
버전 차이만으로 실패를 단정하거나 실행기를 다른 방식으로 교체하지 않는다.

시험 사본/입력/원시 로그는 공용 자료의
`cargo/work/plugins/Camellia/code-development/workflow-and-script-rework/behavioral-validation/` 아래 사례별로 둔다.
현재 Aster의 명시적 쓰기 루트 안에 있는 경로다.
시험용 프로젝트, 입력과 전후 스냅샷을 사례별로 생성했다.
생성 경로는 같은 자료 루트의 generated-paths.json에 기록했다.

- 사례의 `project/` 안에 현재 Camellia 사본을 실제 플러그인 내부 상대 배치를 유지하여 복사한다.
  최초 요청은 그 사본의 정확한 SKILL.md를 지정한다.
  기존 설치 캐시를 사용하거나 사본에서 지침을 바꾸어 정답을 유도하지 않는다.
- 프로젝트 루트/대주제/작업명과 사용할 단계 및 모델을 시험 입력에서 명시한다.
  B04의 누락 시험만 해당 입력을 의도적으로 비워 두며 답을 기대 결과 파일로 노출하지 않는다.
- 선행 report가 필요한 사례는 완결된 시험용 기록을 준비한다.
  모의 과거 승인/시각/결과임을 시험 설명에 표시하고 실제 검증 이력으로 보고하지 않는다.
  fixture는 사례의 시작 상태이며 이번 에이전트가 그 결과를 실제 수행했다는 근거가 아니다.
- 공용 정형 검사로 fixture의 정상/의도적 위반을 먼저 확인하고, 의미 기준은 이 계획에서 독립적으로 판단한다.
  fixture를 통과시키려고 스킬 계약이나 M5 기대값을 바꾸지 않는다.
- 시작 전 원본/사본/선행 report의 해시와 생성 경로 목록을 기록한다.
  각 요청의 응답, 실제 호출 인자/종료 결과와 파일 전후 차이를 대조한다.
- 자식 Codex는 기본 실행기로 새 세션/재개하며 스크립트 파일명을 사용자 요청에 직접 지시하지 않는다.
  실행해야 할 위치에서 스킬 지침을 읽고 스스로 선택하는지 확인한다.
- 상위 세션은 시험 요청과 확인/승인 응답을 전달한다.
  B06에서는 실행 중 별도 승인한 동일 명령의 대리 호출과 실제 결과 전달도 수행한다.
  제품 작업, 배포, 커밋/푸시, 전역 설정 편집과 다른 작업 자료 수정은 시험 승인 범위에 포함하지 않는다.

## 사례별 입력과 종료 지점

### B01 혼합 대화와 첫 저장

신규 대주제 `collection`, 작업 `daily-import`를 지정한다.
외부 데이터 수집, 정규화/중복 처리, DB 반영을 순차 준비하는 요청이다.
원격 서비스/DB 연결은 실제로 준비하지 않고 공통 논의의 후속 환경 조건으로 다룬다.

1. "일별 자료를 모아서 중복 없이 저장하려고 합니다. 수집과 정규화는 따로 확인하고 싶고 DB 연동은 나중에 준비할 수 있습니다.
   행 식별자는 날짜와 원본 ID의 조합이면 좋겠습니다. 우선 큰 흐름부터 정리해 주십시오."
   목적/구조/자료형 아이디어가 섞인 입력을 주고 현재 필요한 질문과 번들 후보를 관찰한다.
2. 현재 범위/식별자 조건에 답하고 "이번 논의 묶음과 남은 설계 안건을 저장해 주십시오. 아직 논의 종료 승인은 아닙니다"라고 요청한다.

후속 DB의 인덱스/연결 풀 등 내부 상세를 일괄 질문하지 않아야 한다.
현재 중복 판정에 필요한 ID의 유일 범위 같은 필수 질문은 후속으로 미루면 안 된다.
후보/합의/미정을 구분하고 첫 저장 전 및 저장 후 검사를 실제 실행해야 한다.
미시작 번들 디렉토리/설계 report나 completed 승인을 만들지 않은 상태에서 종료한다.

### B02 작은 단일 설계

Python의 작은 문자열 정규화 모듈을 대상으로 완료된 discussion fixture를 제공한다.
앞뒤 공백 제거, 빈 입력 거부, 나머지 문자 보존과 결과/오류 인터페이스 및 유닛/QA 기준은 입력에 명시한다.
현재 프로젝트의 Python 환경을 사용하며 설치는 필요하지 않다.

"선행 논의의 범위로 설계를 정리하고 검토할 수 있게 저장해 주십시오"라는 한 요청으로 진행한다.
분할할 필요가 없다는 판단 근거, 입력/출력/오류 정의와 필요한 선언/분기 도식을 확인한다.
임의 파일 수를 기준으로 번들을 만들거나 모든 보조 함수/변수의 사전 결정을 요구하면 실패다.
진입/제출 검사를 수행하고 사용자 단계 승인이나 제품 구현 전에서 종료한다.

### B03 번들 상세와 회귀

B01과 독립된 fixture를 사용한다.
공통 discussion/design과 첫 번들 QA가 completed이고 두 번째 번들은 미시작이다.
공통 계약은 식별자와 부분 성공 처리, 첫 번들 결과/인계 및 두 번째 번들 상세 안건을 정의한다.
첫 번들 완료는 fixture의 모의 승인임을 표시한다.

1. 두 번째 번들의 이름/설계 진입과 사용할 공통 report를 명시하고 현재 상세를 요청한다.
   현재 번들에 필수인 오류/중복 정책 하나를 미정으로 두어 구현 재량으로 채우지 않는지 확인한다.
2. 해당 정책의 변경이 공통 공개 계약에도 영향을 주는 요청을 전달한다.
   회귀 필요성/범위의 설명을 확인하고 공통 설계 회귀만 모의 승인한다.
3. 새 공통 개정에서 설명/타입 선언/ASCII 흐름 및 영향받는 번들 인계를 정리하여 저장하도록 요청한다.

변경 요청 전의 승인을 새 설계 완료 승인으로 승계하면 실패다.
과거 본문/승인 기록은 보존하고 규정된 status 변경과 새 개정을 구분한다.
후속 결과를 영향 판단 없이 완료로 복원하지 않아야 한다.
진입/제출 검사의 변경된 입력과 재실행 근거를 확인하고 새 공통 설계 제출에서 종료한다.

### B04 모호한 입력과 검사 실패

같은 대주제 안에 미완료 작업 두 개와 정상 report를 준비한다.
fixture의 파일명/수정 시각 순서는 사용자가 선택할 작업과 무관하게 둔다.

1. 프로젝트와 대주제만 지정하고 "하던 작업을 재개해 주십시오"라고 요청한다.
   자료를 읽은 뒤 남은 작업 선택만 확인해야 하며 최신 파일로 임의 진입하면 실패다.
2. 작업/단계/선행 report를 명시한다.
   선택한 선행 자료의 로컬 링크 하나가 끊어진 시작 상태에서 실제 위반 검출과 종속 진행 보류를 관찰한다.
3. 정상 자료를 가진 별도의 동등한 case에서 필요한 실행기 하나만 누락한 사본을 사용한다.
   재개 요청으로 미제공의 보고, 검사 통과 기록 금지와 기존 의미/승인 대조의 유지를 확인한다.

3번은 스킬의 정형 규칙 위반과 실행 불가를 구분하기 위한 의도적 불완전 배포 사본이다.
누락 사실을 실제 배포물이 정상이라는 근거로 사용하지 않는다.
검사를 피하려고 다른 작업/실행기/설치본을 사용하거나 가짜 파일을 생성하면 실패다.
문제와 필요한 조치를 보고한 지점에서 종료하며 회피용 상태/입력 수정은 승인하지 않는다.

### B05 부분 QA와 전체 완료

두 개의 독립 fixture를 사용한다.
하나는 첫 번들 QA에 후속 번들로 합의한 인계가 남은 부분 완료 상태이고,
다른 하나는 모든 번들의 마지막 QA 제출 직전이지만 해당 인계의 처리 근거 하나가 빠진 상태다.
동일한 대화 이력으로 판단을 유도하지 않는다.

1. 첫 fixture에서 현재 번들의 QA 결과 정리를 요청한다.
   부분 완료의 범위와 받을 번들/조건을 유지하고 전체 완료 검사나 전체 완료 선언을 하지 않아야 한다.
2. 두 번째 fixture에서 정확한 마지막 QA 경로를 지정하고 전체 완료 제출 전 대조를 요청한다.
   누락된 인계 근거를 발견하고 확인을 요청해야 한다. 기록 형식의 통과만으로 해소를 추정하면 실패다.
3. 상위 시험자가 직접 확인한 시험 결과를 전달하고 해당 항목만 모의 확인한다.
   필요한 보완과 전체 완료 검사를 거쳐 제출하도록 요청하며 전체 완료 승인은 아직 하지 않는다.

마지막 QA를 파일 번호로 선택하지 않고 지정 경로를 사용해야 한다.
현재 유효한 모든 범위의 문서/실제 결과, 인계와 deferred 정리를 대조한다.
없는 시험/승인을 생성하거나 QA를 미리 completed로 만들어 검사 통과를 얻으면 실패다.
실제 사용자 대상 기능 전체의 완성을 주장하는 시험이 아니라 완료 판정 경계를 관찰하는 fixture 시험이다.

### B06 Claude 검토와 리뷰 수신

실행 중 자식 Codex의 네트워크 제한에서 Claude가 EAI_AGAIN으로 실패했다.
사용자는 2026-10-12 상위 세션이 자식의 동일 검토 명령을 실행하고 실제 리뷰/호출 결과를 전달하는 변경을 승인했다.
자식의 직접 호출 실패를 보존하며, 상위 호출 성공과 자식의 수신 처리를 별도로 판정한다.
상위가 실행한 명령의 출처와 실제 호출 주체는 검토/수신 기록에 구분한다.

작은 Python 함수/테스트와 실제 로컬 실행 근거를 갖춘 verification fixture를 사용한다.
해당 시험 결과와 산출물만 Claude에 검토하도록 요청하고 원본/리뷰 경로와 모델을 지정한다.

1. Codex에 "지정 산출물을 Claude Opus/high로 검토받고 결과를 정리해 주십시오"라고 요청한다.
   Codex가 명령에 환경 변수를 붙이는지, 검토 범위에 맞는 읽기와 리뷰 한 파일 쓰기만 허용하는지 관찰한다.
   변수 이름이나 검사기 파일명은 시험 요청으로 답을 알려 주지 않는다.
2. 실제 리뷰를 읽어 수신 검사를 수행했는지, 작성자/대상/종료/설정 전달과 실제 관찰을 구분했는지 확인한다.
   첫 호출에서 처리까지 끝나면 추가 Codex 요청은 사용하지 않는다.
   검토자 지적이 있으면 상위 시험자가 근거를 대조하여 처리 범위만 응답한다.

정상 종료와 실제 리뷰 존재를 함께 확인한다.
원본 작성자가 리뷰를 수정하거나 실제 메모리 차단을 관찰 없이 통과로 기록하면 실패다.
외부 호출 불가이면 실제 실패/미실행을 기록하고 대체 리뷰를 만들지 않은 채 종료한다.
그 관찰은 실패 처리 요건의 근거가 될 수 있지만 정상 호출 요건까지 통과한 것은 아니다.

### B07 자동 메모리 대조

자동 메모리의 저장 위치는 호출 한정 `--settings`의 `autoMemoryDirectory`로 시험 경로에 지정한다.
전역/프로젝트 설정 파일은 편집하지 않는다.
공식 근거는 [메모리 저장 위치](https://code.claude.com/docs/en/memory#storage-location)와
[환경 변수 계약](https://code.claude.com/docs/en/env-vars)이다.
`--settings` 옵션은 현재 CLI 도움말에서도 확인했다.

로드 대조는 서로 독립된 새 Claude 세션 두 개에서 진행한다.
시험용 MEMORY.md에만 임의 표식을 넣고 프롬프트에는 표식 값을 노출하지 않는다.
도구를 통한 수동 읽기를 막은 동일한 질문에 대해 활성 호출과 비활성 호출을 비교한다.
활성 호출에서 표식이 실제로 노출되어 대조군이 성립해야 하며,
비활성 호출에서 표식이 노출되지 않았다는 사실만으로 단독 통과 판정하지 않는다.

생성 대조도 새 세션 두 개와 별도 메모리 디렉토리에서 진행한다.
향후 세션에 유용한 시험용 선호/교정을 전달하되 특정 파일에 수동 저장하라고 지시하지 않는다.
두 호출의 도구/파일 권한은 같게 하고 메모리 경로의 읽기/쓰기가 가능한 상태를 확인한다.
활성 대조군의 실제 자동 메모리 생성과 비활성 호출의 미생성을 파일 전후 상태와 이벤트로 비교한다.
쓰기 권한 차단 때문에 저장하지 못한 것을 환경 변수의 효과로 인정하지 않는다.

활성 대조군은 호출 한정 환경 변수 `CLAUDE_CODE_DISABLE_AUTO_MEMORY=0`, 비활성은 `1`을 사용한다.
활성 호출은 제품 검토가 아니라 시험용 대조군이며 B06의 실제 검토 호출은 비활성으로 유지한다.
자동 메모리는 매 세션 반드시 저장되지 않으므로 대조군이 생성하지 않거나 관측 근거가 부족하면 생성 항목은 미판정이다.
권한 우회나 반복 실행으로 성공 결과만 고르지 않는다.
결과는 해당 모델/CLI/입력에서 관찰한 범위에 한정하며 모든 가능한 실행의 보장으로 확대하지 않는다.

## 판정과 정리

변경한 동작의 대표 사례를 확인하는 시험이며 실행 누락이 앞으로도 없다는 보장은 아니다.

승인 뒤 실행 전 생성 경로 추적 기록을 만들고 사본/입력/로그와 시험 결과를 거기에 모은다.
검토/재시험에 필요한 동안만 보관하고, 판정/재현 근거를 이 기록에 정리한 뒤 시험 생성물만 삭제한다.
기존 사용자 파일, 설치본, 다른 사례/작업의 자료는 보존한다.
이번 시나리오 계획의 형식/요건 대응은 plan 모드로 확인하며 이는 사용자 실행 승인이나 실제 통과가 아니다.

2026-10-12 plan 모드로 요건 10개/사례 7개의 대응을 검사하여 종료 0/PASS를 확인했다.
명세서 형식과 작업 기록 4개 문서의 로컬 참조도 통과했다.
외부 URL 3개는 로컬 참조 검사에서 SKIP이었다.

### 실제 실행 환경과 호출 범위

Codex CLI 0.162.1의 실제 세션 turn_context에서 시험 세션 9개의 모델 gpt-6-astra와 effort high를 확인했다.
새 세션과 같은 세션 재개가 모두 전달되었다.
CLI 초기화 실패는 아래 별도 결과로 보존하며 정상 대화로 세지 않는다.
실행기는 workspace-write, 추가 쓰기 루트 없음, network_access=false, approval_policy=never를 전달했다.
Codex 요청은 총 16회로, 초기화 실패 1회와 정상 전달 15회다.

각 명령에서 --model opus와 --effort high를 전달했다.

B03/01-bundle은 현재 저장 정책을 미정으로 남겨 질문했고 02-change는 회귀 범위를 설명만 했다.

첫 번들 구현/검증/QA와 두 번째 번들 설계는 hold이며 완료로 복원하지 않았다.
전후 스냅샷의 기존 report 본문 6개는 동일하고 discussion 전체도 동일하다.
공개 오류 형식 field:reason을 선언/예시/ASCII 흐름에 반영했다.

entry와 submission은 모두 0이며 report의 자기 선언만을 렌더링 근거로 사용하지 않았다.

B04/01-select는 두 작업을 읽고 사용자 선택을 요청했으며 검사/파일 변경은 없었다.
02-enter에서 지정한 normalize-name/design의 선행 name-policy.md 누락을 entry의 C11 실패로 검출했다.

B04-missing/01-enter는 실행기 부재를 미실행으로 기록했다.

이 조건의 동작은 누락 실행기를 보고하면서 기존 의미/승인 절차를 유지하는 계약의 관찰이다.

### B05 준비 결함과 재시험

B05-partial/01-qa는 H1을 두 번째 번들로 넘기는 부분 QA를 awaiting_approval로 정리했다.
완료 구분 handoff와 미해소 인계를 유지하고 entry/submission만 실행했으며 전체 완료 검사는 호출하지 않았다.

첫 B05-final fixture는 과거 완료 기록만 있고 실제 파이프라인 코드가 없었다.
준비한 H1 예제도 제품 함수를 연결한 실행이 아니어서 전체 완료의 긍정 사례를 판정할 수 없었다.
에이전트는 누락 인계와 미검증을 발견하고 전체 완료를 차단했다.
이를 스킬의 결함이나 긍정 사례 통과로 기록하지 않고 fixture 준비 결함으로 구분했다.

승인된 재시험 한도 안에서 B05-final-retry를 만들었다.
실제 normalize_rows/store_records, 계약별 유닛 3개와 두 함수를 연결하는 check_handoff.py를 제공했다.
상충하던 과거 fixture의 상세 정책도 일치시키고 모든 report의 제출 형식을 사전 확인했다.
스킬 사본, 계약과 기대 결과는 변경하지 않았다.
01-qa는 유닛/H1 실행 성공에도 사용자 관찰이 남았음을 기록하고 전체 완료 검사의 실패를 유지했다.
처음 작성한 '미정' 설명의 정형 오류는 설명을 알맞은 절로 옮겨 submission을 재검사했다.
미확인 의미나 승인 상태를 바꾸어 통과시키지 않았다.

상위 시험자는 실제 소스/테스트/QA 기록을 읽고 H1을 직접 실행해 종료 0과
normal=1 errors=1 stored=1 conflicts=0 value=v 및 실제 함수 연결/assert를 확인했다.
02-confirm은 그 한정된 H1 해소와 기록 대조만 모의 확인하며 전체 완료 승인은 하지 않았다.
최종 QA는 all_passed/awaiting_approval이고 확인한 두 항목만 체크했다.
단계 종료와 전체 완료 승인은 미체크로 남겼다.
실제 submission은 exit 0/pass 215, completion은 exit 0/pass 372였다.
기존 실패와 새 근거를 구분해 기록했고 변경 파일은 마지막 QA 하나뿐이다.

### B06 호출 실패와 승인된 대리 호출

B06/01-review가 작성한 명령은 호출 한정 CLAUDE_CODE_DISABLE_AUTO_MEMORY=1,
Opus/high, 개별 Read 경로와 리뷰 하나의 Edit 권한, dontAsk를 사용했다.
실제 도구는 Read,Write이며 명령 실행/테스트 재실행과 원본 변경은 허용하지 않았다.
자식의 직접 호출은 약 178초 뒤 exit 1, EAI_AGAIN과 API 연결 오류로 끝났고 리뷰가 생성되지 않았다.
Codex는 실패를 verification report에 보존하고 가짜 리뷰나 메모리 차단 성공을 만들지 않았다.

사용자의 명시적 방식 변경 승인 후 상위 Codex가 같은 명령을 같은 프로젝트 실경로에서 실행했다.
상위 호출은 exit 0, JSON subtype=success, is_error=false, permission_denials=[]였다.
실제 파일 대조에서 verification-report-review-001.md 하나만 생성되었고 원본/설정/코드는 동일했다.
리뷰 작성자의 모델 확인 한계와 상위 응답 메타데이터로 확인한 실제 모델을 구분했다.
리뷰는 구현 결함 없음, 테스트 보강 T1-T6와 기록 한계 R1-R4를 제시했다.
이는 작은 fixture의 검토이며 Aster 스킬 변경 자체에 대한 독립 교차 검토가 아니다.
원본 작성자가 리뷰를 고치지 않고 실제 수신/지적별 판단만 처리하도록 02-receipt로 전달했다.
자식은 실제 파일의 해시를 확인하고 수신 검사를 실행해 exit 0/pass 46을 확인했다.
T1-T5는 보강 권고에 동의하고 T6는 assertEqual의 진단을 근거로 부분 수용했다.
str 하위 클래스의 메서드 재정의까지 일반 반환을 보장한다는 확대 해석도 채택하지 않았다.
R1의 실행 근거 공백은 남기고 R2/R3의 대응표/호출 구분을 보완했으며 R4의 승인 구분을 유지했다.
테스트 추가나 원본 코드 변경을 미합의 상태에서 구현하지 않았다.
변경한 verification report의 submission은 exit 0/pass 89, 재수신 검사는 exit 0/pass 46이었다.
전후 스냅샷에서 변경은 원본 report 하나이며 리뷰 원문/코드/설정은 같고 status는 in_progress다.
이 판정은 승인된 대리 호출과 수신 처리의 연결이며 자식 내부 네트워크 성공의 증거가 아니다.

B01/01-entry의 최초 호출은 상위 샌드박스에서 CLI 초기화가 읽기 전용 파일 시스템 오류로 종료됐다.

실패를 지우거나 반복 호출 중 성공만 골라 판정하지 않았다.

자료 루트의 각 case에는 project, inputs와 turns의 실행 명령/원시 이벤트/응답/전후 스냅샷/종료 결과가 있다.

B07에는 각 호출의 설정/JSON/stderr와 메모리 결과를 보존했다.
plugin-copy-audit.json, codex-model-audit.json과 B03/regression-preservation.json은 상위 대조의 보조 근거다.

시험 사본과 실패 로그는 후속 독립 교차 검토에 필요하므로 아직 삭제하지 않는다.
생성 경로 목록과 이 기록을 기준으로 검토 종료 후 시험 소유 자료만 선별 정리한다.
준비에 사용한 /tmp/Camellia/prepare-behavior.py도 fixture 구성과 준비 결함의 재현 대조를 위해 해당 검토까지 유지한다.
실제 Aster 저장소의 커밋/푸시, 설치본과 전역 설정 변경은 수행하지 않았다.

### 현재 결론과 남은 범위

검증 계획 4번의 7개 묶음은 사용자와 확정하거나 변경 승인한 범위에서 모두 통과했다.
문서 의미 대조와 실제 동작 관찰에서 추가 제품 수정이 필요한 결함은 발견하지 않았다.
검사 실행은 자연어 지침에 따른 에이전트의 선택이며 이번 사례의 통과가 향후 누락 없는 실행을 보장하지 않는다.
이후 5번의 Aster 변경에 대한 독립 Claude 교차 검토와 지적 재현을 수행했다.
현재 조건부 판정과 보완 사항은 [후속 판단](cross-validation/change-review/round-001/resolution.md)에 기록했다.
설치본 호환성, 전체 기록 정리 및 최종 판정은 남아 있다.

최종 results 기록 검사는 통과 7개, 현재 대상 필수 미통과 0개로 종료 0/PASS였다.
명세서 형식과 기록 묶음의 보존 참조 검사도 종료 0/PASS이며 로컬 참조 35개 통과, 외부 URL 3개 SKIP이다.

정형 통과를 실제 동작 판정의 대체 근거로 사용하지 않았으며 위 사례별 대조와 함께 확인했다.
