# 개발 진행 방식과 문서 및 스크립트 개편

## problem-definition (문제 정의)

### 진입 조건 확인

기존 code-development 작업을 이어받지 않고 신규 작업으로 다시 진행하기로 했다.
작업 후보와 새 브랜치 및 기록 경로를 확정했다.
자동 메모리 비활성화의 지침 수정과 정적 확인을 마쳤다.
이어서 뼈대 중심 대화와 번들 분할 판단의 지침을 수정했고 구현 당시에는 테스트를 후속 일괄 수행으로 남겼다.
세 번째로 문서의 완결성/가독성 기준과 중간 및 최종 확인 시점을 연결하는 지침 수정을 마쳤다.
네 번째 작업은 기존 스킬 내부 검사기를 제거하고 현행 문서에서 검사 후보를 다시 추출했다.
14개 후보는 아래 실행 계약의 적용 범위와 예외를 기준으로 채택했다.
실행 시점별 독립 실행기 5개와 인자 확보/결과 처리 지침을 정리하고 각 수행 절차에 연결했다.
후속 요청의 1-2번에 해당하는 계약 확정과 자연어 지침 마무리를 수행했다.
이어 3번의 스킬 내부 검사기 코드와 의존성 목록을 구현했고 구현 당시에는 실제 검증을 후속 일괄 수행으로 남겼다.
후속 4번인 M5의 개발용 검사 상세 설계를 정리했다.
실행기 5개, 공통 지원, 검사별 입력/기대 결과와 기존 테스트 대체 및 pre-push 등록 계획을 문서화했다.
사용자가 제안한 모델로 변경하고 진행을 요청하여 5번 구현을 수행했다.
M5의 개발용 실행기 5개/공통 지원 2개/등록 파일을 작성하고 기존 테스트를 대체했다.
이후 승인받은 검증 계획 1-3번을 일괄 수행했고 정적/실행/검사 자체/버전 격리와 로컬 pre-push 검증이 통과했다.
처음 발견한 제품 결함 2개는 계약을 유지하여 구현을 수정한 뒤 재검증했다.
검증 계획 4번의 모델 변경 확인 후 자연어 지침을 대조하고 실제 AI 시나리오 7개 묶음을 확정하여 실행했다.
내용 검토 결과는 validation.md, 시나리오별 입력/실행/판정과 한계는 behavioral-validation.md에 둔다.
Claude 독립 교차 검토와 지적 재현을 수행했고 현재 판정은 조건부 적합이다.
후속 자연어 수정에서 실행 계약의 경계와 검사 설계를 정렬하고 지속 안내의 작업 이력을 정리했다.
이어서 사용자 모델 변경 확인과 요청으로 코드 보완 및 관련 정형 재검증을 수행했다.
5개 등록 검사 863개 항목과 C10 판정 무력화 사본의 검출을 확인했다.
2차 독립 재검토와 N1-N3 보완 후 정형 검사 869개가 통과했다.
설치본 호환성은 아직 수행하지 않았다.
선행 단계의 완료 근거를 현재 조건에 대조해 cross-validation의 커밋 관문으로 진행한다.
부분 작업의 승인/실행 근거를 보존하며 현재 근거 대조 시점의 전이로 기록한다.

### 스킬을 통해 해결해야 할 문제

논의와 설계를 뼈대부터 순차적으로 진행하고 명세 및 보고서의 품질을 개선하려는 요청이 있다.
Claude 교차 검토의 자동 메모리 제어와 스킬 내부 및 개발용 검사 스크립트의 개편도 후보에 포함한다.
변경 전 Claude 교차 검토 호출 지침에는 자동 메모리를 비활성화하는 설정이 없었다.
검토용 호출에서 자동 메모리를 생성하거나 로드하지 않도록 호출 범위를 제어해야 한다.

실제 대화에서는 목적, 요구사항과 설계 아이디어가 섞여 나온다.
공식 단계별로 대화 내용을 제한하면 이미 나온 내용을 다시 질문하거나 필요한 논의를 막을 수 있다.
전체 방향을 정하기 전에 후속 상세까지 질문하지 않도록 현재 결정 범위와 질문 깊이의 기준이 필요하다.
번들 분할도 전체 목적과 구조를 파악하는 과정에서 판단하고 구체화해야 한다.
문서를 마지막에만 정리하면 중간 구현과 번들 진입에서 필요한 정의의 누락이나 충돌을 놓칠 수 있다.
반대로 매번 전체를 정리하면 후속 상세를 앞당겨 요구하거나 과거 승인본을 불필요하게 다시 쓰게 된다.
현재 범위에서 필요한 정보와 표현을 갖추고 회귀/번들/전체 완료의 확인 범위를 구분해야 한다.
M4는 자연어 해석에 맡겼을 때 판정이 달라질 수 있는 정형 규칙을 코드로 판정하려는 작업이다.
기존 검사기의 기능 구분을 승계하지 않고 현재 스킬 문서에서 후보를 다시 추출한다.
M5는 code-development 자체의 기능 안정성을 위해 커밋/푸시 전 정형 조건과 실행 계약을 검사한다.
다른 스킬에서는 검사 내용이 아니라 파일 배치, 보조 모듈, 등록과 호출 구조를 참고한다.
기존 pre-push가 변경 경로에서 code-development를 선택하면 등록한 검사를 모두 실행하며,
실패, 실행 오류와 시간 초과는 푸시를 차단한다. 변경 스킬 선택 기준은 유지한다.
기존 작업의 상세 요건, 구현 결과와 검증 판정은 이번 작업의 확정 근거로 승계하지 않는다.

### 스킬을 사용하는 주체와 스킬이 사용되는 상황

대상은 Camellia의 code-development를 사용하는 사용자와 수행 에이전트다.
M1은 Codex가 Claude CLI를 직접 호출하여 교차 검토를 수행하는 상황에 적용한다.
M2는 논의와 설계 내용이 섞인 개발 대화, 전체 구조의 구체화와 작업 분할 판단에 적용한다.
M3는 모든 단계 report와 연결된 상세 문서를 작성/보완하고 구현/검증에 사용하거나 최종 인계하는 상황에 적용한다.
M4는 설치된 code-development를 사용하는 에이전트가 선택한 개발 작업의 기록을 검사하는 상황에 적용한다.
M5는 Aster에서 code-development 스킬을 개발하여 커밋/푸시하기 전 최종 정형 항목을 검사하는 상황이다.

### 문제가 해결되었을 때 기대하는 결과

현재 작업에 맞는 깊이로 논의와 설계를 순차적으로 진행하고, 작성된 명세와 보고서를 이해하고 활용하기 쉽게 한다.
Claude 교차 검토 프로세스에만 자동 메모리 비활성화를 적용한다.
스킬 내부 스크립트는 확정된 규칙 중 코드로 판정할 수 있는 항목을 기계적으로 검증하는 것이 목적이다.
같은 명시적 입력과 파일 상태에서 참/거짓을 결정할 수 있는 항목만 검사 후보로 삼는다.
의미 해석이나 실제 승인 여부를 코드로 추정하지 않는다.
검사기는 code-development에 종속되어 Camellia 플러그인과 함께 배포되며 스킬 사용 중 실행한다.

M5는 스킬 변경의 최종 정형 검사를 저장소에서 재현하고 pre-push에서 같은 검사를 호출할 수 있게 한다.
스킬 실행 중의 소비자 프로젝트 기록 검사와 구분하며 의미/품질에 대한 자연어 판단은 기계 검사로 대체하지 않는다.

### 요청한 스킬의 생성, 변경, 통합 또는 폐기가 필요한지에 대한 판단과 근거

기존 code-development와 관련 검사 스크립트를 개편하는 요청이므로 작업 유형은 update다.
구체적인 변경 필요성과 범위는 후보별 문제 정의를 통해 확정한다.

### 스킬이 수행할 범위와 제외할 범위

작업 순서는 다음과 같다.

1. Claude 교차 검토 호출의 자동 메모리 비활성화.
2. 뼈대 우선의 단계적 논의와 설계 진행.
   논의의 순서와 깊이, 단계 및 논의 범위 전환 안내를 한 작업으로 다룬다.
3. 명세와 보고서의 완결성 및 가독성 개선.
4. code-development 내부에서 사용하는 스크립트 개편.
5. `tools/tests/skills/code-development/`의 검사 스크립트 개편.

1번은 지침 수정 및 정적 확인을, 2번은 아래 요건과 설계에 따른 지침 수정을 마쳤다.
3번은 아래 M3에 따라 공통 문서 품질과 확인 시점의 지침 수정을 마쳤다.
M4는 기존 scripts의 Python 파일 7개와 그 전용 requirements.txt를 제거한 뒤,
스킬 지침과 템플릿에서 결정적으로 판정할 수 있는 검사 후보를 다시 추출한다.
삭제된 실행기를 호출하지 않도록 기존 검사 안내와 연결 문구도 정리한다.
기존 구현 제거와 후보 추출에 이어 실행 계약 및 자연어 지침을 확정했다.
후속 3번 요청에 따라 확정한 계약의 새 검사기 코드 구현을 마쳤다.
M4는 실행 시점별 독립 실행기 5개와 인자 출처/실행 절차를 문서에 반영한다.
세부 CLI/파싱/출력 계약은 배포용 상세 계약에 정의한다.
M5는 구조, 참조, 템플릿, 실행 계약과 report 판정의 독립 검사기 5개로 구성한다.
4번의 상세 설계에 이어 사용자 모델 변경과 진행 요청으로 5번 코드/등록 구현까지 수행했다.
구현 요청에는 테스트 실행을 포함하지 않았으며 이후 사용자 승인으로 검증 계획 1-3번을 수행했다.
사용자 저장소의 커밋/푸시와 설치/배포는 수행하지 않는다.
스킬 내부 스크립트는 앞선 지침 개선을 마친 뒤, 개발용 검사 스크립트는 마지막에 다룬다.
기존 작업 브랜치와 명세서는 새 작업의 기준으로 사용하지 않는다.
이전 명세/검증 기록 3개는 사용자 후속 요청으로 삭제했으며 기존 작업 브랜치의 삭제는 별도 후속 범위로 유지한다.

### 후속 단계에서 확인할 사항

후보별 문제, 기대 결과와 포함/제외 범위는 현재 단계에서 확인한다.
구체적인 동작과 검증 기준은 요건 정의에서, 변경 대상 스크립트의 실제 역할과 의존 관계는 기존 구성 확인에서 검토한다.
기존 작업의 결과를 재사용하는 전제로 진행하지 않는다.

M1-M5의 문제, 사용 주체/상황, 기대 결과와 포함/제외 범위를 완료 조건에 대조했다.

### 스킬의 사용 형태(내부용 또는 플러그인 배포용)

Camellia 플러그인의 기존 code-development를 변경한다.

- 소스: `plugins/Camellia/skills/code-development/`.
- 개발용 검사 대상: `tools/tests/skills/code-development/`.
- 기록 루트: `records/plugins/Camellia/code-development/workflow-and-script-rework/`.
- 명세서: 위 기록 루트의 `specification.md`.

### 지원 대상 CLI와 각 CLI에 적용할 호환성 요건

M1의 호출 제어는 Codex에서 Claude를 직접 호출할 때 적용한다.
M2는 Codex와 Claude가 공통으로 사용하는 대화 및 진행 지침이다.
M3도 양 CLI의 공통 Markdown 및 설계 산출물 기준으로 적용한다.
기존 Markdown 지침과 리뷰 형식은 유지하며 별도 하네스 전용 파일을 추가하지 않는다.
양 CLI 설치본의 실제 동작은 이번 정적 확인에 포함하지 않았다.

### 스킬 호출 조건과 호출 제외 조건

M1-M4는 기존 code-development의 적용 조건과 단계별 수행 중 해당 절차에 적용한다.
M5는 기존 pre-push의 변경 경로 판정에서 code-development가 선택된 경우 등록 검사 전체를 호출한다.
다른 스킬만의 변경, 원격 ref 삭제와 스킬 경로 밖 변경은 기존 공용 선택 기준을 유지한다.
커밋 전 수동 검사에는 작업 트리를 명시하며 스킬 사용 중 M5를 호출하지 않는다.

### 스킬 실행에 필요한 입력과 기대 결과

M4의 입력과 결과는 아래 실행 단위 및 배포용 실행 계약을 따른다.
M5는 대상 저장소와 revision 또는 working-tree 선택을 받고 정형 조건 및 동작 사례의 boolean 결과를 반환한다.
필수 입력/자료/의존성 부족은 오류로 구분하고 파일/인덱스/커밋을 수정하지 않는다.
선택 규칙, 필수/선택 인자와 결과 스키마는 개발용 검사 안내에서 정의한다.

### 반드시 수행해야 하는 동작과 에이전트가 재량으로 판단할 수 있는 동작

M1: Codex가 교차 검토를 위해 Claude CLI를 직접 호출할 때
`CLAUDE_CODE_DISABLE_AUTO_MEMORY=1`을 해당 명령의 환경 변수로 전달한다.
모델과 강도 및 기존 도구/파일 권한은 승인된 검토 범위를 유지한다.
전역/프로젝트 설정 파일, 셸 초기화 파일이나 지속되는 export는 변경하지 않는다.

호출자는 전달한 환경 변수와 종료 결과를 원본 report에 기록한다.
실제 메모리 생성/로드 차단의 관찰 여부와 미확인 범위를 구분한다.
리뷰 템플릿은 호출자가 전달한 설정과 검토자가 직접 확인한 결과를 구분하여 기록하도록 안내한다.

M2: 대화는 현재 주제와 결정 범위를 기준으로 진행하며 목적, 요구사항과 설계 아이디어가 섞여 나오는 것을 허용한다.
현재 공식 단계와 다르다는 이유로 논의를 차단하거나 이미 확인한 내용을 다시 질문하지 않는다.
전체 목적과 범위에서 주요 구성 요소의 책임/연결/의존 관계로 뼈대를 구체화하고 현재 작업의 상세로 좁힌다.
질문에 대한 답이 현재 범위, 공통 구조, 순서 또는 필수 계약/안전성 판단에 영향을 주면 지금 확인한다.
후속 작업 내부에만 필요한 상세는 해당 작업의 설계 안건으로 남기고 구현 재량은 기존 SDD 기준을 따른다.

번들 분할은 대화 주제 수로 결정하지 않는다.
독립적인 구현/검증/QA 가능성, 의존/준비 조건과 한 번에 검토할 결정의 규모를 근거로 후보를 제안한다.
공통 뼈대에서 분할 여부와 경계 및 순서를 합의하며 단일 작업 유지도 허용한다.
후속 번들 상세를 공통 설계의 완료 조건으로 요구하지 않는다.

에이전트가 내용의 담당 기록과 합의 상태를 구분하고 기존 저장/인계 규칙을 적용한다.
대화 주제의 변경이나 설계 아이디어의 등장을 공식 단계 진입/완료로 처리하지 않는다.
대화의 초점이 바뀔 때 합의한 내용과 다음 결정 범위를 짧게 안내하며 매 응답에 단계명을 붙이지 않는다.
안내를 위한 새 승인 절차는 추가하지 않고 기존 단계/분할/번들 진입 승인은 유지한다.

M3: 다른 세션이 과거 대화 없이 report와 명시된 정본 참조로 목적/범위/상태와 현재 유효한 기준을 이해할 수 있게 작성한다.
현재 구현 범위의 입력/조건, 필수 동작/결과, 관련 예외와 판정 기준을 정의하고 요구사항 및 실제 구현/검증의 대응을 확인한다.
필수 미정은 추정하지 않고 진행에 미치는 영향과 확인할 위치를 구분한다.
단계에 아직 필요하지 않은 후속 상세나 구현 재량까지 사전 결정하도록 요구하지 않는다.

공통 작성 기준은 첫 작성부터 적용하고, 논의 묶음을 저장하거나 각 단계의 검토/승인에 제출하기 전에 해당 범위를 정리한다.
중간 정리는 현재 묶음과 변경 영향 부분을 대상으로 하며 매 응답/수정마다 전체를 검토하지 않는다.
번들 진입/상세 설계는 공통 정본과 현재 번들의 정의/참조를 대조한다.
회귀는 현재 개정의 설명/선언/도식/인계와 영향받는 번들을 함께 대조하고 과거 승인본을 보존한다.
마지막 QA의 전체 완료 제출 전에는 현재 유효한 문서와 모든 범위/번들의 구현/검증 결과를 종합 대조한다.
누락, 충돌과 남은 인계가 없거나 기존 범위/완료 기준에 따라 처리되었는지 확인하며 문서 정리로 미검증을 통과 처리하지 않는다.

설계 표현은 기존 선언/표/ASCII 도식 기준을 재사용한다.
구조체/자료형의 계약은 필요한 선언으로, 분기/관계는 필요한 도식으로 표현하며 자연어로 의미/이유/제약을 보완한다.
설명/선언/도식은 같은 계약을 나타내야 하고 원문 및 실제 표시의 가독성을 확인한다.
문단/목록/개행/들여쓰기를 의미 단위로 정리하되 조건, 예외, 의무와 승인 근거를 보존한다.
M4는 아래 14개 범주를 채택하고 배포용 실행 계약에서 적용 조건과 제외 경계를 구체화한다.
M5는 아래 개발용 검사 계약과 상세 설계에 따라 필수 검사와 구현 재량을 구분한다.

#### M4의 문서 기반 정형 검사 범위

아래는 14개 검사 범주이며 스크립트 파일 14개를 만든다는 뜻이 아니다.
기존 코드의 검사 목록과 구현 정책을 정본으로 삼지 않고 현재 지침 및 템플릿에서 도출했다.
표는 명시된 대상/적용 조건과 읽을 수 있는 자료가 주어졌을 때의 참/거짓 판정 범위다.
세부 문법/예외/출력의 정본은 [정형 검사 실행 계약](../../../../../plugins/Camellia/skills/code-development/references/report-check-contract.md)이다.
파일 읽기 실패는 실행 오류로 구분하며 없는 근거를 추정하여 값을 만들지 않는다.

근거 경로는 `plugins/Camellia/skills/code-development/` 기준이다.

| 검사 범주 | 명시적 입력과 참/거짓 판정 대상 | 문서 근거 |
| --- | --- | --- |
| C1. 주제 이름과 저장 경로 | 선택한 프로젝트/대주제/작업명. 이름이 빈 값, `.`/`..` 또는 경로 구분자를 포함하는지, 도출된 specs 계층과 실제 경로가 일치하는지, 디렉토리 위치에 일반 파일 충돌이 있는지 | guidelines: 프로젝트 루트와 저장 위치 확인, 주제 선택과 경로 확인 |
| C2. manifest와 작업 등록 | 선택한 작업의 manifest 항목. 작업 디렉토리 링크, stages/reference_reports의 존재 및 자료형/구조, 선언한 단계와 실제 report의 단계 식별자 대응 | guidelines: 저장 구조와 작업별 기록, 작업 주제 생성과 manifest 갱신 |
| C3. report 이름과 개정 | 작업/번들 안의 report 파일명과 status. 무번호/rev 또는 기존 번호 형식, 같은 범위/단계의 현재 개정 식별과 이전 개정의 superseded, 신구 형식 혼재 | guidelines: 파일명과 생성 시점, 프론트매터와 참조 확인; legacy-records |
| C4. 메타데이터 | report의 YAML. status/base_on의 존재와 타입, 허용 status, 현행 형식에서 design에 한정된 in_review, 명시적으로 금지한 revision/previous/once/diff 등의 별도 필드 | guidelines: 프론트매터와 참조 확인, 완료 확인과 사용자 승인; legacy-records |
| C5. 선행 report 연결 | manifest stages, report 위치/status/base_on 및 사용 목적. discussion의 null, 실제 선행 파일 존재, 상대 경로/작업 내부 제한, 단계/번들별 연결 규칙, 새 진행 입력의 completed 여부 | guidelines: 프론트매터와 참조 확인; work-bundles: 묶음 report의 식별과 선행 연결, 묶음 진입과 회귀; legacy-records |
| C6. report 공통 영역 | 현재 report의 실제 Markdown 영역. 단계 결과/인계 사항/완료 체크리스트/사용자 승인과 승인 영역의 사용자 판단/보완 요청과 처리 결과/남은 사항과 인계 조건의 존재 및 위치 | guidelines: 파일명과 생성 시점, 승인 과정 기록; assets/stage_reports |
| C7. 체크리스트와 현재 근거 | 현재 report의 완료 체크 목록. completed에 미체크 항목이 있는지, 체크된 항목에 현재 확인 근거 본문이 있는지, 이전 확인 기록만을 현재 근거로 사용하지 않는지 | guidelines: 상호 확인과 체크리스트 갱신, 다음 단계 진입 시 선행 report 확인, 변경 후 체크리스트 재확인 |
| C8. 일괄 반영 기록 | 명시된 반영 묶음. 묶음 식별자 중복, 대상 항목/시각의 존재, KST 시각 표기와 달력상 유효성, 명시적으로 연결한 과거 묶음 식별자의 존재 | guidelines: 상호 확인과 체크리스트 갱신, 변경 후 체크리스트 재확인 |
| C9. 검증/QA 완료 구분 | report 단계/상태와 사용자 승인 영역. 완료 구분 키워드 및 다음 줄의 설명 존재, 현행 all_passed/handoff와 기존 키워드 구분, 단일 플로우의 마지막 QA에 handoff를 쓰지 않았는지 | guidelines: 검증 및 QA의 완료 구분; stages/verification 및 stages/qa: 완료 구분; legacy-records |
| C10. 번들 배치와 묶음표 | 공통 design의 묶음표 및 실제 번들/report. 표의 필수 열/중복, 묶음 이름 중복, 디렉토리 이름/순번 충돌, 시작한 번들의 등록, 같은 번들의 실제 결과 링크, 번들 적용 후 루트 구현/검증/QA 혼재 | work-bundles: 공통 설계와 묶음 기록, 작업 묶음표의 기록 형식, 묶음 report의 식별과 선행 연결, 묶음 진입과 회귀 |
| C11. 로컬 자료 참조와 상세 배치 | report/manifest/리뷰/보류 문서가 명시한 로컬 링크 및 분리한 설계 상세. 해당 위치에서 파일/디렉토리 대상 존재, 설계 상세의 `<report stem>/<그룹명>.md` 배치 | guidelines: 이름 변경과 이동 시 참조 확인, 기록과 인계; design-artifacts: 논의 그룹별 상세 파일; deferred-work |
| C12. 표시한 ASCII 도식의 형식 | `text ascii-flow` 블록. 코드 블록 구분자 형식, 들여쓰기의 탭 사용, 비ASCII 연결선/화살표 기호 사용 | design-artifacts: ASCII 도식의 작성과 표시 확인 |
| C13. 리뷰 파일과 대상 | 실제 리뷰 파일과 원본 report. `<report stem>-review-<검토 번호>.md` 이름 및 같은 디렉토리 배치, 대상 report 존재/표기 일치, 검토자/모델/대상과 템플릿 영역의 존재 | guidelines: 리뷰 파일과 원본 report; assets/review_reports/review-template.md |
| C14. 보류 기록과 정리 상태 | 명시한 보류 파일/작업 루트 및 전체 완료 전 확인 요청. 작업 루트 deferred의 항목별 Markdown 배치와 템플릿 영역, 파일/디렉토리 잔존 여부 | deferred-work: 항목 기록, 전체 완료 전 이동; assets/deferred-item-template.md |

범주별 적용 경계:

- C1은 이름의 의미상 중복이나 작업 선택의 적절성을 판정하지 않는다.
  첫 저장 전의 예정 경로/미생성 자료와 이미 저장된 필수 자료를 구분한다.
- C2/C3은 기존 stages를 새 기본 목록으로 덮어쓰거나 미시작 report 부재를 오류로 만들지 않는다.
  현재 디렉토리 목록만으로 과거 파일 삭제/번호 재사용이나 실제 생성 순서를 증명하지 않는다.
- C4/C6은 임의의 추가 메타데이터를 모두 금지하거나 선택적인 상세 제목을 일괄 필수화하지 않는다.
  과거 superseded 본문에 현재 템플릿을 소급 강제하지 않는다.
- C5는 공통 회귀에서 완료 번들이 과거 superseded/hold 공통 입력을 보존하는 예외를 유지한다.
  예외의 파일/상태/연결 조건은 검사할 수 있지만 영향 없음과 보존 근거의 타당성은 판단하지 않는다.
- C7/C8은 근거 존재 및 기록 형식만 검사한다.
  축약한 대상 이름과 실제 체크 항목의 의미 대응, 근거의 충분함, 실제 시각 조회나 사용자 승인을 증명하지 않는다.
  기존 항목별 시각은 보존하며 새로운 반영 형식을 소급 강제하지 않는다.
- C9는 all_passed의 실제 통과나 handoff의 타당성/해소를 판정하지 않는다.
  번들의 가장 큰 순번을 마지막 QA로 추정하지 않고 적용 목적을 명시적으로 받는다.
- C10은 미시작 행과 아직 없는 후속 산출물을 허용하며 분할/의존 조건의 타당성을 판정하지 않는다.
- C11의 문서 절 링크는 실행 계약에 고정한 앵커 규칙으로 판정하며 모든 뷰어와의 일치를 보증하지 않는다.
  자연어로 쓴 경로나 동적 외부 URL의 접근 가능성을 추정하지 않는다.
- C12는 표시한 블록에만 적용하며 한글 설명을 금지하거나 일반 코드를 도식으로 추정하지 않는다.
  연결선 정렬, 도식과 설계의 의미 일치 및 실제 렌더링은 기계 판정에서 제외한다.
- C13은 실제 검토자 신원/모델, 호출 여부와 리뷰의 충분함을 검증하지 않는다.
  리뷰가 없다는 이유만으로 필수 생성이나 실패를 강제하지 않는다.
- C14는 아직 보류 항목이 있는 진행 중 작업을 실패로 처리하지 않는다.
  전체 완료 전 잔존 여부는 판정할 수 있지만 디렉토리 부재만으로 지정 목적지 보존/이동 성공을 증명하지 않는다.

현재 형식만으로 결정적 판정이 불가능하여 후보에서 제외한 범위는 다음과 같다.
설계/요구사항의 충분함과 의미 일치, 뼈대/번들 분할 타당성, 자연어 인계의 실제 해소,
사용자 승인/모델 적용/교차 검토의 실재, TDD 수행의 진위와 테스트 품질,
변경 영향 및 재검증 범위, 현재 파일만으로 과거 상태 전이/원본 보존을 증명하는 검사다.
제품 코드의 `friend`가 테스트를 위해 추가되었는지 등 목적 해석이 필요한 규칙도 포함하지 않는다.
검사 목적에 맞추려고 모든 코드/문서에 새 필드, 이벤트 이력이나 고정 형식을 자동으로 강제하지 않는다.

#### M4의 실행 단위와 인자 구성

실행 목적을 옵션으로 고르는 통합 실행기 대신 아래 5개 실행기를 독립적으로 제공한다.
파싱과 중복 검사 로직은 공통 모듈로 공유하며 전체 내부 파일 개수는 강제하지 않는다.
공통 입력은 확인한 프로젝트 루트와 그 아래 `specs/<대주제>/<작업 주제>/`의 절대 경로다.
작업 경로는 선택한 이름과 저장 규칙으로 계산하며 별도 저장 위치를 임의로 지정하지 않는다.

| 실행 단위 | 실행 시점 | 추가 입력과 출처 | 검사 후보의 연결 |
| --- | --- | --- | --- |
| 첫 저장 전 | 신규 작업의 이름/시작을 확정한 뒤 첫 저장 직전 | 없음. 선택한 주제의 예정 경로 사용 | C1. 미생성 report를 요구하지 않음 |
| 재개/단계 진입 전 | 기존 기록을 작업 입력으로 사용하기 전. 번들 진입/회귀 후 재개 포함 | 합의한 진입 단계/범위와 명시적 선행 report. 기존 묶음은 bundle 식별자 | C2-C11 중 현재 입력과 관련 자료에 적용되는 항목 |
| 저장 후 검토/승인 전 | 논의 묶음을 정리해 저장했거나 교차 검토/승인에 제출할 기록을 저장한 뒤 | 작성/보완한 report 경로 | C2-C12와 C14의 보류 기록 형식 중 현재 저장 범위에 적용되는 항목 |
| 리뷰 수신 후 | 요청한 리뷰 파일을 받은 뒤 지적 처리를 위한 입력으로 사용하기 전 | 검토 요청의 원본 report와 지정 리뷰 경로 | C13 및 C11 |
| 전체 완료 전 | 마지막 QA에서 보류 자료 정리를 마치고 전체 완료를 제출하기 전 | 전체 완료를 제출할 마지막 QA report. 검사 범위는 작업 전체 | C2-C12, 실제 리뷰의 C13과 C14 정리 상태. 의미/승인 판단 제외 |

인자는 사용자 지정, 유효한 현재 선택 및 실제로 확인한 기록에서 가져온다.
기존 합의는 재사용하며 규칙으로 유일하게 도출되는 경로만 계산할 수 있다.
필수 입력이 없거나 후보가 여러 개이면 임의 기본값, cwd, 수정 시각이나 가장 큰 번들 번호로 채우지 않는다.
확인 가능한 기록을 먼저 읽고 여전히 불명확한 값만 사용자에게 확인한다.
입력이 확보되기 전에는 종속 실행을 하지 않으며 스크립트도 누락/형식 오류를 입력 오류로 반환해야 한다.
검사를 통과시키거나 오류를 피하려고 대상/단계/범위/실행기를 바꾸거나 가짜 입력을 생성하지 않는다.

실행은 훅이 아니라 자연어 지침에 따라 에이전트가 담당한다.
실행 누락 자체를 100% 차단한다고 보장하지 않으며 각 절차의 실행 위치에서 정본 안내를 직접 연결한다.
실행기의 제공 상태, 입력 출처, 실제 호출/종료 결과와 검사 범위/실패/미실행을 확인한다.
미구현/실행 오류/미실행을 통과로 바꾸지 않고 기존 본문 대조와 승인 절차를 유지한다.
파일 상태/입력/참조 및 검사 규칙이 달라졌거나 이전 결과의 적용 범위가 불명확하면 다시 검사한다.
기록은 기존 report의 결과/근거 항목을 사용하며 별도 검사 report나 승인 단계를 만들지 않는다.

계약 구체화에서 회귀의 선행 입력과 마지막 QA를 자동 선택하지 않도록 두 경로를 명시적 인자로 정했다.
최종 파일/옵션/파싱/출력/판정 기준은 위 실행 계약에만 정의하고
[실행 안내](../../../../../plugins/Camellia/skills/code-development/references/report-checks.md)에 명령 예시와 인자 출처를 연결한다.
규칙 판정은 참/거짓으로 반환하고 오류와 미적용은 별도로 구분한다.
위 계약의 코드 구현은 후속 3번에서 수행했다.
계약 변경이 필요한 쟁점은 별도 논의한다.
승인된 검증 계획 1-3번에서 정형 실행 계약을 확인했고 결과는 [검증 기록](validation.md)에 정리했다.

#### M5의 개발용 검사 계약

code-development가 변경 스킬로 선택되면 등록한 구조/참조/템플릿/실행 계약/report 규칙 검사 5개를 모두 실행한다.
실패, 실행 오류, 미판정과 시간 초과는 푸시를 차단하며 검사 내용을 다른 스킬에서 승계하지 않는다.
자연어 의미와 실제 승인/설치 호환성을 자동 판정하지 않는다.
내부 실행기의 정상뿐 아니라 위반/오류/예외/범위 제한을 독립적인 시험 입력과 기대 결과로 확인한다.

입력/출력과 판정 범위의 정본은 [개발용 검사 안내](../../../../../tools/references/code-development-tests.md)다.
공통 훅이 전달한 커밋만 읽는 revision 검사와 명시적인 working-tree 수동 검사를 지원한다.
대상 스킬 전체와 같은 버전의 로컬 참조를 읽으며 소비자의 실제 specs나 설치본을 시험 입력으로 사용하지 않는다.
임시 사본/시험 자료에서만 동작 사례를 수행한다.
전체 boolean과 종료 코드 0/1/2로 통과/위반/실행 오류를 구분한다.
기대한 대상 오류와 일치하는 시험 사례는 개발용 검사 통과이며 두 종료 코드를 혼동하지 않는다.

[상세 설계](structure-design/developer-checks.md)는 검사별 정본/입력/기대 결과와 구현 및 기존 테스트 대체 범위를 정의한다.
실행기 5개, 보조 모듈 2개와 checks.json을 같은 개발용 검사 디렉토리에 두며 별도 통합 실행기는 만들지 않는다.
내부 함수 분할/이름은 구현 재량이지만 필수 사례 생략이나 계약 변경은 허용하지 않는다.
기존 공용 훅의 변경 경로 선택, 검사 파일별 제한 시간과 결과 계약을 재사용한다.

### 스킬 실행에 적용되는 제약, 실패 조건과 대응

M1의 환경 변수는 자동 메모리 제어이며 일반 파일 쓰기 권한이나 세션 저장 제어를 대신하지 않는다.
설정 전달이나 실행이 실패하면 미수행 사실을 기록하고, 설정 전달만으로 실제 차단 시험을 통과했다고 보고하지 않는다.
기존 메모리 파일의 삭제는 이번 변경에 포함하지 않는다.
M2의 자유로운 대화와 선행 아이디어 검토는 승인되지 않은 구현이나 후속 report의 선행 생성을 허용하지 않는다.
필수 미결정은 후속 상세로 넘기지 않으며 승인된 범위/계약을 바꾸는 경우 기존 회귀 절차를 적용한다.
M3의 문서 보완은 기존 보완/회귀 권한 안에서 수행하며 과거 승인/검증 결과를 소급하여 바꾸지 않는다.
새 필수 report나 별도 문서 정리/승인 단계를 추가하지 않는다.

M4는 스킬 사용 시 명시적으로 선택한 프로젝트/작업의 저장 자료를 검사하는 배포용 도구다.
후보는 스킬의 현행 규칙에서 도출하며 기존 구현이나 폐기할 실행 안내만의 세부 정책은 승계하지 않는다.
검사의 대상 범위/적용 조건과 입력 해석을 먼저 고정하고, 충족 여부는 참/거짓으로 판정한다.
자료 읽기 실패나 입력 부족을 규칙 위반 또는 통과로 바꾸지 않는다.
주제 선택, 승인, 상태 변경, 자동 보완 및 실제 작업 완료 판정은 검사기가 대신하지 않는다.

M5는 지정 대상 버전의 스킬과 임시 시험 자료만 검사하며 실제 소비자 기록/설치본에 쓰지 않는다.
검사 실패와 실행 오류/미판정은 모두 푸시 차단 대상으로 유지한다.
다른 스킬의 검사 내용을 복사하거나 현재 M4 구현의 결과를 그대로 기대값으로 삼지 않는다.
네트워크/AI 호출/자동 설치 없이 동작하며 필요한 검사를 생략하여 통과시키지 않는다.

### 사용자 확인 및 승인 조건

최신 integrate/camellia 반영 후 신규 브랜치에서 다시 시작하는 방식과
`workflow-and-script-rework`라는 브랜치 및 기록 디렉토리 이름을 승인받았다.
2026-10-12 로컬 integrate/camellia를 fast-forward로 갱신하고,
`f6a22877d15ab2af662e900209f7251224c4d0d4`에서 `work/camellia/workflow-and-script-rework`를 생성했다.
동일 이름의 origin 브랜치에 최초 푸시하고 upstream을 연결했다.

기존 `work/camellia/outline-first-development`는 추후 제거 대상으로 남긴다.
이전 outline-first-development의 미추적 명세/검증 기록 3개는 사용자 요청으로 정리했다.
기존 작업의 상세 합의, 단계 및 완료 판단은 이번 작업에 승계하지 않는다.
1번의 명세 정리, 호출 지침 수정과 정적 확인에 이어 2번의 논의와 지침 작성을 승인받았다.
뼈대 중심 대화와 번들 구분을 함께 다루고 공식 단계 관리는 에이전트가 담당하는 방향을 합의했다.
당시 1-2번 수행 범위에는 설치/배포, 커밋과 나머지 후보 구현을 포함하지 않았다.
3번은 중간 저장/단계 승인 전의 부분 정리, 회귀/번들 대조와 전체 완료 시 종합 확인을 합의하고 지침 작성을 승인받았다.
GPT-6 Astra/high의 승인 범위를 3번의 지침 작성까지 확대했다.
사용자가 해당 설정으로 적용되어 있음을 확인했다.
적용 확인은 사용자 진술이며 실행 상태를 독립적으로 검증한 결과가 아니다.
테스트는 사용자 요청으로 변경을 모은 뒤 일괄 수행한다.
M1에서 이미 수행한 정적 확인 결과는 보존했고 M2/M3 구현 당시에는 새 검사나 실제 시나리오를 실행하지 않았다.
M4의 기존 스크립트 제거와 현행 문서 기반 후보 재추출은 사용자의 명시적 요청 범위다.
이어서 실행 시점별 개별 스크립트, 인자의 임의 입력 금지와 에이전트의 실행 지침 정리를 요청받았다.
이번 수정은 합의한 호출 절차의 문서 반영이다.
후속 요청으로 현재 모델에서 스크립트 계약 확정과 자연어 지침 마무리까지 수행한다.
실행기 이름/인자/검사 범위/예외/결과/오류와 검증 기준을 정하고 실제 명령 예시를 연결한다.
후속 3번의 코드 구현은 GPT-6.1 Sol/high로 진행하도록 제안했고 사용자가 모델 변경을 확인했다.
실제 적용 확인의 근거는 사용자 진술이며 실행 상태를 독립적으로 검증한 결과가 아니다.
범위는 스킬 내부 실행기 5개, 내부 공통 모듈 및 의존성 목록의 구현이다.
해당 구현 당시에는 테스트를 기존 합의대로 후속 일괄 수행 시점으로 남겼다.
해당 3번 수행에는 설치/배포, 테스트 실행과 M5의 개발용 테스트 개편을 포함하지 않았다.

M5의 4번 상세 설계는 GPT-6 Astra/high로 진행하며 사용자가 현재 설정을 확인했다.
적용 확인의 근거는 사용자 진술이다.
사용자는 제안한 개발용 검사기 5개 구성과 기존 pre-push의 변경 스킬 선택 기준 사용에 이견이 없다고 확인했다.
검사 기준, 시험 입력/기대 결과, 공통 실행 처리 및 기존 테스트 대체 범위를 문서로 구체화하도록 요청했다.
4번 요청에서는 코드와 등록 파일 변경, 검사 실행을 수행하지 않았다.
