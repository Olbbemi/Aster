# Code Development 개발용 검사 상세 설계

## 상태와 역할

[명세서](../specification.md)의 M5를 구현하기 위한 상세 설계다.
사용자가 승인한 실행기 5개 구성과 기존 pre-push 연결을 기준으로 작성했다.
이 설계를 기준으로 코드/등록 구현과 기존 테스트 대체를 마쳤다.
아래 사례는 지속 검사 정의이며 실제 실행 결과가 아니다.
현재 구현 파일과 수행 결과는 명세서의 구현 항목에서 확인한다.

지속 사용 기준과 입력/출력 및 운영 계약은
[개발용 검사 안내](../../../../../../tools/references/code-development-tests.md)에 둔다.
이 문서는 내부 책임, 사례별 입력/기대 결과와 대체 범위를 담당한다.
스킬 동작의 정본은
[정형 검사 실행 계약](../../../../../../plugins/Camellia/skills/code-development/references/report-check-contract.md)이다.
이하 `계약`은 그 문서를, `스킬 루트`는 `plugins/Camellia/skills/code-development/`를 뜻한다.
다른 스킬의 검사에서는 배치/호출/격리 구조만 참고하며 기능과 판정 조건을 가져오지 않는다.

## 파일과 책임

아래 Python 파일과 등록 파일은 `tools/tests/skills/code-development/` 바로 아래에 둔다.
독립 실행기 5개, 보조 모듈 2개와 등록 파일 1개로 구성한다.
별도 하위 디렉토리와 통합 실행기는 만들지 않는다.

| 파일 | 변경 | 책임 |
| --- | --- | --- |
| `check_skill_structure.py` | 생성 | S 계열: 메타데이터, 계약상 실행 자료와 Python 구문 |
| `check_skill_references.py` | 생성 | L 계열: 배포 문서의 로컬 참조와 절 |
| `check_report_templates.py` | 생성 | T 계열: 단계/지침/템플릿 대응과 원본 형식 |
| `check_runtime_contract.py` | 생성 | R 계열: 실제 CLI와 출력, 환경/오류, 비변경성 |
| `check_report_rules.py` | 생성 | D 계열: C1-C14와 시점별 범위의 동작 사례 |
| `repository_support.py` | 생성 | 지정 버전의 파일 읽기, Markdown/YAML 해석, 스킬 배포 범위의 경로 해석 |
| `check_support.py` | 생성 | 공통 인자/결과, 시험용 사본/자료, 실행과 장애 주입, 기대 결과 대조 |
| `checks.json` | 생성 | 위 순서대로 실행기 5개만 등록 |
| `test_code_development_reports.py` | 대체 후 제거 | 삭제된 `check_reports.py`/`Checker` API와 이전 출력 구조에 의존하는 기존 테스트 |

보조 함수의 분할과 함수명은 구현 재량이지만 책임과 입력/출력 및 검증 범위는 유지한다.
보조 모듈에 특정 다른 스킬의 검사 내용을 복사하거나 다른 스킬 검사 디렉토리를 import하지 않는다.
M4의 내부 보조 모듈을 개발용 형식 판정/기대값 생성에 재사용하지 않는다.

Python 3.10 이상과 현재 `tools/requirements.txt`가 연결한 PyYAML/markdown-it-py 범위로 구현할 수 있다.
추가 패키지나 저장소 전역 테스트 프레임워크는 요구하지 않는다.
검증 당시 기존 의존성의 준비와 격리 모드 접근을 확인했고 새로 설치하지 않았다.

개발용 사용 안내는 `tools/references/code-development-tests.md`에 작성했다.
`tools/references/skill-pre-push.md`와 루트 README의 기존 검사 안내 목록에 연결했다.
제공 상태도 구현 상태로 갱신했다.
구현 사실과 실제 검증 통과는 구분하며 후속 실행의 결과는 [검증 기록](../validation.md)에 정리했다.
배포용 스킬 문서에서 개발용 검사 자료를 필수 실행 의존성으로 참조하지 않는다.

## 읽기와 실행 관계

| 호출자 | 대상 | 조건과 결과 |
| --- | --- | --- |
| 기존 `check_push.py` | `checks.json`의 5개 실행기 | 변경 스킬이 code-development일 때 전송할 커밋 SHA를 전달 |
| 각 실행기 | `check_support.py` | 공통 CLI/결과와 필요한 시험 지원을 사용. 다른 실행기를 대신 호출하지 않음 |
| 실행기와 시험 지원 | `repository_support.py` | revision 또는 명시 작업 트리에서 같은 대상 버전의 자료를 읽음 |
| S/L/T 실행기 | 선택한 스킬과 필요한 참조 파일 | 대상 Python 실행 없이 문법/구조/참조 판정 |
| R/D 실행기 | 임시 위치의 대상 스킬 사본과 소비자 fixture | 실제 공개 진입점으로 실행하고 독립적인 기대 결과와 대조 |

각 실행기는 자신에게 속한 모든 필수 사례를 수행한다.
S 실패를 이유로 공통 훅이 R/D 전체를 자동 생략하도록 하지 않는다.
개별 실행기 안에서 전제 파일이 없으면 해당 위반을 먼저 기록하고 실행 불가능한 종속 사례를 오류로 표시한다.
독립적인 다른 파일/사례는 계속 확인한다.

### 저장소 읽기

revision은 시작 시 실제 커밋으로 해석하고 이후 같은 객체를 사용한다.
Git 조회는 인자 배열로 호출하고 대상 루트를 명시한다.
`ls-tree`/객체 읽기 등의 읽기 전용 연산으로 파일 모드와 내용을 가져오며 경로는 NUL 구분으로 읽는다.
작업 트리와 인덱스에 파일이 있어도 지정 커밋에 없으면 부재다.

working-tree는 검사 파일로부터 정한 기본 저장소 또는 명시 루트에서 읽는다.
스킬 경로 아래의 현재 일반 파일을 열거하고 미추적 파일도 포함한다.
Git 관리 전체나 소비자 specs로 범위를 넓히지 않는다.
읽기 실패/잘못된 UTF-8은 조용히 건너뛰지 않는다.

로컬 링크의 `..`, percent encoding과 심볼릭 링크는 선택한 버전의 경로로 해석한다.
심볼릭 링크가 있으면 링크와 대상 모두 배포 경계 안에 있는지 확인한다.
경계 이탈/순환/깨진 참조를 통과시키지 않는다.
실행용 사본에 심볼릭 링크나 submodule이 있어 온전한 복사를 보장할 수 없으면 준비 오류다.
링크를 따라 개발자의 실제 경로를 읽거나 내용으로 치환하여 조용히 실행하지 않는다.

### 시험 자료와 기대값

실제 스킬 소스의 사본은 선택한 버전에서 만들고 시험용 소비자 프로젝트는 별도로 생성한다.
fixture의 report 본문, manifest, 기대 코드/상태는 계약을 근거로 개발용 코드에서 정의한다.
템플릿이나 대상 실행기의 상수에서 기대값을 자동 생성하여 양쪽의 같은 누락을 통과시키지 않는다.
템플릿을 직접 확인하는 T 검사와 독립 fixture를 쓰는 D 검사는 역할이 다르다.

기본 fixture는 다음 계열로 분리한다.

| 계열 | 기본 자료와 목적 |
| --- | --- |
| 신규 작업 | 존재하는 프로젝트와 미생성 예정 주제. 첫 저장 검사 전제 |
| 현행 단일 | 5단계의 올바른 base_on, 완료한 선행 자료와 작성 중 대상. 제출/진입의 정상 기준 |
| 현행 번들 | 공통 discussion/design, 정형 묶음표, 별도 design 유무가 다른 번들. 등록/연결 예외 |
| 기존 번호 | `-001.md`와 bundle 필드, 기존 완료 구분/표. 현행과 분리된 호환 사례 |
| 전체 완료 | 앞선 모든 현재 report 완료, 명시적 마지막 QA와 부재인 deferred. 완료 검사 기준 |
| 리뷰/보류 | 실제 원본/리뷰 쌍 및 진행 중 보류 문서. 다른 단계의 상태와 독립된 검사 |

각 위반 사례는 정상 fixture에서 판정할 조건 하나를 바꾸는 것을 기본으로 한다.
오류/위반 공존과 범위 배제 검사는 여러 조건을 의도적으로 바꾸고 그 목적을 사례에 적는다.
fixture 작성기가 status에 따라 근거나 필수 영역을 자동으로 누락시키지 않게 한다.
정상 fixture가 먼저 계약에 맞는 결과를 내는지 같은 검사에서 확인한다.

검사 사례는 다음 정보로 식별한다. 실제 자료구조의 이름은 고정하지 않는다.

```text
Case = {
  id: string,
  source_rule: string,
  fixture: string,
  change: string,
  entrypoint: string,
  arguments: [string],
  expected: {
    exit_code: integer,
    outcome: string,
    required_results: [{category: string, status: string}],
    forbidden_categories: [string]
  }
}
```

`required_results`는 해당 규칙의 범주와 결과 상태를 함께 대조한다.
예를 들어 `C7` 실패를 기대하는 사례가 다른 규칙만 실패해 종료 1이 된 경우에는 통과하지 않는다.
세부 결과 ID는 계약상 안정성을 확인하되 구현의 함수명이나 설명 문장 전체를 고정하지 않는다.
정상/위반/오류에서 출력 스키마와 집계의 일치도 확인한다.

### 진입점 실행과 격리

R 검사는 내부 실행기 5개를 사본의 파일 경로로 직접 Python 호출한다.
각 파일의 정상 호출, 필수 인자 오류와 help 단독 호출은 실제 프로세스로 확인한다.
D의 많은 조합은 같은 사본의 공개 진입점을 `runpy` 등으로 호출할 수 있다.
그 경우 argv/cwd/표준 출력/종료 코드를 포착하고 상태를 복원하며 내부 판정 함수를 직접 호출한 결과로 대신하지 않는다.
사본이 달라지면 import 캐시도 분리하고 이전 코드나 문서 캐시를 사용하지 않는다.

대상 소스는 쓰지 않고, 검사용 모듈 경로 추가는 해당 사본의 scripts에 한정한다.
대상 자료의 준비와 기대값 대조를 수행하는 개발용 코드와 검증받는 코드를 구분한다.
권한 오류는 OS 권한 설정만으로 재현되지 않을 수 있으므로 파일 읽기 경계에 한정한 장애 주입을 허용한다.
의존성 누락도 패키지 탐색/가져오기 경계에서 재현하며 원래 환경을 제거하거나 설치하지 않는다.
장애 주입은 예상 판정 자체를 바꾸지 않으며 적용 지점과 복원을 사례에 명시한다.

실제 자식 호출/Git 조회의 제한 시간은 사용 안내를 따른다.
동일 사본의 재사용과 in-process 사례로 반복 준비 비용을 줄이되 실행기 파일별 필수 범위를 줄이지 않는다.
후속 일괄 실행에서 필수 사례가 파일별 60초 제한을 충족한 것을 확인했다.
실제 실행 시간은 [검증 기록](../validation.md)에 정리했다.
시간 제한 상향, 필수 사례 제외나 합의한 실행기 분할 변경이 필요하면 구현 재량으로 처리하지 않는다.

## 정적 검사 정의

표의 실패는 대상 규칙 위반이면 개발용 종료 1, 파일 접근/검사 준비의 오류이면 2다.
S/L/T의 검증 코드는 대상 스킬의 Python 모듈을 import하지 않는다.
아래 표는 현재 파일만 통과시키는 문자열 스냅샷이 아니라 유지할 형식 조건을 정의한다.

| ID | 대상과 참인 조건 | 거짓/오류 및 경계 |
| --- | --- | --- |
| S01 | SKILL.md가 있고 안전한 YAML 매핑, 유일한 키, 유효한 name/비어 있지 않은 문자열 description | 파일 부재/메타데이터 형식/타입/이름 불일치는 위반. 본문 의미/하네스별 선택 필드는 미추정 |
| S02 | 계약의 5개 실행기와 requirements.txt 및 SKILL에서 연결한 실행 계약/안내가 존재 | 필수 파일 부재는 위반. 공통 모듈명이나 전체 파일 개수는 고정하지 않음 |
| S03 | 스킬 scripts의 모든 Python 소스가 구문 분석됨 | SyntaxError는 위반. 읽기 불가는 오류. import/실행/캐시 생성 없이 확인 |
| S04 | requirements에 계약상의 두 패키지와 호환 버전 범위가 선언됨 | 패키지 누락이나 범위 불일치는 위반. 줄 순서/공백/주석을 소스 동일성으로 비교하지 않음. 현재 설치 상태는 R의 준비 조건 |
| L01 | 스킬 Markdown의 인라인/참조형 링크와 이미지의 로컬 대상 존재 | 빠진 경로, 잘못된 percent encoding, NUL은 위반. 코드/HTML 주석/일반 경로 문장은 링크로 세지 않음 |
| L02 | 로컬 Markdown 절이 `aster-markdown-headings-v1`의 제목/명시 앵커에 있음 | 중복 제목 suffix, Unicode/인코딩/Setext를 포함. 없는 절은 위반, 비Markdown fragment 미판정은 오류 |
| L03 | 로컬 필수 자료가 Camellia 배포 안의 같은 대상 버전에 있음 | 절대 로컬 경로와 배포 밖 참조는 위반. 외부 URI는 제외이며 네트워크 접근하지 않음 |
| T01 | workflow의 기본 단계 표 식별자에 중복이 없고 단계 지침과 대응 템플릿 링크가 실제 동일 단계 파일로 이어짐 | 누락/중복/잘못된 단계 연결은 위반. 순서는 workflow 정본과 대조. 모든 단계별 문장/제목을 고정하지 않음 |
| T02 | 각 단계 템플릿의 YAML 필드, C6의 4개 H2와 사용자 승인 아래 3개 H3가 정확히 하나 | 코드/주석/인용 속 가짜 제목은 제외. 추가 상세 제목 허용. 기본 in_progress/null과 빈 작성란 허용 |
| T03 | 각 단계 템플릿의 완료 체크리스트 아래 일괄 반영 기록란, verification/qa의 사용자 승인 아래 완료 구분란 존재 | 기록란 누락/잘못된 부모/중복은 위반. 실제 반영 표/시각/완료 키워드 값은 원본에 요구하지 않음 |
| T04 | 리뷰 템플릿의 상단 필수 3개 목록 라벨과 5개 H2, 보류 템플릿의 4개 H2 존재 | 중복/누락/잘못된 깊이는 위반. 값과 본문은 빈 작성란 허용 |

T01은 workflow의 `단계 순서와 지침` 표, 단계 지침의 `report 작성과 인계` 절에서 실제 템플릿 링크를 읽는다.
기본 단계 식별자 집합을 계약이 지원하는 discussion/design/implementation/verification/qa와 대조하고,
단계 지침 및 템플릿의 대응 누락을 확인한다.
스킬 기본 흐름을 검사하며 소비자 manifest에 기본 5단계를 강요하는 검사가 아니다.
기본 단계/공개 실행 계약이 바뀌면 근거 문서와 검사 기준을 함께 갱신한다.
파싱할 정본 구조가 없어졌는데 임의 기본값으로 대체하지 않는다.

T04의 H2는 현재 원본과 계약 C13/C14를 기준으로 다음 이름을 사용한다.
리뷰는 `실행 대상과 근거`, `검토 범위와 기준`, `검토 결과`, `확인하지 못한 사항`, `종합 의견`이다.
보류는 `필요한 작업`, `보류 이유와 현재 범위`, `논의 내용과 근거`, `재검토 조건과 미결정 사항`이다.
리뷰 상단은 `검토자:`, `모델명/버전:`, `검토 대상:`이다.
정본을 바꾸지 않고 검사에서 새로운 제목이나 승인란을 추가로 요구하지 않는다.
선택적으로 생성하는 design 묶음표를 빈 설계 템플릿에 강제하지 않는다.

R05의 JSON 검사는 대상 계약의 모든 필수 키, status/value 관계와 오류 우선 집계를 독립적으로 확인한다.
`inputs`에 명시적 인자가 보존되며 출력 옵션이 들어가지 않는지도 확인한다.
현재 패키지 버전을 특정 문자열로 하드코딩하지 않고 실제 준비 환경과 대조한다.
외부 URL fixture에는 네트워크 접속이 필요하지 않은 예약된 테스트 주소를 사용한다.
자동 설치/외부 명령 호출 금지는 시험 프로세스의 해당 호출 경계를 감시하는 보조 사례로 확인한다.
이를 운영 샌드박스가 모든 부작용을 차단한다는 보장으로 표현하지 않는다.

## report 규칙 검사 사례

표에서 P는 종료 0/pass, F(Cn)는 해당 C 범주 fail을 포함하는 종료 1/fail이다.
E는 종료 2/error이며 괄호의 fail도 함께 요구하면 이미 확인한 위반을 보존해야 한다.
표의 선택적 범주는 계약이 정한 경우에만 not_applicable을 허용한다.
신구 형식에 공통인 규칙은 각 형식에서 확인하고 형식별 차이는 별도 사례로 둔다.
종속 판정 오류의 경계는 [실행 계약](../../../../../../plugins/Camellia/skills/code-development/references/report-check-contract.md#위반과-종속-판정-오류의-구분)을 따른다.
F의 조건을 바꾸는 과정에서 별도 필수 해석 정보까지 훼손한 입력은 E가 될 수 있으므로 사례를 분리한다.

| D26 | 리뷰/C13 | 같은 디렉토리/올바른 번호/정확한 원본/필수 라벨과 H2, 모델 확인 불가: P | 잘못된 이름/대상/중복 라벨/빈 필수값/누락 제목: F(C13). 지정 리뷰 부재/다른 위치 입력은 E |
| D27 | 제출/C14 | 진행 중 정상 보류 문서와 실제 비어 있지 않은 내용: P | 필수 영역 부재/주석뿐/하위 디렉토리/비Markdown 항목: F(C14) |
| D28 | 완료/전체,C9 | 모든 선행 완료, 마지막 QA in_progress/awaiting_approval/completed와 all_passed+설명: P | 앞선 미완료/필수 report 부재/미시작 번들: 전체 조건 fail. 현행 마지막 handoff: F(C9) |
| D29 | 완료/전체,C9 | 앞선 번들의 handoff, 기존 마지막 QA의 next_cycle_handoff 보존: P | hold/superseded/현재가 아닌 최종 QA: 해당 전체/대상 위반. 최신 mtime/큰 번들 번호로 명시 QA를 대체하지 않음 |
| D30 | 완료/C13,C14 | 현재 실제 리뷰 모두 유효, 리뷰 없음은 미적용, deferred 부재: P | 실제 현재 리뷰 오류: F(C13). 빈/비어 있지 않은 deferred, 일반 파일/끊어진 링크 잔존: F(C14) |

종속 검사를 할 수 없는 입력에 대해서는 F만 기대하여 오류를 숨기지 않는다.
위 표가 별도 분류를 적지 않은 전체/대상 위반은 계약에 맞는 안정적 결과 ID와 exit 1을 확인한다.
구현의 세부 ID가 아직 정해지지 않은 부분은 범주와 대상 위치로 실패 원인을 확인한다.
반대로 단순히 어떤 오류든 비정상 종료이면 통과시키는 검사를 만들지 않는다.

## 기존 테스트 대체

기존 파일은 직접 읽어 사례의 목적만 대조했다.
삭제된 모듈 import, `Checker(topic).run()`, `checker.AREAS`로 기대 fixture를 만드는 구조와
이전 결과 키/세부 ID를 새 검사의 근거로 재사용하지 않는다.

| 기존 검증 주제 | 새 위치 | 처리 |
| --- | --- | --- |
| 체크/근거/반영 기록/완료 키워드 | D13-D18 | 현행 계약을 기준으로 fixture와 기대 결과 재작성 |
| manifest/개정/상태/선행/신구/번들/회귀 | D02-D12, D19-D21 | 유효한 목적 유지. 현행/기존의 다른 선행 규칙과 보존 예외를 분리 |
| 링크/상세/도식/인코딩 | D22-D25, R08/R10 | 의미 검토와 분리한 기존 정형 사례를 새 공개 진입점에 맞춤 |
| 복사 실행/cwd/비변경성/결정성/오류 | R01-R12 | 새 5개 실행기와 새 JSON 계약으로 재작성 |
| 옛 6개 명령과 모드별 합집합/내부 순회 재사용 | 대체 없음 | 폐기한 구조 또는 구현 최적화 전제. 새 시점별 범위 D31-D36으로 필요한 기능만 검증 |
| 리뷰/보류/마지막 QA, 신규 첫 저장과 명시 진입 인자 | D01, D07-D08, D26-D36 | 새 계약에서 추가된 경계 사례 보강 |

새 코드와 사례 대응을 작성한 뒤 기존 파일을 제거했다.
제거 사실을 검증 통과로 취급하지 않았다.
이후 사용자 승인에 따라 일괄 시험을 수행했고 실제 결과를 검증 기록에 남겼다.
기존 테스트 개수를 유지하거나 이전 통과 결과를 새 코드의 통과 근거로 기록하지 않는다.

## 검증 기준과 실제 결과의 연결

아래 표는 구현 전에 정의한 완료 기준이다.
지원 모듈, S/L/T와 R/D의 구현 및 등록/기존 테스트 대체 후 승인받은 일괄 검증으로 확인했다.
공용 훅 정책과 M4 공개 계약을 검사 편의에 맞춰 바꾸지 않았다.

| 확인 항목 | 입력/조건 | 완료 근거 |
| --- | --- | --- |
| 실행기 실제 동작 | working-tree 대상 5개, R/D 모든 사례 | 전체 필수 사례 결과와 오류 없음. 기능 결함은 원인/수정 후 다시 확인 |
| 정적 검사 음성 대조 | 임시 사본의 메타데이터/문법/링크/필수 제목을 하나씩 훼손하고 복구 | S/L/T가 실제 위반을 검출하고 정상 상태에서는 통과 |
| 커밋 격리 | 임시 Git 저장소의 서로 다른 두 커밋과 그에 반하는 작업 트리/인덱스, 미추적 파일 | revision은 커밋만, working-tree는 현재 자료만 판정 |
| 출력/오류와 환경 | 잘못된 입력/커밋/의존성, 다른 cwd, JSON/텍스트 | 개발용 0/1/2와 boolean 일치. 필요한 범위 미실행은 통과 아님 |
| pre-push 연결 | 기존 Git 운영 시험 구조의 로컬 저장소/bare 원격 또는 동등한 ref 입력 | code-development 선택 시 5개 전부 호출, 실패/오류/시간 초과 차단, 다른 스킬만의 변경에는 미호출 |
| 제한 시간과 정리 | 전체 등록 검사, 실패/오류 실행 후 자료 확인 | 각 파일 60초 이내, 정상/오류 종료 시 임시 자료 정리와 원본 보존 |

공용 훅 선택 기능을 code-development 검사 자체에서 매번 재시험하거나 실제 원격에 시험 푸시하지 않는다.
강제 종료로 Python 정리가 실행되지 못한 경우의 임시 잔존은 검사 통과로 표시하지 않고 시험 후 정리한다.
이 표는 구현 전에 정의한 검증 계획이다.
설계 문서 작성 중에는 실행하지 않았으며 이후 승인된 검증 계획 1-3번에서 수행하여 통과했다.

## 판단과 남은 사항

필수 설계 미정 사항은 없다.
검사별 제한 시간/환경/실행 계약과 검사 자체/Git 격리/pre-push를 확인했다.
최초 제품 결함과 교차 검토의 보완 및 재검증은 [검증 기록](../validation.md)을 따른다.
자연어 적용과 설치본 동작은 별도 검증했으며 전체 완료 상태는 명세서의 최종 관문에서 판단한다.
