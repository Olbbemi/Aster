# 번들/회귀/보류 개선의 검증 결과

## 대상과 근거 구분

Camellia의 code-development를 3.1.0에서 4.0.0으로 변경했다.
문제/범위/계약과 승인 정본은 [명세서](specification.md)다.
소스 기준은 b5e1f6112029351e67c720aad19bd2ba682dea64,
변경 커밋은 37f6522637d7876cf514edc2cde1b08e8b39e5ae이며
[PR #41](https://github.com/Olbbemi/Aster/pull/41)의 통합 커밋은 e26cbef82410a1c3d2bf2fe3b358b7fbbe2909e3다.
검증한 내용이 통합 결과와 같고 양 설치본 파일 31개/버전/marketplace HEAD가 해당 배포물과 일치했다.
업무 동작은 변경 개발 사본, 호환성은 실제 설치본으로 각각 확인했다.

## 기계 검사

Python 3.12.3, PyYAML 6.0.1과 markdown-it-py 3.0.0을 사용했다.

| 대상/방법 | 실제 결과 | 한계 |
| --- | --- | --- |
| check_structure.py, 대상 code-development | PASS | 형식 검사이며 동작 판정 아님 |
| check_references.py, 대상 code-development | 로컬 315 PASS, 외부 URL 2 SKIP | 외부 URL 유효성 미검증 |
| check_distribution.py, 대상 Camellia | 예정/실제 구성 31개 일치 | 설치/로드는 별도 확인 |
| work-bundles ASCII 문자 검사 | 도식 1개 PASS | 실제 UI 렌더링/가독성 전수 시험 아님 |
| report 계약 시험 | 최종 101 PASS, 기존 77/신규 24 | 승인/범위의 의미는 기계 판정하지 않음 |
| 명세서/시나리오 기록 대조 | 형식/요건/사례 대응 PASS | 실제 승인/시험 통과를 대신하지 않음 |

역할별 공용 검사기는 Aster tools/scripts/validation을 사용했다.
현재 소스의 계약 회귀 시험은 저장소 루트에서 다음 명령으로 재현한다.

```bash
python3 -B -m unittest discover -s tools/tests/validation -p test_code_development_reports.py
```

[시험 소스](../../../../../tools/tests/validation/test_code_development_reports.py)에
신구 기록, 개정/선행 연결, 범위/상태 거부와 과거 완료 참조 예외의 정상/오류 입력이 있다.
기계 결과와 실제 의미 검토는 구분한다.

GPT-6.1 Sol/high로 별도 Codex CLI 공통 실행기를 사용했다.
총 34회로 사용자 승인 상한 35회/요청당 600초를 유지했다.
모델/강도는 34개 실제 turn_context에서 확인했으며 compaction 재기록은 새 호출로 세지 않았다.

## 주요 실패와 보완

S3 공통 회귀는 150 PASS/1 FAIL이었다.
completed 번들의 과거 공통 design을 hold라는 이유로 거부한 검사와 보존 계약의 충돌이다.
이 상태에서 자동 승인을 전달하지 않고 중단했다.
completed 번들 design/implementation의 과거 공통 hold design만 허용하는 좁은 예외를 추가했다.
진행/승인 대기, root와 같은 번들 내부 hold 입력은 계속 거부한다.
5개 정상/거부 시험을 추가했으며 수정 전 새 재현 2개 실패, 수정 후 총 101개 PASS와 공통 구간 재시험 최종 231 PASS를 확인했다.
현재 검사 예외는 [report 검사 계약](../../../../../plugins/Camellia/skills/code-development/references/report-checks.md)에 정의돼 있다.
실제 유지 근거와 완료 타당성은 사람이 대조한다.

초기 링크 시험의 기대 rule ID 오류는 올바른 link.target 검출에 맞춰 기대값을 고쳤다.
상위 입력 준비에서 원본 보존을 접두어 일치로 과도하게 판단한 입력 부재 1회는 종료 2/모델 호출 없음이었다.
이 두 항목은 각각 시험 기대값/입력 준비 오류이며 스킬 동작 실패로 계산하지 않았다.

## 독립 읽기 교차 검토

검증 대상 report-flow의 마지막 회차는 round-001이며 작성자는 Claude Sonnet 5다.
사용자가 Sonnet/high 1회/900초를 승인했고 실제 331.770초/종료 0으로 완료했다.
Read/Glob/Grep만 사용하여 25개 변경/32개 전체 대상과 8개 계약 기준 및 대표 산출물을 검토했다.
검토 후 원문/32개 소스 해시가 그대로였고 후속 version 한 필드 변경 외 검토한 로직은 유지됐다.
필수 결함/수정 요구는 없었다.
아래는 검토 원문을 고친 것이 아니라 요청자의 후속 판단 요약이다.

| 관찰 한계/지적 | 요청자의 판단 |
| --- | --- |
| M1 독립 시험/해시 재계산 미수행 | 읽기 범위로 수용. 요청자가 실제 101개 실행/현재 대상 해시를 대조함 |
| M2 S2/S3 전체 turn 미열람 | 표본 한계로 수용. 요청자가 종료 응답/outcome과 기존 직접 동작 판정을 대조함 |
| M3 레거시 응답 원문 미열람 | 요청자의 실제 응답/outcome 변경 0 및 초기 36개 해시로 보완. Claude의 독립 관찰로 표현하지 않음 |
| M4 실제 렌더링/설치본 제외 | 범위를 유지. 필수 R8은 후속 설치본 시험으로 확인하고 UI 렌더링은 전수 시험하지 않음 |
| M5 모의 승인 타당성을 보고서 신뢰 외 독립 비교할 수 없다는 서술 | 의미를 기계 판정으로 대체할 수 없다는 한계는 수용. 입력/승인 범위/실제 결과의 독립 비교가 불가능하다는 일반화는 채택하지 않음 |

추가 소스 수정이나 독립 호출이 필요한 미해결 지적은 없었다.
읽기 검토를 실제 사람 QA, 전체 로그 검토나 독립 실행으로 확대하지 않는다.

## 실제 설치본 호환성

두 marketplace의 참조는 integrate/camellia이며 실제 커밋과 4.0.0 설치본 31개 파일이 통합 배포물과 일치했다.
각 새 CLI 세션의 목록/명시 호출/신규 자료 읽기는 Garden의 직접 실행 근거를 대조해 재사용했다.
신규 보류 템플릿/지침과 기존 기록 지침을 포함한 공용 배치가 두 CLI에서 접근됐다.
설치본 변경은 Garden에서 처리했으며 Aster는 전역 설정을 바꾸지 않았다.

| 사례 | 환경/실제 실행 | 정상 입력 | 의도적 오류 입력 | 최종 판정 |
| --- | --- | --- | --- | --- |
| C1 | Codex 0.160.1, 실제 gpt-6.1-sol/high, 공통 실행기 1회 | 231 PASS/종료 0 | 231 PASS와 report.predecessor FAIL 1/종료 1 | 통과 |
| C2 | Claude 2.1.283, 실제 claude-sonnet-5/argv high, 최초 1회와 환경 복구 1회 | 실제 Bash 종료 0, 전체 출력 231 PASS | 실제 Bash 종료 1/status FAIL. 생략된 counts/ID는 동일 입력의 상위 전체 출력 확보에서 231 PASS/FAIL 1과 report.predecessor로 확인 | 통과, 관찰 한계 구분 |

입력은 S3 공통 회귀의 정상 report 상태를 격리 복사했다.
오류 입력은 03-retention-policy의 in_progress design이 superseded 공통 design을 base_on으로 참조하도록 한 줄만 변경했다.
설치본 check_reports.py를 절대 경로로 실행해 작업 상태/승인과 파일을 변경하지 않았다.

Claude 최초 호출은 명령 허용 규칙과 맞지 않아 검사 Bash 권한 거부 8건이 있었고,
불필요한 진단 반복을 상위가 중단하여 종료 143/실제 검사 미실행으로 보존했다.
같은 두 명령을 일시적 세션 settings의 정확한 allow 규칙으로 지정하고 리다이렉션/도움 명령을 제거했다.
도구 허용을 넓히거나 global/user 설정을 바꾸지 않았다.
[Claude 공식 권한 문서](https://code.claude.com/docs/en/permissions)의 정확한 명령 규칙을 적용했다.
복구 호출은 135.389초, CLI 종료 0/result.is_error=false/permission_denials=[]였다.

Claude는 오류 Bash 출력의 10,000자 제한 때문에 counts/FAIL ID를 직접 보지 못했다고 보고했다.
상위가 입력/설치본 해시 무변경을 확인하고 같은 검사기를 한 번 더 실행해 누락된 전체 결과를 확보했다.
이를 Claude의 독립 관찰로 바꾸거나 원래 실패를 통과로 덮어쓰지 않았다.
두 CLI의 설치본 31개 파일과 모든 사전 입력/승인 상태는 실행 전후 그대로다.
새 제품/업무 수행, 모의 승인, 전체 시나리오 반복과 전역 설정 변경은 없었다.

## 완료 판단의 한계와 정리

현재 필수 R1~R8과 사례 S1~S4/C1/C2에 미해결 실패/미실행/미판정은 없다.
동작은 격리 사본/모의 QA, 교차 검토는 읽기 표본, 호환성은 실제 설치본 최소 사례의 범위다.
ASCII 문자 형식을 실제 UI 렌더링 전수 확인으로 확대하지 않는다.
원시 turn/임시 프로젝트/스킬 사본/전체 해시/중간 초안은 최종 독자의 이해에 필수인 근거가 아니므로
실제 대조와 위 판단 통합 후 현재 작업 소유 중간/시험 파일 826개와 역할이 끝난 작업 루트를 정리했다.
보존 자료의 무변경과 현재 정본/원본 부재를 확인했고 다른 작업/설치본/기존 사용자 자료는 유지했다.
기록 이관/생명 주기 완료와 실제 커밋/main 반영은 별도 절차다.
