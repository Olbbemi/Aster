# 번들, 회귀와 보류 기록 개선 명세서

## problem-definition (문제 정의)

### 진입 조건 확인

사용자가 code-development의 번들과 회귀 번호 혼선을 제기하고 Rosemary 사례를 지정했다.

### 스킬을 통해 해결해야 할 문제

단계별 번호에 번들 전환과 회귀 개정이 섞여 현재 결과와 과거 결과의 관계를 파악하기 어렵다.
단계 전달, 범위 밖의 작업과 조건부 종료를 이관이라는 표현으로 함께 관리하여 완료 범위도 모호하다.

### 스킬을 사용하는 주체와 스킬이 사용되는 상황

사용자와 Codex/Claude 에이전트가 공통 설계를 여러 번들로 수행하거나 검증 후 이전 단계로 회귀하는 개발 작업에 사용한다.

### 문제가 해결되었을 때 기대하는 결과

번들, 회귀, 인계와 보류를 구분하고 현재 기준과 과거 승인 근거를 정확한 파일 참조로 추적한다.
전체 완료 때 보류 자료의 사용자 지정 위치 이동까지 확인한다.

### 요청한 스킬의 생성, 변경, 통합 또는 폐기가 필요한지에 대한 판단과 근거

기존 code-development의 흐름, 기록 구조와 템플릿을 변경하는 update 작업이다.
별도 스킬을 생성하지 않는다.

### 스킬이 수행할 범위와 제외할 범위

설계 점검 상태, 번들 배치, 회귀 개정, 인계와 보류 및 최종 정리 절차를 변경한다.
지침, 템플릿과 관련 검사 영향 검토를 포함한다.
Rosemary 실제 자료의 자동 전환과 Aster에서의 전역 설정 변경은 제외한다.
소스 Git 반영은 후속 사용자 승인으로 수행했고 실제 전역 설치 업데이트는 Garden에서 처리했다.

### 후속 단계에서 확인할 사항

최초 논의의 후속 확인은 검증 기준/CLI 요건과 기존 번호/상태/참조 가정의 조사였다.
요건 정의와 기존 구성 확인에서 이를 확정했고 동작/호환성 검증으로 실제 결과를 확인했다.

### 완료 조건 확인

문제, 사용 주체, 기대 결과, 변경 필요성과 범위를 대화 및 실제 Rosemary report로 확인했다.
문제 정의를 막는 미확인 사항은 없으며 후속 확인 대상을 구분했다.

### 단계 이동 기록

최초 기록 전 논의에는 lifecycle 모델 승인/명세서가 없었다.
보류 템플릿 작성 요청 때 최초 명세서를 작성하여 선행 조건을 확인했다.
초기 논의를 lifecycle 전체 준수로 소급 기록하지 않는다.

## requirements-definition (요건 정의)

### 진입 조건 확인

문제 정의의 완료 조건과 위 근거를 확인했다. 이번 기록은 최초 상태 산정이다.

### 스킬의 사용 형태(내부용 또는 플러그인 배포용)

Camellia 플러그인 배포용 code-development를 유지한다. 대상은 plugins/Camellia/skills/code-development다.

### 지원 대상 CLI와 각 CLI에 적용할 호환성 요건

Codex와 Claude에서 같은 SKILL.md, Markdown/YAML, 템플릿과 Python 3.10 이상 검사기를 사용한다.
하네스별 별도 파일이나 다른 업무 동작은 추가하지 않는다.
설치본에서 변경 지침/템플릿 접근과 검사 실행을 각각 확인해야 하며 한 CLI 결과를 다른 CLI 결과로 대신하지 않는다.
호출명/description/등록은 유지하므로 자동 선택 긍정/부정 사례를 전부 반복하지 않는다.

초기 요건 합의는 설치/커밋/푸시의 실행 승인이 아니었다.
후속 사용자 승인으로 커밋/푸시/PR을 수행하고 실제 설치본은 별도 설치 반영을 확인한 뒤 검사했다.
Aster 세션에서는 전역 설치 설정을 변경하지 않으며 Garden에서의 반영이 필요하면 인계한다.
이 제약은 호환성 완료를 뜻하지 않는다. 설치 전 격리 사본 결과와 실제 설치본 결과를 구분한다.

### 스킬 호출 조건과 호출 제외 조건

요구사항 구체화나 설계 판단이 필요한 신규 개발, 개선, 수정과 리팩터링 및 기존 report 기반 재개에 사용한다.
명시적 요청은 유지하고, 별도 설계 없이 수정/확인 가능한 작은 국소 작업은 기존 자동 적용 제외를 유지한다.
코드 분석만 수행하거나 테스트만 별도로 보강하는 작업과 구분한다.
이 기준은 현행 SKILL.md의 호출 조건을 보존하며 이름/description 변경은 범위 밖이다.

### 스킬 실행에 필요한 입력과 기대 결과

개발 요청과 프로젝트/작업 루트는 필수다.
신규 작업은 첫 저장 전에 주제와 시작 단계를 합의한다.
재개/중간 진입은 해당 report와 실제 승인 근거가 필요하며 누락하면 의존 작업을 시작하지 않고 필요한 입력/진입 경로를 사용자와 확인한다.
번들 진입은 공통 설계, 해당 범위와 의존/준비 조건, 이름/시작 승인을 확인한다.

출력은 단일 플로우 또는 번들 구조의 report, 실제 개발 산출물과 필요한 deferred 항목이다.
번들/개정은 명확히 구분하고 실제 사용한 기준 파일 및 승인 이력을 보존해야 한다.
신규 작업에 새 형식을 적용하고 기존 작업은 요청 없이 자동 전환하지 않는다.

### 반드시 수행해야 하는 동작과 에이전트가 재량으로 판단할 수 있는 동작

| 구분 | 합의한 동작 |
| --- | --- |
| 용어 | 같은 플로우의 단계/번들 전달은 인계, 범위 밖으로 미룬 작업은 보류, 선행 단계 수정은 회귀다. |
| 보류 대상 | 처음부터 범위 밖인 작업과 사용자 합의로 기존 범위/완료 기준에서 제외한 작업을 포함한다. 후자는 관련 명세를 먼저 변경한다. |
| 설계 상태 | 설계에만 in_progress -> in_review -> awaiting_approval -> completed를 적용한다. 보완이 필요하면 in_progress로 돌아간다. |
| 설계 점검 | 승인 대상의 설계와 근거, 규모/분할 필요성, 번들 범위/순서/의존/인계, 보류 분리와 현재 상세/후속 설계 안건을 확인한다. 후속 번들의 상세 완성을 요구하지 않는다. |
| 분할 제안 | 상세 설계 부담, 구현/검증/QA 규모, 준비 조건 차이, 실패 시 재작업 영향으로 분할을 검토한다. 사용자 요청이 없어도 제안하고 사용자와 확정한다. 고정 파일/테스트 수로 강제하지 않는다. |
| 분할 경계 | 번들 생성과 변경은 설계에서 결정한다. 이후 단계는 승인된 기준을 따르며 기준 변경이 필요하면 회귀한다. 현재 필수 오류 처리나 안전성 검증을 단순 작업량 때문에 넘기지 않는다. |
| 번들 배치 | 작업 루트 바로 아래 01-public-contracts 형식의 두 자리 순번-이름을 사용한다. bundles 계층은 두지 않는다. |
| 이름과 생성 | 번들 시작 시 디렉토리명을 제안하고 사용자 승인 후 생성한다. 미시작 디렉토리/report를 미리 만들지 않는다. |
| 공통/상세 | 작업 루트에 공통 논의/설계를 두고 번들 안에 필요한 상세 설계/구현/검증/QA를 둔다. 공통 설계로 충분하면 번들 상세 설계를 생략할 수 있다. |
| 단일 흐름 | 번들이 없으면 작업 루트에 모든 단계 report를 둔다. |
| 구조 유지 | 한 번 번들 구조로 진행하면 공통 설계 회귀 후에도 유지한다. 기존 수정은 기존 번들, 새 범위는 다음 순번 번들에서 진행한다. 번호는 추가 순서이며 의존/실행 순서는 설계에서 확인한다. |
| 최초/개정 | 최초는 implementation-report.md 같은 무번호 파일이다. 대체 시 implementation-report-rev-001.md부터 단계/디렉토리별 증가한다. 기존 이름과 본문/승인 근거를 보존하고 superseded로 표시한다. |
| 회귀 영향 | 번들 내부 및 공통 논의/설계 변경의 영향을 식별하고 영향받는 후속 report를 hold로 둔다. 영향 없는 결과는 유지 근거를 남긴다. 유지 가능한 hold는 참조/재검토 기록을 갱신하여 재승인, 결과 변경은 새 rev로 대체한다. |
| 기준 추적 | 공통 논의/설계도 작업 루트에서 rev로 개정한다. 번들 번호로 기준 개정을 추정하지 않고 내부 report가 실제 사용한 공통 파일과 선행 개정을 명시적으로 참조한다. |
| handoff | qa_handoff를 handoff로 바꿔 같은 번들의 QA와 후속 번들의 검증/QA에 사용한다. 대상, 현재 미수행 이유, 현재 완료 타당성, 받을 번들/단계, 실행 조건/판정 기준과 실제 처리 결과를 연결한다. 전체 완료 시 처리 결과를 확인한다. |
| 보류 기록 | next_cycle_handoff의 별도 작업 이관은 보류로 정리한다. 작업 루트 deferred/에 항목별 파일로 모으며 첫 항목 기록 시 생성한다. 별도 공용 todo 기록은 의무가 아니다. |
| 최종 정리 | 전체 플로우 완료 시 deferred 파일이 있으면 사용자와 이동 위치를 논의한다. 지정 위치로 이동하고 파일/참조를 확인한 뒤 빈 deferred 디렉토리를 삭제해야 전체 완료 조건을 충족한다. |
| 신규/기존 | 신규 작업부터 적용한다. 진행 중 작업은 사용자 요청 시 전환하고 기존 이력과 승인을 보존한다. |

설계 중간 상태는 절차상 점검 단계다. 상태 변경을 강제하는 전용 도구나 별도 기계적 차단 장치를 요구하지 않는다.

### 스킬 실행에 적용되는 제약, 실패 조건과 대응

현재 필수 항목은 보류 기록만으로 완료하지 않는다. 범위/완료 기준 변경은 사용자와 합의한다.
이동 목적지가 없거나 접근/이동에 실패하면 원본을 보존하고 사용자와 후속 처리를 논의한다. 임의 경로 생성/대체/자료 삭제로 완료하지 않는다.
전체 완료는 자료 이동과 빈 deferred 정리를 포함하며 이동은 보류 작업의 착수/완료를 뜻하지 않는다.

### 각 요건의 충족 여부를 검증할 수 있는 기준

구조/형식과 로컬 링크는 기존 읽기 전용 검사로 확인한다.

중간 상태 전환을 강제하는 신규 실행 도구는 만들지 않는다.
이름/호출 조건 등 무변경 동작을 전부 재시험하지 않으며 4개 대표 시나리오는 R1~R7에 대응한다.
R8의 설치본 검증은 업무 흐름 전체를 반복하지 않고 변경 자료 접근과 필요한 실행을 최소 사례로 확인한다.

### 확인하지 못한 사항과 사용자의 판단이 필요한 사항

요건 정의를 막는 추가 동작 결정은 없다.
당시 후속 확인인 base_on/번들표/검사기 처리 방향은 기존 구성 확인과 구조 설계에서 확정했다.
시험 모델/입력/종료 조건과 실제 설치 반영을 해당 실행 전에 확인했다.
합의와 실제 실행 승인을 구분한다. 각 검증의 최종 결과는 [검증 결과](validation-results.md)에 보존한다.

### 완료 조건 확인

사용 형태/호출/입력/산출물, 필수/재량 동작, 실패/승인 경계, 지원 CLI와 요건별 검증 기준을 정의했다.
문제 정의의 범위와 대응하며 현재 확정할 동작 간 충돌은 확인되지 않았다.
실행 권한/시험 환경은 후속 단계에서 확인할 사항으로 구분했다.
요건 정의의 완료 조건을 충족했다.

### 단계 이동 기록

requirements-definition -> existing-configuration-review.

최초 상태 산정의 한계는 문제 정의의 단계 이동 기록에 보존했다.

SKILL은 진입, guidelines는 기록/승인, work-bundles는 설계 분할/순차 진행, deferred-work는 보류 이동, legacy-records는 기존 형식 유지의 정본이다.

### 스킬을 구성하는 파일과 자료 사이의 참조 방향 및 의존 관계

[공통 기록/승인 계약](../../../../../plugins/Camellia/skills/code-development/references/guidelines.md)와 [번들 계약](../../../../../plugins/Camellia/skills/code-development/references/work-bundles.md)의 상대 참조를 따른다.
신규 base_on은 report 위치 기준의 실제 선행 파일이며 공통 design은 discussion, 번들 design은 공통 design, 구현은 해당 상세 또는 공통 design, 검증/QA는 같은 번들의 직전 단계다.
다른 번들 의존은 본문에서 연결한다. 과거 결과와 현재 진행 입력의 유효성을 구분한다.

deferred-item-template.md, deferred-work.md와 legacy-records.md를 추가했다.
항목별 보류 내용/이유/범위/근거/재검토 조건은 [보류 계약](../../../../../plugins/Camellia/skills/code-development/references/deferred-work.md)에서 정의한다.

내부 lifecycle/공용 검사기는 개발 단계에서만 사용하며 배포 스킬의 실행 의존성으로 추가하지 않았다.

### 플러그인 단위 자료와 플러그인 내부 공용 자료

plugins/Camellia/.claude-plugin/plugin.json을 버전 정본으로 유지했다.
스킬/플러그인별 버전 중복이나 하네스 전용 manifest를 추가하지 않았다.

### 개발 전용 자료와 스킬 사용 자료의 구분

SKILL/references/assets/scripts만 배포물에 포함한다. Aster tests/명세서/중간 시험 자료와 완료 기록은 개발 전용이다.

### 지원 CLI에서 함께 사용하는 공용 구성

양 CLI는 같은 Markdown/YAML/템플릿과 Python 검사기를 사용한다. 현재 배포 구성은 31개 파일이다.

### 특정 지원 CLI에서만 사용하는 전용 구성

없음. 실제 비호환 근거 없이 CLI 전용 업무 지침이나 구현을 추가하지 않았다.

S1 단일 흐름, S2 분할/인계, S3 내부/공통 회귀와 레거시, S4 보류/정리로 설계했다.
최종 입력/종료 조건과 판정은 [검증 결과](validation-results.md)에 보존했다.

### 구조 설계에 영향을 주는 미확인 사항과 확인 단계

실제 승인 경계/인계/보류 이동은 동작 시험, 설치본 로드/검사 역할은 호환성 시험에서 확인했다.
Git/전역 설치 권한은 설계 완료와 구분했다.

파일 역할, 정본 참조, 신구 기록 구분과 최소 검증 범위를 확정했다. 후속 번들의 상세 완성을 공통 분할 조건으로 요구하지 않는다.

### 단계 이동 기록

structure-design -> implementation. 사용자 승인 범위로 구현했다.

## implementation (구현)

### 진입 조건 확인

사용자가 같은 모델로 구현 진행을 확인했고 확정한 설계/요건을 기준으로 시작했다.

### 새로 만들거나 수정, 이동 또는 제거한 파일과 디렉토리

SKILL, 공통 지침 6개와 다섯 단계 지침/템플릿, review 템플릿, report 검사 4개와 계약 시험을 수정했다.

### 구현하지 못한 요건과 구현하지 못한 이유 및 보완할 단계

미구현 요건은 없다. 실제 제품/사용자 자료 전환과 전역 설정 변경은 구현 범위 밖이다.

### 완료 조건 확인

정본/단계/템플릿/검사가 새 구조와 신구 호환성 계약에 대응한다. 파일 배치와 명명/참조를 실제 소스에서 대조했다.

### 동작 검증에서 발견한 국소 보완

공통 설계 hold를 이유로 완료 번들의 과거 참조까지 거부하던 충돌을 보완했다.
completed 번들 design/implementation의 과거 공통 hold design만 허용하고 진행/승인 대기, root와 같은 번들 내부 hold는 계속 거부한다.
실제 유지 근거의 타당성은 사람이 대조하며 기계 검사가 대신하지 않는다.

## mechanical-validation (기계 검사)

### 진입 조건 확인

구현된 지침/템플릿/검사기와 요건의 형식 부분을 대조했다.

### 작업 대상 스킬의 기계 검사 항목과 적용 여부

스킬 구조, 로컬 참조, 배포 구성, ASCII 문자 형식, report 계약 시험과 명세서/시나리오 기록 형식을 검사했다.
분할/승인/완료의 의미와 실제 설치본 호출은 기계 검사의 범위가 아니다.

### 기계 검사에 사용한 명령과 각 명령의 적용 대상

Python 3.12.3/PyYAML 6.0.1/markdown-it-py 3.0.0으로 Aster 역할별 검사기를 실행했다.
명령과 대상/검증 범위는 [검증 결과](validation-results.md)의 기계 검사에 보존했다.

### 기계 검사별 통과 또는 실패 결과

구조 PASS, 로컬 참조 315개 PASS/외부 2개 SKIP, 배포 구성 31개 일치, ASCII 도식 1개 형식 PASS다.
초기 96개 계약 시험 뒤 S3 보완으로 5개를 추가하여 최종 101개(기존 77/신규 24)가 PASS다.

### 검사 실패가 발생한 위치와 위반한 개발 규격

초기 링크 시험의 기대 ID를 link.path로 잘못 작성했으나 실제 검출은 link.target이었다. 시험 기대값을 수정했다.
S3 보완 전 새 재현 시험 2개가 실패했고 좁은 검사 수정 후 101개가 통과했다. 현재 기계 실패는 없다.

### 실행하지 못한 검사와 실행했지만 결과를 판정하지 못한 항목

현재 범위에 미실행/미판정 기계 항목은 없다. 외부 URL SKIP은 검증 통과로 확대하지 않는다.

### 의미 판단이 필요한 항목과 그 이유 및 확인할 후속 단계

실제 설계 점검, 이름/단계 승인, 회귀 영향, 인계 해소와 보류 이동은 동작 시험에서 대조했다. 실제 UI 렌더링은 문자 형식 검사로 대체하지 않았다.

### 완료 조건 확인

현재 소스에 유효한 검사/보완 후 결과가 있다. manifest의 version 한 필드 변경은 로직/파일 목록 변경이 아니므로 기존 결과를 재사용했다.

### 단계 이동 기록

mechanical-validation -> behavioral-validation. 사례/입력/모의 승인/모델과 부담을 사용자와 확정했다.

## behavioral-validation (동작 검증)

### 진입 조건 확인

기계 검사와 사용자 지정 Sol/high, 4개 큰 흐름 및 모의 승인/종료 조건을 확인했다.

### 확정한 시나리오와 실행 조건

4개 사례, 총 35회 이내/요청당 600초를 확정했다. 실제 34회이며 S1 6/S2 13/S3 11/S4 4회다.
모의 승인은 준비한 단계/회귀/이름/범위/이동에 한정하고 필수 실패의 통과 승인, 외부 변경과 추가 목적을 제외했다.

### S2 handoff 직접 분기 보완 승인

S2 기본 시험의 첫 QA all_passed는 배정 범위에 맞았다. 미확인 QA의 handoff 직접 분기는 별도 조건/3회 보완을 사용자에게 승인받았다.
원래 결과를 바꾸지 않고 S2 상한 13/전체 35회와 Sol/high를 유지했다.

### 동작 검증을 수행한 사용 사례와 입력

[검증 결과](validation-results.md)의 S1~S4 입력/관찰/종료 조건을 수행했다. 입력/완료 사전 조건과 상위가 제공한 수신 fixture는 실제 모델 수행으로 계산하지 않았다.

### 동작 검증에 사용한 CLI와 실행 환경

격리 Python 제품/시험과 미커밋 개발 스킬 사본을 Codex 공통 실행기로 호출했다.
34개 실제 turn의 gpt-6.1-sol/high를 확인했으며 S2 compaction context는 추가 호출이 아니다.

### 작업 대상 스킬의 인식 여부와 호출 결과

각 사본의 명시 SKILL.md 경로를 읽고 사용했다. 실제 설치 플러그인의 인식/호출 판정은 별도 C1/C2 근거다.

### 요건별 동작 검증 결과와 판정 근거

R1~R7과 4개 필수 사례가 통과했다. 정확한 현재 판정/근거는 [검증 결과](validation-results.md)의 요건 대응과 사례 표에 둔다.

### 이전 단계에서 넘긴 미확인 사항과 의미 판단 항목의 확인 결과 및 근거

점검 진입/제출/승인을 나눠 실제 저장 상태를 관찰했다. 인계의 현재 완료 타당성/수신 결과, 목적지 실패 시 보존과 이동 후 정리를 실제 응답/전후 파일로 대조했다.

### 동작 검증에서 발견한 실패와 재현 조건

S3의 공통 회귀에서 150 PASS/1 FAIL이 발생했다. 과거 완료 번들의 공통 hold 참조를 잘못 거부한 검사 충돌이며 해당 구간을 멈췄다.
좁은 보완과 101개 기계 시험 및 공통 회귀 4회 재시험으로 해소했다. 최종 231 PASS와 새 03 번들 입력 연결을 확인했다.
상위 입력 준비 중 원본 보존을 접두어 일치로 잘못 비교한 1회 입력 부재는 모델 호출/스킬 실패로 계산하지 않았다.

### 실행하지 못한 사용 사례와 결과를 판정하지 못한 동작

현재 필수 사례에 미실행/미판정은 없다. 모의 QA와 독립 사용자 QA를 구분하며 실제 업무 전체 완성을 의도한 종료 조건으로 확대하지 않았다.

### 완료 조건 확인

R1~R7, 호출 상한/실제 모델과 초기 사본 217개 및 레거시 36개 파일 보존을 대조했다. 현재 동작 실패는 없다.

### 단계 이동 기록

behavioral-validation -> cross-validation. 재현에 필요한 실패/보완/관찰 한계를 최종 검증 결과에 통합했다.

## cross-validation (교차 검증)

### 진입 조건 확인

4개 동작 사례와 국소 보완 후 실제 소스/101개 시험 및 종료 조건을 확인했다.

### 교차 검증의 수행 여부와 판단 근거

자연어 계약/승인/참조 예외의 해석을 다른 하네스에서 독립 대조할 필요가 있어 읽기 교차 검토를 수행했다.
사용자 승인한 Claude Sonnet/high 1회/900초로 331.770초에 완료했다.

### 교차 검증 대상과 검증에 포함한 파일 및 변경 내용

지침/단계/템플릿/검사/계약 시험 25개 변경과 32개 전체 대상 파일 해시를 고정해 검토했다.
검토 후 version 필드만 4.0.0으로 변경했고 검토한 스킬/시험 로직은 동일하다.

### 교차 검증의 판정 기준과 제외 범위

8개 기준은 설계 점검/분할, 이름 승인, 개정/영향 보존, handoff/완료, 보류 이동, 레거시 구분, 검사 구현/시험과 기록 근거다.
Read/Glob/Grep만 허용하고 소스 변경/독립 테스트 실행/전체 turn 전수 열람/설치 호출/실제 UI 렌더링을 제외했다.

### 교차 검증 요청, 검토 결과와 후속 판단 기록

검증 대상 report-flow, 마지막 회차 round-001이다. 실제 검토자는 Claude Sonnet 5, high는 argv 근거다.
검토 원문/대상 해시/후속 판단을 대조한 핵심 판단은 검증 결과의 교차 검토에 출처와 함께 보존했다.
다른 작성자의 원문을 수정하거나 요약을 검토자의 새 원문으로 표시하지 않았다.

### 교차 검증에서 제시된 각 지적에 대한 수용, 반박 또는 재검증 판단과 그 근거

필수 결함/수정 지적은 없었다. 독립 실행/전수 로그 미열람 등 M1~M5를 항목별로 실제 근거와 대조했다.
의미 판단을 기계 검사로 대체할 수 없다는 한계는 수용하되 모의 승인 근거를 독립 비교할 수 없다는 일반화는 채택하지 않았다.

### 이전 단계에서 넘긴 사항의 확인 결과와 교차 검증에서 남은 미확인 사항

요청자가 실제 종료 응답/outcome과 레거시 변경 0/36개 해시, 소스 32개 해시/원문 보존을 확인했다.
이는 Claude가 미열람한 범위의 독립 관찰이 아니다. 필수 R8은 후속 실제 설치본 검증에서 확인했다.

### 수용한 지적에 따른 재검토와 수정 및 이후 재검증 결과

교차 검토가 요구한 소스 수정이나 추가 검토는 없다. 기존 101개/동작 근거를 재사용했다.
version 한 필드 변경과 호환성 실행 조건 보완은 검토한 사용 계약/로직을 바꾸지 않아 기존 검토가 유효하다.

### 교차 검증을 수행하지 않은 사실이 완료 판단에 미치는 영향

해당 없음. 독립 읽기 검토를 수행했다. 설치본 호출/독립 테스트 실행으로 확대하지 않는다.

### 완료 조건 확인

실제 대상/원문/후속 판단과 8개 기준 및 관찰 한계를 대조했고 필수 미해결 사항이 없다.

### 단계 이동 기록

cross-validation -> compatibility-validation. 실제 배포물/설치/접근/검사 역할을 별도로 확인했다.
