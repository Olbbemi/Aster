# code-development 설계 산출물과 정형 검사 생명 주기 명세서

## problem-definition (문제 정의)

### 진입 조건 확인

기존 code-development의 설계 마무리 및 정형 검사 개선 요청을 확인했다.
대상 스킬과 작업 유형 update가 식별되었으며, 최초 기록 전 실제 요청과 파일로 조건을 대조했다.

### 스킬을 통해 해결해야 할 문제

설계 결과에서 필요한 구조체와 처리 흐름을 읽기 쉽게 보존하고 인계할 기준이 부족하다.
ASCII 도식의 작성 시점, 논의 그룹별 파일 분리와 표시 확인 기준이 없다.
반복 가능한 문서 형식 및 참조 검사를 자연어 판단에 맡기고 있다.

작업 분할 판단은 [설계 지침](https://github.com/Olbbemi/Aster/blob/f9fcc9ef831c679244921c8d7ae62c2d3192ea84/plugins/Camellia/skills/code-development/references/stages/design.md)과 [설계 템플릿](https://github.com/Olbbemi/Aster/blob/f9fcc9ef831c679244921c8d7ae62c2d3192ea84/plugins/Camellia/skills/code-development/assets/stage_reports/design-template.md)에 이미 정의되어 있지만 실제 실행 여부를 확인할 과거 시험 근거가 없다.
이번 작업의 기존 명세와 완료 기록은 초기 조회에서 찾지 못했다.
지침의 존재와 실제 준수를 구분하여 검증해야 한다.

### 스킬을 사용하는 주체와 스킬이 사용되는 상황

Codex와 Claude에서 code-development를 사용하는 개발 에이전트와 설계 결과를 검토하는 사용자.
설계를 최종 검토하거나 후속 구현으로 인계하고, 작업을 재개하면서 report와 연결 자료를 확인하는 상황이다.

### 문제가 해결되었을 때 기대하는 결과

설계 마무리 때 필요한 구조체 설명과 흐름도를 읽을 수 있으며, 긴 내용은 관련 논의 그룹별로 찾을 수 있다.
불필요한 반복 작도 없이 최종 설계와 도식이 일치한다.
분할 판단과 필요한 제안이 실제 실행에서 관찰된다.
정형 오류는 재현 가능한 검사로 찾고 의미 판단 및 사용자 승인과 혼동하지 않는다.

### 요청한 스킬의 생성, 변경, 통합 또는 폐기가 필요한지에 대한 판단과 근거

update가 필요하다.
설계와 report 인계는 기존 스킬의 책임이며 신규 스킬로 분리할 이유가 없다.
기존 분할 절차는 재사용하고 누락된 설계 산출물 기준과 읽기 전용 검사 절차를 보완한다.

### 스킬이 수행할 범위와 제외할 범위

합의한 작업 범위는 다음 여섯 항목이다.

1. 설계 최종 승인 전에 필요한 구조체 설명과 ASCII 흐름도를 정리한다.
2. 긴 내용은 논의 그룹별 상세 파일로 묶고 report에 설명과 링크를 둔다.
3. 중간 초안은 필요할 때만 작성하며 매 응답 재작도를 요구하지 않는다.
4. ASCII 도식의 정렬과 실제 표시를 확인한다.
5. 기존 작업 분할 절차를 필요/불필요 사례로 실제 검증한다.
6. 스크립트화 가능한 검사를 조사하고 합의한 판정 기준에 따라 구현 및 검증한다.

1번의 선행 확인으로 설치본과 소스의 report 본문 정리 차이를 검토한다.
다른 설치본 변경의 일괄 반영, 전역 설정 변경, 무관한 기존 기록 정리, 자동 승인과 작업 상태 변경은 범위 밖이다.
Git 반영 및 설치는 기존 권한과 규칙을 따르며 이번 착수 요청만으로 실행하지 않는다.

### 후속 단계에서 확인할 사항

요건 정의에서 자동 검사 항목과 적용 시점 및 오류/미판정 경계를 확정한다.
기존 구성 확인에서 정리 절차의 소스 차이와 검사기 재사용 범위를 판단한다.
구조 설계에서 상세 파일 배치, 도식 표시 확인 방법과 시나리오 초안을 정한다.

### 완료 조건 확인

문제, 사용 주체와 상황, 기대 결과, update 필요성, 포함/제외 범위가 실제 요청과 대상 파일로 확인되었다.
미확인 사항은 위 후속 단계에 배치했으며 문제 정의 완료를 막지 않는다.

### 단계 이동 기록

최초 기록 전 조건 대조 결과다.
과거 전이를 추정하지 않으며 최초 단계 선정 근거는 요건 정의의 단계 이동 기록에 둔다.

## requirements-definition (요건 정의)

### 진입 조건 확인

문제 정의의 완료 조건과 이번 여섯 항목의 작업 필요성 및 범위를 확인했다.
기존 배포용 스킬의 개선이며 입력과 기존 지침을 확인할 수 있다.

### 스킬의 사용 형태(내부용 또는 플러그인 배포용)

기존 Camellia 플러그인 배포용 스킬 code-development를 유지한다.
대상 경로는 plugins/Camellia/skills/code-development다.
배포 경계는 plugins/Camellia/이며 사용자 실행에 필요한 검사기와 지침은 그 안에 포함되어야 한다.

### 지원 대상 CLI와 각 CLI에 적용할 호환성 요건

Codex와 Claude를 유지한다.
변경된 설계 지침/템플릿 접근과 새 검사기의 호출 및 결과 해석을 각 CLI의 실제 설치본에서 확인한다.
한 CLI의 결과나 격리 사본 시험으로 다른 CLI 또는 실제 설치 호환성을 통과 처리하지 않는다.
현재 CLI별 전용 동작을 추가할 근거는 없다.

설치본 호환성 시험은 변경 커밋/버전과 실제 로드 위치를 확인해야 한다.
전역 설정 또는 설치 변경이 필요하면 Aster에서 우회 수행하지 않고 해당 작업 경계와 사용자 이관 절차를 따른다.

### 스킬 호출 조건과 호출 제외 조건

기존 [SKILL.md](https://github.com/Olbbemi/Aster/blob/f9fcc9ef831c679244921c8d7ae62c2d3192ea84/plugins/Camellia/skills/code-development/SKILL.md)의 description과 적용 범위를 유지한다.
요구사항 구체화나 설계 판단이 필요한 개발과 기존 report를 통한 재개에 적용한다.
별도 설계 판단이 필요 없는 작은 국소 수정의 자동 적용 제외도 유지한다.
이번 작업은 이 스킬 자체를 skill-lifecycle로 개발하며, 일반 개발용 report를 중복 생성하지 않는다.

### 스킬 실행에 필요한 입력과 기대 결과

설계에는 유효한 discussion report와 사용자 합의, 현재 design report 및 관련 코드가 필요하다.
검사에는 사용자가 선택한 프로젝트/작업 범위와 실제 저장된 report, manifest 및 연결 자료가 필요하다.
미선택 주제나 미시작 report를 검사를 위해 생성하지 않는다.

결과는 설계 report와 필요한 그룹별 상세 자료, 검사 항목별 결과 및 판정 근거다.
읽기 실패, 입력 부족과 의존성 부재는 통과와 구분하여 알린다.
검사기의 입력 단위와 정확한 출력 계약은 구조 설계에서 확정한다.

### 반드시 수행해야 하는 동작과 에이전트가 재량으로 판단할 수 있는 동작

R1. 설계 최종 검토/승인 전에 필요한 구조체 설명과 처리 흐름을 정리한다.
모듈 간 계약과 핵심 데이터는 설계 대상으로 유지하고 모든 내부 자료구조나 함수의 명세를 강제하지 않는다.

R2. 긴 설계는 관련 논의 그룹별로 상세 파일에 모을 수 있다.
report에는 짧은 설명과 링크를 두고 상세 기준을 중복 정의하지 않는다.
흐름 하나마다 파일을 만들거나 작은 설계에도 분리를 강제하지 않는다.

R3. 중간 초안의 작성 여부는 논의 필요에 따라 판단한다.
매 응답/수정마다 작도하지 않으며 최종 제출 전 합의한 설계와 도식을 대조한다.

R4. ASCII 도식의 코드 블록, 공백/탭, 줄바꿈과 연결선 정렬 및 실제 표시를 확인한다.
표시를 확인하지 못하면 그 한계를 명시하고 확인 완료로 처리하지 않는다.
한글 설명 자체를 금지하지 않으며 자동 문자 검사를 가독성 판정으로 사용하지 않는다.

R5. 설계 후 작업 분할 필요성은 항상 재평가하고 근거를 남긴다.
필요하면 사용자에게 분할을 제안하며 승인 없이 범위를 축소하지 않는다.
기존 지침을 실제 필요/불필요 사례로 시험한다.

R6. 반복 가능하고 판정 기준이 명확한 검사를 식별하여 합의한 항목을 읽기 전용으로 구현한다.
스크립트가 report를 생성/수정하거나 체크/상태를 바꾸고 승인 또는 설계 타당성을 판정하지 않는다.

R6의 아래 네 검사 범위는 사용자 확인을 받았다.
상세 판정과 파일 배치는 구조 설계에서 구체화한다.

| 후보 | 판정할 내용 | 경계 |
| --- | --- | --- |
| report 형식 | YAML 파싱, status/base_on 형식과 허용값, 공통 필수 영역 | 내용의 충실도와 승인 진위는 판정하지 않음 |
| 기록 연결 | manifest의 선택 작업/stages와 report 파일명/번호, base_on 대상 및 단계 연결 | 해당 작업의 stages 사용. 미시작 후속 report 부재는 오류가 아님 |
| 로컬 참조 | report/manifest/상세 파일의 로컬 링크 대상과 절 존재 | 외부 URL은 미검사. 예시 코드 속 경로는 제외 |
| 도식 형식 보조 | 식별된 ASCII 도식의 탭/제어문자와 비ASCII 도형 기호 등 | 일반 코드/한글 설명은 일괄 금지하지 않음. 시각적 가독성은 별도 확인 |

기존 report의 제목 변형/과거 형식과 superseded 기록을 검사 때문에 일괄 변환하지 않는다.
자동 판정 범위가 명확하지 않으면 오류로 단정하지 않고 미판정 또는 사람/에이전트 판단으로 구분한다.

### 스킬 실행에 적용되는 제약, 실패 조건과 대응

SDD, SSOT 및 기존 단계/승인/회귀 규칙을 유지한다.
code-development에 lifecycle의 기계 검사 단계를 새로 추가하는 작업은 아니다.
검사 기준은 먼저 지침에 정의하고 코드만으로 새로운 필수 조건을 만들지 않는다.

검사 실행 실패/의존성 부족/읽기 실패는 미실행 또는 미판정으로 보고한다.
누락이나 모순이 확인되면 기존 선행 report 확인 규칙에 따라 처리하며 검사기가 진행을 승인하거나 상태를 변경하지 않는다.
ASCII 정렬이 깨지면 폭과 배치를 단순화하고 다시 확인한다.
한정된 문자 검사 통과만으로 실제 렌더링을 확인했다고 주장하지 않는다.
배포물은 Aster tools/ 또는 개인 설치 캐시를 필수 실행 의존성으로 요구하지 않는다.

### 사용자 확인 및 승인 조건

설계/분할 결과와 단계 종료는 기존 code-development 승인 절차를 유지한다.
이번 여섯 항목의 작업과 skill-lifecycle 사용은 대화에서 합의되었다.
진행 모델은 GPT-6 Astra / high이며 적용 확인 출처는 사용자의 "모델은 astra/high 가 맞는데"라는 확인이다.
실행 상태를 별도로 독립 검증한 것으로 표현하지 않는다.
6번의 조사/설계/구현/검증이 추가된 범위로 이어서 진행한다는 요청을 함께 반영한다.

report 형식, 기록 연결, 로컬 참조와 도식 형식 보조 검사를 읽기 전용으로 구현하는 범위를 확인받았다.
확인 근거는 네 범위로 구체 설계를 진행할지 제시한 요청에 대한 사용자의 "네" 응답이다.
상세 판정 기준은 구조 설계에 반영한 뒤 구현에 적용한다.
시나리오 입력, 모의 승인, 호출 수와 환경은 묶음별 사용자 확인 후 실행했다.
추가 승인 경계 시험과 실제 설치본 시험도 별도 진행 요청을 확인했다.
Git/설치/별도 에이전트 실행 권한은 모델 승인이나 착수 요청으로 대체하지 않는다.

### 각 요건의 충족 여부를 검증할 수 있는 기준

검증의 공통 기준은 Aster의 standards/skills/skill-validation.md다.

| 요건 | 검증 방법과 통과 기준 |
| --- | --- |
| R1 | 설계 종료 시 필요한 구조체/계약 설명과 흐름도가 승인 대상에 포함되고 report에서 찾을 수 있음 |
| R2 | 긴 설계는 논의 그룹으로 묶이며 요약/링크/상세의 내용이 일치함. 작은 설계에 불필요한 파일을 강제하지 않음 |
| R3 | 중간 논의마다 다시 그리지 않으면서 최종 변경이 도식에 반영됨 |
| R4 | 실제 출력에서 연결선/정렬을 대조하고, 표시 미확인은 통과와 구분함 |
| R5 | 분할 필요와 불필요 사례 각각에서 근거 기록, 필요한 제안과 승인 전 경계가 관찰됨 |
| R6 | 확정한 정상/오류/미판정 입력의 반복 실행 결과와 종료 코드가 일치하고 입력 파일이 변경되지 않음 |
| 배포/호환성 | Codex와 Claude 실제 설치본에서 변경 자료 및 검사기 접근/실행을 각각 확인함 |

검사기 자체 회귀 테스트와 에이전트의 실제 지침 수행 시험은 별도 근거로 관리한다.

### 확인하지 못한 사항과 사용자의 판단이 필요한 사항

구현 기준 소스의 차이와 후속 파일 배치 등은 기존 구성 확인과 구조 설계에서 처리한다.

## structure-design (구조 설계)

### 진입 조건 확인

기존 구성 확인 완료와 R1~R6, 배포형 및 두 CLI 지원 조건을 확인했다.

### 작업 대상 스킬과 지원 파일 및 디렉토리의 구조

기존 SKILL.md, workflow.md, guidelines.md, stages/design.md와 design-template.md를 수정한다.
references/report-checks.md, scripts/check_reports.py, scripts/requirements.txt를 추가한다.
개발 테스트는 tools/tests/validation/test_code_development_reports.py에 두며 기존 파일의 삭제/이동은 없다.

### 각 파일과 자료가 담당할 역할

설계 지침은 구조체/계약과 ASCII 흐름의 최종 정리, 그룹 상세와 인계를 담당한다.
템플릿은 정본 지침을 참조한다. 공통 지침은 검사 적용 시점과 오류/미판정 대응을 정의한다.
검사기는 합의한 형식만 읽기 전용으로 판정한다.

### 스킬을 구성하는 파일과 자료 사이의 참조 방향 및 의존 관계

SKILL/workflow/guidelines -> report-checks -> check_reports.py/requirements.txt.
설계 템플릿 -> 설계 지침 -> 본문 정리/검사 안내.
검사기는 선택 작업의 manifest/report/상세와 라이브러리를 읽으며 Aster tools에 의존하지 않는다.

### 작업 대상 스킬 전용 자료

설계 상세는 design-report-NNN/ 아래 논의 그룹별 Markdown으로 필요할 때 생성한다.
report에는 설명과 링크만 두고 같은 규칙을 독립 정의하지 않는다.
회귀한 현재 그룹은 새 번호의 상세를 정본으로 삼고 이전 자료는 이력으로 보존한다.
기존 독립 외부 문서의 참조 유지와 과거 설계 상세의 정본 재사용을 구분한다.

### 내부 스킬 공용 자료

스킬 런타임용 공용 자료는 추가하지 않았다. Aster 공용 검사기를 개발 검증에 사용했다.

### 플러그인 단위 자료와 플러그인 내부 공용 자료

플러그인 공용 자료 추가 없음. 최종 버전은 3.0.0이며 필수 검사 의존성 도입의 major 판단은 [검증 기록](validation.md)에 기록했다.

### 개발 전용 자료와 스킬 사용 자료의 구분

검사기/실행 계약/의존성과 지침은 배포물에 포함한다.
개발 테스트, 작업 명세, 시험 사본과 결과는 배포 경계 밖이다.

### 지원 CLI에서 함께 사용하는 공용 구성

두 CLI는 같은 Markdown, 템플릿과 Python 검사기를 사용한다.
설치 경로 차이는 호출 환경의 차이이며 파일 내용과 판정 계약은 동일하다.

### 특정 지원 CLI에서만 사용하는 전용 구성

없음. 별도 하네스 전용 구성을 요구하는 비호환 근거가 없었다.

### 동작 검증 시나리오 초안

B1 작은 설계/분할 불필요, B2 복잡한 설계/분할 필요, B3 중간 초안/최종 변경, B4 오류/승인 경계로 R1~R6을 연결했다.

## behavioral-validation (동작 검증)

### 진입 조건 확인

기계 검사와 사용자 승인 시나리오 묶음/모델/모의 승인 경계를 확인했다.

### 확정한 시나리오와 실행 조건

Codex/Astra-high, B1~B4 격리 사례와 회당 600초 상한을 승인받았다.
추가 B2-approval 최대 2회와 미결정 없는 approval-positive 1회도 별도 승인받았다.
600초는 운영 중단 상한이며 스킬 성능 기준이 아니다. [검증 기록](validation.md)에 입력/기대 결과/횟수와 실제 결과를 보존했다.

### 동작 검증을 수행한 사용 사례와 입력

B1 이름 정규화, B2 인증/CSV 내보내기, B3 길이 32->64 변경, B4 선행 연결/누락 링크/탭 오류다.
B2-approval은 분할 직전부터 새 논의 승인 전 대기까지, approval-positive는 미결정 없는 개정 논의 승인 후 설계 재개까지만 확인했다.

### 동작 검증에 사용한 CLI와 실행 환경

Codex CLI 0.160.0, 실제 turn_context의 gpt-6-astra/high.
배포 구조의 스킬 사본을 격리 프로젝트에서 명시 호출했으며 실제 설치 인식과 구분했다.

### 작업 대상 스킬의 인식 여부와 호출 결과

지정 사본과 참조 지침을 읽고 검사기를 호출했다. 사본 원문은 유지됐다.
실제 설치본 인식은 후속 호환성 검증에서 별도로 확인했다.

### 요건별 동작 검증 결과와 판정 근거

R1/R2는 B1/B2/B3, R3는 B3, R4는 자식의 표시 미확인 고지와 상위 Chrome 표시 대조,

최초 B2의 승인 경계 실패는 후속 사례 통과와 구분하여 [검증 기록](validation.md)에 보존했다.

### 이전 단계에서 넘긴 미확인 사항과 의미 판단 항목의 확인 결과 및 근거

필요/불필요 분할, 그룹 자료 정본과 이력, 재작도 시점 및 실제 표시를 확인했다.
Chrome 고정폭 16px/pre와 제한된 뷰포트에서 확인했으며 모든 뷰어의 표시를 보장하지 않는다.

### 동작 검증에서 발견한 실패와 재현 조건

B1 첫 사전 검사는 삭제된 무관한 쓰기 루트 때문에 실패하여 공통 실행기를 보완했다.
B2 최초 호출의 명령 오류/timeout과 재시험의 과거 승인 승계/사전 완료를 구분했다.
승인 지침은 이미 있었으나 실행과 상위 판정이 위반을 놓쳤고, 지침 연결 보완과 추가 시험으로 확인했다.

### 실행하지 못한 사용 사례와 결과를 판정하지 못한 동작

원래 B2의 D1-D5 제품 계약은 미결정으로 유지했다.
B2-approval에서 긍정 경로는 입력 모호함과 미결정 계약 때문에 미실행이며 사후 통과로 바꾸지 않는다.
사용자 합의한 별도 최소 사례로 남은 승인 후 동작을 확인했다. 현재 확정 범위의 필수 미실행은 없다.

### 완료 조건 확인

현재 필수 요건에 유효한 근거가 있고 승인 전 대기/명시 승인 후 진행과 이력 보존을 확인했다.
한 번의 성공을 모든 모델 실행의 재발 방지 보장으로 해석하지 않는다.

### 단계 이동 기록

behavioral-validation -> cross-validation. 보완 및 추가 시험 후 현재 소스에 대한 기존 검토 유효성을 재판단했다.

## cross-validation (교차 검증)

### 진입 조건 확인

동작 근거를 대조한 뒤 독립 검토를 수행했고, 발견된 실패는 이전 단계로 돌아가 보완했다.

### 교차 검증의 수행 여부와 판단 근거

읽기 전용 검사기의 판정 계약과 승인 경계를 독립 확인하기 위해 사용자 승인 Claude Opus/high 검토 1회를 수행했다.

### 교차 검증 대상과 검증에 포함한 파일 및 변경 내용

검토 당시 Camellia 지침/검사/테스트 9파일과 공통 실행기 3파일, 총 12파일을 대상으로 했다.
종료까지 해시가 동일했다. 버전 manifest는 기능 보완 이후 Git 준비에서 변경했다.

### 교차 검증의 판정 기준과 제외 범위

R1~R6, 검사 계약, 실행기의 경로 허용 경계를 대조했다.
실제 설치/전역 설정, 다른 공용 변경과 제품 구현은 제외했다.

### 교차 검증 요청, 검토 결과와 후속 판단 기록

검토자 Claude Opus 5.5/high, 요청자 및 후속 판정자 Codex.
검증 대상 design-artifacts-and-checks의 마지막 회차는 round-001이다.
원문은 변경하지 않았고 보존에 필요한 지적/처리/한계를 출처와 함께 [검증 기록](validation.md)에 통합했다.

### 교차 검증에서 제시된 각 지적에 대한 수용, 반박 또는 재검증 판단과 그 근거

M1의 미판정 종료 코드 변경 제안은 명시 계약에 따라 반박했다.
M2/M3와 L1~L6는 재현/소스 대조 후 수용했고 보완 및 필요한 재검증을 수행했다.
개별 근거와 기존 실행기 범위 밖 문제는 [검증 기록](validation.md)를 참조한다.

### 이전 단계에서 넘긴 사항의 확인 결과와 교차 검증에서 남은 미확인 사항

R5의 분할 판단은 유효하나 최초 B2의 논의 재승인 주장은 철회했다.
지침 연결과 축소/긍정 시험으로 확인했다. 실제 설치는 당시 후속 단계에 남겼고 이제 별도 통과했다.

### 수용한 지적에 따른 재검토와 수정 및 이후 재검증 결과

오류/문서/인코딩/도형/출력과 지침을 수정한 5파일의 차이를 직접 대조했다.
33개 회귀 검사와 승인 전후 동작을 재검증했다. 기존 검토의 변경 없는 영역은 유효하다.

### 교차 검증을 수행하지 않은 사실이 완료 판단에 미치는 영향

독립 검토는 수행했다. 보완은 기존 지적의 한정된 수정이며 재현과 추가 동작 근거로 닫을 수 있어 두 번째 Claude 검토는 불필요하다고 판단했다.
이는 Codex 후속 판정이며 Claude가 수정 후 소스를 다시 승인한 것은 아니다.

### 완료 조건 확인

지적별 수용/반박 근거와 보완/재검증을 확인하여 미해결 차단 사항이 없다.

### 단계 이동 기록

cross-validation -> compatibility-validation. 필요한 보완과 검토 유효성 판단을 완료했다.

## compatibility-validation (호환성 검증)

### 진입 조건 확인

교차 완료와 두 CLI의 실제 설치 조건을 확인했다. 사용자 승인 커밋/푸시 후 두 PR을 사용자가 병합했다.
Garden에서 설치를 갱신하고 Aster가 대상 3.0.0/20파일/활성화/의존성을 직접 대조했다.

### 지원 대상 CLI와 호환성 요건 및 검증 기준의 명세서 위치

요건 정의의 지원 대상 CLI와 배포/호환성 기준을 적용한다.
각 설치본의 변경 자료 접근, 정상/깨진 링크 입력 실행과 결과 해석, 파일 비변경이 필수다.

### 각 CLI의 실행 환경과 호환성 검증 결과

Codex 0.160.0/Astra-high와 Claude 2.1.283/Opus-high에서 각각 통과했다.
설치 커밋 f9fcc9ef831c679244921c8d7ae62c2d3192ea84, 버전 3.0.0이다.
각 CLI의 입력/모델/시간/권한 제한과 파일 대조 근거는 [검증 기록](validation.md)의 설치 호환성 절에 보존했다.

### 지원 CLI의 공용 구성과 동작 확인 결과

양쪽에서 설치 SKILL, 설계 지침/템플릿, 검사 계약/의존성에 접근했다.
설치 검사기가 valid는 PASS/0, broken은 missing.md의 link.target FAIL/1로 처리했다.
시험 전후 각 프로젝트 4파일과 각 설치본 20파일의 목록/해시가 동일하다.

### 명세서에서 허용한 CLI별 차이와 각 차이의 근거

CLI별 설치 경로와 명시 호출 방식, 실행 권한 설정만 다르다.
Codex는 제공된 설치 스킬을 읽고 Claude는 Skill 도구로 호출했다. 공용 파일과 검사 결과 계약은 같다.

### 명세서의 허용 범위를 벗어난 CLI별 동작 또는 구성의 차이와 그 영향

없음. Claude 보조 명령 일부의 권한 거절은 파일 내용이나 검사기 동작의 비호환이 아니다.
필수 경로/버전/해시/의존 조건은 상위의 직접 대조로 확인했다.

### 이전 단계에서 넘긴 미확인 사항과 의미 판단 항목의 확인 결과 및 근거

교차 단계에서 미확인이던 실제 설치본 인식/변경 자료 접근/검사 실행을 두 CLI에서 확인했다.
반영된 20파일은 검증 소스와 동일해 기존 검증을 다시 무효화하는 소스 변경은 없다.

### 지원 대상 CLI별로 실행하지 못한 호환성 검증 항목과 결과를 판정하지 못한 항목 및 그 이유

현재 필수 범위의 미실행/미판정은 없다.
Claude 최초 연결 재시도는 모델 응답 전에 중단했고 같은 입력을 네트워크 권한으로 재실행했다.
보조 shell 조회 실패와 상위 대조를 구분했다. 전체 개발 흐름은 앞선 유효 근거를 사용하고 반복하지 않았다.

### 완료 조건 확인

두 지원 CLI에서 필수 인식/접근/정상 및 오류 실행/파일 비변경을 확인해 완료했다.

### 단계 이동 기록

compatibility-validation -> completed. 남은 작업은 검증 자료 선별/이관과 시험 정리이며 소스 변경이나 추가 모델 시험은 필요하지 않다.

## completed (완료)

### 진입 조건 확인

교차/호환성 완료와 이전 보완의 재검증 근거를 확인했다.

### 생명 주기의 완료 여부에 대한 판단

생명 주기를 완료했다. R1~R6과 지원 CLI의 필수 검증을 충족했고 보존 대조 및 시험 정리를 마쳤다.

### 생명 주기의 완료 여부를 판단한 근거

각 단계의 조건과 R1~R6 근거를 재대조했다.
이 명세서와 validation.md로 결정/실패/보완/현재 결과를 보존한다.
보존 위치는 records/plugins/Camellia/code-development/design-artifacts-and-checks/다.
명세서 형식과 두 파일의 로컬 참조를 검사하고 원본 결정/지적/실패/보완/실제 결과를 대조했다.
이번 작업의 원시 사본/입력/로그/중간 자료 387파일과 중복 임시 스냅샷 1파일을 목록/해시 대조 후 정리했다.
다른 작업의 자료와 전역 세션/설치본, Git 작업 트리는 유지했다.
선별한 두 파일이 정본이며 필수 참조는 삭제한 자료나 개인 경로를 요구하지 않는다.
보존 파일의 실제 커밋/푸시는 별도 승인을 따르며 이관만으로 커밋됐다고 주장하지 않는다.

### 완료 여부를 판단하는 시점에 남아 있는 미확인 사항과 위험

제품 스킬의 필수 미확인 사항 없음. 모든 모델 실행/Markdown 뷰어/의존성 하위 버전과 OS 전반을 보장하지 않는다.
main 병합과 완료 기록의 Git 반영은 생명 주기 검증과 별도 운영 절차다.

### 완료 조건 확인

필수 검증, 보완 영향 확인, 기록 선별/이관과 시험 정리를 완료했다.
임시 추적 기록도 최종 검사 후 마지막으로 삭제했다.
완료 판단 시점의 두 보존 파일은 미커밋이었으며 이후 Git 반영 여부는 커밋/PR 이력으로 확인한다.
사용자가 완료 기록 두 파일은 integrate/common으로 제출하도록 지정했다.
해당 PR 병합 후 integrate/common -> main, integrate/camellia -> main 순서로 반영한다.

### 단계 이동 기록

completed를 유지한다. 실제 검증 결과와 정리/보존 대조를 근거로 완료를 판단했다.
