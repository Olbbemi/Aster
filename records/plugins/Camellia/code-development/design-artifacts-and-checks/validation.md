# 설계 산출물과 정형 검사 검증 기록

작성자는 Codex이며 2026-10-04 수행한 실제 파일/실행 결과를 대조한 보존 요약이다.
요건과 완료 판단의 정본은 [명세서](specification.md)다.
원시 로그나 로컬 설치 경로의 계속 존재를 전제로 하지 않는다.

- 기준: `ad5de10`, Camellia 2.0.1.
- Camellia 구현: `f7b6d8ec9be7b60d9a4c002eddbf81dd54daeee8`, 10파일.
- 통합/설치: `f9fcc9ef831c679244921c8d7ae62c2d3192ea84`, Camellia 3.0.0,
  [PR #29](https://github.com/Olbbemi/Aster/pull/29).
- 공통 실행기: `da290b6405b8bf3c99430299cea4d001803d7095`, 3파일.
- 공통 통합: `7fb5eadaf9d9d53146760f99ed200aac8a385e69`,
  [PR #30](https://github.com/Olbbemi/Aster/pull/30).

두 PR의 승인된 파일만 커밋/푸시했고 사용자가 통합 브랜치에 병합했다.
통합된 플러그인 전체와 공통 실행기 3파일은 각각 검증한 작업 커밋과 차이가 없었다.
다른 공용 미커밋 변경과 전역 구성은 변경하지 않았다.
이 기록은 main 병합을 뜻하지 않는다.
완료 기록 두 파일의 추가 반영 경로는 사용자가 integrate/common으로 지정했다.
이후 common과 camellia를 순서대로 main에 반영하며, 제품 소스의 기존 PR 경로는 유지한다.

필수 검사 실행에 Python 3.10 이상 및 새로운 패키지 준비가 요구되므로
기존 사용 환경의 대응 변경이 필요한 major로 판단하여 3.0.0을 적용했다.
스테이징 전 승인 대상, 스테이징 내용 해시, 버전 사전 검사와 실제 pre-push를 대조했다.

환경은 Linux, Python 3.12.3, PyYAML 6.0.1, markdown-it-py 3.0.0이다.

공통 실행기 테스트는 공통 구현 커밋에서 실행한다.

python3 -I -B -m unittest discover -s tools/tests/scenario -p test_scenario_runner.py -v
python3 -B tools/scripts/validation/check_structure.py plugins/Camellia/skills/code-development --json
python3 -B tools/scripts/validation/check_references.py plugins/Camellia/skills/code-development --json
git diff --check

과거 설계는 hold -> superseded만 바뀌었다. 정형 검사 24항목 PASS도 확인했다.

### 실패, 재시험과 판정 정정

최초 B1은 모델 실행 전 사전 검사에서 실패했다.
설정에 남은 삭제된 무관한 루트가 원인이었으며 공통 실행기의 해당 처리만 보완했다.
FileNotFoundError인 루트만 제외하고 실제 case는 유효한 명시적 루트 안에 있어야 한다.
PermissionError/NotADirectoryError 등의 다른 오류 처리로 범위를 확대하지 않았다.

B2 최초 모델 호출은 문서 수정 명령 오류와 600초 시간 초과로 미판정이었다.
명령 안내를 보완한 새 사례에서 분할/그룹 자료를 확인했다.
그러나 교차 검토로 발견한 새 논의의 과거 승인 승계는 명시적 실패이며 최초 전체 통과 판정을 철회했다.
기존 지침에 승인 규칙은 있었으나 모델의 실행과 상위의 판정이 이를 놓쳤다.
분할 단계에서 승인 정본으로 직접 연결한 뒤 필요한 경계만 재시험했다.

B2-approval 첫 입력은 후속 report 생성 금지가 현재 논의 개정까지 금지하는지 모호했다.
두 번째 호출로 금지 범위를 후속 CSV 작업으로 설명했다.
또한 D1-D2가 현재 논의의 미결정 계약이므로 완료 승인을 전달할 선행 조건이 부족했다.
이 시험에서 승인 후 정상 진행은 미실행으로 보존한다.
사용자 합의로 미결정 없는 approval-positive를 별도 실행하여 현재 필수 범위의 긍정 경로를 확인했다.
원래 B2의 D1-D5 제품 계약을 해결하거나 기존 실패를 사후 통과로 바꾸지 않았다.

최초 B1~B4 실행기는 9회, 실제 모델 호출은 8회/5세션이었다.
B1 2회, B2 3회, B3 3회, B4 1회로 승인 상한을 유지했다.
이후 별도 승인 B2-approval 2회는 225.4초/221.1초, approval-positive 1회는 216.927초로 끝났다.
B3 마지막 입력/응답은 일본어였으나 승인한 의미/범위/판정 기준을 대조했다.
이 성공은 모든 모델 실행에서 같은 위반이 재발하지 않는다는 보장이 아니다.

### 실제 도식 표시

자식은 실제 표시를 확인했다고 주장하지 않고 미확인을 고지했다.
상위가 Markdown을 HTML로 렌더링하여 Google Chrome 151.0.7922.173에서 캡처를 직접 확인했다.
고정폭 16px, white-space:pre, 900px 뷰포트에서 B2 두 그룹과 B3/B4의 연결선/분기/줄바꿈이 정렬됐다.
B3는 390px 폭에서도 도식 잘림이나 줄바꿈이 없었다.
B2 분할 후 auth 도식은 앞서 표시 확인한 코드 블록과 동일해 기존 근거를 재사용했다.
최초 Chrome 실행은 샌드박스 소켓 제한으로 실패했고 권한을 받은 로컬 표시로 확인했다.
이 확인은 모든 사용자 뷰어/폰트의 표시 보장이나 설계 승인 대체가 아니다.

## 독립 교차 검토와 후속 판정

검토자는 Claude, 요청자와 후속 판정자는 Codex다.
대상 `design-artifacts-and-checks`의 마지막 회차는 `round-001`이다.
사용자 승인으로 Claude Opus 5.5/high, Read/Glob/Grep만 사용한 독립 검토 1회를 수행했다.
실제 모델은 `claude-opus-5-5`, high는 CLI 인수로 확인했다.
484.335초/종료 0이며 검토 전후 대상 12파일 해시가 동일했다.

Claude 원문의 전체 판정은 차단 결함 없이 조건부 수용이며 M1~M3 판단/보완을 요구했다.
검토자는 해시 계산, 실제 테스트 실행, 캡처와 모든 과거 report/의존성 버전을 직접 확인하지 못했다.
상위는 해시/실행/표시 자료를 직접 대조했으며 검토자의 독립 확인으로 표현하지 않는다.
아래는 원문을 수정한 것이 아닌 출처를 밝힌 지적별 보존 요약이다.

ASCII stdout 예외, is_dir PermissionError 미처리와 기하 화살촉 누락을 재현했다.
보완 후 33개 회귀 검사로 통과했다. 잘못된 필수 report 프론트매터는 형식 위반으로 유지한다.

기존 실행기의 symlink 순환 RuntimeError 종료 분류와 다른 무관한 루트 오류의 차단은
이번 missing-root 수정으로 생긴 문제가 아니며 실행을 막지 않아 범위 밖으로 두었다.
문서의 기존 확인 버전 0.154.0과 이번 실제 0.160.0 실행을 구분했다.

교차 후 5파일 수정은 기존 지적의 한정된 보완이다.
구조 설계/구현/기계 검사 및 승인 전후 동작을 재검증했고 변경 없는 영역의 기존 검토는 유효하다.
추가 Claude 소스 검토는 필요하지 않다고 Codex가 판단했다.
Claude가 수정 후 소스를 재검토하거나 승인한 것으로 표현하지 않는다.

## 실제 설치 호환성

사용자가 설치 확인 후 진행을 승인한 두 CLI의 최소 사례를 실행했다.
Garden에서 지원 CLI 명령으로 3.0.0을 갱신한 뒤 Aster가 실제 상태를 읽기 전용으로 확인했다.
각 CLI의 `plugins/cache/aster/camellia/3.0.0/` 아래 설치본 20파일은 통합 커밋과 모두 일치했다.
Codex/Claude 모두 설치/활성화됐고 두 marketplace HEAD도 대상 통합 커밋과 같았다.
시스템 Python 3.12.3, PyYAML 6.0.1, markdown-it-py 3.0.0과 실제 import가 확인됐다.

각 격리 프로젝트는 README, freight-manifest와 valid/broken의 discussion-report-001로 구성했다.
manifest는 두 주제와 stages discussion/design을 지정한다.
두 report는 in_progress/base_on null과 공통 H2 네 영역을 갖고 승인을 체크하지 않는다.
broken의 14행에 `[없음](missing.md)` 링크 하나만 추가하고 해당 파일은 만들지 않는다.
설치된 스킬의 자료를 읽고 설치 경로의 검사기를 다음 형태로 실행했다.

```bash
/usr/bin/python3 -B <설치된-스킬>/scripts/check_reports.py <valid-절대경로> --json
/usr/bin/python3 -B <설치된-스킬>/scripts/check_reports.py <broken-절대경로> --json
```

| CLI | 실제 모델/호출 | 관찰 |
| --- | --- | --- |
| Codex 0.160.0 | gpt-6-astra/high, 공통 실행기 새 세션 1회, 약 76.5초 | 설치 스킬과 지정된 다섯 자료를 읽음. valid 7 PASS/0, broken 7 PASS + link.target FAIL/1. 문서 연결 오류와 설치/승인 판정을 구분함 |
| Claude 2.1.283 | claude-opus-5-5, CLI --effort high, 정상 모델 호출 1회, 51.620초 | Skill 도구로 camellia:code-development를 호출하고 설치 경로/manifest/다섯 자료를 읽음. valid와 broken이 Codex와 같은 결과를 반환함 |

지정 다섯 자료는 SKILL.md, references/stages/design.md,
assets/stage_reports/design-template.md, references/report-checks.md, scripts/requirements.txt다.
실제 코드 실행 도구 로그에서 설치 경로의 check_reports.py와 종료 코드 및 JSON을 확인했다.
상위가 실행 전후 각 프로젝트 4파일과 각 설치본 20파일의 목록/해시 일치를 직접 확인했다.
설정/의존성 설치, report 수정과 제품 설계/구현은 수행하지 않았다.

Claude의 최초 프로세스는 제한 네트워크에서 API 연결 재시도만 반복했다.
모델 응답 전에 중단하여 종료 130으로 기록하고 네트워크 권한을 받아 같은 입력으로 재실행했다.
600초 상한 안에서 성공했으며 연결 실패를 스킬 결함이나 통과로 바꾸지 않는다.

Claude는 허용된 검사 명령 외의 경로/버전/해시 보조 shell 조회 및 복합 명령에서 일부 권한 거절을 받았다.
Read/Glob/Skill과 허용된 단독 검사 명령으로 필수 자료 접근/실행을 완료했다.
설치 경로/대상 커밋/의존 버전과 비변경은 상위의 실제 대조가 추가 근거다.
이 제한을 모든 도구가 무승인 실행됐다는 주장으로 바꾸지 않는다.
사례별 필수 요건은 모두 충족했으므로 호환성 통과로 판단했다.

설치 검증에서 전체 B1~B4를 반복하지 않았고 자동 스킬 선택이나 모든 제품 개발 흐름을 확인했다고 주장하지 않는다.
실제 설치본의 명시 호출, 이번 변경 자료와 검사 실행이라는 확정 범위로 한정한다.

## 보존과 정리

명세서의 필수 단계 항목과 R1~R6, 중요한 설계 판단 및 실패/보완 근거를 이 두 파일에 통합한다.
다른 작성자의 검토 원문을 편집하지 않고 지적별 의미/처리/미확인 범위를 위에 보존했다.
원시 대화, 시험 사본, 입력/해시 전체, 캡처와 중간 초안은 보존 내용 대조 후 정리했다.
다른 작업의 자료, 전역 세션 기록과 설치 캐시 및 Git 작업 트리는 이 정리의 대상이 아니다.
최종 이관/정리 결과와 생명 주기 완료 판단은 명세서에 기록한다.
