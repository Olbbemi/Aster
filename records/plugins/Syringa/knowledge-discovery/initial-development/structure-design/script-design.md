# 문서 구조와 기능별 스크립트 설계

## 범위

0.1.1의 동작을 유지하면서 문서와 실행 기능을 나누는 설계와 구현 근거다.
아래 문서와 Python 구성을 구현하여 1.0.0으로 배포했다.
기존 discovery.py는 제거했고 개발 전용 테스트의 import, 직접 호출과 mock 대상을 갱신했다.
요건과 실제 검증 결과는 명세서 및 연결된 검증 기록에서 관리한다.

[명세서](../specification.md)는 문제, 요건과 단계 상태의 정본이다.
[실행 계약](../../../../../../plugins/Syringa/skills/knowledge-discovery/references/execution.md)은
명령, 스키마와 외부 동작의 정본이다.
여기서는 외부 계약을 반복하지 않고 구현 방식과 선택 이유를 남긴다.

## 책임 경계

| 구성 | 책임 | 보장하지 않는 내용 |
| --- | --- | --- |
| 에이전트 | 자료 해석, 주제와 개념 결정, 자연어 선택 해석, 의미 충실성 | 파일 충돌과 경로 안전성을 추정으로 대신하지 않음 |
| 입력 및 범위 검사 | 실제 경로, Git 루트, 명시 파일 집합과 소스 변경 확인 | 대화에서 사용자가 직접 답했는지 독립 증명 |
| 상태 관리 | 단계 순서, 후보 목록 식별값, 승인 집합과 주제별 저장 결과 | 하네스 밖의 임의 파일 접근을 차단하는 보안 샌드박스 |
| 렌더러 | 승인된 개념별 제목과 지원 필드만 출력 | 자연어 본문에 숨은 출처와 기술 오류의 완전 탐지 |
| 저장기 | 새 파일, 경로 검증, 충돌 보존, 부분 저장 결과 | 외부 프로세스가 저장 뒤 내용을 바꾸지 않는다는 보장 |

기존 `scripts/discovery.py`의 명령별 처리를 아래 직접 호출 파일로 나눈다.
각 파일에 해당 기능의 실행 본체와 `main(argv=None)`을 두고 직접 실행할 수 있게 한다.
기존 파일에 모든 로직을 남긴 채 호출용 파일만 추가하지 않는다.
공통 명령 분기기, 호환용 discovery.py와 범용 플러그인 로더를 남기지 않는다.
빈 패키지나 사용하지 않는 디렉토리는 만들지 않는다.
명령 인자는 argparse, JSON은 표준 라이브러리로 처리하고 Git은 shell=False 인자 배열로 호출한다.
입력과 출력 경로를 shell 문자열로 합성하지 않는다.

## 직접 호출 스크립트

아래 파일은 모두 scripts/ 바로 아래에 둔다.
인자와 응답의 정본은 실행 계약이며 여기서는 기존 코드의 책임 이동을 정의한다.
기존 함수명은 분리 누락을 대조하기 위한 기준이지 내부 API 고정 요구가 아니다.

| 파일 | 기존 기능의 이동 범위 | 호출 시점과 완료 결과 |
| --- | --- | --- |
| inspect_inputs.py | inspect 및 해당 인자 파싱 | 준비 단계의 범위 확인 전. 경로와 구조만 반환 |
| start_run.py | start 및 시작 입력 검증 | 준비 단계의 범위/모델 확인 후. 고정한 파일 집합과 새 run 반환 |
| read_source.py | read_file 및 잠금 안의 읽기 호출 | 후보 추출 또는 승인 후 상세 분석. 범위/해시를 확인한 본문 반환 |
| propose_candidates.py | propose 및 입력 읽기/잠금/상태 저장 연결 | 후보 선별 후 제시 전. 목록과 digest 등록 |
| approve_candidates.py | approve 및 입력 읽기/잠금/상태 저장 연결 | 명확한 실제 선택 답변 확인 후. 승인 집합 고정 |
| save_topic.py | save_topic, render, prose, visible_angles, FIELDS 및 저장 실패 기록 연결 | 승인된 한 주제의 원자료 대조 후. 렌더링/저장 또는 실패 기록 |
| run_status.py | status 및 잠금/복구 결과의 상태 저장 연결 | 종료/실패/중단 보고 또는 재개 전. 완료/실패/미처리와 복구 상태 반환 |

렌더링은 save_topic.py만 사용하므로 별도 모듈로 더 나누지 않는다.
run_command의 명령별 잠금과 save_state 호출 및 예외 후 기록은 각 파일의 실행 흐름으로 옮긴다.
특히 저장 실패를 failed로 기록하는 처리와 status의 복구 결과 저장을 빠뜨리지 않는다.
독립 호출은 프로세스별 호출을 뜻하며 필요한 기능들이 같은 명시적 run을 공유한다.
스킬의 순서와 승인 조건을 생략해도 된다는 의미는 아니다.

## 공통 보조 모듈과 의존 방향

반복 사용되는 검증, 파일 접근과 상태/복구 구현만 공유한다.
보조 모듈에는 사용자용 CLI나 명령 이름에 따른 업무 분기를 두지 않는다.

| 파일 | 기존 기능 및 공통 책임 | 의존할 보조 모듈 |
| --- | --- | --- |
| runtime_common.py | DiscoveryError, fail, text_value, shape, unique_strings, identifier, ID, digest_bytes, canonical, digest, json_pairs, Parser와 공통 JSON 응답/예외 처리 | 없음 |
| source_access.py | absolute, no_links, directory_fd, regular_bytes, decode_source, load_json, output_root, targets, unchanged | runtime_common.py |
| run_state.py | save_state, locked_run, completed_phase | runtime_common.py, source_access.py |
| storage_recovery.py | output_folder, reconcile | runtime_common.py, source_access.py, run_state.py |

직접 호출 파일은 위 보조 모듈을 사용하되 서로의 진입점을 호출하거나 import하지 않는다.
보조 모듈은 직접 호출 파일에 의존하지 않는다.
모든 모듈은 같은 scripts/에 있으므로 직접 파일 실행에서 형제 모듈을 import한다.
저장소 루트, records, tools, 특정 CLI 캐시 위치와 추가 Python 패키지에 의존하지 않는다.

공통 응답 처리는 호출자가 넘긴 단일 처리 함수의 응답/예외를 포장하는 역할만 한다.
명령 목록, 하위 명령 파서와 명령별 업무 처리를 다시 한곳에 모으지 않는다.
각 진입점은 자신의 필수 인자를 정의하고 파싱 성공 뒤 논리 command 식별자를 반환한다.
인자 파싱 실패의 command는 기존과 같이 null이며 입력 오류 코드와 JSON 형식을 유지한다.

## 처리 순서와 저장 상태

1. `inspect`는 필수 입력과 루트를 확인하고 파일 구조만 반환한다.
2. 범위 확인 후 `start`는 사용자 전용 임시 상태를 만든다.
   확인된 실제 파일 목록, 파일별 해시, 출력 루트와 모델 승인 기록을 고정한다.
3. `read`는 고정한 범위의 자료를 소스 해시 확인 후 반환한다.
4. `propose`는 후보 목록을 저장하고 정규화된 JSON으로 목록 digest를 계산한다.
5. `approve`는 목록 digest와 ID 집합을 검사하여 승인 범위를 고정한다.
6. 승인 범위의 자료를 `read`로 다시 확인하고 상세 내용을 작성한다.
7. `save-topic`은 승인 집합과 상세 입력을 대조하고 렌더링을 완료한 뒤 저장한다.
8. `status`는 완료, 실패, 미처리와 복구 필요 상태를 구분한다.

내부 상태에는 schema_version, 실행 ID, 생성 시각, 단계와 주제별 처리 기록을 둔다.
정확한 외부 스키마는 실행 계약에만 정의한다.
생성된 run에 접근하는 읽기, 후보/승인, 저장과 상태 조회는 실행별 잠금을 사용한다.
동시 호출 시 자동으로 다른 실행 상태를 합치거나 잠금을 무시하지 않는다.
Linux의 프로세스 종료 시 해제되는 파일 잠금을 사용한다.
지원 환경은 Python 3.10 이상과 Git이 있는 Linux이며 Python 표준 라이브러리를 사용한다.

자료가 변경되면 기존 snapshot을 현재 파일과 섞지 않는다.
`read`와 저장 전 검사에서 변경을 발견하면 `SOURCE_CHANGED`로 멈춘다.
사용자에게 범위와 후보 재확인이 필요함을 알리고 새 실행에서 처리한다.
기존 파일을 재귀 탐색하여 이전 실행의 상태를 자동 추정하지 않는다.

## 파일 저장 알고리즘

먼저 모든 입력과 승인 범위를 검사하고 전체 주제 문서를 메모리에서 완성한다.
파일 생성 시각을 정하고 허용된 출력 경로만 생성한다.
기존 `knowledge-candidate` 또는 날짜 경로가 링크이거나 디렉토리가 아니면 실패한다.
각 경로 성분을 O_NOFOLLOW로 열고 디렉토리 핸들을 기준으로 쓰므로 검사와 쓰기 사이의 링크 교체도 방어한다.

최종 디렉토리 안에 배타적으로 임시 파일을 만들고 전체 본문을 쓴다.
파일을 flush/fsync한 뒤 기존 대상을 교체하지 않는 원자적 공개를 수행한다.
동일 파일시스템의 hard-link 공개를 사용하며 기존 이름이 있으면 다음 접미사로 시도한다.
실제 환경에서 지원되지 않으면 명시적으로 실패하며 덮어쓰기 방식으로 우회하지 않는다.
파일명 충돌은 최종 공개 단계의 배타성으로 판정하여 다음 구분자로 재시도한다.
최종 대상에는 무조건 덮어쓰는 os.replace를 사용하지 않는다.

공개 전에 주제 ID, 본문 해시와 예정 경로의 저장 의도를 상태에 기록한다.
공개 후 완료 receipt를 기록한다.
상태 파일 자체의 갱신은 같은 실행 잠금 안에서 원자적으로 처리한다.
임시 파일과 내부 상태에는 원본 경로가 있을 수 있지만 최종 문서에는 넣지 않는다.

중단 후 의도만 남으면 예정 경로와 본문 해시를 대조한다.
일치하면 완료로 복구하고, 경로가 없으면 재시도 가능한 미저장 상태로 남긴다.
파일은 있으나 내용이 다르거나 판정할 수 없으면 `RECOVERY_REQUIRED`로 중단한다.
상태 갱신 실패를 정상 완료 응답으로 감추지 않는다.
실패 정리는 이번 호출이 만든 임시 파일만 대상으로 하며 다른 실행의 파일은 건드리지 않는다.

## 구현 후 검증 인계

기존 29개 검사는 0.1.1의 근거이며 분리 후의 통과 근거가 아니다.
입력, Git 루트, 범위, 승인 집합, 렌더링과 저장의 경계 조건은
[실행기 검사 안내](../../../../../../tools/references/knowledge-discovery-tests.md)에 따라 확인한다.
실제 AI 검증의 입력과 기대 결과는 [검증 조건과 결과](../behavioral-validation/plan.md)에서 관리한다.
검사 통과로 의미 판단이나 설치 성공을 대체하지 않는다.

## 구현 대조 결과

기존 본체 35개의 AST 동일성과 갱신한 30개 계약 검사 및 기존 승인 상태 재개를 확인했다.
이 대조는 분리 구현 시점의 근거이며 지속 검사에 고정하지 않는다.
기대 목록의 배포 파일 21개/등록 대조와 실제 D5/D6 결과는 명세서와 검증 기록에서 관리한다.

## 기능별 푸시 전 검사

추가 요구사항 R11에 따라 기존 실행 계약 검사 30개를 기능별 파일 5개로 분리했다.
스킬 형식, 로컬 참조와 Python 구문의 독립 검사 파일을 추가하고 총 6개 파일을 등록했다.
스킬명 디렉토리 아래 추가 디렉토리와 통합 명령 진입점은 두지 않는다.
기능별 파일, 판정 기준과 수동 호출의 정본은 [푸시 전 검사 안내](../../../../../../tools/references/knowledge-discovery-tests.md)다.

repository_support.py는 대상 커밋의 Git 객체와 명시 작업 트리 및 Markdown 구조를 읽는다.
check_support.py는 실행용 사본과 독립 자료, 제한 시간 및 JSON/종료 코드 출력을 공유한다.
스킬의 런타임을 시험용 사본에서 호출하며 명세서나 실제 지식 자료를 검사 대상으로 읽지 않는다.
동일 커밋을 검사할 때 미커밋 변경과 미추적 파일을 섞지 않으며 검사 대상의 Git 상태를 변경하지 않는다.

33개 항목과 커밋 격리, 등록 파일 호출 및 실패 차단을 확인했다.
특정 변경의 AST 동일성이나 과거 버전 상태 재개는 이번 구현 확인 근거로만 유지하고 지속 검사에는 넣지 않았다.
