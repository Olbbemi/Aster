# 스킬 검증 규격

이 문서는 Aster에서 개발하는 스킬의 구조, 내용, 동작과 대상 하네스 호환성을 검증하는 기준을 정의한다.
구조 기준은 `skill-layout.md`, 내용 작성 기준은 `skill-content.md`에서 정의한다.
이 문서는 그 규칙을 반복하지 않고 검증 방법과 판정 책임을 연결한다.

## 검증 원칙

- 대상 스킬 명세서의 작업 유형과 구조 설계를 기준으로 생성하거나 유지할 대상과 제거할 대상을 구분한다.
  제거할 대상은 제거 여부와 남아 있으면 안 되는 참조 및 등록의 정리 여부를 검증한다.
- `scripts/`, `assets/`와 특정 하네스에서만 사용하는 파일은 대상 스킬에 있을 때만 해당 검증을 적용한다. 플러그인 배포 검증은 플러그인 배포용 스킬에만 적용한다.
- 동작 검증과 호환성 검증 모두 신규 스킬은 정의한 요건을, 기존 스킬의 개선, 기능 추가와 수정은
  변경 내용 및 영향을 받는 기존 동작과 연결 자료를 기준으로 범위를 정한다.
- 각 사례를 해당 요건 또는 변경 영향에 연결하고, 작업의 위험을 고려하여 종류와 수를 정한다.
  영향이 없는 기존 사례를 관례적으로 반복하지 않는다.
  공용 자료 변경은 이를 사용하는 흐름에 미치는 영향도 확인한다.

## 검증 구분

아래 구분은 검증 대상과 판정 방식에 따른 분류이며, 생명 주기의 단계 목록이 아니다.
수행 순서와 단계별 절차는 [생명 주기 운영 규칙](../../.agents/skills/skill-lifecycle/references/lifecycle.md)과 해당 단계 문서를 따른다.
내용 검토가 필요한 항목은 확인할 검증 단계를 정하고, 해당 단계의 검토 또는 검증 결과에 포함한다.

| 구분 | 확인 대상 | 판정 방식 |
| --- | --- | --- |
| 구조 검증 | 필수 파일, 허용 이름, 참조 경로, 불필요한 항목 | 가능한 항목은 기계 검사 |
| 내용 검토 | 적용 범위, 지침의 명확성, 책임 분리, 중복과 누락 | 사람 또는 AI 에이전트 판단 |
| 동작 검증 | 선택, 실행 흐름, 결과, 실패 및 중단 동작 | 독립된 실제 사용 시나리오 |
| 호환성 검증 | 대상 하네스의 발견, 호출, 파일 접근과 전용 기능 | 하네스별 실제 실행 |
| 배포 검증 | 플러그인 포함 파일, 설치 후 경로와 실행 | 설치된 배포물 기준 실제 실행 |

## 구조 검증

생성하거나 유지할 스킬에는 다음 항목을 적용한다.

- 스킬 디렉토리에 `SKILL.md`가 존재한다.
- YAML frontmatter를 파싱할 수 있고 필수 필드가 존재한다.
- `name`과 디렉토리 이름이 일치하고 대상 하네스의 이름 제한을 충족한다.
- `description`이 비어 있지 않고 대상 하네스의 형식 제한을 충족한다.
- 문서가 읽거나 실행하도록 참조하는 기존 파일과 디렉토리는 명시된 경로 기준에서 실제로 존재한다. 작업 중 생성할 경로는 생성 시점과 생성 조건이 지침에 정의되어 있다.
- 자료가 없는 선택 디렉토리와 자리 표시 파일이 남아 있지 않다.

선택 항목이 있으면 다음 검증을 추가한다.

- `references/`: 필요한 작업 조건에서 참조 경로를 찾을 수 있고, 문서가 가리키는 파일과 링크가 유효하다.
- `scripts/`: 구문 검사를 통과하고, 지침에서 실행하도록 지정한 스크립트는 대표 입력에서 지침에 명시한 호출 방법과 실행 조건으로 실행했을 때 정상 처리와 예상 가능한 오류 상황을 구분해 결과를 낸다.
- `assets/`: 필요한 자료가 존재하고 지침에 명시한 용도로 사용할 수 있다.
- 공용 자료: 이를 참조하는 모든 스킬이 `standards/repository-layout.md`에서 스킬의 배치 위치별로 정의한 공용 자료 경로를 사용하며, 자료가 없거나 경로가 달라졌을 때 실패를 식별할 수 있다.

### 작업용 lifecycle 명세서 형식

표준 lifecycle 명세서는 [명세서 형식](../../.agents/skills/skill-lifecycle/references/specification.md)을
기준으로 프론트매터, 단계 구조와 기록 제목을 검사할 수 있다.
단계 문서와 템플릿의 제목 대응도 해당 규격을 기준으로 확인한다.

적용 시점과 자체 수정용 축약 기록의 구분은 같은 문서의
[최소 형식 검사](../../.agents/skills/skill-lifecycle/references/specification.md#최소-형식-검사)를 따른다.
형식 검사로 본문의 의미, 실제 승인이나 단계/완료 판단을 대신하지 않는다.

lifecycle 자체의 단계 지침을 수정하면
[단계 정의 공통 항목](../../.agents/skills/skill-lifecycle/references/lifecycle.md#단계-정의-공통-항목)에 따라
단계 목록과 파일/문서 제목의 대응 및 공통 구역과 운영 항목의 구조를 검사한다.
단계별 기록 제목과 템플릿의 대응은 위 검사로 확인하며, 단계 진행 판단은 의미 검토로 구분한다.

### 로컬 Markdown 절 링크의 기계 판정

로컬 Markdown의 절 링크는 `aster-markdown-headings-v1` 정책으로 판정한다.
[GitHub의 절 링크와 사용자 지정 앵커 안내](https://docs.github.com/en/get-started/writing-on-github/getting-started-with-writing-and-formatting-on-github/basic-writing-and-formatting-syntax#section-links)를
근거로 다음 범위를 적용한다. 임의 렌더러의 전체 동작이나 설치 환경 호환성을 보증하지 않는다.

- Markdown 파서가 식별한 ATX/Setext 제목에서 텍스트, 인라인 코드와 이미지 대체 텍스트를
  사용한다. 강조/링크 표식과 HTML 태그는 제외하고 제목의 줄바꿈은 공백으로 처리한다.
- 앞뒤 공백을 제거하고 소문자로 바꾼다. Unicode 문자/결합 문자/숫자와 `-`, `_`를 유지하고,
  ASCII 공백은 `-`로 바꾸며 그 밖의 문자는 제거한다. 연속 공백을 임의로 합치지 않는다.
- 문서 순서대로 자동 앵커를 배정한다. 이미 사용한 이름이면 `-1`, `-2` 등을 붙여 아직
  사용하지 않은 이름을 찾는다. 사용자 지정 앵커는 자동 번호 계산에 개입하지 않는다.
- 파서가 식별한 HTML의 `id`와 `<a name="...">`도 명시 앵커로 인정한다.
  코드 예시, 주석과 YAML 프론트매터의 제목/앵커 표기는 수집하지 않는다.
- `#절`은 같은 문서, `파일.md#절`은 해당 Markdown 문서의 앵커와 대조한다.
  fragment의 UTF-8 URL 인코딩은 한 번 해제하며 대소문자나 Unicode 정규형을 바꾸지 않는다.
  잘못된 percent escape/UTF-8/NUL은 실패다. 빈 fragment는 문서 자체를 가리킨다.
- 대상 파일과 절이 존재하면 통과, 대상 파일이나 절이 없으면 실패다. 읽기/파싱 오류는
  실행 오류로 구분한다. 다른 Markdown 문서는 절 확인을 위해 읽을 수 있지만 그 문서의
  링크까지 따라가며 검사 범위를 재귀 확장하지 않는다.
- 외부 URL/URI는 로컬 검사에서 제외한다. 존재하는 비Markdown 파일이나 디렉토리의
  비어 있지 않은 fragment는 미판정으로 표시한다. 쿼리의 동적 의미는 검사하지 않는다.

### 완료 보고서의 로컬 참조

완료 기록을 Git 관리 경로로 이관한 뒤에는 현재 보존 묶음의 Markdown 링크와 이미지 참조를 검사한다.
파일과 절의 존재는 위 절 링크 판정 기준을 재사용하고, 다음 보존 조건을 추가로 확인한다.
검사 대상 Markdown 자체에도 같은 저장소 경계와 Git 제외 기준을 적용한다.

- 로컬 참조는 문서 위치를 기준으로 한 상대 경로를 사용한다.
  로컬 절대 경로와 `file:` URI는 파일이 존재해도 실패다.
- 참조는 같은 Git 저장소 안에서 해석되어야 한다.
  저장소 밖의 자료, Git 내부 메타데이터와 Git에서 제외된 미추적 자료는 실패다.
- 심볼릭 링크를 거치면 연결 파일과 실제 대상의 경계 및 보존 상태를 함께 확인한다.
  절대 경로를 사용하는 연결이나 저장소 밖으로 나가는 연결은 실패다.
- 디렉토리 참조에는 Git으로 보존할 수 있는 파일이 있어야 한다.
  빈 디렉토리나 제외된 파일만 있는 디렉토리는 보존 가능한 대상으로 판정하지 않는다.
- 저장소 안에 존재하고 Git 제외 대상이 아닌 새 파일은 경로 검사를 통과할 수 있다.
  미추적 파일은 커밋 필요 목록에 별도로 표시한다.
  경로 검사 통과는 실제 커밋이나 다른 체크아웃에서의 접근을 확인했다는 뜻이 아니다.
- Git 조회나 파일 읽기에 실패하면 실행 오류이며, 미확인 상태를 통과로 처리하지 않는다.

현재 보존 묶음의 Markdown을 검사하며 링크를 따라 저장소 전체로 검사 범위를 확장하지 않는다.
외부 URL과 `file:` 이외 URI, 일반 문장이나 코드/주석에 적힌 과거 경로는 자동 판정하지 않는다.

원문 경로 표기의 필요성, 참조가 필수 근거인지와 보고서의 내용 완결성은 별도로 검토한다.
검사기는 파일, 인덱스나 Git 상태를 변경하지 않으며 커밋 대상 확인과 승인 절차를 대신하지 않는다.

### 시나리오 기록의 대응

시나리오의 요건/계획/결과 표는 [시나리오 기록 대조 형식](scenario-records.md)을 따른다.
기록의 형식과 ID 대응 검사, 실제 시험 판정 및 단계 완료 판단을 구분한다.

### ASCII 도식의 기계 판정

명시적으로 지정한 Markdown에서 `text ascii-flow` fenced code block만 검사한다.
일반 코드와 표시 없는 도식을 추정하거나 변환하지 않는다.
시작 구분자에 대응하는 닫는 구분자가 있어야 한다.

- 탭과 Unicode 범주 `C`의 제어/형식/대리/미지정/개인용 문자를 허용하지 않는다.
  줄바꿈은 LF/CRLF를 허용하며, 그 밖의 공백은 ASCII 공백만 사용한다.
- 연결 기호는 ASCII를 사용한다.
  Unicode 박스/블록/기하 도형(U+2500-25FF), 이름에 `ARROW`가 있는 비ASCII 문자,
  en/em dash(U+2013/U+2014)와 전각 `+ - | < >`는 실패다.
- 한글 등 설명 문자는 허용하며 고정 줄 폭 제한은 두지 않는다.

검사한 도식 수를 표시하며 0개를 실제 도식 검증 완료로 표현하지 않는다.
문자 검사는 연결선의 정렬, 흐름의 의미나 글꼴/뷰어에서의 표시를 판정하지 않는다.
실제 표시 확인은 해당 설계 절차를 따른다.

## 내용 검토

다음 항목은 단순 문자열 검사로 합격 처리하지 않는다.

- 같은 규칙이나 사실이 여러 파일에서 독립적으로 정의되어 있지 않다.
- 파일과 자료가 역할에 맞게 배치되어 있으며, `scripts/`의 작업 수행용 코드와 `assets/`의 결과물용 코드가 사용 목적에 따라 구분되어 있다.
- `description`만 보고 적용해야 할 요청과 적용하지 않아야 할 요청을 구분할 수 있다.
- 본문이 일반적인 설명을 반복하지 않고 해당 작업에 필요한 지식, 판단 기준과 제약을 제공한다.
- 고정 순서와 절대 규칙에는 이를 요구하는 실제 실패 위험이나 외부 제약이 있다.
- 사용자 요청과 승인 범위를 스킬이 임의로 넓히지 않는다.
- 명세서에 정의된 입력, 기대 결과, 실패 및 중단 시 대응과 사용자 확인 및 승인 조건이 `SKILL.md` 또는 필요한 상황에 연결되는 지침에 반영되어 있다.
- 상대 경로의 기준과 스크립트의 실행 또는 참조 방법을 지침만으로 판단할 수 있다.
- 세부 자료를 읽을 조건이 명확하고 관련 없는 자료를 모두 읽도록 요구하지 않는다.
- 스킬 전용 자료, 내부 스킬 공용 자료와 플러그인 내부 공용 자료의 책임이 섞이지 않는다.
- 저장소나 조직의 공통 운영 규칙과 권위 있는 외부 문서를 불필요하게 복제하지 않는다.

## 동작 검증

실제 사용 시나리오는 [검증 원칙](#검증-원칙)에 따라 신규 요건 또는 변경 영향으로 범위를 정하고,
그 범위의 주요 동작과 중요한 경계 조건을 확인한다.
시나리오 수를 고정하지 않고 필요한 항목을 충족하는 사례를 선정한다.
사용 형태별 시험 환경의 준비와 실행은
[시나리오 절차](../../.agents/skills/skill-lifecycle/references/scenario-validation.md#시험-환경)를 따른다.

계속 제공할 스킬은 다음 항목 중 현재 검증 범위에 해당하는 항목을 적용한다. 통합 또는 폐기로 더 이상 제공하지 않을 스킬은 명세서에 정의된 인식 및 호출 상태가 실제 환경에 반영되었는지 확인한다.

- 명시적으로 스킬을 지정한 요청에서 스킬이 로드되고 기대 흐름을 수행한다.
- 자동 선택을 지원하면 대표적인 긍정 요청에서 선택된다.
- 자동 선택을 지원하면 비슷하지만 범위 밖인 부정 요청에서 선택되지 않는다.
- 필요한 입력이 부족할 때 지침에 맞게 확인하거나 중단한다.
- 명세서에 사용자 확인 및 승인 조건이나 중단 조건이 있으면 실제 실행에서 이를 지킨다.
- 권한, 의존성 또는 외부 상태 때문에 실행할 수 없을 때 실패를 숨기지 않는다.
- 대표 작업의 산출물과 작업 중 유지되어야 하는 주요 조건이 해당 스킬 명세의 완료 기준을 충족한다.

평가는 기대 문구의 일치 여부만 확인하지 않고 실제 결과와 판단을 확인하는 시나리오로 수행한다.
발견한 실패는 재현 조건과 영향을 기록하고, 수정 뒤 같은 시나리오로 다시 확인한다.

## 하네스 및 배포 검증

호환성 검증은 실제 사용 환경에서 스킬과 변경분의 인식, 호출, 자료 접근과 필요한 실행이 가능한지 확인한다.
대상 하네스는 [스킬 내용 작성 규격의 하네스 호환성](skill-content.md#하네스-호환성)을 따른다.

지원 CLI별로 해당 요건을 확인하며, 한 CLI의 성공을 다른 CLI의 통과 근거로 사용하지 않는다.
기존 근거는 대상 소스, 배치, CLI 환경과 조건 및 변경 영향을 대조해 현재도 유효한 항목에 재사용한다.

### 사용 형태별 확인

내부용 스킬은 저장소에서 직접 사용하는 환경에서 검증한다.
플러그인 설치와 배포 파일 구성은 적용하지 않는다.

플러그인 스킬은 커밋한 변경을 실제 위치에 설치하거나 업데이트한 뒤 검증한다.
의도한 커밋의 변경과 버전이 반영됐는지, 실제 호출이 개발 저장소 원본이 아닌 설치본을 사용하는지 확인한다.
필요한 파일이 배포물에 포함되고 개발 초안, 검사 결과와 작업 기록이 제외되는지 확인한다.

설치 전 사본의 동작 결과를 실제 설치 및 인식의 통과 근거로 사용하지 않는다.
신규 설치와 업데이트를 매번 모두 시험하도록 범위를 자동 확대하지 않는다.

두 사용 형태 모두 [검증 원칙](#검증-원칙)에 따라 다음 중 해당하는 항목을 선정한다.
제거할 스킬은 명세서에 정의된 인식 및 호출 상태가 실제 환경에 반영됐는지 확인한다.

- 스킬 이름과 설명의 발견 및 정해진 방식의 호출.
- 실제 배치 위치에서 `SKILL.md`, 참조 문서, 템플릿과 공용 자료 접근.
- 필요한 스크립트, 의존성과 CLI 기능의 사용.
- 하네스 전용 메타데이터, 정책과 공용/전용 구성의 차이가 필요한 사용 절차에 미치는 영향.

### 호환성 사례 선정

사례는 설치, 업데이트, 배치 또는 CLI 차이로 확인할 필요가 있는 항목과 종료 지점을 중심으로 선정한다.
기존 동작 시나리오는 참고 자료이며, 기존 사례 목록과 상세 판정을 그대로 반복하지 않는다.

필요한 호환성 항목을 충족하는 최소한의 사례를 사용하고 모든 업무 유형과 경우의 수를 나열하지 않는다.
사례 종류와 CLI별 실행 횟수는 구분한다.

변경분을 확인하는 흐름에서 설치본 호출과 자료 접근을 관찰했다면 함께 확인한 것으로 판단한다.
이름, 설명, 호출 조건이나 등록 방식이 바뀌면 해당 발견 및 호출 방식을 별도로 검증한다.
호출 관련 변경이 없다면 명시 호출, 자동 선택과 자동 선택 제외의 모든 조합을 반복하지 않는다.

통과 기준은 해당 호환성 항목에 필요한 관찰로 한정하고 목적을 확인하면 종료한다.
자동 선택 제외 사례에 일반 작업 산출물의 완성이나 실행 성공을 자동으로 포함하지 않는다.
CLI 차이가 특정 동작에 영향을 줄 근거가 있으면 이유와 범위를 명시하여 해당 부분만 추가 확인한다.

## 결과 기록과 완료 판정

검증 결과는 [명세서 형식](../../.agents/skills/skill-lifecycle/references/specification.md#작업-내용과-결과)과
해당 단계의 기록 지침에 따라 대상 명세서에 기록한다.
시험별 상세 자료의 보관과 정리 후 기록도 위 공통 기록 기준을 따른다.
검증 결과에는 다음 내용을 남긴다.

- 검증한 스킬 버전 또는 변경 상태
- 적용한 규격 항목과 검증 시나리오
- 사용한 하네스, 스킬의 사용 형태와 실행 환경
- 항목별 기대 결과, 실제 결과와 판정 근거 및 근거 자료의 위치
- 실행하지 못한 항목, 실행했지만 결과를 판정하지 못한 항목, 적용하지 않은 항목과 각각의 이유
- 남은 항목을 확인하거나 보완하는 데 필요한 사항과 현재 단계의 완료에 미치는 영향

실행하지 못했거나 결과를 판정하지 못한 항목을 임의로 통과 또는 적용 제외로 처리하지 않는다.
현재 검증 단계에 적용되는 필수 검증을 모두 통과하고, 남은 미확인 사항이 완료를 막지 않는다는 근거와 해당 단계 문서의 모든 완료 조건이 확인되었을 때 현재 단계를 완료한다.

교차 검증의 수행 여부와 기록은 Aster의 작업 규칙과 해당 작업 명세에서 별도로 결정한다.
