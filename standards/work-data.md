# 작업 데이터와 공용 기록

이 문서는 Aster 작업 데이터의 저장 위치, 공용 기록에 필요한 정보와 관리 기준을 정의한다.
기록 생성 조건은 프로젝트 또는 해당 스킬의 절차를 따르며, 기본 템플릿은 선택해서 사용한다.

## 경로와 적용 범위

todo와 로컬 작업 자료는 대표 작업 트리의 `data/todo/`와 `data/cargo/`에 저장하고 Git에서 제외한다.
공용 접근 경로 `~/.local/share/aster/`는 그 `data/`를 가리키는 심볼릭 링크다.

Git에 보존할 기록은 저장소의 `records/`에 둔다.
`skill-lifecycle`의 새 명세서와 부가 문서는 [전용 작업 자료 규격](../.agents/skills/skill-lifecycle/references/work-data.md)에 따라
경로를 확정한 뒤 초안부터 `records/`에서 작성한다.

clone 별칭과 추가 worktree마다 자료를 나누지 않으며, 현재 링크의 대상을 사용한다.
완료 시 기록의 정리와 선별은 [완료 기록의 Git 보존](#완료-기록의-git-보존)을 따른다.

아래 `todo/`와 `cargo/`는 공용 접근 경로 기준이다.
`standards/`, `assets/`, `.agents/`와 `records/`는 저장소 루트 기준이다.

규격과 템플릿은 저장소에서 관리한다.
데이터 경로에 규격/템플릿 사본이나 필수 README를 두지 않는다.
초기 준비와 충돌 처리는 [작업 경로 준비](../tools/references/prepare-todo.md)를 따른다.
경로를 읽을 수 없으면 이유를 보고하며 할 일이 없다고 판단하거나 임의의 대체 경로를 만들지 않는다.

```text
data/
|-- todo/
`-- cargo/
    |-- work/
    |   |-- repository/
    |   |-- internal/
    |   `-- plugins/
    `-- cross-validation/
```

`todo/`와 `cargo/`는 경로 초기화 때 준비한다.
그 아래의 작업/검증 디렉토리는 실제 기록을 작성할 때 생성한다.

## 공용 기준과 스킬별 기준

이 규격은 Aster의 일반 작업과 내부 스킬이 작업 데이터를 사용할 때 적용한다.
개별 스킬이 데이터나 템플릿을 사용한다는 이유로 lifecycle의 단계와 산출물을 적용하지 않는다.

기록의 생성 조건은 사용자 요청, 전역/프로젝트 규칙 또는 해당 스킬의 절차에서 정한다.
공용 템플릿의 존재만으로 작업 기록이나 교차 검증을 추가하지 않는다.

저장 위치, 필요한 정보, 기록의 진위와 보존 및 삭제 원칙은 지킨다.
스킬에서 파일명이나 형식을 따로 정의하면 그 형식에 필요한 정보를 담고 공용 양식을 중복 작성하지 않는다.

별도 형식이 없으면 이 문서의 기본 형식을 사용한다.
설치된 배포용 플러그인이 독립 실행에 이 저장소의 규격/템플릿을 요구하도록 만들지 않는다.

## 완료 기록의 Git 보존

사용자와 보존을 합의했거나 해당 스킬의 완료 절차에서 요구하는 기록은
[저장소 배치 규격](repository-layout.md#records)의 `records/`에서 관리한다.
처음부터 해당 위치에 작성한 기록은 완료 시 같은 위치에서 정리한다.
기존 로컬 기록은 해당 작업의 기준에 따라 선별하여 이관한다.
일반 작업과 다른 스킬에 lifecycle의 완료 절차를 자동 적용하지 않는다.
구체적인 선별 기준과 하위 경로는 해당 작업이나 스킬의 규격에서 정한다.
`skill-lifecycle`의 기록 루트에서 필요하여 생성하고 유지하는 문서는 모두 커밋 대상이며,
통합하여 정리한 중복본과 로컬 원시 자료의 처리는 같은 전용 규격을 따른다.

- 보존본은 목적, 결정과 결과를 독립적으로 이해할 수 있도록 정리한다.
  Git에서 제외한 자료나 개인 절대 경로를 필수 근거로 요구하지 않는다.
- 이관이 필요하면 결과를 대조한 뒤 정본을 전환하고 관련 참조를 갱신한다.
  진행/보존 사본을 이중 관리하지 않는다.
- 파일을 작성하거나 옮겼다는 사실만으로 실제 커밋이나 작업 완료를 주장하지 않는다.
  커밋/푸시/PR은 기존 Git 운영 규칙과 승인 범위를 따른다.
- todo는 이 절차로 이관하지 않으며 명세서와의 독립성을 유지한다.

## 기본 템플릿

[assets/work-records/](../assets/work-records/)의 양식은 필요한 정보를 빠뜨리지 않도록 돕는 기본안이다.
양식을 그대로 복사하는 것은 필수가 아니며 동등한 정보를 가진 스킬 전용 형식도 허용한다.
템플릿 원본에 실제 기록을 쓰지 않는다.

| 템플릿 | 필요한 정보와 작성 조건 |
| --- | --- |
| [todo](../assets/work-records/todo-template.md) | 전역 지침에서 정한 제목/상태/발생 및 대상 프로젝트/작업/근거/완료 조건. 합의한 보류 및 추가 작업을 기록할 때 사용 |
| [work](../assets/work-records/work-template.md) | 작업 목적, 수행 결과, 남은 작업과 참조, 상태. 작업 이력이 필요한 경우 사용 |
| [검증 요청](../assets/work-records/cross-validation-request-template.md) | 작성자, 검증 대상과 상태, 항목/판정 기준, 범위/제외. 교차 검증을 수행할 때 사용 |
| [검증 결과](../assets/work-records/cross-validation-review-template.md) | 작성자, 판정, 발견한 문제/근거, 미확인 사항. 검증자가 결과를 기록할 때 사용 |
| [후속 판단](../assets/work-records/cross-validation-resolution-template.md) | 작성자, 지적별 판단/근거, 후속 조치/재검증. 지적에 대한 후속 판단이 필요한 경우 사용 |

## todo/와 명세서의 독립성

별도 보류/추가 작업과 인계 요청은 공용 경로의 `todo/`에서 관리한다.
파일명, 필수 정보와 상태는 전역 공통 지침을 따른다.
기록은 실행 승인이 아니며 실제 착수 전에 현재 요청과 범위를 확인한다.

- 현재 작업의 범위와 제외 사유, 현재 작업 안에서 뒤 단계에 다룰 논의/설계는 해당 명세서에 기록한다.
- 현재 작업 밖에서 따로 수행할 후속 과제로 합의했거나 사용자가 보관을 요청한 실행 항목은 todo에 기록한다.
  단순한 아이디어나 미확정 논의를 자동으로 todo로 만들지 않는다.
- 명세서와 todo는 서로의 파일, 경로, 식별자, 존재 여부나 상태를 참조하지 않는다.
  todo만 읽어도 목적, 필요한 작업, 근거와 완료 조건을 알 수 있게 작성한다.
- 같은 논의에서 두 기록이 필요하면 명세서에는 현재 범위의 경계와 결정 이유를,
  todo에는 독립적으로 실행할 후속 과제를 남긴다.
  상세 명세와 진행 상태를 양쪽에서 중복 관리하지 않는다.
- 착수 후 todo의 상태와 결과는 그 파일에서 관리한다.
  새 작업의 명세서가 필요하면 별도로 작성한다.
- 완료에는 결과와 검증, 제외에는 근거, 보류에는 재개 조건을 남긴다.
  삭제는 사용자가 정리를 요청한 범위에서 수행한다.
- Codex와 Claude 모두 Aster의 todo를 읽고 작성/수정할 수 있다.
  다른 프로젝트의 요청 기록은 전역 인계 규칙을 따른다.

## cargo/work/

### 용도와 배치

원시 로그, 시험용 사본과 입력 등 로컬 자료를 `cargo/work/`에 저장한다.
작업 기록과 중간 산출물은 해당 작업의 규격이 이 위치를 정한 경우에 저장한다.
`skill-lifecycle`의 새 명세서와 설계 및 검증 문서는 아래 전용 규격에 따라 `records/`에 둔다.
하위 디렉토리는 작업 대상에 따라 구분하며 재개 시 정본 위치는 해당 작업의 기준을 따른다.

| 경로 | 담당 범위 | 자료의 예 |
| --- | --- | --- |
| `cargo/work/repository/` | Aster 저장소 전체의 구조와 운영 | 저장소 배치안, 공통 규격 초안, 운영 규칙 검토 자료 |
| `cargo/work/internal/` | Aster 저장소 전용 구성 요소 | 내부용 스킬의 원시 시험 로그, 일회성 입력과 시험용 사본 |
| `cargo/work/plugins/` | 개별 플러그인과 그 구성 요소 | 플러그인 시험용 사본, 설치 시험 로그와 로컬 작업 자료 |

- 작업을 이어갈 때는 대상 범위의 공유 작업 경로와 records에서 관련 기록을 확인하고 정본 위치를 식별한다.
- 구성 요소별 자료는 해당 작업 디렉토리에 모은다.
  구체적인 파일명과 하위 경로는 관련 규격과 작업 기록에서 확인한다.
- 자료의 배치는 작업을 수행한 에이전트가 아니라 작업 대상을 기준으로 구분한다.

### 스킬별 작업 자료

스킬 전용 단계, 파일 형식과 추가 산출물은 해당 스킬의 규격을 따른다.
`skill-lifecycle`의 소스와 기록 경로 확정, 단일 명세서와 필요한 부가 문서 및 로컬 자료 배치는
[전용 작업 자료 규격](../.agents/skills/skill-lifecycle/references/work-data.md)에 정의한다.
새 내부 스킬은 실제 필요한 기록만 자체 절차에서 정의하며, 공용 기준을 다시 복제하지 않는다.

### 기록 관리

- 작업 이력을 기록하기로 한 경우 작업별로 정본 하나를 두고 중복 상태 관리를 피한다.
- 파일명과 저장 위치를 정한 스킬별 배치 기준이나 관련 규격이 있으면 그 기준을 따른다.
  별도 기준이 없으면 파일명 형식은 강제하지 않는다.
- 새 작업 기록에는 [기본 템플릿](#기본-템플릿)의 필요한 정보를 담는다.
  스킬 전용 형식이 있으면 그 형식을 따른다.
- Codex와 Claude 모두 작업 기록을 읽고 작성하거나 수정할 수 있다.
- 기록의 저장 위치는 위 배치 기준을 따른다.
  Git에 보존할 정본은 [완료 기록의 Git 보존](#완료-기록의-git-보존)과 해당 스킬의 기준을 따른다.
- 작업 제목과 본문에는 작업 대상, 수행 내용과 결과, 남은 작업과 관련 자료의 위치를 기록한다.
- 별도 형식이 없는 작업 기록의 상태는 문서 상단 프론트매터의 `status` 필드로 관리한다.
- 새 작업 기록의 초기값은 `active`로 둔다.
- 작업을 식별하거나 검색하는 데 추가 정보가 필요한 경우에만 프론트매터에 필드를 추가한다.
- 공용 기본 형식에 필드를 추가할 때는 이 문서에 의미, 작성 기준과 필수 여부를 정의하고 work 템플릿에도 반영한다.
  스킬 전용 형식의 필드는 해당 스킬에서 정의한다.

기본 형식의 허용 상태:

- `active`: 현재 진행 중인 작업
- `paused`: 재개할 수 있도록 일시 보류한 작업
- `completed`: 목적을 달성하여 완료한 작업
- `cancelled`: 더 이상 진행하지 않기로 결정한 작업

상태 전이:

```text
active -> paused
paused -> active
active -> completed
active -> cancelled
paused -> cancelled
```

## 교차 검증 기록

### 용도

- Codex와 Claude가 서로의 산출물을 독립적으로 검증할 때 작성하는 요청, 검토 결과와 후속 판단을 저장한다.
- 검증 대상과 회차를 기준으로 관련 기록을 찾는다.
- 일반 기계 검사와 동작 시험은 이 절의 교차 검증 기록으로 다루지 않는다.
- 교차 검증의 수행 조건은 Aster 저장소 루트의 `AGENTS.md`와 해당 작업에 적용되는 규격에서 확인한다.

### 저장 구조

- 스킬을 사용한 작업의 교차 검증 기록은 [스킬별 작업 자료](#스킬별-작업-자료)에서 작업 수행에 사용하는 스킬의 기준을 확인한다.
  해당 기준에 교차 검증 저장 위치가 정의되어 있으면 그 위치를 사용한다.
- 해당하는 스킬별 저장 기준이 없거나 그 밖의 작업에서 수행하는 교차 검증 기록은 공유 경로 기준 `cargo/cross-validation/`에 둔다.
- 위 기준으로 선택한 교차 검증 디렉토리 아래에 검증 대상별 디렉토리를 두고, 이름에서 어떤 내용을 검증하는지 알 수 있게 정한다.
- 회차 디렉토리는 `round-` 접두어와 세 자리 순번을 사용한다.
- 회차는 검증 대상별로 `round-001`부터 순차적으로 증가한다.
- 검증 대상별 마지막 사용 번호는 관련 작업 기록의 정본 한 곳에 검증 대상 디렉토리 경로와 함께 기록한다.
  기본 양식을 사용하면 "수행 내용과 결과"에 적는다.
  스킬 전용 기준이 별도 history를 요구하지 않으면 명세서의 교차 검증 항목을 정본으로 사용할 수 있다.
  새 회차를 만들 때 이 기록과 기존 회차 디렉토리를 확인하여 다음 번호를 정하고, 생성한 번호로 갱신한다.
- 회차를 삭제하기 전에 마지막 사용 번호가 작업 기록에 반영되어 있는지 확인하고, 삭제 후에도 해당 경로와 번호는 유지한다.
- 삭제한 회차의 번호는 다시 사용하지 않는다.
- 저장 기준 변경 전의 기록은 기존 경로에서 근거로 참조한다.
  같은 검증 대상의 새 회차를 새 위치에 작성할 때는 기존 기록과 마지막 사용 번호를 확인하여 이어가고, 관련 작업 기록에 이전 경로와 새 경로의 연결을 남긴다.
  경로 변경을 새 검증 대상으로 간주하여 번호를 초기화하지 않는다.

```text
<위 기준으로 선택한 교차 검증 디렉토리>/
`-- <검증 대상>/
    `-- round-001/
        |-- request.md
        |-- review.md
        `-- resolution.md  # 후속 판단이 필요한 경우에만 작성
```

### 파일과 작성

- 검증 요청자는 [기본 템플릿](#기본-템플릿)의 정보를 담아 `request.md`를 작성한다.
  스킬 전용 기록 형식이 있으면 그것을 사용한다.
- 상대 검증자는 [기본 템플릿](#기본-템플릿)의 정보를 담아 `review.md`를 독립적으로 작성한다.
  스킬 전용 형식도 허용한다.
- 요청과 검토를 기본 기록으로 두고, 검증 지적의 수용, 반박 또는 재검증 판단이 필요한 경우에만 [기본 템플릿](#기본-템플릿)의 정보를 담아 `resolution.md`를 작성한다.
  스킬 전용 형식도 허용한다.
- 각 파일은 실제 작성자만 수정한다.
- 요청자와 검증자 이름은 파일명이나 디렉토리가 아니라 파일 내용에 기록한다.
- 이전 회차의 `review.md`는 작성자도 수정하지 않는다.

### 보관과 정리

- 관련 작업이나 후속 검증에서 근거로 참조하는 교차 검증 기록은 유지한다.
- 관련 작업이 끝나고 더 이상 근거로 참조하지 않는 기록은 정리 대상으로 분류한다.
- 기록을 삭제할 때는 해당 회차를 참조하는 문서와 작업 기록을 확인하고, 남은 참조도 함께 정리한다.
