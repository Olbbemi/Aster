# 설계 단계 수행 지침

- 단계 식별자: `design`
- 상대 링크는 이 파일이 있는 디렉토리를 기준으로 한다.

## 공통 흐름과의 연결

시작과 재개는 [workflow.md](../workflow.md)의 흐름을 따른다. 선행 report 확인, report 작성, 승인 및 회귀 절차는 [guidelines.md](../guidelines.md)의 해당 상세 지침을 따른다. 설계의 기준으로 사용할 승인된 discussion report와 관련 자료는 아래 [입력과 시작 시 확인](#입력과-시작-시-확인)에 따라 확인한다.

대화 내용의 기록, 단계 진입 시 인계 반영과 저장 후 대조는 guidelines의 [여러 단계의 내용이 섞인 대화의 기록과 인계](../guidelines.md#여러-단계의-내용이-섞인-대화의-기록과-인계)를 따른다.

## 단계 역할

승인된 논의 결과를 바탕으로 구현에 필요한 구조, 동작, 설계 결정과 테스트 계획을 정리한다.

## 입력과 시작 시 확인

- 현재 design report와 선행 discussion report의 선택 및 base_on은
  [참조 기준](../guidelines.md#프론트매터와-참조-확인)을 따른다.
  [선행 report 확인](../guidelines.md#다음-단계-진입-시-선행-report-확인)을 마친 뒤 시작한다.
- 해당 discussion report에 연결된 요구사항, 제약과 근거, 관련 코드와 모듈/저장소 구성, 넘겨받은 미결정 사항을 확인한다.

## 사용자 역할

아래 수행 흐름과 report 템플릿의 항목을 바탕으로 사용자와 설계를 구체화하고, 구현과 검증 및 QA의 기준으로 사용할 내용과 인계 사항을 함께 정한다. 정리한 결과의 체크리스트 상호 확인과 사용자 승인은 guidelines의 공통 규칙을 따른다.

## 수행 흐름

1. discussion report를 입력으로 설계 대상과 제약을 확인하고 설계에서 결정할 질문을 식별한다. [스펙의 단위와 작업 범위](../guidelines.md#스펙의-단위와-작업-범위)에 따라 선택한 기준과 이유를 정리한다. 요구사항 전문을 중복 정의하지 않는다.
2. 구성 요소의 책임, 의존 관계, 공개 인터페이스와 관련 저장소/모듈 경계를 설계한다. [SDD 경계](../guidelines.md#sdd와-설계-및-구현의-경계)에 따라 모듈 간 계약에 해당하는 구조체/핵심 데이터를 정의하고 내부 구현 세부와 구분한다.
3. discussion report에서 정리한 목적, 범위와 기대 방향을 바탕으로 주요 처리 흐름, 데이터 이동, 필요한 상태 변화와 오류 처리를 구체화한다. 각 동작이 성공했다고 판단할 기준을 정하고, 설계한 방식의 실현 가능성을 확인한다.
4. 주요 설계 결정의 이유와 제약, 실제 검토한 대안과 영향을 기록한다. 넘겨받은 질문의 처리 결과와 남은 사항을 구분한다. 저장소와 빌드 구성은 프로젝트의 요구사항과 기존 환경에 맞게 정한다. 특정 빌드 구성이나 빌드 도구(CMake, Ninja 등)를 스킬 사용의 필수 요건으로 두지 않는다.
5. 아래 [테스트 계획과 배치](#테스트-계획과-배치)에 따라 적용할 테스트, 검증용/QA용 항목과 실행 준비 정보를 design report에 정리한다.
6. 설계와 테스트 계획, 필요한 환경과 준비 조건을 바탕으로 아래 [범위 재평가와 분할](#범위-재평가와-분할)에 따라 한 플로우에서 완료할 범위를 평가하고, 필요하면 사용자와 분할 결과를 합의한다.
7. 현재 범위를 기준으로 아래 [환경 준비](#환경-준비)를 완료하고 실제 확인 근거를 기록한다. 분할한 경우에는 합의한 범위에 맞춘다.
8. 아래 [구현에 사용할 모델과 추론 강도](#구현에-사용할-모델과-추론-강도)에 따라 구현 범위의 조합과 승인 상태를 확인하고 인계한다.
   분할 결과, 조정된 설계와 검증/QA 계획 및 환경 준비 결과를 최종 설계 승인 대상으로 제출한다.

## 범위 재평가와 분할

설계 완료 시점에 구현부터 검증과 QA까지 한 플로우에서 다룰 수 있는 범위인지 재평가한다.
논의에서 하나의 작업 주제로 정했더라도 설계에서 드러난 복잡도를 근거로 분할을 제안할 수 있다.
문서 길이나 테스트 개수에 고정 한도를 두지 않고 다음 내용을 살펴본다.

- 독립적으로 완료하고 검증할 수 있는 목적이 여러 개 포함되어 있는지.
- 검증과 QA에 필요한 환경, 사전 조건과 시나리오가 다양하여 한 번에 다루기 어려운지.
- 일부 수정에 따른 재검증 범위가 넓어 결과를 판단하기 어려운지.

분할 필요성과 판단 근거를 design report에 기록한다.
분할한다면 현재 범위가 자체적으로 완결되도록 나누며,
현재 목적에 필요한 실패 처리나 필수 검증을 작업량을 줄이기 위해 임의로 후속 플로우에 넘기지 않는다.
필수 범위는 해당 요구사항과 설계를 기준으로 판단한다.

분할 결과도 설계 승인 대상이다. 다음 내용을 함께 제시하여 사용자와 합의하고,
조정된 설계가 승인된 뒤 구현으로 진행한다.

- 현재 플로우에 남길 범위와 완료 기준
- 후속 플로우로 이관할 범위와 의존 관계
- 분할에 맞게 조정한 현재 설계와 검증/QA 계획

discussion report의 요구사항이나 범위가 바뀌면 [회귀 승인 절차](../guidelines.md#회귀-승인-시-상태-변경)에 따라
논의로 돌아가 조정하고, 유효한 논의 결과에 맞춰 설계와 검증/QA 계획의 범위를 대조한다.
기존 승인 기록을 덮어쓰거나 분할 승인으로 다른 필수 완료 조건을 면제하지 않는다.
분할 제안만으로 현재 범위를 축소하거나 구현을 시작하지 않는다.

이관 범위, 이유와 의존 관계 및 후속 재개에 필요한 설계 근거는 현재 report에 보존한다.
후속 작업의 시작/생성은 [작업 주제 생성](../guidelines.md#작업-주제-생성과-manifest-갱신),
자료 연결은 [이전 작업 참조와 이관](../guidelines.md#이전-작업-참조와-이관)을 따른다.
분할 합의만으로 후속 플로우를 시작하거나 미시작 작업의 manifest 항목/report를 미리 만들지 않는다.

## 구현에 사용할 모델과 추론 강도

- [모델 제안과 승인](../ai_agents/model-selection.md)에 따라 구현 범위의 기존 승인을 확인한다.
  새 제안이 필요하면 조합/범위/이유를 함께 제시하며 설계 승인 요청과 함께 확인할 수 있다.
- design report의 "구현용 모델과 추론 강도"에는 해당 모델 기록과 승인 상태를 연결한다.
  권장만 한 조합을 승인이나 실제 적용으로 기록하지 않는다.
  설계 종료만으로 구현용 모델의 승인과 적용을 대신하지 않으며, 남은 확인은 구현 작업 전에 마친다.

## 테스트 계획과 배치

- 테스트 종류별 적용 여부와 범위, 검증용/QA용 항목을 구분하고 각각의 대상, 확인 절차, 기대 결과와 판정 기준을 정한다. 테스트 종류만으로 수행 단계를 결정하지 않는다.
- 테스트 코드를 둘 저장소와 내부 디렉토리를 정한다. 통합 테스트는 모듈 간 연결을 책임지는 상위 저장소에 두는 것을 기본으로 한다. 실제 배치는 작업별 설계에서 정한다.
- E2E는 최상위 플랫폼에 한정한다. 설계 시 프로젝트의 역할과 전체 사용 흐름을 바탕으로 어떤 대상이 최상위 플랫폼에 해당하는지 사용자와 확인한다. 확인한 대상과 판단 근거, E2E로 확인할 흐름의 시작점과 최종 결과를 design report의 "E2E 테스트 적용 여부와 범위"에 기록한다.
- 구현 지침의 [코드와 테스트 작성 기준](implementation.md#코드와-테스트-작성-기준)을 참조하여 외부 의존성의 격리 및 대체 방법, 통합 테스트와 E2E의 적용 여부 및 범위, 실행 환경과 테스트 데이터의 준비 및 정리 방법을 기록한다.
- 테스트의 필요 여부와 실행 가능성의 확인 상태를 구분한다. 실행 환경을 아직 확인하지 못했다는 이유만으로 필요한 테스트를 불필요한 것으로 판단하지 않는다.

### 검증과 QA의 대상 구분

- 검증용 항목과 QA용 항목은 변경의 성격과 판정 기준에 따라 정한다. 명확한 기준으로 결과를 판정할 수 있는 항목은 자동 검증 대상으로 정할 수 있으며, 시각적 적합성, 가독성, 사용성처럼 사용자 판단이 필요한 항목은 QA에 포함한다.
- 동작과 상태 처리는 TDD와 검증을 중심으로 확인한다. 모든 화면 표현 변경에 유닛 TDD를 강제하지 않는다.
- 같은 대상에 자동 판정과 사용자 판단이 모두 필요하면 검증용과 QA용에 함께 포함한다. 검증 대상을 특정 종류로 미리 제한하지 않으며, 자동 검사 통과만으로 사용자 확인을 대신하지 않는다.

## 환경 준비

- 범위 재평가에 필요한 도구, 의존성, 외부 서비스, 장비와 권한 및 준비 조건을 먼저 식별한다.
- 분할 여부와 현재 범위를 합의한 뒤 그 범위의 구현/검증/QA에 필요한 환경의 사용 가능 여부를 확인한다.
  필요한 설치/설정은 기존 권한/승인 범위에서 수행하고 실제 근거와 결과를 남긴다.
  후속으로 이관한 기능의 환경 준비를 현재 설계의 완료 조건으로 남기지 않는다.
- 설치 계획만으로 준비 완료로 처리하지 않는다. 후속 단계에 필요한 환경 준비는 설계에서 완료하고 이후 단계는 준비된 환경을 전제로 진행한다. 아직 작성하지 않은 제품 코드/테스트의 성공을 미리 판정하는 것은 아니다.

필수 환경의 준비가 끝나지 않았다면 준비 완료로 처리하여 다음 단계로 넘기지 않는다. 준비 후 장애나 변경은 guidelines의 [공통 환경 대응](../guidelines.md#환경-준비와-이후-예외-대응)을 따른다.

## report 작성과 인계

- [report 템플릿](../../assets/stage_reports/design-template.md)으로 `design-report-<번호>.md`를 작성한다.
  저장 위치와 생성/번호/상태 처리는 [공통 report 규칙](../guidelines.md#report-작성과-인계)을 따른다.
- 템플릿의 단계 결과, 인계 사항, 완료 체크리스트와 사용자 승인 영역에 실제 결과를 기록한다. 템플릿 원본은 유지하고 실제 report의 제목과 자료 참조를 작업에 맞게 작성한다.
- 구현 단계에서 참조할 설계와 관련 코드, 검증용 및 QA용 계획, 구현 순서와 주의사항, 환경 준비 결과와 남은 쟁점을 인계한다. 설계에서 제외하거나 보류하기로 한 항목은 이유와 재검토 조건을 남긴다. discussion report의 요구사항 변경이 필요하면 논의 단계로 회귀한다. verification report와 qa report는 미리 생성하지 않는다.
- 미결정 사항과 제외 항목의 분류 및 이관은 guidelines의 [공통 규칙](../guidelines.md#미결정-사항과-제외-범위의-이관)을 따른다.

## 완료 확인과 이관

구현에 필요한 결정과 남은 확인 사항을 구분하고, 분할한 경우 조정된 범위와 계획을 승인 대상에 포함한다.

템플릿의 체크 항목과 근거는 [상호 확인](../guidelines.md#상호-확인과-체크리스트-갱신)하고,
[공통 승인 절차](../guidelines.md#완료-확인과-사용자-승인)에 따라 단계 종료와 인계를 처리한다.
같은 report의 보완은 [체크리스트 재확인](../guidelines.md#변경-후-체크리스트-재확인),
hold 상태의 재개는 [재개 절차](../guidelines.md#hold-상태인-후속-단계-재개)를 따른다.
