# TDD 기반 작성 및 리팩터링 단계 수행 지침

- 단계 식별자: `implementation`
- 상대 링크는 이 파일이 있는 디렉토리를 기준으로 한다.

## 공통 흐름과의 연결

시작과 재개는 [workflow.md](../workflow.md)의 흐름을 따른다. 선행 report 확인, report 작성, 승인 및 회귀 절차는 [guidelines.md](../guidelines.md)의 해당 상세 지침을 따른다. 구현의 기준으로 사용할 승인된 design report와 관련 자료는 아래 [입력과 시작 시 확인](#입력과-시작-시-확인)에 따라 확인한다.

대화 내용의 기록, 단계 진입 시 인계 반영과 저장 후 대조는 guidelines의 [여러 단계의 내용이 섞인 대화의 기록과 인계](../guidelines.md#여러-단계의-내용이-섞인-대화의-기록과-인계)를 따른다.

## 단계 역할

승인된 design report에 따라 코드와 테스트를 작성하고, 검증 단계에서 재현할 수 있는 결과와 근거를 남긴다.

## 입력과 시작 시 확인

- 필요한 선행 report가 없으면 이 단계 작업을 시작하거나 계속하지 않고 [중간 단계 시작의 기록 연결](../guidelines.md#중간-단계-시작의-기록-연결)에 따라 사용자와 회귀 또는 신규 플로우 진행을 결정한다.
- 기존 implementation report가 있으면 같은 회차에서 가장 큰 번호를 확인한다. 파일 생성과 hold 재개는 공통 규칙을 따르며, 읽기만으로 상태를 바꾸지 않는다.
- 기준으로 사용할 design report를 확인한다. 후보가 여러 개면 현재 참조와 상태를 제시하고 사용자 확인을 받는다.
- 선택한 design report가 completed 상태인지 확인하고, 같은 디렉토리의 전체 파일명을 base_on에 기록한다.
- design report에 연결된 요구사항, 설계와 테스트 계획, 변경할 코드와 기존 테스트, 관련 의존성과 실행 환경 정보를 확인한다.
- design report의 "구현용 모델과 추론 강도"를 확인한다. 권장 정보가 없거나 조정이 필요하면 [모델 선택 안내](../ai_agents/model-selection.md)를 참고한다. 사용자 지정과 현재 환경의 사용 가능 여부를 확인하고, 실제 사용한 조합 및 권장과 다른 경우의 이유를 implementation report에 기록한다. 세션 모델을 변경할 수 없으면 변경했다고 기록하지 않는다.

구현에 필요한 환경은 설계 단계에서 준비된 상태를 전제로 한다. 이후 장애나 변경이 발생하면 guidelines의 [환경 준비와 이후 예외 대응](../guidelines.md#환경-준비와-이후-예외-대응)을 따르며, 구현 단계의 필수 조건을 충족했는지 실제 결과로 확인한다.

## 사용자 역할

코드와 테스트 작성의 내부 작업은 에이전트가 수행한다. 사용자는 제출된 구현 결과와 근거를 검토하고, 체크리스트 상호 확인과 단계 종료 승인에 참여한다. 요구사항이나 설계의 합의 변경이 필요하면 guidelines의 공통 규칙에 따라 사용자와 논의하며, 에이전트가 임의로 확정하지 않는다.

## 수행 흐름

1. design report와 변경 대상을 확인하고 구현할 동작을 식별한다. 설계에서 정한 저장소와 빌드 구성을 적용한다. guidelines의 [SDD 기준](../guidelines.md#sdd와-설계-및-구현의-경계)에 따라 승인된 명세가 허용하는 범위에서 세부 구현을 구체화한다. 기존 테스트의 구조, 도구와 작성 관례를 확인하고, 아래 [기존 테스트의 관례와 필수 규칙](#기존-테스트의-관례와-필수-규칙)에 따라 적용한다.
2. 구현할 동작을 확인하는 유닛 테스트를 먼저 작성하고, 해당 동작이 아직 구현되지 않았거나 요구사항을 충족하지 못해 테스트가 실패하는지 확인한다. 테스트를 통과하도록 코드를 구현한 뒤, 통과 상태를 유지하며 필요한 리팩터링을 수행한다.
3. 테스트 실행 시점과 묶음은 에이전트가 판단하며 매 파일 저장이나 테스트 하나 작성마다 실행하도록 강제하지 않는다. 다만 앞 항목의 실패 확인과 구현 후 통과 확인은 수행한다. 완료 보고 전에는 최종 코드 상태에서 이번에 작성하거나 수정한 유닛 테스트와 변경 영향을 받는 기존 유닛 테스트를 실행한다. 테스트가 존재하거나 과거에 통과했다는 사실로 현재 실행을 대신하지 않는다. 세부 실행 및 재검증 기준은 [guidelines](../guidelines.md#테스트-실행과-재검증)를 따른다.

   유닛 테스트는 이번 구현의 동작을 확인하는 데 필요한 최소 범위로 작성한다. 테스트가 통과했거나 TDD를 수행했다는 사실만으로 테스트 품질이 충분하다고 판단하지 않는다.

4. 유닛 테스트의 외부 의존성(네트워크, DB 등)은 아래 [테스트를 위한 외부 의존성 격리 및 대체](#테스트를-위한-외부-의존성-격리-및-대체) 기준에 따라 테스트 영역에서 제어한다. 작업별 격리 대상과 방법은 승인된 design report를 따른다. 실제 외부 대상과의 연동 확인은 적용하기로 한 통합 테스트에서 다룬다.
5. design report에서 통합 테스트 또는 E2E를 적용하기로 결정한 경우에만 해당 테스트 코드를 작성한다. E2E는 design report의 "E2E 테스트 적용 여부와 범위"에서 최상위 플랫폼으로 확인한 대상에 한정하며, 기록된 판단 근거와 흐름의 시작점 및 최종 결과를 기준으로 작성한다. 테스트의 작성 상태와 실행 상태는 구분하여 기록한다. 구현 단계에서 사전 실행한 경우 빌드와 실행 가능 여부, 크래시 발생 여부를 참고 정보로 남긴다. 이때 설계 기준의 충족 여부까지 판정할 의무는 없다. 설계 기준에 따른 실행과 판정은 검증용 항목은 검증 단계에서, QA용 항목은 QA 단계에서 수행하며, 구현 단계의 사전 실행 성공으로 이를 대신하지 않는다.
6. TDD 수행 결과는 implementation report에 결과 요약, 동작별 상세 근거와 재현 정보로 나누어 기록한다. 사용자가 읽고 확인할 수 있도록 정리하되 필요한 근거를 생략하지 않는다. 긴 로그는 별도 자료로 저장하고, [implementation report 템플릿](../../assets/stage_reports/implementation-template.md)의 "재현 정보" 작성 안내에 따라 report에 해당 자료의 위치를 연결한다.

   적용하기로 한 통합 테스트와 E2E는 작성 및 실행 준비 상태를 기록하고, 실행하지 않은 경우와 실행했지만 판정할 수 없는 경우를 구분한다. 결과의 의미는 guidelines의 [검사 결과 구분](../guidelines.md#검사-결과-구분)을 따른다. 작성한 코드와 테스트는 이후 변경이나 회귀 시 다시 확인할 수 있도록 산출물로 유지한다.

7. design report와 실제 구현의 차이, 구현하지 못한 사항과 실행 제약을 implementation report에 기록한다. 명세 변경이 필요하면 guidelines의 [회귀 절차](../guidelines.md#보완-복귀와-재검증)에 따라 해당 선행 단계로 돌아가 사용자와 합의하고, 관련 report를 갱신한 뒤 변경된 명세에 따라 구현한다. 승인받지 않은 변경을 승인된 것으로 기록하지 않는다.

TDD와 화면 확인 범위는 설계의 [검증과 QA의 대상 구분](design.md#검증과-qa의-대상-구분)과 승인된 design report를 따른다.

## 코드와 테스트 작성 기준

### 원본 코드의 책임과 파일 구성

- 프로젝트/모듈의 역할에 속하는 코드를 해당 저장소에 두고 다른 역할은 하위 모듈의 인터페이스를 통해 사용한다. 상위 기능에 맞게 요청과 반환값/오류를 처리하는 연결 코드는 상위 프로젝트의 책임에 포함될 수 있다.
- 역할과 변경 이유를 기준으로 묶는다. 밀접하게 협력하고 함께 변경되는 코드는 같은 파일에 배치하고, 독립적인 책임/변경 이유가 있으며 이해와 유지보수가 쉬워지는 경우 분리한다.
- 함수/클래스/세부 기능마다 파일을 만드는 방식이나 파일 수/줄 수를 일률적으로 강제하지 않는다. 기존 관례와 규모를 고려하여 에이전트가 판단하고 구현/검토 과정에서 책임 혼재나 불필요한 파일 이동이 드러나면 조정한다. 명세를 바꾸는 조정은 SDD 회귀 절차를 따른다.

### 테스트 파일과 공통 코드 구성

- 같은 동작이나 책임을 검증하고 준비 조건이 비슷한 테스트끼리 묶는다. 원본 파일의 구분이 테스트 범위와 잘 맞으면 같은 구분을 따르고, 그렇지 않으면 준비 조건과 가독성을 고려하여 묶거나 나눈다. 원본과 테스트의 1:1 대응을 강제하거나 배제하지 않는다.
- 특정 테스트에서만 사용하는 준비 코드와 의존성 대체 코드는 해당 테스트 가까이에 둔다. 여러 테스트에서 공유하는 준비/정리, 대체 함수와 설정/해제는 별도 공통 파일로 분리한다. 공통 코드도 책임이 다르면 나눌 수 있으며 전부 한 파일에 모으도록 강제하지 않는다.
- 파일 수와 크기는 고정하지 않고 읽기/수정 편의에 따라 에이전트가 구성한 뒤 검토 과정에서 조정한다.

### 개별 테스트 케이스

- 테스트 이름에서 확인할 동작, 조건과 기대 결과를 알아볼 수 있게 작성한다. 이름의 문법은 언어와 프로젝트 관례를 따른다.
- 본문은 준비, 실행, 결과 확인 순서로 구성한다. 짧고 명확하면 구분 주석까지 강제하지 않는다.
- 하나의 테스트는 하나의 동작이나 시나리오에 집중하고 필요한 assertion은 여러 개 사용할 수 있다.
- 테스트가 변경한 의존성과 공통 상태는 종료 시 복구하여 다음 테스트에 영향을 남기지 않는다.

### 기존 테스트의 관례와 필수 규칙

- 기존 테스트의 구조/작성 형식이 위 기본 예시와 다르면 기존 프로젝트의 파일 배치, 이름 표기, 코드 구성 관례를 따른다. 새로 추가/수정하는 테스트에도 같은 관례를 적용하고 형식 통일만을 위해 기존 테스트 전체를 재구성하지 않는다.
- 기존 관례가 달라도 TDD 수행, 필요한 테스트 실행과 결과 확인, 의존성 격리 시 원본 영향 최소화 및 테스트 종료 시 상태 복구 등의 필수 규칙은 유지한다. 충돌하면 차이와 필요한 조정을 사용자와 논의하고, 기존 관례를 필수 규칙 면제 근거로 삼지 않는다.
- 기존 테스트의 형식 차이를 이유로 과거 개발 방식의 증명이나 과거 테스트 전체 재작성을 요구하지 않는다.

### 테스트를 위한 외부 의존성 격리 및 대체

- 외부 의존성은 가능한 한 원본 코드를 변경하지 않고 테스트 영역에서 격리하거나 대체한다. 도구 명칭보다 원본 코드에 미치는 영향과 실제 적용 가능성을 기준으로 선택한다.
- 기존 호출이나 의존성을 테스트 쪽에서 대체하는 방법을 우선한다. 대체에 필요한 설정과 해제는 테스트용 코드에서 관리하며, 테스트 종료 시 변경한 상태를 복구한다.
- 테스트 편의만을 위해 원본 코드의 공개 범위를 넓히거나, 불필요한 추상화 또는 테스트 전용 분기를 추가하지 않는다.
- 원본 변경 없이 해결할 수 없다면 제약, 시도한 방법과 변경 영향을 사용자에게 설명하고 처리 방법을 논의한다. 에이전트가 임의로 원칙을 완화하지 않는다.
- 언어와 실행 환경에 따라 사용할 수 있는 대체 방법이 다를 수 있다. 실제 적용 가능성을 확인하고, 확인하지 못한 방법을 검증된 것으로 안내하지 않는다.

### 언어별 참고 후보

아래 목록은 참고할 수 있는 예시이며, 지원 언어 제한이나 필수 도구, 일괄 설치 목록이 아니다. 다른 언어도 공통 규칙과 해당 프로젝트의 도구 및 관례에 따라 진행한다. 기존 도구를 예시의 도구로 자동 교체하지 않는다.

| 언어 예시 | 참고 후보 |
| --- | --- |
| C++ | GoogleTest(gtest) |
| Python | pytest |
| Rust | `cargo test`, `#[test]`, `#[tokio::test]` |
| TypeScript | Vitest, Testing Library, MSW, Playwright |

특정 도구의 실제 적용 가능성은 해당 작업에서 확인한다.

#### 언어별 주의사항

- C++에서는 테스트를 위한 `friend` 선언을 추가하지 않는다.
- 언어별 주의사항은 실제 구현과 검증에서 확인된 제약이나 반복되는 문제를 바탕으로 필요할 때 보완한다. 추가할 때는 적용 조건과 이유, 필요한 처리 방법을 구체적으로 기록한다. 확인하지 않은 제약을 미리 가정하여 제한을 추가하지 않는다.

## report 작성과 인계

- [report 템플릿](../../assets/stage_reports/implementation-template.md)을 사용하여 선택된 회차 디렉토리에 `implementation-report-<번호>.md` 형식으로 작성한다. 번호는 `001`부터 시작하는 세 자리 순번이며, 기존 report의 재사용 또는 새 파일 생성 여부와 새 번호 부여는 guidelines의 공통 규칙을 따른다. status/base_on 처리도 같은 규칙을 따른다.
- 템플릿의 단계 결과, 인계 사항, 완료 체크리스트와 사용자 승인 영역에 실제 결과를 기록한다. 템플릿 원본은 유지하고 실제 report의 제목과 자료 참조를 작업에 맞게 작성한다.
- 변경 대상은 저장소 이름, 저장소 내 상대 디렉토리 또는 서브모듈 단위로 요약한다. 개별 파일 목록, 커밋 연결과 절대경로를 필수로 요구하지 않는다. 코드와 테스트, 실행 방법과 환경 및 데이터, 기대 결과와 판정 기준의 참조, 남은 사항을 검증 단계에 인계한다. 아직 시작하지 않은 verification report와 qa report는 미리 생성하지 않는다.

## 완료 확인과 이관

guidelines의 [상호 확인과 체크리스트 갱신](../guidelines.md#상호-확인과-체크리스트-갱신)을 적용한다. 항목별 상호 확인 전에는 체크하지 않고, 확인 후 근거와 KST 기준 완료 시각을 기록한다.

구현 결과와 상세 TDD 수행 근거를 제출하고, 적용하기로 한 통합 테스트와 E2E의 작성 및 실행 준비 상태를 함께 제시한다. 통합 테스트와 E2E의 통과 여부는 구현 단계의 완료 조건으로 삼지 않는다.

implementation report의 체크 항목과 근거를 사용자와 검토하고, guidelines의 [완료 확인과 사용자 승인](../guidelines.md#완료-확인과-사용자-승인)에 따라 이관한다. 같은 implementation report의 변경은 [변경 후 체크리스트 재확인](../guidelines.md#변경-후-체크리스트-재확인) 규칙을 적용하며, hold 상태의 implementation report를 재개하는 경우에도 일반 승인 흐름을 거친다.
