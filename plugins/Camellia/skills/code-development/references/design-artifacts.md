# 구현에 사용할 설계 산출물

설계의 뼈대를 기록하거나 최종 검토/승인에 제출하기 전에 읽는다.
단계 진행과 분할은 [설계 지침](stages/design.md)과 [작업 묶음](work-bundles.md)을 따른다.

## 설계 정의

논의 중에는 자연어로 질문과 방향을 정리할 수 있다.
설계 종료 시에는 다음 중 대상에 해당하는 정의를 선언, 표 또는 도식으로 남긴다.
자연어는 정의의 의미, 선택 이유와 제약을 보완한다.
짧은 설명과 구현 순서만으로 설계를 완료 처리하지 않는다.

| 대상 | 남길 정의 |
| --- | --- |
| 구성/모듈 | 책임, 경계, 의존 관계와 공개/내부 구분 |
| 인터페이스 | 이름/시그니처, 입력/출력, 오류, 부수 효과와 호출 조건 |
| 구조체/핵심 데이터 | 타입/필드, 필수성/기본값, 제약, 관계와 필요한 소유권/수명 |
| DB | 테이블/컬럼 타입, 키/제약/인덱스, 관계, 저장/변경의 원자성 |
| 처리/데이터/상태 | 시작/종료, 주요 분기, 상태 변화, 실패/복구/취소와 판정 기준 |
| 테스트 | 대상/조건/입력, 기대 결과, 검증/QA 역할과 준비 조건 |

- API나 DB가 없는 작업에 해당 산출물을 강제하지 않는다.
- 모듈 간 계약과 핵심 데이터는 설계하되, 모든 내부 구조체와 보조 함수까지 사전 명세하지 않는다.
- 구현 가능한 정의가 있는지 확인하고 이름만 나열한 표를 충분한 설계로 판단하지 않는다.

## 논의 그룹별 상세 파일

독립된 논의 그룹의 상세가 길거나 서로 섞여 읽기 어려우면 분리한다.
흐름 하나마다 파일을 만들지 않으며 작은 설계에는 분리를 강제하지 않는다.

문서 분리와 작업 묶음 분할은 별개이며 파일 개수로 작업 분할을 결정하지 않는다.

- 상세 파일은 해당 작업 주제의 `design-report-<번호>/<그룹명>.md`에 둔다.
  - design report에는 전체 구조와 그룹별 간단한 설명/상대 링크 목록을 남긴다.
  - 디렉토리는 실제 분리할 내용을 저장할 때만 만든다.
- 상세 파일은 해당 report의 일부이며 별도 상태/승인 절차를 만들지 않는다.
  승인/구현 인계에는 연결한 상세 정의도 포함한다.
- 타입, 인터페이스, DB와 동작의 정본은 본문 또는 상세 파일 중 한 곳에 두고 다른 위치에서 참조한다.
- 같은 report를 보완할 때는 상세 파일과 영향받는 체크 항목을 함께 대조한다.
- 회귀로 새 report를 만들면 현재 설계에 포함할 그룹의 상세를 새 report 번호의 상세 파일에 정본으로 반영한다.
- 과거 superseded report가 참조하는 상세를 수정하여 당시 설계/승인 내용을 바꾸지 않는다.

순차 묶음에서 공통 설계를 재사용할 때는 [공통/묶음 설계의 정본](work-bundles.md#공통-설계와-묶음-기록)을 따른다.

## 최종 정리

[report 본문 정리](guidelines.md#report-본문-정리)와 함께 최종 검토/승인 전에 다음 사항을 확인한다.
완료 승인 후 별도 산출물을 추가하는 단계로 만들지 않는다.

- 적용 대상의 구현용 정의와 검증 기준이 있으며 현재 범위 및 인계와 일치하는지
- 공통 뼈대, 현재 묶음의 확정된 상세와 후속 미정 사항이 구분되는지
- 설명/정의/도식/링크가 같은 계약을 가리키며 폐기한 초안이나 해결된 질문이 남지 않았는지
- 분할 필요/불필요 판단과 실제 제안/합의 근거가 있는지

## ASCII 도식의 작성과 표시 확인

주요 분기나 관계를 도식으로 설명하는 편이 명확하면 ASCII 흐름도를 둔다.
단순한 순서나 표로 충분한 내용까지 모두 작도하지 않는다.

중간 초안은 논의에 필요할 때 작성하며 매 응답/수정마다 재작도하지 않는다.
최종 제출 전에는 합의한 현재 정의와 도식/인계를 대조한다.

- 도식은 `text ascii-flow` fenced code block에 둔다.
- 연결선/화살표에는 `+`, `-`, `|`, `<`, `>` 등 ASCII 기호를, 들여쓰기에는 공백을 사용한다.
- 짧은 세로 흐름과 영문 식별자를 우선하고 긴 설명은 도식 밖에 둔다.
- 한글을 포함하면 글자 폭 차이에 따른 정렬을 실제 표시로 확인한다.

표시 확인은 다음 순서로 수행한다.

1. 원문과 고정폭 렌더링에서 줄바꿈, 연결선 끝점/분기와 설명의 대응을 확인한다.
   깨지는 부분은 폭과 배치를 단순화한 뒤 다시 확인한다.
2. 확인한 표시 환경, 범위와 결과를 report의 설계 정리 근거에 남긴다.

직접 표시를 확인하지 못하면 미확인 사실을 알리고 사용자 확인을 받는다.
확인 전에는 해당 표시 검토를 완료로 처리하지 않는다.
[정형 검사](report-checks.md)의 문자 검사 통과는 실제 표시/정렬 확인을 대신하지 않는다.
