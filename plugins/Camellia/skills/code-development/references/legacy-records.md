# 기존 번호 형식의 기록

`<단계>-report-001.md` 형식의 기존 작업을 읽거나 재개할 때 사용한다.
신규 작업에는 [현재 report 규칙](guidelines.md#파일명과-생성-시점)을 적용한다.
기존 작업의 이력, 승인과 참조를 조회만으로 새 형식으로 바꾸지 않는다.

## 기존 형식 해석과 재개

- report는 작업 루트에 있으며 단계별 번호는 001부터 전체 묶음에 걸쳐 증가한다.
  현재 개정은 같은 단계/`bundle`의 가장 큰 번호이고, 이전 개정은 superseded다.
  다른 bundle의 완료 report를 대체하지 않는다.
- 공통 report는 bundle을 생략한다.
  묶음 report의 bundle은 소문자 영문/숫자로 시작하는 소문자 영문/숫자/하이픈 식별자다.
- base_on은 같은 작업 루트의 파일명이다.
  묶음 design은 공통 discussion, implementation은 해당 묶음 design 또는 별도 설계가 없을 때 공통 design을 참조한다.
  verification/qa는 같은 묶음의 직전 단계를 참조한다.
- 기존 작업 묶음표의 열은 `묶음 | 제목 | 범위/완료 기준 | 의존/진입 | 설계 정본 | 결과 참조`다.
  묶음 열은 bundle 식별자이며 결과 링크는 해당 묶음의 실제 구현/검증/QA다.
- 검증의 `qa_handoff`는 QA로 남은 검사를 넘긴 당시 합의다.
  QA의 `next_cycle_handoff`는 별도 작업으로 미룬 당시 합의다.
  둘 다 전체 테스트 통과로 해석하지 않는다.
- 기존 상태와 완료 구분은 당시 승인 범위/사유/남은 항목 및 실제 결과와 함께 판단한다.
  신규 `in_review`나 디렉토리 구조를 기존 승인에 소급하지 않는다.

전환 요청 없이 이어갈 때는 위 파일명/선행 연결/완료 기록을 유지한다.
이전 이관 기록의 의미를 확인하여 같은 플로우의 인계와 범위 밖 보류를 구분하고,
당시 합의한 처리 방향을 바꾸려면 사용자와 합의한다.
`next_cycle_handoff`로 정한 대상 작업이 있으면 해당 작업을 재개하고,
없으면 실제 시작을 정할 때 새 작업의 이름과 범위를 확정한다.
기존 기록의 이관을 즉시 착수 승인으로 사용하지 않는다.
새로 합의하는 보류와 전체 완료 전 정리는 [보류 지침](deferred-work.md)을 따른다.

## 요청받은 전환

1. 사용자가 전환을 요청하면 기존 단계/묶음/개정, base_on과 본문/리뷰/manifest 참조를 대조한다.
2. 원본과 새 경로의 대응, 승인/결과 보존 및 현재 유효 범위를 정한다.
   번들 순번과 개정 번호를 같은 번호로 대응시키지 않는다.
3. 합의한 범위만 변경하고 모든 참조와 실제 내용을 확인한다.
   이전 승인을 새 범위나 새 결과의 승인으로 복사하지 않는다.
4. 신구 report 형식이 혼재하지 않는지 검사한다.
   검사기는 형식을 식별하고 읽을 뿐 자동 전환하지 않는다.

혼재를 발견하면 전환 상태와 사용자 의도를 확인하여 처리한다.
파일명만 보고 어느 형식을 정본으로 삼을지 임의로 선택하지 않는다.
