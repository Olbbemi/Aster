# Code Development 상세 지침

작업 조건에 해당하는 공통 절을 읽고 적용한다. 단계별 수행 방법과 완료 기준은 [workflow의 단계 목록](workflow.md#단계-순서와-지침)에서 연결한 해당 단계 지침을 따른다.

## 공통 적용과 작업 원칙

### 공통 적용과 자료 사용 기준

- 상대 링크는 이 파일이 있는 references/ 기준이다. 단계별 작업과 사용자 참여, report 템플릿은 해당 단계 지침에서 확인한다. 템플릿은 전체 단계의 실행 지침이 아니다.
- 실제 코드, 테스트와 report는 개발 대상 프로젝트의 자료이며 배포 파일이나 템플릿에 결과를 기록하지 않는다. 확인한 사실/결과와 미확인 사항을 구분한다.
- 작성과 검증의 내부 작업은 에이전트가 수행한다. 명세/환경 변경 결정과 리뷰 지적 처리는 해당 공통 절차로 사용자와 확인하며, 모든 단계의 종료는 사용자 승인을 받는다. QA는 내부 테스트와 판단에도 사용자가 참여한다. 테스트 종류만으로 검증/QA를 분류하지 않는다.
- 분석 자료는 [선택 입력](stages/discussion.md#선택적-분석-자료), 환경 준비 후 장애/변경은 [환경 대응](#환경-준비와-이후-예외-대응), 테스트 변경 영향과 결과 구분은 [실행 및 재검증](#테스트-실행과-재검증)을 따른다.

### SDD와 설계 및 구현의 경계

- SDD를 필수로 적용한다. design report의 합의한 명세를 구현/검증 기준으로 삼고, implementation report에 요구사항/설계와 실제 구현/테스트 근거를 연결한다. 검증은 현재 유효한 명세로 실제 결과를 판정한다.
- 모듈별 책임, 주요 흐름, 외부 인터페이스, 모듈 간 핵심 데이터와 테스트 판정 기준은 설계에서 사용자와 합의한다. 구조체 등 모듈 간 계약도 포함한다.
- 세부 파일 분리, 보조 함수, 지역 변수와 내부 자료구조는 명세 범위에서 에이전트가 구체화한다. 요구사항이나 모듈 연동에 영향을 주면 설계에서 다루되 모든 함수/변수의 사전 명세를 강제하지 않는다.
- 승인된 설계를 구현할 때는 이미 합의한 내용을 다시 논의할 필요가 없다. 명세 변경이 필요하면 선행 단계로 회귀하여 사용자와 합의하고 명세를 먼저 갱신한다. 구현 재량은 명세 변경 권한이 아니다.

### 환경 준비와 이후 예외 대응

후속 작업에 필요한 환경은 [설계의 환경 준비](stages/design.md#환경-준비)에서 마련한다. 준비 후 장애나 변경이 발생하면 아래 기준을 적용한다.

- 준비 후 장애나 환경 변경으로 구현/검증/QA 작업이 막히면 원인과 영향을 알리고 미확인 원인을 단정하지 않는다. 기존 합의/권한 안에서 해결 가능한 부분은 처리하며 새로운 환경/설계 변경 결정은 사용자와 논의한다.
- 막힌 작업에 의존하지 않는 작업은 진행할 수 있으나 필수 조건을 충족하지 못한 작업을 완료로 처리하지 않는다. 실제 실패/미실행, 재검증 및 검증/QA 이관은 기존 기준을 따른다.

### 테스트 실행과 재검증

테스트 계획은 [설계](stages/design.md#테스트-계획과-배치), 코드 작성과 TDD 실행은 [구현](stages/implementation.md#수행-흐름), 실제 검증 및 사용자 QA는 각각 [검증](stages/verification.md#수행-흐름)과 [QA](stages/qa.md#수행-흐름)의 지침을 따른다. 준비 정보와 실제 실행/판정을 구분하고, 아직 시작하지 않은 단계의 report는 미리 생성하지 않는다.

- 검증 후 코드나 테스트가 수정되면 영향받는 검증 항목을 다시 실행한다. 영향 범위가 불명확하면 관련 범위를 넓혀 확인한다. 이전 결과를 유지하는 항목은 영향받지 않는 근거를 남긴다. QA에서 회귀한 경우에도 같은 기준을 적용한다.
- 실패나 실행하지 못한 항목을 숨기고 문제없다고 완료 보고하지 않는다. 실제 확인 범위와 결과를 알리고 검증/QA 종료는 기존 완료 구분의 조건을 따른다. 구현 중 통합/E2E 사전 실행과 검증 판정의 구분은 유지한다.

#### 검사 결과 구분

| 구분 | 의미 |
| --- | --- |
| 통과 | 검사를 실행했고 판정 기준을 충족함 |
| 실패 | 검사를 실행했지만 판정 기준을 충족하지 못함 |
| 미실행 | 검사를 실행하지 못했거나 실행하지 않음 |
| 판정 불가 | 검사를 시도했지만 확보한 결과만으로 기준 충족 여부를 판단할 수 없음 |

## 등록과 회차 관리

### 스킬 호출 시 등록 정보 확인

에이전트가 기존 도구와 대화로 아래 절차를 수행한다. 스킬 운영 전용 스크립트 제작 및 이를 위한 훅 연결은 제외한다. 절차의 누락이나 외부 세션의 수정을 완전히 차단한다고 보장하지 않는다.

#### 진입과 선택 유지

| 상황 | 처리 |
| --- | --- |
| 같은 세션의 일반 작업 요청 | 선택한 topic/path를 유지한다. 사용자 변경 요청이 있으면 전환한다. |
| 필요한 자료만 컨텍스트에 없음 | 확인 가능한 선택 경로에서 다시 읽는다. 자료가 컨텍스트에 없다는 이유만으로 신규 생성하지 않는다. |
| 명시적 스킬 재호출이며 선택 정보가 있음 | 기존 topic/path를 함께 보여주고 계속 사용할지 한 번 확인한다. |
| 선택 정보를 확인할 수 없음 | 아래 등록 확인과 선택 절차로 돌아간다. |
| 신규 세션 또는 클리어 후 호출 | 이전 선택의 유지를 전제하지 않고 등록 확인부터 진행한다. |

명시적 호출과 모델 선택으로 스킬을 실제 사용할 때 적용한다. 목록에 이름/설명만 나타난 것은 호출이 아니다. 컴팩션 자체는 별도 시작 이벤트가 아니며, 이후 요청에는 위 기준을 적용한다. 현재 선택을 위한 별도 파일/세션 ID는 추가하지 않는다. 다른 에이전트에 검토를 요청하는 방식은 [교차 검증](#교차-검증의-연결-위치)의 요청 전달 규칙을 따른다.

#### 등록 파일과 값 확인

- 호출 시점 cwd의 `.code-dev-registry.json`을 확인한다. 파일이 없으면 topic/path를 요청하기 전에 `{"entries": []}`로 생성하고 저장 성공을 확인한다. topic/path 입력을 받을 때까지 빈 등록 파일 생성을 미루지 않는다.
- 기존 파일은 내용을 읽어 확인하며 초기화하지 않는다. 등록 파일의 위치를 프로젝트/Git 루트나 스킬 설치 경로로 치환하지 않는다.
- 주제와 report 저장 루트를 매핑한다. 주제 단위/언어와 디렉토리 이름은 사용자가 정한다.

```json
{
  "entries": [
    {"topic": "로그인 기능", "path": "/home/user/dev-notes/login"}
  ]
}
```

- topic/path는 필수이고 path는 절대 경로다. 누락/빈 값은 잘못된 등록이며 실제 디렉토리 부재와 구분한다. 잘못된 항목을 알리고 선택 후보에서 제외하며 임의로 채우지 않는다.
- 파일 읽기 실패는 문제와 수정 내용을 알리고 사용자 확인 후 수정한다. 초기화하지 않으며 해결 전에는 해당 등록에 의존하는 report 작업을 진행하지 않는다.
- 주제의 오타/유사성/의미상 중복과 경로 중복을 확인한다. 기존 등록의 재사용/변경을 권유할 수 있으나 사용자 판단 없이 병합하거나 덮어쓰지 않는다.

#### 등록 선택과 경로 확인

| 유효한 등록 수 | 제시할 내용 |
| --- | --- |
| 0개 | topic과 절대 path를 함께 요청하고, 일부만 답하면 누락 값만 확인 |
| 1개 | 기존 topic/path와 기존 등록 사용/새 등록 추가를 함께 제시 |
| 여러 개 | 기존 목록과 새 등록 추가를 함께 제시 |

- 기존 등록은 작업 대상으로 확인하고 신규 등록은 topic/path를 입력받는다. 불명확한 부분만 다시 묻고 무응답이면 기다린다. 취소 시 선택 절차를 끝내고 기존 등록을 유지한다.
- 기존/신규 모두 실제 경로의 내부 조회, 기존 기록 읽기와 report 저장 가능 여부를 확인한다. 경로가 없으면 사용자 확인 후 생성하고 같은 접근/쓰기 확인을 한다. 일반 파일이면 다른 경로를 요청한다.
- 경로의 동일성이나 작업 범위 포함 여부를 판단할 때는 심볼릭 링크 등으로 표기가 달라질 수 있으므로 실제로 가리키는 위치를 확인한다. 표기 차이만으로 다른 경로 또는 작업 범위 밖이라고 판단하지 않는다.
- 확인 실패는 원인을 알리고 경로 재선택이나 접근 문제 해결을 요청한다. 권한/환경으로 확인하지 못한 경로를 사용 가능으로 처리하지 않는다. 경로 확인 실패나 저장 전 취소 시 신규 등록을 저장하지 않는다.
- 경로 확인 후 신규 항목을 등록 파일에 저장한다. 저장 실패 시 원인과 재시도/중단을 사용자에게 확인하며 기존 등록을 유지한다. 중단해도 이미 생성한 디렉토리는 임의 삭제하지 않는다.
- 주제/경로 선택과 사용 가능 여부, 신규 등록의 저장 성공을 확인한 뒤에만 해당 report 작업을 시작한다. 선택은 대화에 명시하고 [선택 유지 기준](#진입과-선택-유지)을 따른다.
- 등록 파일의 Git 추적은 사용자가 정한다. 자동으로 Git에 추가하거나 .gitignore를 수정하지 않는다.

#### 작업 시작과 재개의 확인 절차

1. 선택한 루트의 freight-manifest.md, 회차별 report와 요청을 대조한다. 회차의 stages로 순서/진행 상황을 확인하고, [현재 report와 참조 기준](#프론트매터와-참조-확인)에 따라 상태/참조/승인 근거를 읽는다. superseded는 경위 확인용이며 회차 완료 판정에서 제외한다.
2. 파일 수만으로 판단하지 않고 다음 상황을 사용자에게 제시한다.

| 확인 결과 | 사용자 확인 |
| --- | --- |
| 회차/report가 없음 | 첫 회차 시작 여부 |
| stages의 모든 단계에 현재 유효한 completed report가 있음 | 완료 근거와 새 회차 진행 여부 |
| 일부 단계만 있거나 미완료 report가 있음 | 진행 상황/남은 단계와 기존 회차 재개 여부 |
| 후보가 여러 개이거나 상태/참조가 불명확함 | 대상과 진행 방향. 임의 선택하지 않음 |

3. 확인 후 필요한 자료를 읽고 기록을 갱신하여 합의한 단계로 진행한다. 이미 확인한 등록/회차 현황을 별도 인수 절차로 반복하지 않는다. 필요한 선행 report와 승인 근거가 있으면 구현/검증/QA부터 시작할 수 있다.
4. 논의부터 시작할 때만 요청과 대상을 가볍게 확인한다. 별도 단계/승인 절차나 알려진 내용의 재질문을 추가하지 않고, 이후 단계 시작/재개 시 도입 대화를 반복하지 않는다.
5. 다음 단계 진입에는 [선행 report 확인](#다음-단계-진입-시-선행-report-확인)과 [인계 반영](#여러-단계의-내용이-섞인-대화의-기록과-인계), 회귀 후 재개에는 [hold 재개](#hold-상태인-후속-단계-재개)를 적용한다. 선행 report가 없으면 아래 절차로 진입을 차단한다.

최신 번호라는 사실은 사용 승인이 아니다. 번호/상태/참조의 불일치는 사용자에게 제시하고 확인한 현상에 따라 처리 방향을 정한다.

##### 중간 단계 시작의 기록 연결

- 중간 진입과 회귀 대상도 [선행 report 확인](#다음-단계-진입-시-선행-report-확인) 및 참조/승인 조건을 충족해야 한다. 누락한 report와 진행 불가 이유를 설명하고 회귀 또는 신규 플로우 및 대상을 사용자와 정할 때까지 해당 단계 작업을 시작하거나 계속하지 않는다.
- 회귀는 [승인 절차](#회귀-승인-시-상태-변경), 신규 플로우는 [회차 생성](#회차-생성과-manifest-갱신) 후 논의부터 진행하며 각 절차의 기록 보존 규칙을 따른다.
- 기존 설계 문서/코드/테스트는 참고 자료이며 선행 report의 승인 근거를 대신하지 않는다. 미수행 report의 승인이나 base_on 값을 꾸미지 않는다. 선행 report 없는 진입을 위한 base_on, stages/회차 완료 판단, reference_reports의 별도 예외는 두지 않는다.

### 저장 루트와 회차별 기록

- 등록 루트 바로 아래에 freight-manifest.md와 round-001, round-002 형식의 회차 디렉토리를 둔다. 호출 cwd의 등록 파일은 이 루트의 상위에 있을 필요가 없다.
- 회차는 생성 시 정한 단계 목록을 순서대로 진행하는 개발 흐름이다. 기본 흐름은 논의부터 QA까지이며 신규 개발, 개선과 이전에 미룬 항목 등을 다룬다. 회귀/재작업을 포함한 같은 회차의 모든 report는 해당 round에 두며 report 번호와 회차 번호는 독립적이다.
- manifest는 회차 디렉토리, stages와 직전 회차 참조를 연결한다. 작업 항목/처리 상태는 report에서 관리하고 미처리 내용을 이관하며, manifest에 중복 목록이나 상태 필드를 두지 않는다.
- 회차 제목은 실제 디렉토리의 상대 링크이고 그 아래에 필수 stages 목록과 reference_reports를 둔다. report/manifest는 Git 관리 대상이나 자동 커밋하지 않는다.
- stages는 회차 생성 당시 확정한 단계 순서다. 새 단계는 스킬 변경 완료 후 생성하는 신규 회차부터 적용한다. 기존 회차는 새 단계를 제외한 생성 당시 구성을 유지하며 현재 기본 목록으로 덮어쓰지 않는다.
- 해당 회차의 stages로 단계 순서, 선행 단계/base_on, 회귀 범위와 report 존재/전체 완료를 판단한다. report 존재와 승인을 구분해 상태/참조/체크리스트를 확인하고, 미시작 단계의 report 부재는 미진행으로 본다.

manifest 예시(round-001 QA가 all_passed인 경우):

```markdown
# Freight Manifest

## [round-001](round-001/)

- stages: [discussion, design, implementation, verification, qa]
- reference_reports: 없음

## [round-002](round-002/)

- stages: [discussion, design, implementation, verification, qa]
- reference_reports:
  - [discussion-report-001.md](round-001/discussion-report-001.md)
  - [design-report-002.md](round-001/design-report-002.md)
```

#### 회차 생성과 manifest 갱신

1. [시작/재개 확인](#작업-시작과-재개의-확인-절차) 후 사용자와 신규 회차를 확정한다. 제안 중에는 생성하지 않는다.
2. 첫 회차는 round-001, 이후에는 번호를 1 올린다. 회차 디렉토리, manifest 항목(stages/reference_reports), 합의한 시작 단계의 첫 report를 함께 작성한다. 기존 manifest에는 추가하며 재개/회귀는 회차를 새로 만들지 않는다. 논의부터 시작하면 discussion-report-001.md를 만든다. 선행 report 없는 중간 진입은 [기록 연결](#중간-단계-시작의-기록-연결)을 따르며 신규 플로우 선택 시 논의부터 시작한다.
3. 회차 추가/참조 변경 등 필요할 때 manifest를 갱신한다. 미시작 회차의 항목이나 report는 미리 만들지 않는다.
4. 주제 기록 최초 접근과 manifest 갱신 직전에 관련 항목/디렉토리/report의 일치를 확인한다. 갱신 시 변경할 항목과 연결 기록을 대조하며 매번 전체 이력 검사는 요구하지 않는다.
5. 필수 디렉토리/report 부재, stages 누락이나 기록 불일치는 작업 중 발견한 경우도 알리고 처리 방향을 요청한다. 해당 처리는 보류하며 임의 수정/선택하지 않는다.

#### 직전 회차 참조와 이관

- reference_reports는 직전 회차의 최종 discussion/design report를 연결한다. QA가 next_cycle_handoff이면 qa report도 추가하고, all_passed이면 앞의 두 report만 연결한다. completed만 보고 완료 구분을 생략하지 않는다.
- 각 회차 제목 아래 Markdown 목록 필드로 적는다. 링크는 manifest 기준으로 직전 회차 디렉토리와 전체 파일명을 포함하며 최초 회차는 `reference_reports: 없음`이다.
- 신규 회차에서는 미처리 항목과 필요한 근거만 현재 discussion report로 이관하고 수행/재보류, 이유와 재검토 조건을 구분한다. 완료/완전 제외 항목은 가져오지 않는다.
- 이관할 내용이 없어도 discussion/design 링크는 유지한다. 오래된 회차를 재귀적으로 읽지 않도록 계속 미룬 항목의 근거는 현재 report에 보존한다. QA 전체 통과 후에도 논의/설계에서 미룬 항목은 이관할 수 있다.
- 이전 회차 자료는 본문에 연결하며 discussion report의 base_on은 null을 유지한다.

## report 작성과 승인 및 복귀

### report 작성과 인계

#### 여러 단계의 내용이 섞인 대화의 기록과 인계

대화 주제는 현재 단계에 한정하지 않는다. 담당 항목과 지금 기록할 위치를 구분한다.

| 담당 항목 | 기록 기준 |
| --- | --- |
| 명확함 | 내용, 합의 상태와 근거를 해당 항목에 기록. 정본이 있으면 참조 |
| 여러 항목에 걸침 | 정본 한 곳에 기록하고 나머지는 참조 |
| 불명확함 | 현재 report의 인계 사항에 "배치 미확정", 내용, 이유와 관련 단계 후보를 보존. 후보도 모르면 미확정으로 표시 |

- 현재 단계에서 정할 내용은 단계 결과에 둔다. 이후에 사용한다는 이유만으로 인계 사항으로 분류하지 않는다. 아직 작성할 시점이 아닌 후속 report의 내용은 현재 인계 사항에 대상 단계/내용/합의 상태/근거를 보존하며, 미리 논의했다고 후속 report를 만들거나 진입/완료로 처리하지 않는다.
- 배치 미확정도 위 기준으로 보존하며 별도 파일을 만들거나 미착수/없음으로 처리하지 않는다.
- 단계 진입 시 해당 단계의 인계와 배치 미확정 사항을 확인한다. 기존 합의는 입력과 충돌하지 않으면 재사용하고 미확정 제안은 사용자와 검토한다. 배치할 수 있으면 적절한 항목에 정리하고 출처를 연결하며, 여전히 불명확하면 이유와 단계 후보를 인계 사항에 유지한다.
- 기존 기록은 보존하며 합의한 내용을 처음부터 다시 논의할 필요는 없다. 합의 변경은 사용자와 논의하여 [회귀/승인](#보완-복귀와-재검증), 필수 미결정과 단계/회차 이관 및 완전 제외는 [이관 기준](#미결정-사항과-제외-범위의-이관)을 따른다.
- 저장 시 이번 합의/변경/미확정 내용 각각을 실제 본문 또는 참조 위치와 대조하고 배치 미확정의 보존 위치도 확인한다. 저장 후 전체 파일명과 반영 항목을 알린다. 요약 보고만으로 저장 완료로 판단하지 않는다.

#### 파일명과 생성 시점

- report 하나에 단계 결과, 인계 사항, 완료 체크리스트와 사용자 승인을 둔다. 템플릿은 `<단계명>-template.md`, 실제 파일은 `<단계명>-report-<번호>.md`다.
- 번호는 회차/단계별 001부터 시작하여 새 파일마다 증가한다. 단계 간 번호는 독립적이며 새 회차는 다시 001부터 시작한다.
- 작성 중/승인 전 보완이나 세션 변경 후 같은 작업 재개는 기존 파일을 유지한다. 미시작 단계의 report는 미리 만들지 않는다.
- 회귀 검토만으로 생성하지 않는다. 사용자 승인 후 [회귀 상태 변경](#회귀-승인-시-상태-변경)을 적용한다. 후속 hold의 유지/신규 생성은 [재개 절차](#hold-상태인-후속-단계-재개)로 결정하며 대체할 기존 본문부터 수정하지 않는다.
- superseded의 본문과 과거 승인은 보존하고 하단 요약으로 대체하지 않는다.

#### 프론트매터와 참조 확인

```yaml
status: in_progress
base_on: null
```

- 위 값은 새 report의 기본값이며 실제 상태와 구분한다. base_on은 같은 회차의 이전 단계 report 하나의 전체 파일명(확장자 포함)이다. 경로를 넣지 않으며 선행 단계 없는 discussion은 null이다.
- 이전 단계 report를 확인하고 base_on에 기록하여 작업 기준으로 따른다. 후보가 여러 개면 시작/재개 시 현재 참조와 후보의 상태/변경 내용을 제시하여 사용자에게 사용할 파일을 확인받는다.

예시 질문:

> 현재 implementation-report-001.md는 design-report-001.md를 참조하고 있습니다. design-report-002.md는 완료된 상태입니다. 이번 구현은 design-report-002.md를 기준으로 진행할까요?

- 새 선행 report 생성만으로 참조를 갱신하지 않는다. superseded나 completed 전의 새 report를 승인된 입력으로 사용하지 않고 [선행 report 확인](#다음-단계-진입-시-선행-report-확인) 후 작업한다.
- 같은 단계의 가장 큰 번호를 현재 대상으로 열고 status와 본문의 결과/승인 근거를 확인한다. 작은 번호는 superseded여야 하며 불일치는 알린다. 조회만으로 상태를 바꾸거나 파일을 만들지 않으며 각 상태/생성 규칙을 따른다.
- report를 새로 만들어도 선행 입력이 유효하면 base_on을 유지한다. 새 입력을 확인하여 대체한다면 확인한 파일명을 쓴다.
- 같은 단계의 바로 이전 번호가 대체 대상이다. 별도 대체 파일 항목이나 revision/once/diff 필드를 추가하지 않고, 회귀 계기 report는 [본문 기록](#기록과-인계)에 연결한다.

#### 기록과 인계

- 단계 결과 첫 항목에 복귀 사유, 변경 대상과 이전 report 대비 변경을 적고 실제 변경/검토 후 유지한 결정을 구분한다. "복귀 및 재검토 기록"의 "회귀 계기가 된 report"에는 전체 파일명, 사유와 문제 위치를 남긴다. 복귀가 없으면 복귀 관련 항목은 해당 없음이다.
- 파일을 유지하면서 참조를 바꾸면 전후 파일명, 선행 변경의 영향과 기존 합의/결과 유지 근거를 기록한다. 참조 변경만으로 결과 검토가 완료되지 않는다.
- 단계별 결과/인계 항목은 템플릿, 공통 메타데이터/상태는 이 문서를 따른다. report에는 실제 제목과 자료를 연결하고 링크는 report 위치에서 성립해야 한다. 템플릿 작성 안내와 스킬 지침을 구분하며 개발용 검토 상태/미정 목록을 결과로 복사하지 않는다.

### 완료 확인과 사용자 승인

현재 승인 완료 여부는 status로, 과정과 근거는 사용자 승인 본문으로 확인한다. 검증/QA는 [완료 구분](#검증-및-qa의-완료-구분)을 함께 읽으며 다음 단계 진입에는 상태값 외에 [선행 report 대조](#다음-단계-진입-시-선행-report-확인)가 필요하다.

| status | 의미 및 조건 |
| --- | --- |
| `in_progress` | 초기 작성, 보완 또는 hold 해제 후 재검토 중 |
| `awaiting_approval` | 결과/인계 작성, 체크리스트 근거 대조, 미충족/미확인 항목과 이유 기록 및 결과/남은 사항 제시를 마쳐 사용자 판단을 요청할 준비가 됨 |
| `completed` | 근거로 완료 조건을 확인하고 사용자가 이번 결과/이관을 승인한 유효 report. 마지막 QA는 작업 완료 승인 |
| `hold` | 회귀로 보류한 후속 report. 재검토 전에는 현재 진행/완료 근거로 사용 불가 |
| `superseded` | 새 report로 대체된 이력. 본문/과거 승인은 보존하되 현재 진행 근거로 사용 불가 |

- 일반 흐름은 in_progress -> awaiting_approval -> completed다. 무응답이면 awaiting_approval을 유지하고 보완 요청은 in_progress로 돌아간다.
- 승인 대상은 인계 내용, 체크리스트와 연결된 단계 결과다. 구체 산출물은 report에서 연결하며 별도 승인 대상 필드는 두지 않는다. 승인은 이번 결과에만 적용하고 새 report나 변경 결과에 승계하지 않는다.
- 미충족 사유 기록이나 사용자 승인만으로 필수 완료 조건을 면제하지 않는다. 검증/QA의 완료 구분과 [미결정 이관](#미결정-사항과-제외-범위의-이관)을 적용한다.
- 승인 본문은 [승인 과정 기록](#승인-과정-기록)을 따른다. 실제로 없는 요청/남은 사항은 없음으로 적고 미승인을 승인으로 채우지 않는다. 에이전트 작성/무응답은 승인이 아니며 기계적 승인 차단 스크립트는 만들지 않는다.

#### 검증 및 QA의 완료 구분

- 두 report의 사용자 승인 영역에 "완료 구분"을 두고 키워드 다음 줄에 이유와 근거를 적는다. 프론트매터 필드와 status 값은 추가하지 않는다. 미결정 상태는 미정으로 표시한다.
- 단계별 키워드와 조건은 [검증의 완료 구분](stages/verification.md#완료-구분)과 [QA의 완료 구분](stages/qa.md#완료-구분)을 따른다.
- 해당 기준과 체크리스트를 확인하고 실제 사용자 승인 후 completed로 바꾼다. 단계 종료와 전체 테스트 통과는 구분하며, 후속 단계를 시작하거나 신규 회차를 준비할 때는 해당 report의 사용자 승인 영역에 기록된 완료 구분과 설명을 확인한다.

#### 상호 확인과 체크리스트 갱신

- 논의/확인/승인이 필요한 모든 지점에서 대상과 판단할 내용을 설명하고 명시적인 응답을 받는다. 위임된 작업은 수행할 수 있지만 포괄 위임이나 진행 요청이 개별 안건의 합의/승인을 대신하지 않는다.
- 체크리스트는 [ ]로 시작한다. 항목별 근거와 미흡한 부분을 설명하고 사용자 명시적 승인과 에이전트의 근거 충족 확인을 모두 마친 뒤에만 [x]로 바꾼다. 독자 판단이나 사용자/에이전트의 사전 체크는 대체 근거가 아니다.
- "알아서 처리해", "통과할 정도로 보완해", "다음 단계 진행해"도 항목별 확인을 생략할 근거가 아니다. 보완 후 다시 확인받으며 무응답/승인 대상 불명확 시 [ ]를 유지한다. 규칙 위반 요청은 [위반 대응](#공통-규칙-위반-대응)을 따른다.
- 체크한 항목 아래 확인 근거(내용과 위치)와 실제 상호 확인 완료 시각을 남긴다. 시각은 조회한 한국 표준시 `YYYY-MM-DD HH:mm:ss.SSS (KST)`이며 근거/시각/밀리초를 추정하지 않는다. 별도 "사용자 확인" 문구는 반복하지 않고 조건/보완 요청은 승인 영역에 적는다.

형식 예시:

```markdown
- [x] 체크 항목
  - 확인 근거: 함께 확인한 내용과 근거 위치
  - 확인 완료 시각: 2026-09-10 15:30:12.345 (KST)
```

- 시각은 검토 보조 정보이며 승인 증명이나 기계적 강제가 아니다. 외부 편집 차단을 전제하지 않으며 에이전트의 승인 대행/생략을 줄이기 위한 기록이다.
- 현재 단계의 근거 대조는 승인 요청 전에, 다음 단계의 대조는 [선행 report 확인](#다음-단계-진입-시-선행-report-확인)에서 수행한다. report 전체의 승인 완료는 status로 판단한다.

#### 다음 단계 진입 시 선행 report 확인

- 필요한 선행 report가 없으면 [중간 단계 시작의 기록 연결](#중간-단계-시작의-기록-연결)에 따라 진입을 차단하고 회귀 또는 신규 플로우를 사용자와 결정한다.
- 선행 report의 completed 상태와 참조 관계를 확인한다. 각 체크 항목의 [x], 확인 근거 요약 및 확인 완료 시각까지 확인하고 본문과 대조한다.
- 누락이나 본문과의 모순이 있으면 사용자에게 알리고 해소하기 전에는 다음 단계 작업을 시작하지 않는다.
- 이상이 없으면 선행 단계의 항목별 승인 대화를 반복하지 않는다. status에 의한 현재 승인 완료 판정과 검증/QA의 완료 구분은 유지한다.

#### 변경 후 체크리스트 재확인

- 같은 report에서는 변경 영향이 있는 항목만 [ ]로 되돌리고 나머지 체크/기록은 유지한다. report 전체의 재승인/상태 전환은 기존 절차를 따른다.
- [x]를 다시 열면 근거/시각을 해당 항목의 "이전 확인 기록"으로 옮기고 재확인 사유를 남긴다. 현재 근거/시각은 재확인 완료 후 적는다. [ ] 상태의 반복 보완은 승인 영역에만 기록하고, 다시 [x]가 된 항목을 재개방할 때 이전 확인 기록을 추가한다.
- 아래 형식을 우선 사용하며 완료 이력은 같은 항목 안에서 시간순으로 누적한다. 실제 분량/가독성에 따라 형식을 재검토한다.

```markdown
- [ ] 체크 항목
  - 확인 근거: <!-- 재확인 완료 후 작성 -->
  - 확인 완료 시각: <!-- 재확인 완료 후 실제 밀리초 KST 시각 작성 -->
  - 이전 확인 기록:
    - 확인 근거: 변경 전 함께 확인한 내용

      확인 완료 시각: 2026-09-10 15:30:12.345 (KST)

      재확인 사유: 이번 변경이 해당 항목에 영향을 준 이유
```

- 위 내용/시각은 예시다. 재확인 후 실제 근거/시각과 [x]를 기록한다. 새 report로 대체하면 과거 승인은 기존 파일에 보존하고 복사하지 않는다.

#### 승인 대기 중 보완과 변경 권한

- 오탈자, 빠진 참조와 확인된 근거 정리 등 합의를 바꾸지 않는 보완은 수행할 수 있다. 범위/설계/테스트 기준/제외 여부 등 새 결정이나 합의 변경은 사용자와 논의한다. 교차 검증 지적의 수정은 [리뷰 검토와 합의](#리뷰-의견-검토와-사용자-합의)를 먼저 따른다.
- 합의한 작업의 코드/테스트/report 작성과 수정은 단계 수행 범위다. 보완으로 영향받은 항목은 재확인하며 보완 완료를 승인이나 자동 체크의 근거로 삼지 않는다.
- 커밋/푸시/배포는 별도 요청 없이는 제안하거나 실행하지 않는다. 단계 승인은 그 권한이 아니다. 요청받으면 사용자 요청과 저장소 규칙을 따르며 명확히 승인된 범위는 다시 묻지 않는다.

#### 미결정 사항과 제외 범위의 이관

- 현재 단계의 필수 미결정은 해결해야 한다. 사유 기록이나 사용자 승인만으로 필수 완료 조건을 면제하지 않는다.
- 이후 단계에서 결정하기로 합의하면 현재 report의 인계 사항에 내용, 미결정 이유와 결정할 단계를 적는다.
- 다음 회차로 미루면 discussion/design report의 제외/보류 항목에 사유와 재검토 조건을 남기고 [직전 회차 이관](#직전-회차-참조와-이관)을 따른다.
- 완전 제외는 근거를 보존하며 다음 회차로 자동 이관하지 않는다. 합의된 제외는 미결정이 아닌 완료된 결정이다.
- 처리 중 안건을 위 세 구분으로 바꾸려면 사용자와 합의한다. 진행을 위해 임의 재분류하거나 별도 관리 파일을 만들지 않는다.

#### 승인 과정 기록

- 사용자 승인 영역의 세 항목인 사용자 판단, 보완 요청과 처리 결과, 남은 사항과 이관 조건에 실제 내용을 기록한다.
- 사용자 판단에는 기준 선행 report의 전체 파일명, 검토 내용과 판단 근거를 줄을 나눠 적는다. 선행 단계 없는 discussion은 파일명을 생략하며 별도 참조 필드는 두지 않는다.
- 같은 파일의 재승인은 기존 기록을 보존하고 항목별 새 과정을 시간순으로 추가한다. 선행 변경, 현재 합의/결과에 미치는 영향과 유지 근거, 실제 사용자 판단을 남기며 상세 단계 결과는 참조한다.
- 새 파일에는 이번 과정만 적고 과거 승인은 superseded에 보존하여 복사/승계하지 않는다. 과거 문구가 있어도 status가 completed가 아니면 현재 승인 완료가 아니다. 별도 승인 번호나 유효 승인 기록 선택 필드는 두지 않는다.

### 보완, 복귀와 재검증

#### 회귀 승인 시 상태 변경

1. 회귀 필요성/사유/대상 단계를 사용자와 확인하고 승인받는다.
2. 대상의 기존 report를 superseded로 바꾸고 다음 번호를 in_progress로 생성한다. 이전 본문과 승인은 보존한다.
3. 대상보다 앞선 report는 내용/상태를 유지한다. 앞선 단계도 변경해야 하면 사유/대상을 확인하고 승인 후 회귀를 다시 적용한다. 대상 다음 단계부터 회귀 직전 현재 단계까지 현재 report를 hold로 바꾼다. superseded/기존 hold는 유지하고 없는 파일은 만들지 않는다.
4. 새 report에 회귀 사유/변경 대상을 기록하고 작업한다. 기존 결과를 전면 변경할 수 있으며 보존은 재사용 의무가 아니다.

예: QA 진행 중 설계로 회귀하는 것을 사용자가 승인한 경우.

```text
QA 진행 중 설계로 회귀 승인
|
|-- 유지
|   `-- discussion-report-001.md: completed 유지
|
|-- 기존 설계를 보존하고 새 설계 작성
|   |-- design-report-001.md: completed -> superseded
|   `-- design-report-002.md: 새로 생성 -> in_progress
|
`-- 후속 단계 보류
    |-- implementation-report-001.md: completed -> hold
    |-- verification-report-001.md: completed -> hold
    `-- qa-report-001.md: in_progress -> hold
```

#### hold 상태인 후속 단계 재개

1. 회귀 단계의 완료/승인 후 후속 단계에 진입하여 가장 큰 번호의 hold report를 연다.
2. hold를 in_progress로 바꾸어 재검토한다. 단순 이력 조회로 상태를 바꾸지 않는다.
3. base_on과 선행 report를 [참조 기준](#프론트매터와-참조-확인)에 따라 사용자와 확인한다. superseded는 선택할 수 없다. 승인된 새 입력을 거부하며 기존 입력으로 진행하라는 요청은 [위반 대응](#공통-규칙-위반-대응)을 적용하며 정상 회귀/중단 요청과 구분한다.
4. 선행 내용과 기존 합의/결과를 대조하여 아래 판단을 사용자와 확인한다. 영향이 불명확하면 먼저 검토하고 유지/신규를 추정하지 않는다.

| 결과 | 처리 |
| --- | --- |
| 기존 합의/결과를 유지할 수 있음 | 기존 파일의 base_on과 기록을 갱신하고 유지 근거를 남김. 본문 결과가 같아도 참조/상태/검토 기록은 갱신 |
| 합의/결과가 하나라도 어긋나 변경이 필요함 | 기존 본문 수정 전에 superseded로 바꾸고 다음 번호를 in_progress로 생성. 확인한 base_on과 변경 결과를 새 파일에 기록 |

5. 보완/검증과 결과 정리 후 awaiting_approval을 거쳐 사용자 승인으로 completed가 된다. 파일 유지 시에도 이번 재검토의 승인을 받으며 hold -> completed 직접 복원은 금지한다.
6. 아직 hold인 다음 단계도 각각 재검토한다. 선행 완료로 후속 결과/승인을 자동 복원하지 않으며 실행하지 못한 검사는 제약/미검증 범위를 남긴다.

기존 파일 유지 흐름:

```text
hold -> in_progress -> awaiting_approval -> completed
```

신규 파일 분기:

```text
현재 report: hold -> in_progress -> superseded
다음 번호 report: 생성 -> in_progress -> awaiting_approval -> completed
```

회귀 계기/대체 관계는 [report 기록](#report-작성과-인계), 재승인은 [승인 과정](#승인-과정-기록)을 따른다. 재검증은 [테스트 기준](#테스트-실행과-재검증), 남은 사항은 [미결정 이관](#미결정-사항과-제외-범위의-이관)과 [검증/QA 완료 구분](#검증-및-qa의-완료-구분)을 적용한다.

## 교차 검증의 연결 위치

수행 시점과 검토 범위는 [검토 대상과 수행 시점](#검토-대상과-수행-시점)을 확인하고, 해당하는 경우 아래 공통 절차를 따른다.

### 검토 대상과 수행 시점

- 코드 개발 산출물을 대상으로 교차 검증한다. 기본 파이프라인에 독립 단계를 추가하지 않는다.
- Codex가 작성한 산출물은 Claude가, Claude가 작성한 산출물은 Codex가 검토하는 방향으로 운영한다. 실제 사용 가능한 에이전트를 확인한다.
- 기본 시점과 범위는 [검증 단계](stages/verification.md#교차-검증), 필요 시 추가 검토는 [QA 단계](stages/qa.md#교차-검증)를 따른다.
- 코드가 요구사항과 설계에 맞는지 검토할 때는 필요한 범위에서 discussion report와 design report를 참고한다.
- 논의, 설계, 구현 단계마다 별도의 교차 검증을 수행할 의무는 없다. 각 단계의 체크리스트 상호 확인과 사용자 승인은 유지한다.
- 사용자가 요청하면 단계에 관계없이 그 시점의 산출물과 요청 범위를 추가 검토한다. 요청에 따른 검토와 기본 수행 시점을 구분한다.

### 수행 불가와 진행

- 다른 에이전트를 사용할 수 없는 등 교차 검증이 불가능하면 report에 미수행 사실/사유를 남기고 사용자 최종 승인으로 진행한다. 교차 검증 자체는 필수 완료 조건이 아니며 다른 체크리스트/승인 조건은 유지한다.
- 자동 호출 불가와 검토자 부재를 구분한다. 실제 검토가 없으면 리뷰 파일을 만들거나 완료로 표시하지 않고 자체 검토로 대체 기록하지 않는다. 리뷰 부재만으로 진행을 막지 않는다.

### 요청 전달과 검토자 역할

- [교차 검증 실행 안내](ai_agents/review-execution.md)에 따라 상대 CLI를 직접 호출한다. 모델과 추론 강도는 실행 안내에서 연결한 모델 선택 기준을 따른다. 직접 호출이 불가능하면 사용자가 전달할 요청문을 제공하며 자료/기준은 동일하게 유지한다. 검토자를 이용할 수 없으면 [미수행 절차](#수행-불가와-진행)를 따른다.
- 요청에는 대상 report 경로/검토 범위, 기준 선행 report와 코드/테스트/실행 근거 위치, 확인 기준/집중 사항과 리뷰 저장 경로를 포함한다.
- 검토자는 원본 report/코드를 수정하지 않고 리뷰만 작성한다. 대상 위치, 문제와 근거, 필요하면 개선 방향을 적는다. 미확인 사항을 구분하고 지적 없음도 실제 확인 범위에 한정한다.
- 호출 명령, 옵션, 작업 경로와 실행 근거의 전달 및 확인은 [실행 안내](ai_agents/review-execution.md#요청과-작업-경로)를 따른다. 지침에 명령이 있다는 사실만으로 실제 실행이나 검토 완료로 판단하지 않는다.

### 리뷰 파일과 원본 report

- 리뷰는 대상 report와 같은 회차에 `<단계명>-<report 번호>-review-<검토 번호>.md`로 저장한다. 예: verification-report-001.md의 첫 리뷰는 verification-001-review-001.md다. 검토 번호는 대상별 001부터 시작하며 재검증마다 증가한 새 파일을 만들고 이전 리뷰는 보존한다. 원본 작성자는 리뷰를 수정하지 않는다.
- 상단에는 검토자(에이전트와 실제 모델명/버전), 대상 report 전체 파일명을 적는다. 정확한 모델을 모르면 확인 불가로 적고 CLI 버전으로 대체하지 않는다. 업데이트 후 장애는 모델 정보/실패 기능과 현상/영향을 기록하되 확인 없이 버전을 원인으로 단정하지 않는다.
- 실행 대상과 근거는 리뷰 템플릿에 검토자가 작성한다. 전달받은 호출 정보와 검토자가 직접 확인한 결과를 구분하며, 기록 주체와 호출 종료 후 확인은 [실행 안내](ai_agents/review-execution.md#결과-확인과-기록)를 따른다. 본문은 검토 범위/기준, 결과, 미확인 사항과 종합 의견으로 구성한다.
- 원본 작성자는 별도 대응 파일 없이 report의 "보완 요청과 처리 결과"에 리뷰 링크, 지적별 의견/근거, 사용자 합의와 보완/재검증 결과를 남긴다. 사용자 판단/남은 사항은 해당 항목에 연결하며 기존 상태/번호/회귀 규칙을 유지한다.
- 리뷰는 단계 report, 단계 완료나 base_on의 선행 입력을 대신하지 않는다.

### 리뷰 의견 검토와 사용자 합의

1. 원본 작성 에이전트가 지적별로 명세/실제 코드/확인 가능한 근거를 대조한다.
2. 수용/반박/추가 확인 의견과 근거를 report에 기록하되 확정 결정과 구분한다. 다른 에이전트의 지적이라는 이유만으로 무조건 수용하거나 근거 없이 반박하지 않는다.
3. 사용자와 리뷰 원문 및 작성자 의견을 함께 보고 수정 여부/범위를 합의한다. 합의 전 원본을 수정하지 않는다.
4. 합의한 조치를 수행하고 report/근거를 갱신한다. 요구사항/설계 변경은 SDD와 회귀 절차를 따른다.
5. 필요한 재검증/후속 검토 후 사용자가 산출물, 리뷰와 지적 처리를 함께 확인하여 최종 승인한다. 교차 검증은 사용자 승인을 대체하지 않는다.

### 재검증 범위와 시점

| 지적 검토 후 처리 | 재검증 방향 |
| --- | --- |
| 코드/설계/테스트 기준/결론 수정 | 수정 부분과 영향받는 항목 재검증 |
| 근거로 반박하고 유지 | 사용자와 근거를 검토하여 재검증 여부 결정 |
| 오탈자/의미 불변 표현 정리 | 재검증 생략 가능 |
| 판단 근거 부족 | 근거 보완 후 여부 결정 |

- 지적을 논의할 때 재검증 여부/범위/이유를 합의하여 report에 기록한다. 합의한 보완 묶음과 영향 범위를 대상으로 하며 무관한 변경은 기존 명세 변경/회귀/재검증 규칙을 따른다.
- 보완 묶음과 report/근거 갱신 후 최종 사용자 승인 전에 재검증한다. 개별 수정마다 요청할 필요는 없다.
- 영향받은 체크 항목은 재확인하고 필요한 테스트도 재실행한다. 교차 검증이 이를 대신하지 않는다. 교차 재검증 불가는 [미수행 기록](#수행-불가와-진행)을 남기며 완료로 가장하지 않는다.

리뷰 작성 시 [공통 리뷰 템플릿](../assets/review_reports/review-template.md)을 대상 report의 회차에 복사한다. 원본 템플릿에 결과를 기록하지 않는다.

## 공통 규칙 위반 대응

1. 모든 필수 규칙의 위반 요청에 적용한다. 설명마다 적용 규칙/이유, 충돌 지점과 규칙에 따른 진행 방법을 제시하며 위반 작업은 실행하지 않는다.
2. 단순 질문/이해를 위한 확인과 위반 반복을 구분한다. 설명 후 같은 위반 요청을 반복할 때만 그 사안의 횟수로 세고 다른 사안과 합산하지 않는다.
3. 사안별 최대 3회 설명한 뒤에도 요청을 유지하면 해당 작업을 중단한다. 정상 규칙 변경 논의와 중단 요청은 위반이 아니다.

자연어 지침으로 운영하며 전용 스크립트/훅을 추가하지 않는다.
