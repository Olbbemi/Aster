# 작업 분할과 순차 묶음

설계의 뼈대에서 규모가 드러났을 때, 설계의 in_review 점검과 번들 진입/재개 때 읽는다.
번들은 같은 목적 아래 독립적으로 설계 또는 구현부터 QA까지 진행하는 범위다.
[스펙 단위](guidelines.md#스펙의-단위와-작업-범위)와 승인/회귀 절차를 함께 따른다.

## 뼈대 우선 진행

큰 설계는 책임/경계, 공개 계약, 핵심 데이터, 주요 흐름과 전체 성공 기준을 먼저 정한다.
이 뼈대로 번들 범위, 의존 관계와 검증/QA 준비 조건을 정한다.
현재 번들에 필요한 계약/흐름/검증과 필수 환경을 확정한 뒤 구현한다.
후속 번들의 내부 세부는 해당 번들의 설계에서 구체화한다.
현재 계약/안전성에 영향을 주는 필수 미결정을 후속 상세로 넘기지 않는다.

```text ascii-flow
             Shared design
                   |
                   v
        in_review: split assessment
                   |
                   v
                Approval
                   |
                   v
      Bundle entry and name approval
                   |
                   v
         Design or Implementation
                   |
                   v
           Verification -> QA
                            |
                            +-- Next bundle entry
                            `-- Overall completion
```

## 분할 판단과 방식 선택

번들 분할/추가와 경계 변경은 설계 단계에서 결정한다.
설계 중 사용자가 요청하거나 에이전트가 필요성을 발견하면 먼저 논의할 수 있다.
모든 설계는 [in_review 점검](stages/design.md#설계-점검과-승인-전이)에서 분할 필요성을 확인하고 근거를 남긴다.
공통 설계나 번들 상세 설계로 회귀한 경우에도 같은 절차를 적용한다.

사용자 요청이 없어도 다음 근거가 있으면 분할을 제안한다.

- 상세 논의가 커서 한 번에 필요한 결정을 정리하고 검토하기 어려움
- 구현/검증/QA의 작업량과 시나리오가 커서 단계 결과를 한 번에 판단하기 어려움
- 범위별 의존성, 환경이나 실행 준비 시점이 달라 순차 진행이 필요함
- 실패나 변경의 영향이 커서 독립된 결과와 재검증 범위를 나누는 것이 유효함

문서 길이, 파일 수나 테스트 수에 고정 한도를 두지 않는다.
단일 플로우를 유지할 때도 목적/계약과 검증/QA를 한 번에 판단할 수 있는 근거를 기록한다.
같은 목적과 뼈대를 공유하면 번들로 나누고, 이번 플로우 밖에서 다룰 작업은
[보류](deferred-work.md)로 구분한다.

현재 목적의 필수 실패 처리, 취소/정리와 검증은 이를 사용하는 범위에 포함한다.
필수 범위를 단순 작업량 때문에 넘기지 않는다.
마지막 번들에는 전체 연결과 변경 영향을 받는 회귀 확인을 포함한다.
부분 완료를 전체 기능의 사용 가능이나 전체 테스트 통과로 확대하지 않는다.

범위/완료 기준, 의존 관계와 조정된 설계/검증/QA 계획은 사용자와 합의한다.
목적/요구사항을 바꾸려면 [논의 회귀](guidelines.md#회귀-승인-시-상태-변경)를 적용한다.
분할 합의를 각 번들의 시작이나 단계 종료 승인으로 승계하지 않는다.
구현/검증/QA 중 설계 전제가 성립하지 않으면 회귀하며 그 자리에서 번들을 만들지 않는다.

## 공통 설계와 묶음 기록

기본 다섯 단계인 discussion/design/implementation/verification/qa를 사용하는 작업에 적용한다.
작업 디렉토리와 manifest의 stages를 유지하며 번들별 manifest 항목은 만들지 않는다.
기존 번호 형식의 작업은 [기존 기록 지침](legacy-records.md)을 따른다.

```text
daily-collection/
|-- discussion-report.md
|-- design-report.md
|-- 01-public-contracts/
|   |-- implementation-report.md
|   |-- verification-report.md
|   `-- qa-report.md
`-- 02-db-preparation/
    |-- design-report.md
    `-- implementation-report.md
```

이 구조는 실제 진행 후의 예다. 미시작 디렉토리/report는 만들지 않는다.
번들이 없으면 구현/검증/QA report도 작업 루트에 둔다.
공통 discussion/design은 뼈대와 전체 분할을 담당하고 번들 design은 필요한 상세를 정의한다.
공통 design 완료는 뼈대와 분할 결과의 승인이며 모든 번들의 상세 설계 완료를 뜻하지 않는다.
공통 정의는 참조하며 번들에서 복제하지 않는다.

### 작업 묶음표의 기록 형식

공통 design의 `단계 결과` 안에 H3 `작업 묶음표`와 아래 열을 둔다.
열 순서는 바꿀 수 있지만 각 열을 한 번만 사용한다.

| 열 | 내용 |
| --- | --- |
| 묶음 | 표 안에서 고유한 범위의 이름 |
| 범위/완료 기준 | 구현할 목적/계약, 필수 검증/QA와 부분 완료의 한계 |
| 의존/진입 | 선행 결과, 준비 조건과 시작 단계 |
| 설계 정본 | 사용할 공통/상세 설계와 후속 상세 논의 안건 |
| 디렉토리 | 실제 시작 후 승인한 디렉토리명. 시작 전에는 미시작 |
| 결과 참조 | 실제 생성한 같은 번들의 구현/검증/QA report 링크. 시작 전에는 미시작 |

```markdown
### 작업 묶음표

| 묶음 | 범위/완료 기준 | 의존/진입 | 설계 정본 | 디렉토리 | 결과 참조 |
| --- | --- | --- | --- | --- | --- |
| 공개 계약 | API와 오류 계약 확인 | 선행 없음, 구현부터 | 공통 설계의 공개 계약 | 미시작 | 미시작 |
```

예시는 실제 합의와 결과로 바꾸며 없는 파일의 링크나 빈 report를 만들지 않는다.
범위/완료 기준과 진입 조건의 타당성은 에이전트와 사용자가 판단한다.

### 묶음 report의 식별과 선행 연결

번들 디렉토리는 `01-public-contracts`처럼 순번과 목적을 드러내는 이름을 사용한다.
이름 부분은 소문자 영문자로 시작하며 소문자 영문자/숫자/하이픈을 사용한다.
번들 식별은 디렉토리가 담당하며 report에 bundle 필드를 새로 요구하지 않는다.
순번은 작업 내 추가 순서로 계속 증가하며 최소 두 자리, 99 다음은 100으로 확장한다.
기존 디렉토리와 기록된 번호를 확인하여 재사용/충돌을 피한다.
실제 수행 순서는 숫자만으로 결정하지 않고 의존 조건을 확인한다.
report 이름/개정은 [공통 규칙](guidelines.md#파일명과-생성-시점)을 따른다.

| report | base_on |
| --- | --- |
| 번들 design | 승인된 공통 design의 상대 경로. 공통 설계를 상세화하는 연결 |
| 번들 implementation | 같은 번들의 승인된 design. 별도 design이 없으면 승인된 공통 design |
| 번들 verification/qa | 같은 번들의 직전 단계 report |

base_on은 해당 report 위치 기준의 정확한 상대 경로다.
예를 들어 번들 design은 `../design-report-rev-001.md`를 참조할 수 있다.
사용한 공통 논의는 공통 design의 base_on을 따라 확인한다.
다른 번들의 QA는 본문의 의존 근거로 연결하며 base_on을 대신하지 않는다.

## 묶음 진입과 회귀

1. 공통 설계의 묶음표, 선행 번들의 결과와 기존 report를 대조한다.
   범위/완료 기준, 의존/환경, 받을 인계 항목과 선행 승인 근거를 확인한다.
2. 시작 단계를 정한다. 계약/흐름/검증이 미정이면 번들 설계부터 상세화하고,
   공통 design으로 충분하면 구현부터 시작한다.
3. 새 번들 시작 시 디렉토리명을 제안하고 이름과 시작의 사용자 승인을 받는다.
   기존 승인 범위는 재사용하고 모델 적용도 확인한다.
4. 첫 저장 시 승인한 디렉토리와 실제 시작 단계의 report를 만들고 공통 묶음표에 연결한다.
   미시작 번들 디렉토리나 후속 report는 미리 만들지 않는다.
5. 각 단계의 체크와 최종 승인을 수행하고 QA 후 다음 번들의 진입 조건을 대조한다.

회귀는 같은 범위의 앞선 단계로 돌아가는 절차이며 새 번들과 구분한다.
기존 범위의 수정은 같은 번들 안에서 [개정/hold 절차](guidelines.md#보완-복귀와-재검증)를 적용한다.
번들 상세가 공통 계약을 바꾸면 공통 설계로 회귀한다.

공통 논의/설계 회귀는 루트에 새 rev를 만들고 모든 번들의 영향을 대조한다.
영향이 있거나 불명확한 후속 결과는 hold로 두어 재검토한다.
영향이 없는 completed 결과는 당시 기준/결과/승인을 보존한다.
회귀를 기록한 report에 유지 근거를 남기고 새 공통 설계에서 연결한다.
공통 설계가 hold인 회귀 중간에도 이미 완료된 번들 design/implementation은
그 파일을 당시 완료의 과거 근거로 참조할 수 있다.
이 예외는 새 작업의 입력이나 같은 번들 내부 hold 연결에 적용하지 않는다.
과거 기준이 superseded여도 보존된 완료 결과의 참조를 새 파일로 일괄 변경하지 않는다.
새 진행의 입력은 유효한 completed 기준이어야 한다.

번들 구조를 한 번 적용한 작업은 공통 회귀 후에도 유지한다.
새 범위를 추가하기로 결정하면 계속 증가하는 순번으로 새 번들을 시작한다.
그 시점의 분할 판단이 추가 분할 불필요여도 루트에 구현/검증/QA를 섞지 않는다.
새 공통 묶음표에는 이전 번들과 유지한 결과/근거를 보존하고 새 범위를 추가한다.

## 전체 완료

번들 QA 완료는 해당 번들의 범위에만 적용한다.
모든 번들의 결과, 전체 연결/회귀 확인, [인계 처리](guidelines.md#확인-항목의-인계와-해소)와
[보류 정리](deferred-work.md#전체-완료-전-이동)를 대조하여 마지막 QA에 전체 완료 판단을 기록한다.
공통 설계에서는 그 결과를 참조한다.
미완료 번들, 미해소 인계나 정리하지 못한 deferred가 있으면 전체 완료를 선언하지 않는다.
