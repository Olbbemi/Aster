# 작업 분할과 순차 묶음

설계의 뼈대에서 규모가 드러났을 때, 최종 설계의 범위를 재평가할 때와 순차 묶음을 재개할 때 읽는다.
기존 [스펙 단위](guidelines.md#스펙의-단위와-작업-범위)와 승인/회귀 절차를 함께 따른다.

## 뼈대 우선 진행

큰 설계는 책임/경계, 공개 계약, 핵심 데이터, 주요 흐름과 전체 성공 기준을 먼저 정한다.
이 뼈대로 의존 관계와 검증/QA 준비 조건을 파악하여 분할 필요성을 판단한다.
모든 묶음의 내부 세부를 처음부터 확정하려고 논의를 늘리지 않는다.

```text ascii-flow
Scope and shared contracts
            |
            v
Split assessment and agreement
            |
            v
Current bundle design and readiness
            |
            v
Implement -> Verify -> User QA
            |
            +-- more bundles
            |      |
            |      v
            |   Entry check
            |      |
            |      +-- Design
            |      `-- Implementation
            |
            `-- last bundle
                   |
                   v
              Overall check
```

- 분할이 필요한 경우 뼈대에 영향을 주는 미결정 사항을 먼저 해결하고 묶음을 합의한다.
- 현재 묶음의 계약/흐름/검증과 필수 환경을 확정한 뒤 구현한다.
  - 후속 묶음의 상세가 미정이라는 이유만으로 준비된 현재 묶음을 대기시키지 않는다.
  - 현재 계약/안전성에 영향을 주는 미결정 사항을 후속 상세로 분류하여 구현을 시작하지 않는다.

## 분할 판단과 방식 선택

설계 종료 시에는 항상 구현부터 검증/QA까지 한 플로우에서 완료할 범위인지 재평가한다.
뼈대에서 이미 분할했다면 현재 범위와 의존/검증 계획이 여전히 적절한지 확인한다.

- 문서 길이나 테스트 수에 고정 한도를 두지 않고 독립된 목적, 환경/시나리오 차이와 재검증 영향을 살핀다.
- 분할하지 않는 경우도 근거를 남긴다.

| 방식 | 선택 기준 | 진행 |
| --- | --- | --- |
| 단일 플로우 유지 | 목적/계약과 검증/QA를 한 번에 판단 가능 | 기존 단계 순서 유지 |
| 신규 작업 주제로 분리 | 독립된 목적/요구사항/완료 기준으로 별도 논의와 승인 필요 | 새 주제에서 논의부터 진행. 이전 결과는 참고/이관 출처 |
| 같은 주제의 순차 묶음 | 공통 목적/요구사항/뼈대를 공유하며 순차적으로 완료할 수 있음 | 공통 설계와 묶음표를 기준으로 각 묶음의 설계 또는 구현부터 QA까지 진행 |

- 현재 목적의 필수 실패 처리, 취소/정리와 검증은 이를 사용하는 묶음에 포함한다.
  필수 범위를 단순히 작업량을 줄이려고 후속으로 넘기지 않는다.
- 마지막 묶음에는 전체 연결과 변경 영향을 받는 회귀 확인을 포함한다.
- 부분 완료를 전체 기능을 사용할 수 있다는 선언으로 확대하지 않는다.

분할 결과와 조정된 설계/검증/QA 계획은 사용자와 합의한다.

- 논의의 목적/요구사항/범위가 바뀌면 [논의 회귀](guidelines.md#회귀-승인-시-상태-변경)를 적용한다.
- 분할 승인을 새 논의나 각 묶음의 단계 종료/착수 승인으로 승계하지 않는다.

새 작업의 생성/이관은 [작업 생성](guidelines.md#작업-주제-생성과-manifest-갱신)과
[이전 작업 참조](guidelines.md#이전-작업-참조와-이관)를 따른다.
분할 합의만으로 미시작 작업/묶음의 report와 manifest 항목을 만들지 않는다.

## 공통 설계와 묶음 기록

같은 주제의 순차 묶음은 기존 작업 디렉토리와 manifest의 `stages`를 유지한다.

- 현재 기본 다섯 단계인 discussion/design/implementation/verification/qa 순서의 작업에 적용한다.
  다른 단계 구성을 사용하는 기존 작업은 이 방식으로 자동 전환하지 않는다.
- 기존 작업을 이 방식으로 바꾸려면 범위/승인 기록과 실제 결과를 확인하여 사용자와 합의한다.
  기존 report에 bundle을 자동 부여하거나 과거 승인을 다른 묶음으로 옮기지 않는다.

공통 discussion/design report는 뼈대와 전체 분할 기준을 담당한다.

- 공통 report에는 `bundle`을 생략한다.
- 공통 design의 완료는 뼈대와 분할 결과에 대한 승인이다.
  모든 묶음의 상세 설계가 완료되었다는 뜻은 아니다.

공통 design에 다음 정보를 갖춘 묶음표를 두고 묶음 report에서 참조한다.

| 필수 정보 | 기록 내용 |
| --- | --- |
| 묶음 | 같은 주제 안에서 고유하고 유지되는 식별자와 제목 |
| 범위/완료 기준 | 구현할 계약/목적, 필수 검증/QA와 부분 완료의 한계 |
| 의존/진입 | 선행 묶음 결과, 준비 조건과 시작 단계 |
| 설계 정본 | 공통 정의 및 필요한 묶음 상세의 링크 |
| 결과 참조 | 실제 생성한 구현/검증/QA report 링크. 미시작 파일은 생성 예정 코드 표기로만 기록 |

### 작업 묶음표의 기록 형식

공통 design의 `단계 결과` 안에 H3 `작업 묶음표`를 두고 아래 열의 표를 작성한다.

- 열 순서는 바꿀 수 있지만 각 열은 한 번만 사용한다.
- `묶음`에는 식별자만 적고 제목과 구분한다.

```markdown
### 작업 묶음표

| 묶음 | 제목 | 범위/완료 기준 | 의존/진입 | 설계 정본 | 결과 참조 |
| --- | --- | --- | --- | --- | --- |
| public-api | 공개 계약 | 공개 API와 오류 계약 확인 | 선행 묶음 없음, 구현부터 | [공통 설계](#공통-계약) | 미시작 |
```

- 범위와 준비 조건은 실제 합의한 내용을 기록하며 예시를 그대로 결과로 사용하지 않는다.
- `결과 참조`에는 같은 작업/묶음의 실제 구현/검증/QA report를 Markdown 링크로 연결한다.
  미시작 report의 링크나 빈 파일을 미리 만들지 않는다.

기존 비정형 표는 자동 변환하지 않으며 정형 대조가 불가능하면 검사기는 미판정으로 알린다.
실제 범위/완료 기준, 시작 조건과 결과의 의미는 에이전트와 사용자가 대조한다.

### 묶음 report의 식별과 선행 연결

묶음 report에는 `bundle: public-contracts`와 같이 문자열 식별자를 둔다.

- 소문자 영문/숫자로 시작하며 소문자 영문/숫자/하이픈만 사용한다.
- 이 식별자는 개발 작업 묶음을 구분하며 체크리스트의 B1/B2 같은 일괄 반영 기록과 별개다.
- 단일 플로우와 공통 report에는 이 필드를 추가하지 않는다.

report 경로/파일명과 필수 `status`/`base_on`은 유지한다.

- 번호는 묶음별로 나누지 않고 같은 단계의 전체 report에 걸쳐 증가한다.
- 현재 report와 개정 여부는 같은 단계/묶음별로 판단한다.
  다른 묶음의 완료 report를 다음 번호가 생겼다는 이유로 superseded로 바꾸지 않는다.

| 묶음의 시작 | 조건과 선행 report |
| --- | --- |
| 설계부터 | 묶음의 구현용 계약/흐름/검증이 미정. 묶음 design의 base_on은 승인된 공통 discussion |
| 구현부터 | 해당 묶음의 계약/흐름/검증과 환경이 공통 design에 확정됨. 묶음 implementation의 base_on은 그 공통 design |

- 같은 묶음 design이 있으면 현재 진행/승인용 implementation은 그 report를 선행으로 사용한다.
  hold/superseded implementation이 기존 공통 design을 참조했다면 그 과거 연결은 보존한다.
- verification/qa는 같은 묶음의 바로 앞 단계 report를 선행으로 사용한다.
- `base_on`은 기존처럼 같은 디렉토리의 전체 파일명이며 경로를 넣지 않는다.

사용한 공통 설계와 묶음 범위는 결과 첫 항목과 승인 대상에서 링크로 식별한다.

- 공통 설계를 재사용하면 해당 정본을 참조하고 복제하지 않는다.
- 묶음 상세가 공통 계약을 바꾸려면 공통 설계로 회귀하여 영향을 확인한다.

## 묶음 진입과 회귀

1. 공통 설계의 묶음표, 선행 묶음의 QA 결과와 해당 묶음의 기존 report를 대조한다.
2. 현재 범위/완료 기준, 의존/환경과 시작 단계에 필요한 선행 승인 근거를 확인한다.
   묶음표에 구현 시작으로 적혀 있어도 필요한 설계가 미정이면 설계부터 보완한다.
3. 묶음의 시작과 모델 적용을 사용자와 확인하고 실제 시작 단계의 report를 첫 저장 때 작성한다.
4. 해당 묶음의 각 단계에서 기존 체크리스트 확인과 최종 승인을 수행한다.
   QA까지 확인한 뒤 다음 묶음의 진입 조건을 대조한다.

회귀/hold/개정은 현재 묶음 안에서 적용하며 [기존 절차](guidelines.md#보완-복귀와-재검증)를 따른다.

- 공통 논의/설계를 바꾸면 영향받는 묶음의 결과와 재검증 범위를 함께 확인한다.
- 영향이 없는 완료 묶음은 근거를 확인하여 유지하고, 영향을 받는 결과를 유효한 것으로 사용하지 않는다.
- 과거 report/상세와 승인 근거를 보존한다.

## 전체 완료

묶음의 단계 승인과 QA 완료는 해당 묶음에만 적용한다.

- 합의한 모든 묶음의 결과, 전체 연결/회귀 확인과 남은 사항을 대조한 뒤 전체 완료를 판단한다.
- 전체 완료의 판단은 마지막 QA report에 기록하고 공통 설계에서는 그 결과를 참조한다.
- 미완료 묶음이 남았는데 공통 design이나 일부 QA의 completed로 전체 완료를 선언하지 않는다.
