# 작업 기록의 정형 검사

이 문서는 code-development 사용 중 에이전트가 실행할 정형 검사의 시점, 인자 출처와 결과 처리를 정의한다.

## 제공 상태

스킬의 `scripts/`에 실행 시점별 실행기 5개와 내부 공통 모듈 및 의존성 목록을 제공한다.
파일명, 인자, 검사 범위와 출력 계약은 [정형 검사 실행 계약](report-check-contract.md)을 따른다.
아래 명령은 호출 형식이며 파일의 존재만으로 검증 완료나 실제 검사 통과를 기록하지 않는다.

설치본에 실행기가 없거나 프로세스를 시작하지 못하면 자동 검사는 미실행으로 구분한다.
실행을 시작한 뒤 내부 모듈 로딩 등에 실패하면 실행 오류이며 검사 통과가 아니다.
지원 호출 환경과 정형 오류 출력은 [실행 계약](report-check-contract.md#실행-환경과-공통-경계)을 따른다.
기존 [기록 대조](guidelines.md#다음-단계-진입-시-선행-report-확인)와
[완료 확인 및 사용자 승인](guidelines.md#완료-확인과-사용자-승인)은 유지하며,
사람이나 에이전트의 대조를 자동 검사 통과로 기록하지 않는다.

## 실행 방식과 판정 경계

검사기는 code-development의 문서에 정의된 규칙 중
명시적 입력과 파일 상태만으로 참/거짓을 판정할 수 있는 항목을 대상으로 한다.
Camellia 플러그인에 포함하여 배포하고 스킬 사용 중 사용한다.
실행 시점별 독립 실행기 5개를 사용하며 목적 선택 옵션을 받는 통합 실행기로 합치지 않는다.
파싱과 중복 검사 로직은 내부 모듈로 공유할 수 있다.

에이전트가 아래 시점에 실행 조건과 인자를 확인하고 도구로 호출한다.
훅으로 실행을 강제하거나 주제 선택, 상태 변경과 승인을 자동 처리하지 않는다.
지침이 있다는 사실만으로 실행 누락이나 잘못된 호출을 완전히 차단한다고 보장하지 않는다.

내용의 타당성, 실제 사용자 승인과 작업 완료 여부는 기계 판정으로 대체하지 않는다.
스킬 소스의 개발용 테스트와 이 검사기의 역할은 구분한다.

## 실행 시점과 입력

모든 실행기는 확인한 프로젝트 루트와 작업 주제의 절대 경로를 공통 입력으로 받는다.
작업 경로는 [주제 선택](guidelines.md#주제-선택과-경로-확인)에서 확정한 이름으로
`<프로젝트 루트>/specs/<대주제>/<작업 주제>/`를 도출한다.
사용자에게 별도 report 저장 위치를 다시 선택하게 하지 않는다.

파일명/입출력과 세부 판정은 [실행 계약](report-check-contract.md)을 따른다.
실행 시에는 아래 절에서 해당 명령과 인자 출처를 함께 확인한다.

| 실행 단위 | 실행 시점 | 추가 입력과 확인 위치 | 검사 범위 |
| --- | --- | --- | --- |
| [첫 저장 전](#첫-저장-전) | 신규 작업의 이름/시작을 확정한 뒤 첫 저장 직전 | 없음. 선택한 주제의 예정 경로 사용 | 이름, 저장 계층과 경로 충돌. 아직 생성하지 않은 report/manifest는 요구하지 않음 |
| [재개/단계 진입 전](#재개와-단계-진입-전) | 기존 report를 작업 입력으로 사용하기 전. 번들 진입과 회귀 후 재개 포함 | 합의한 단계/범위와 사용할 선행 report. 번들이면 승인된 경로 또는 기존 bundle 식별자 | 작업 등록, 현재 개정, 상태와 선행 연결, 입력 report의 기록 형식 및 관련 번들/참조 |
| [저장 후 검토/승인 전](#저장-후-검토-및-승인-전) | 논의 묶음을 정리해 저장했거나 교차 검토/승인에 제출할 기록을 저장한 뒤 | 이번에 작성하거나 보완한 report 경로 | 저장한 기록과 연결 자료의 형식. 번들/도식/보류 자료는 해당할 때 검사 |
| [리뷰 수신 후](#리뷰-수신-후) | 요청한 리뷰를 받은 뒤 지적 처리의 입력으로 사용하기 전 | 검토 요청에서 지정한 원본 report 경로와 리뷰 경로 | 리뷰의 이름/배치/필수 기록, 대상 일치와 로컬 참조 |
| [전체 완료 전](#전체-완료-전) | 마지막 QA에서 보류 자료 정리를 마치고 전체 완료를 제출하기 전 | 전체 완료를 제출하기로 한 마지막 QA report 경로 | 현재 유효한 report와 모든 번들의 기록/연결 및 deferred 정리 상태 |

매 응답이나 파일 수정마다 실행하지 않는다.
표의 시점에 해당하는 실행기를 선택하고 [결과 재사용과 재실행](#결과-재사용과-재실행)을 적용한다.
아직 없는 후속 report나 미시작 번들을 검사 목적으로 생성하지 않는다.
승인 대기/작성 중 기록에 completed의 조건을 적용하거나 부분 QA에 전체 완료 검사를 적용하지 않는다.

## 실행 명령

명령의 `<...>`는 설명용 자리표시자이며 실제 인자가 아니다.
현재 로드한 스킬의 절대 경로와 [확보한 인자](#인자-확보와-실행-전-확인)로 모두 바꾼 뒤 사용한다.
인자값 안의 셸 특수문자는 실행 도구에 맞게 인용하며 아래 예시의 따옴표만으로 임의 문자열이 안전하다고 가정하지 않는다.
`--json`은 출력만 바꾸며 생략하면 텍스트 결과다. 실행 목적을 선택하는 옵션은 없다.

실행 환경은 [계약의 환경 조건](report-check-contract.md#실행-환경과-공통-경계)을 따른다.
패키지가 없으면 기존 프로젝트 Python 환경/권한으로
`python3 -m pip install -r "<스킬 경로>/scripts/requirements.txt"`를 수행할 수 있다.
검사기가 대신 설치하지 않으며 requirements.txt는 해당 스킬의 scripts 안에 포함된다.

### 첫 저장 전

사용자가 정한 대주제/작업명에서 예정 경로를 계산한다.
이름을 검사에 맞추려고 먼저 정규화/교체하지 않는다.

```bash
python3 -B "<스킬 경로>/scripts/check_task_start.py" \
  --project-root "<프로젝트 절대 경로>" \
  --topic-dir "<작업 주제 절대 경로>" --json
```

통과해도 파일은 생성되지 않는다. 실제 첫 저장은 기존 생성 절차를 따른다.
이미 작업이 있다는 결과이면 이름을 바꿔 재시도하지 말고 기존 작업과 요청을 대조한다.

### 재개와 단계 진입 전

stage는 진행하기로 합의한 단계, scope-dir는 공통/단일 작업이면 작업 루트,
현행 번들이면 합의한 번들 경로다.
base-report는 대화와 기록에서 사용할 것으로 확인한 선행 report다.
현재 report의 base_on과 다른 후보가 있으면 자동으로 최신 파일로 바꾸지 않는다.

```bash
python3 -B "<스킬 경로>/scripts/check_stage_entry.py" \
  --project-root "<프로젝트 절대 경로>" \
  --topic-dir "<작업 주제 절대 경로>" \
  --stage "<합의한 단계>" --scope-dir "<작업 또는 번들 절대 경로>" \
  --base-report "<확인한 선행 report 절대 경로>" --json
```

선행 단계 없는 공통 discussion만 `--base-report none`으로 실행한다.
기존 번호 형식의 묶음은 scope-dir를 작업 루트로 지정하고
`--bundle-id "<기록에서 확인한 bundle 식별자>"`를 추가한다.
신규 번들의 예정 경로는 허용하지만 선행 공통 자료를 가짜로 생성하지 않는다.
hold 재개 통과는 상태 변경/재승인을 대신하지 않는다.

### 저장 후 검토 및 승인 전

report는 방금 작성/보완한 현재 개정이다. 관련 상세/번들/보류 자료는 계약에 따라 수집한다.

```bash
python3 -B "<스킬 경로>/scripts/check_report_submission.py" \
  --project-root "<프로젝트 절대 경로>" \
  --topic-dir "<작업 주제 절대 경로>" \
  --report "<대상 report 절대 경로>" --json
```

작성 중/승인 대기/완료는 저장된 status에 따라 판정한다.
통과를 얻으려고 상태를 낮추거나 검사 대상에서 실패한 연결 자료를 빼지 않는다.

### 리뷰 수신 후

두 경로는 검토 요청에서 지정한 원본과 리뷰를 사용한다.
실제 리뷰가 없으면 미수행 절차를 따르며 다른 리뷰나 빈 파일을 대신 넣지 않는다.

```bash
python3 -B "<스킬 경로>/scripts/check_review_receipt.py" \
  --project-root "<프로젝트 절대 경로>" \
  --topic-dir "<작업 주제 절대 경로>" \
  --report "<검토 원본 report 절대 경로>" \
  --review "<요청한 리뷰 절대 경로>" --json
```

실패 결과는 원본 report에 남기고 검토자에게 필요한 확인/보완을 요청한다.
원본 작성자가 수신 리뷰를 고쳐 검사 통과를 만들지 않는다.

### 전체 완료 전

qa-report는 전체 완료를 제출하기로 한 마지막 QA의 정확한 경로를 사용한다.
앞선 번들의 부분 완료와 구분하기 위한 입력이며 파일 순번으로 정하지 않는다.

```bash
python3 -B "<스킬 경로>/scripts/check_task_completion.py" \
  --project-root "<프로젝트 절대 경로>" \
  --topic-dir "<작업 주제 절대 경로>" \
  --qa-report "<마지막 QA report 절대 경로>" --json
```

검사 범위는 선택 작업 전체이며 qa-report 하나로 축소되지 않는다.
마지막 QA의 제출 전 상태를 허용하므로 검사 통과를 위해 미리 completed로 바꾸지 않는다.
통과 후에도 실제 인계 해소, 보류 자료의 지정 위치 보존과 전체 완료 승인은 따로 확인한다.

## 인자 확보와 실행 전 확인

1. 현재 진행 위치를 위 표와 대조하여 필요한 실행기와 대상 범위를 식별한다.
   실행 파일은 현재 로드한 code-development 설치 경로에서 확인하며 Aster 개발 저장소나 다른 설치본을 임의로 사용하지 않는다.
   제공되지 않은 실행기는 [제공 상태](#제공-상태)에 따라 미실행으로 구분한다.
2. 사용자 지정, 유효한 현재 선택 정보와 실제로 읽은 기록에서 인자를 확보한다.
   확인한 프로젝트/주제와 기록 위치, 진입 단계/번들 또는 검토 요청의 대상을 대조한다.
   기존의 명확한 선택과 합의는 재사용하고 실행할 때마다 다시 질문하지 않는다.
3. 정해진 규칙으로 유일하게 도출되는 값만 계산한다.
   필수 값이 없거나 여러 후보가 있으면 확인 가능한 기록을 먼저 읽고,
   여전히 불명확한 값만 사용자에게 확인한다.
   cwd, 수정 시각, 파일 정렬 순서나 가장 큰 번들 번호로 대상/범위를 정하지 않는다.
4. 필수 입력이 확보되기 전에는 해당 실행을 보류한다.
   무응답을 선택으로 처리하거나 임의 기본값, 예시값, 가짜 report/번들을 넣지 않는다.
   오류를 피하거나 검사를 통과시키려고 대상, 단계, 범위나 실행기를 바꾸지 않는다.
5. 실제 실행기의 문서화된 인자와 위 입력을 대조하여 호출한다.
   경로는 하나의 인자로 전달되도록 인용하고 셸 확장으로 대상이 달라지지 않게 한다.
   입력 인자를 보고 실행기가 의미상 올바른 작업을 선택했음을 보증한다고 가정하지 않는다.

실행기에서도 필수 인자 누락, 잘못된 형식과 명시된 범위 불일치를 입력 오류로 반환해야 한다.
에이전트의 사전 확인과 실행기의 입력 검사를 서로 대신하지 않는다.

## 결과 확인과 기록

호출 후 실제 종료 여부, 종료 코드와 항목별 결과 및 검사한 범위를 확인한다.
호출 명령을 작성한 사실이나 오류 출력이 없다는 이유만으로 통과로 기록하지 않는다.

[출력 계약](report-check-contract.md#출력과-종료-코드)에 따라 0은 적용 검사 통과,
1은 규칙 위반, 2는 입력/실행/판정 오류다.
2에도 확인된 위반이 함께 있을 수 있으므로 항목별 결과를 읽는다.
`--help`의 0이나 프로세스를 시작하지 못한 상태는 검사 통과가 아니다.

- 규칙 충족/위반과 입력/읽기/실행 오류, 미실행을 구분한다.
  미적용 항목이나 확인하지 못한 범위를 통과에 포함하지 않는다.
- 실패 위치와 이유를 확인하고 기존 보완/회귀 권한에 따라 처리한다.
  미해결 위반이나 오류를 숨긴 채 정상 입력 또는 검사 완료의 근거로 사용하지 않는다.
  해결에 필요한 사용자 결정이나 권한이 없으면 해당 문제를 알리고 이에 의존하지 않는 작업만 진행한다.
- 검사 근거는 기존 report의 관련 결과/근거 항목에 명령과 인자, 대상 범위, 종료 결과와 남은 문제를 함께 남긴다.
  첫 저장 전 결과는 첫 report를 작성할 때 반영하고,
  리뷰 수신 결과는 원본 report의 보완 요청과 처리 결과에 기록한다. 수신한 리뷰는 원본 작성자가 수정하지 않는다.
  전체 완료 확인은 마지막 QA의 전체 완료 항목에 연결한다.
- 기록은 [기존 저장 시점](guidelines.md#report-저장-시점)에 모아서 반영한다.
  검사만을 위한 별도 report나 승인 절차를 만들지 않는다.
- 검사 후에도 내용의 타당성, 실제 승인과 전체 완료는 기존 단계 지침으로 판단한다.
  입력 부족이나 검사기 미제공을 자연어 대조로 대신했더라도 자동 검사 통과로 기록하지 않는다.

## 결과 재사용과 재실행

이전 결과의 실행기/규칙, 인자와 검사 범위 및 읽은 자료/참조가 현재 대상과 같고
변경되지 않았음을 확인할 수 있을 때만 해당 결과를 재사용한다.
다른 report/번들의 통과나 일부 검사 결과를 현재 전체 범위의 통과로 확대하지 않는다.

저장 후 보완, 참조 변경이나 회귀로 관련 자료가 달라졌으면 영향받는 실행기를 다시 수행한다.
변경 영향 또는 이전 결과의 적용 범위가 불명확하면 필요한 범위를 다시 검사한다.
검사 결과의 기록만 추가한 경우에는 검사 대상 규칙에 영향을 주는 변경인지 대조하며,
기록했다는 이유만으로 반복 실행하거나 모든 변경을 영향 없음으로 간주하지 않는다.
