# 작업 기록의 정형 검사

이 문서는 code-development 사용 중 report와 연결 자료를 검사할 때 읽는다.
스킬 소스 자체나 제품 코드의 테스트를 대신하지 않는다.
검사는 선택한 작업을 읽기만 하며 상태, 체크리스트와 파일을 변경하지 않는다.

## 실행 시점

- 저장한 결과를 최종 검토/승인에 제출하기 전에 실행한다.
- 재개하거나 다음 단계에서 기존 report를 입력으로 사용하기 전에 실행한다.
- 같은 파일 상태에 대한 검사 근거가 있고 변경이 없으면 재사용한다.
  매 응답이나 저장마다 반복하지 않는다.
- manifest, report 또는 연결 자료를 보완하면 영향받는 작업을 다시 확인한다.
  아래 역할 선택 기준에 따라 영향받는 검사만 실행하며 매 저장마다 전체 검사를 반복하지 않는다.
  검사 통과는 기존 [선행 report 대조](guidelines.md#다음-단계-진입-시-선행-report-확인)를 대신하지 않는다.

아직 작업 주제를 선택하지 않았거나 최초 report를 저장하기 전에는 실행하지 않는다.
검사를 위해 미시작 단계의 report나 디렉토리를 생성하지 않는다.

## 실행 환경과 명령

- Python 3.10 이상과 [requirements.txt](../scripts/requirements.txt)의 패키지를 사용한다.
  - 필요한 패키지가 없으면 프로젝트 Python 환경과 기존 권한 범위에서 준비한다.
  - 검사기는 패키지를 자동 설치하지 않는다.
- 입력은 UTF-8이며 BOM과 CRLF도 허용한다.

아래 `<스킬 경로>`는 현재 로드한 code-development의 실제 설치 경로이며,
`<작업 주제 경로>`는 선택한 프로젝트의 `specs/<대주제>/<작업 주제>/` 절대 경로다.
현재 작업 디렉토리에 의존하지 않도록 두 경로를 절대 경로로 전달한다.

```bash
python3 -m pip install -r <스킬 경로>/scripts/requirements.txt
python3 -B <스킬 경로>/scripts/check_reports.py <작업 주제 경로> --json
```

입력 폴더 상위의 `freight-manifest.md`에서 선택한 작업의 항목을 찾는다.

- [검사기](../scripts/check_reports.py)는 `--json`을 생략하면 텍스트로 출력한다.
- 결과는 표준 출력으로 제공하며 검사기가 별도 로그나 캐시를 저장하지 않는다.
- 네트워크와 Aster 개발 저장소를 실행 의존성으로 요구하지 않는다.

### 역할별 실행과 선택

전체 실행기 `check_reports.py`는 아래 5개 검사를 같은 입력 컨텍스트로 수행한다.
개별 실행기는 해당 역할의 실제 구현을 포함하며 서로의 검사를 대신 실행하지 않는다.
모든 파일은 이 스킬의 `scripts/` 안에 배포하고 Aster 공용 도구를 호출하지 않는다.

| 역할 | 개별 실행기 | 주요 검사 |
| --- | --- | --- |
| structure | [check_report_structure.py](../scripts/check_report_structure.py) | report 구조, 현재 개정과 선행 단계/상태/묶음 연결 |
| completion | [check_completion_records.py](../scripts/check_completion_records.py) | 완료 체크리스트, 검증/QA 완료 구분과 반영 기록 |
| bundles | [check_work_bundles.py](../scripts/check_work_bundles.py) | 공통 설계의 묶음표와 report 등록/결과 연결 |
| links | [check_report_links.py](../scripts/check_report_links.py) | 선택 manifest/현재 report/설계 상세의 링크와 절 |
| diagrams | [check_report_diagrams.py](../scripts/check_report_diagrams.py) | 현재 report/설계 상세의 ASCII 문자 형식 |

[report_common.py](../scripts/report_common.py)는 입력 파싱/현재 report 수집/출력을 공유하는 내부 모듈이며 직접 실행하지 않는다.

개별 실행기도 작업 선택과 현재 report 판정에 필요한 manifest, 파일명과 메타데이터를 읽고 형식/읽기 오류를 보고한다.
이 선행 입력 검사는 다른 역할의 본문 검사나 전체 구조 검사를 통과했다는 뜻이 아니다.
예를 들어 도식 실행기는 잘못된 YAML을 보고하지만 완료 체크나 묶음표, 링크 대상을 검사하지 않는다.

개별 명령도 작업 주제의 절대 경로와 출력 옵션을 사용한다.
파일명을 위 표에서 선택하며 검사별 추가 옵션은 없다.

```bash
python3 -B <스킬 경로>/scripts/check_report_structure.py <작업 주제 경로> --json
python3 -B <스킬 경로>/scripts/check_completion_records.py <작업 주제 경로> --json
python3 -B <스킬 경로>/scripts/check_work_bundles.py <작업 주제 경로> --json
python3 -B <스킬 경로>/scripts/check_report_links.py <작업 주제 경로> --json
python3 -B <스킬 경로>/scripts/check_report_diagrams.py <작업 주제 경로> --json
```

| 시점/변경 | 선택 기준 |
| --- | --- |
| 최종 검토/승인 제출 | 필요한 역할 전체의 유효한 결과 확보. 첫 종합 검사이거나 여러 역할의 결과가 없으면 전체 실행 |
| 재개/다음 단계의 선행 사용 | structure/completion과 해당하는 bundles를 확인. links/diagrams는 자료 변경 여부와 이전 결과를 대조 |
| 파일명, manifest 또는 report 메타데이터 변경 | structure. 작업 선택/단계/묶음/현재 report가 바뀌면 영향받는 나머지 역할도 실행 |
| 체크리스트, 완료 구분, 반영 기록 변경 | completion. 근거 링크/제목/경로도 바뀌면 links 추가 |
| 묶음표, 묶음 식별자, 결과 연결 변경 | bundles. 메타데이터/선행 연결 변경은 structure, 링크 변경은 links도 실행 |
| 링크, 제목, 파일 경로 변경 | links. report 식별/선행 입력도 바뀌면 structure와 영향받는 역할 추가 |
| 표시한 도식 변경 | diagrams. 실제 표시 확인은 별도로 유지 |
| 변경 영향이 여러 역할에 걸치거나 불명확 | 전체 실행 |

실행 단위는 선택 작업이며 개별 파일만 검사하는 옵션은 없다.
유효한 기존 결과는 역할별 입력/참조/현재 report가 바뀌지 않았을 때 재사용한다.
재사용과 변경 영향은 에이전트가 판단하며 실행기는 캐시, 변경 감지나 상태 수정을 하지 않는다.
개별 실행의 통과로 실행하지 않은 역할까지 통과했다고 기록하지 않는다.

## 기계적으로 확인하는 범위

### report 형식과 연결

정본은 [report 작성과 인계](guidelines.md#report-작성과-인계), [저장 구조](guidelines.md#저장-구조와-작업별-기록),
[번들 계약](work-bundles.md)과 [기존 기록 형식](legacy-records.md)이다.
작업 루트와 즉시 하위의 번호-이름 번들 디렉토리에서 report를 읽는다.
deferred와 설계 상세 디렉토리는 독립 단계 report로 수집하지 않는다.
번호 형식과 무번호/rev 형식의 혼재는 FAIL이며 검사 중 전환하거나 수정하지 않는다.

| 항목 | 판정 |
| --- | --- |
| 프론트매터 | YAML 매핑, 중복 키, 필수 status/base_on과 타입/허용값. in_review는 신규 design에만 허용 |
| 현재 report 영역 | H2 단계 결과, 인계 사항, 완료 체크리스트와 사용자 승인 각각의 존재/중복 |
| manifest | 선택 작업의 H2 디렉토리 링크, stages/reference_reports와 중복 없는 단계 목록 |
| 신규 파일명/개정 | 최초 무번호, rev-001부터 양수 최소 세 자리. 같은 디렉토리/단계의 최신 개정과 이전 superseded |
| 기존 파일명/개정 | 기존 단계/bundle별 현재/이전 번호와 superseded. 파일 번호는 001부터 양수 최소 세 자리 |
| 신규 base_on | report 위치 기준으로 작업 안의 실제 선행 report. 번들 design은 공통 design, 구현은 번들 또는 공통 design, 검증/QA는 같은 번들의 직전 단계 |
| 기존 base_on | 작업 루트 파일명. 기존 bundle 필드와 당시 선행 연결 계약 |
| 선행 상태 | 진행/점검/승인용 입력은 completed. hold/superseded의 과거 연결은 보존 |

- 단계 순서는 manifest stages를 따른다. 미시작 report 부재와 개정 번호 공백만으로 오류를 만들지 않는다.
- 번들은 기본 다섯 단계 작업에 적용하며 공통 논의/설계와 번들 산출물의 배치를 확인한다.
  번들 design이 있으면 현재 진행용 implementation은 같은 번들 design을 사용한다.
  다른 번들의 선행 입력은 허용하지 않는다.
- 신규 completed 결과는 공통 회귀에서 보존한 과거 completed/superseded 기준을 참조할 수 있다.
  완료된 번들 design/implementation의 과거 공통 design은 회귀 중 hold여도 참조를 보존한다.
  [유지 근거](work-bundles.md#묶음-진입과-회귀)는 사람이 대조하며 새 진행/승인 입력이나 같은 번들 내부 hold에는 적용하지 않는다.
  당시 공통 입력과 승인/결과 유지 근거는 에이전트가 대조한다.
  기계 검사가 이 근거의 타당성이나 전체 완료를 판정하지 않는다.
- 과거 superseded 본문에는 현재 템플릿을 소급 강제하지 않는다.
  추가 메타데이터의 의미와 실제 승인, in_review의 실제 수행/전이 이력은 판정하지 않는다.
- H3 이하 제목은 아래 검사에서 지정한 영역만 확인한다.
  코드/주석/인용 속 제목을 실제 영역으로 세지 않는다.

### 완료 상태와 체크리스트

현재 report의 H2 `완료 체크리스트` 안에 있는 실제 Markdown 체크 목록을 검사한다.

- `completed`이면 최소 한 항목이 있어야 하고 모든 항목이 `[x]` 또는 `[X]`여야 한다.
- 작성 중/승인 대기/hold의 미체크 항목이나 비어 있는 체크리스트는 이 검사만으로 실패하지 않는다.

상태와 관계없이 체크된 항목에는 비어 있지 않은 현재 `확인 근거:`가 필요하다.
항목의 직접 하위 목록 또는 이어지는 설명에서 읽으며 `이전 확인 기록`의 근거를 대신 사용하지 않는다.

- 코드 예시, 주석과 인용문은 실제 체크 항목/근거로 세지 않는다.
  주석만 남아 있는 확인 근거도 빈 값이다.
- 근거의 충분함, 누락된 업무별 완료 조건과 실제 승인은 판정하지 않는다.
- superseded report 본문에는 이 검사를 소급 적용하지 않는다.

### 검증/QA의 완료 구분

verification/qa report의 H2 `사용자 승인` 안 H3 `완료 구분`을 검사한다.
영역은 중복될 수 없으며, `awaiting_approval`/`completed`에는 정확히 하나와 실제 값이 필요하다.
첫 본문 줄은 단계 지침의 키워드 하나이고 다음 줄부터 선택 이유/근거를 적는다.
인라인 코드로 감싼 키워드도 허용한다.

- 신규 verification/qa: `all_passed` 또는 `handoff`.
- 기존 형식은 [기존 키워드](legacy-records.md#기존-형식-해석과-재개)를 유지한다.
- in_progress/hold는 미작성 또는 `미정`을 허용한다.
  값이 작성되어 있으면 같은 형식을 검사한다.

설명 없이 키워드만 있거나 허용 키워드를 여러 줄에 중복 기재하면 실패다.
주석/예시/인용으로 값이나 설명을 채울 수 없다.

설명이 실제 결과와 맞는지와 인계/보류와 현재 완료의 타당성, 인계의 실제 해소 여부는 기계 판정하지 않는다.

### 체크리스트 반영 기록

H2 `완료 체크리스트` 안 H3 `일괄 반영 기록`의 표 또는 기존 목록 형식을 검사한다.

- 표의 열은 `묶음`, `대상 항목`, `반영 시각`이며 열 순서는 자유지만 중복은 금지한다.
- 식별자는 `B1`처럼 B 뒤에 0으로 시작하지 않는 양수를 붙이며 같은 report에서 중복될 수 없다.
- 각 행의 대상 항목은 비어 있을 수 없다.
- 반영 시각은 `YYYY-MM-DD HH:mm:ss (KST)` 형식과 실제 달력/시각 범위를 확인한다.
  현재 시각과 비교하거나 실제 조회/승인이 있었는지는 판정하지 않는다.

기존 목록 형식은 `- B1: 대상 항목` 아래 `- 반영 시각: 값`이며 문장 끝 마침표도 허용한다.
목록과 표가 함께 있으면 식별자 중복을 두 형식 전체에서 확인한다.

체크된 항목이 있으면 반영 기록이 필요하지만, 기존 형식의 항목별 `확인 완료 시각:`은 허용한다.

- 기존 형식의 체크 항목 모두에 유효한 시각이 있으면 일괄 반영 표가 없어도 된다.
- 혼합 형식에서는 기존 시각을 유지하면서 새 확인 결과의 표를 검사한다.
- 내용이 없는 예시 주석만으로 기록을 채울 수 없다.

축약된 대상 이름과 체크 항목의 의미 대응, 누락된 개별 반영 이력은 본문 대조로 확인한다.

### 작업 묶음표와 report의 일치

[묶음표 형식](work-bundles.md#작업-묶음표의-기록-형식)에 따라 현재 공통 design의 표를 읽는다.
번들 디렉토리/report가 있거나 해당 영역을 작성했다면 다음을 검사한다.

- 필수 열/빈 값과 묶음 이름의 중복. 기존 표는 bundle 식별자 형식도 확인
- 신규 번들의 양수 순번/최소 두 자리 형식과 번호 중복, 디렉토리의 실제 존재/중복
- 시작한 디렉토리와 현재 번들 report가 표에 등록되어 있는지
- 결과 참조의 실제 Markdown 링크가 같은 작업/묶음의 구현/검증/QA report인지

검사 결과와 예외는 다음과 같이 구분한다.

- 디렉토리 열의 `미시작`과 아직 없는 후속 report는 허용하며 결과 링크 생성을 강제하지 않는다.
- 과거 superseded report의 묶음 등록은 현재 표에 소급 요구하지 않는다.
- 기존 비정형 표나 현재 공통 design의 부재로 표를 읽을 수 없으면 `UNCHECKED`로 알린다.
- 명시한 정형 영역의 중복/잘못된 표, 미등록 식별자와 잘못된 결과 연결은 `FAIL`이다.

범위, 분할의 타당성, 의존/진입 조건의 충족과 전체 완료는 판정하지 않는다.

### 로컬 링크

선택 manifest 항목, 현재 report와 현재 design report와 같은 위치의 report stem 상세 디렉토리를 검사한다.

- 다른 작업이나 과거 report는 링크 대상/절 확인에 필요한 만큼 읽으며 재귀 검사하지 않는다.
- 하위 심볼릭 링크 디렉토리는 순회하지 않고 미판정으로 알린다.

CommonMark 파서가 인식하는 링크와 이미지의 로컬 대상을 해당 문서 위치 기준으로 해석한다.

- `/`로 시작하는 로컬 경로는 파일시스템 절대 경로이며 저장소 뷰어의 루트 경로를 추정하지 않는다.
- HTML의 href/src 속성은 검사하지 않는다.
- 참조형 링크도 포함하며 코드 예시, 주석과 프론트매터 속 경로는 추출하지 않는다.
- 외부 URL/별도 URI는 SKIP이며 실제 접근을 확인한 것이 아니다.
- 쿼리의 동적 의미와 자연어로 쓴 파일 경로는 판정하지 않는다.
- 실제 링크로 작성한 아직 없는 대상은 누락으로 보고하므로 생성 예정 경로는 코드 표기로 구분한다.

Markdown 절은 제목의 텍스트/인라인 코드/이미지 대체 텍스트를 기준으로 판정한다.

- 앞뒤 공백을 제거하고 소문자로 바꾸며 ASCII 공백을 `-`로 치환한다.
- 문자/결합문자/숫자와 `-`, `_`를 유지하고 다른 문자를 제거한다.
- 동일 이름은 문서 순서대로 `-1`, `-2` 등을 붙인다.
- HTML id/a name도 인정한다.
- 코드 예시/주석의 제목과 앵커는 제외한다.

일반 연결 문서와 상세 파일은 첫 `---`부터 닫는 구분자 사이가 유효한 YAML 매핑일 때만 프론트매터로 제외한다.
그 외는 일반 Markdown으로 읽는다.
report의 필수 프론트매터 검사는 별도로 유지한다.

URL 인코딩은 한 번 해제한다.

- 잘못된 인코딩과 NUL은 실패다.
- 대상 문서의 UTF-8 디코딩 실패는 링크 문법 위반이 아닌 읽기 오류다.
- 비Markdown 파일/디렉토리의 절은 미판정으로 표시한다.

이 정책은 모든 뷰어의 앵커 생성 방식을 보증하지 않는다.

### ASCII 도식의 형식 보조

[설계 도식 기준](design-artifacts.md#ascii-도식의-작성과-표시-확인)에 따라
`text ascii-flow`로 표시한 fenced code block만 대상으로 한다.
일반 코드와 기존의 표시 없는 도식을 자동으로 추정하거나 변환하지 않는다.

- CommonMark 파서가 도식의 닫는 구분자로 인식한 줄이 있는지 확인한다.
  과도한 들여쓰기나 인용 기호 등으로 본문에 남은 구분자 모양의 줄은 닫는 구분자로 세지 않는다.
- 탭 및 제어문자, Unicode 박스/블록/기하 도형(U+2500-25FF)을 확인한다.
- 이름에 ARROW가 있는 비ASCII 기호, en/em dash(U+2013/U+2014)와 전각 `+ - | < >`도 확인한다.

한글 설명 자체를 금지하지 않는다.

결과에는 검사한 도식 수를 표시한다.
0개라는 결과가 모든 흐름을 확인했다는 뜻은 아니다.
문자 형식 통과는 연결선의 정렬, 실제 글꼴/뷰어에서의 표시와 가독성 통과가 아니다.

## 결과와 후속 처리

결과에는 범위, 읽은 파일, 항목별 상태/식별자/위치와 이유를 포함한다.

- JSON의 `groups`에 요청한 실행 역할을 표시한다.
  입력 오류로 중단되면 해당 역할의 검사 완료를 뜻하지 않는다.
- 읽은 파일은 실제 경로 기준으로 중복을 제거하고 과거 본문 검사에서 제외한 report도 나열한다.
- 링크의 줄 번호는 링크가 포함된 Markdown 블록의 시작 위치다.

| 종료 코드 | 의미 |
| --- | --- |
| 0 | 적용한 정형 검사 통과 |
| 1 | 형식 또는 연결 위반 발견 |
| 2 | 입력/의존성/읽기 오류 또는 미판정. FAIL이 함께 있으면 그 항목도 확인 |

실패/미판정 항목의 위치와 이유를 확인하고 기존 보완/회귀 규칙에 따라 처리한다.

- 같은 종료 코드 2라도 ERROR와 UNCHECKED는 항목별 상태와 이유로 구분한다.
- 미판정 절 링크를 지워 통과를 만들지 않으며 필요한 수동 대조 결과는 별도로 기록한다.
  수동 대조를 하더라도 검사기 실행 통과로 기록하지 않는다.
- 입력이나 의존성이 부족하여 실행하지 못했으면 그 사실과 필요한 준비를 알린다.

기존 [검사 결과 구분](guidelines.md#검사-결과-구분)과 승인 절차를 유지한다.

통과만으로 사용자 승인, 단계 완료, 설계 타당성, 분할 필요성이나 도식 표시 확인을 판정하지 않는다.
검사기가 해당 판단을 강제하는 훅이나 상태 변경기를 추가하지 않는다.
