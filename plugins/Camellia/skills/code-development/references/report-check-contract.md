# 정형 검사 실행 계약

5개 실행기의 인자, 대상 수집, 판정과 결과 형식의 정본이다.
검사기 구현 및 판정 오류 조사에 사용하며 호출 시점과 인자 확보는 [실행 안내](report-checks.md)를 따른다.
계약 버전은 `1`이다.
검사 결과는 실제 호출 후에만 기록한다.

## 실행 환경과 공통 경계

- 구현 대상은 Python 3.10 이상이다.
  YAML은 PyYAML `>=6.0,<7`, Markdown은 markdown-it-py `>=3.0,<4`를 사용한다.
  의존성은 스킬의 `scripts/requirements.txt`에 선언하며 설치된 패키지 버전은 결과에 포함한다.
  패키지 자동 설치, 네트워크 접근, Git/상대 AI CLI 호출은 하지 않는다.
- 5개 실행기와 내부 모듈 및 의존성 목록은 해당 스킬의 `scripts/` 안에 배포한다.
  각 실행기가 담당 검사를 직접 조합하며 다른 실행기를 서브프로세스로 호출하지 않는다.
  공통 모듈 분리는 구현 재량이며 통합 실행기나 목적 선택 옵션은 만들지 않는다.
- 입력은 UTF-8이며 BOM과 CRLF를 허용한다.
  report/manifest/연결 자료를 읽기만 하며 생성, 수정, 삭제, 상태 전환과 자동 보완을 하지 않는다.
  명령은 `python3 -B`로 호출하고 직접 호출 시에도 바이트코드 캐시를 남기지 않게 한다.
  실행 파일의 경로를 지정하며 호출 cwd나 `PYTHONPATH`로 필수 내부 모듈의 누락을 보충하지 않는다.
  `-I`, `-P` 또는 `PYTHONSAFEPATH`로 모듈 검색 경로를 제한한 호출의 지원은 이 계약에 포함하지 않는다.
  개발용 검사기의 격리 모드 호출 계약과 구분한다.
- 같은 계약, 패키지 버전, 인자 및 읽은 파일/디렉토리 상태이면 같은 판정을 반환한다.
  현재 시각, 수정 시각, 파일 열거 순서나 자연어 모델 응답을 판정에 사용하지 않는다.
  동시 변경을 완전히 차단하는 잠금이나 이력 검증은 제공하지 않는다.

## 실행 파일과 인자

모든 실행기에 `--project-root PATH`, `--topic-dir PATH`가 필수다.
`PATH`는 절대 경로이며 topic-dir는 지정 프로젝트의 `specs/<대주제>/<작업 주제>`다.
새 주제의 두 이름은 빈 값, `.`/`..`, `/` 또는 `\`를 포함하지 않는 단일 디렉토리명이다.
프로젝트 루트는 존재하는 디렉토리여야 한다.
작업 경로의 문자열 계층과 실경로의 프로젝트 내부 포함 여부를 모두 확인한다.
미생성 경로는 가장 가까운 기존 부모의 실경로와 나머지 이름으로 검사한다.
공통 인자의 절대 경로/계층/범위 문법 위반은 입력 오류다.
첫 저장 검사에서 확인한 일반 파일 충돌이나 기존 작업 등록은 C1의 거짓 결과로 구분한다.

| 파일명 | 추가 필수 인자 | 선택 인자 |
| --- | --- | --- |
| `check_task_start.py` | 없음 | 없음 |
| `check_stage_entry.py` | `--stage STAGE`, `--scope-dir PATH`, `--base-report PATH_OR_NONE` | 기존 번호 형식의 묶음이면 `--bundle-id ID` |
| `check_report_submission.py` | `--report PATH` | 없음 |
| `check_review_receipt.py` | `--report PATH`, `--review PATH` | 없음 |
| `check_task_completion.py` | `--qa-report PATH` | 없음 |

공통으로 `--json`과 `--help`만 추가 지원한다.
`--json`은 출력 형식만 바꾸며 검사 범위/판정에는 영향을 주지 않는다.
인자 축약, 알 수 없는 옵션과 같은 옵션의 중복은 입력 오류다.
값을 받는 옵션은 같은 값을 반복해도 거부하며, 값 없는 `--json`과 `--help`의 반복도 거부한다.
`--help`만 요청한 경우 필수 인자 없이 사용법을 표시하고 0으로 종료하며 검사를 수행했다고 기록하지 않는다.

- STAGE는 `discussion`, `design`, `implementation`, `verification`, `qa` 중 하나이며 manifest의 stages에 있어야 한다.
- scope-dir는 공통/단일 범위이면 topic-dir와 같고, 현행 번들이면 그 바로 아래 번들 경로다.
  기존 번호 형식은 scope-dir를 topic-dir로 주고 묶음일 때만 bundle-id를 전달한다.
  현행 형식에 bundle-id를 주거나 기존 형식에 번들 디렉토리를 주면 입력 오류다.
- base-report는 사용자/기록으로 확인한 선행 report의 절대 경로다.
  선행 입력 없는 공통 discussion에만 문자열 `none`을 사용한다.
  후보가 여러 개이거나 회귀 중이면 에이전트가 사용할 입력을 확인하며 실행기는 대체 파일을 선택하지 않는다.
- report/review/qa-report는 존재하는 일반 파일이어야 한다.
  report와 qa-report는 같은 작업의 단계 report이고 review는 지정 report와 같은 디렉토리의 리뷰다.
  인자로 지정한 파일 부재는 입력 오류이며 문서 안에서 참조한 필수 대상의 부재는 규칙 위반이다.
- 마지막 QA는 인자로 명시한다. 가장 큰 번들 순번/파일 시각으로 선택하지 않는다.
  qa-report가 가리키는 현재 QA의 형식적 조건만 검사하며 마지막 QA라는 사용자 판단의 타당성은 검사하지 않는다.
- 인자를 임의 기본값으로 채우지 않는다.
  형식 오류, 경로/범위 모순과 필수 값 누락을 조용히 수정하지 않는다.

## 대상 수집과 읽기

선택한 작업만 검사한다. 다른 작업은 명시적인 링크 대상 확인에 필요한 만큼만 읽는다.
주제/단계/report를 자동 선택하거나 오래된 자료의 본문을 현재 템플릿에 맞춰 다시 검사하지 않는다.

1. 첫 저장 전 검사 이외에는 topic-dir의 부모에 있는 `freight-manifest.md`에서
   H2 제목 안의 디렉토리 링크로 선택한 작업에 해당하는 항목을 정확히 하나 찾는다.
   제목 링크의 목적지는 manifest 기준으로 해석하며 절 없는 작업 디렉토리의 실경로와 대조한다.
   같은 작업을 가리키는 제목이 없거나 여러 H2에 있으면 C2 위반과 작업 선택 오류를 함께 반환한다.
   H2 본문의 reference_reports나 설명에 있는 링크는 작업 식별과 중복 등록 판단에 사용하지 않는다.
   다른 작업 항목의 본문은 재귀 검사하지 않는다.
2. 작업 루트와 바로 아래 번들 디렉토리에서 단계 report의 파일명과 메타데이터를 수집한다.
   `deferred/`, 설계 상세 디렉토리와 리뷰 파일은 단계 report로 세지 않는다.
   지원 stage 이름 뒤에 `-report`가 오는 `.md` 파일을 단계 report 후보로 수집한다.
   그중 `-review-`가 들어간 파일은 리뷰 후보로 분리한다.
   수집된 후보의 파일명이 해당 형식에 맞지 않으면 무시하지 않고 위반을 보고한다.
3. 현행 형식은 디렉토리/단계별로 가장 큰 rev를 현재 report로 식별한다.
   rev가 없으면 무번호 report가 현재다.
   기존 형식은 단계/bundle별 가장 큰 번호를 사용한다.
   이 계산은 현재 파일 식별이며 작업/선행 입력의 승인이나 선택을 대신하지 않는다.
4. 각 실행기의 검사 범위에 포함된 현재 report 본문, 그 report stem의 설계 상세,
   해당하는 리뷰/보류 기록과 로컬 링크 대상을 읽는다.
   과거 report는 개정/상태/선행 연결과 명시된 링크 대상의 존재/절 확인에 필요한 만큼만 읽는다.

번들 디렉토리 후보는 작업 루트 바로 아래에서 십진 숫자와 `-`로 시작하는 이름,
공통 묶음표에서 명시한 디렉토리 및 직접 단계 report 후보를 포함한 디렉토리의 합집합이다.
deferred와 실제 report stem의 상세 디렉토리는 여기서 제외한다.
후보를 수집한 뒤 C10의 이름/배치 규칙을 판정하며 유효한 이름만 먼저 골라 위반을 누락하지 않는다.

필수 디렉토리 열거/파일 읽기 실패, UTF-8 디코딩 실패와 누락된 파서 의존성은 실행 오류다.
첫 저장 전만 topic-dir의 부재를 허용하며 나머지는 존재하는 작업 디렉토리를 요구한다.
재개 검사에서 부재를 허용하는 경로는 새 단계 report와 신규 번들 scope-dir에 한정한다.
검사할 디렉토리의 심볼릭 링크를 재귀 순회하지 않는다.
필수 범위가 그 경로에만 있어 확인하지 못하면 오류로 보고하며 빈 범위로 통과시키지 않는다.
명시한 파일 링크는 실경로를 확인하되 base_on의 작업 내부 제한과 일반 자료 링크의 범위를 구분한다.
일반 자료 링크는 프로젝트 밖의 명시적 로컬 근거도 허용하며 존재/절 확인 외에는 순회하지 않는다.

## Markdown과 YAML 해석

- Markdown은 CommonMark 블록/인라인 해석에 표 확장을 적용한다.
  실제 제목/목록/링크를 파싱하고 코드 예시, HTML 주석과 인용문 속 항목을 실제 기록으로 세지 않는다.
  검사에 사용하는 고정 제목은 인라인 텍스트를 풀고 앞뒤 공백을 제거한 값으로 비교한다.
  필수 고정 영역은 지정된 부모 아래 정확히 하나여야 한다. 작업별 추가 제목은 허용한다.
- 본문 값 존재 검사는 공백과 주석만 있는 경우 거짓이다.
  빈 코드 구분자만으로 값을 채울 수 없다. 비어 있지 않은 실제 코드/표/링크는 내용으로 인정한다.
  `없음`, `해당 없음`, `미정`의 적절성은 키워드 계약에서 정한 경우 외에는 의미 판정하지 않는다.
- 단계 report는 파일 첫머리의 `---`로 시작하고 별도 줄의 `---`로 닫는 YAML 프론트매터를 요구한다.
  매핑이 아니거나 중복 키/유효하지 않은 YAML이면 규칙 위반이다.
  파싱할 수 없어 수행하지 못한 종속 검사는 별도로 오류를 반환하며 통과로 처리하지 않는다.
- 일반 연결 문서는 첫 블록이 유효한 YAML 매핑이면 그 블록만 프론트매터로 제외한다.
  그 외는 일반 Markdown으로 읽으며 단계 report의 메타데이터 규칙을 강제하지 않는다.
- YAML은 안전한 로더로 읽고 사용자 태그를 실행하지 않는다.
  status는 문자열, base_on은 null 또는 문자열이다. 불리언/숫자를 문자열로 자동 보정하지 않는다.

## 판정 규칙

아래 ID는 검사 범주다. 세부 결과 ID는 `C번호.조건명`으로 구분하여 동일 규칙에 항상 같은 ID를 사용한다.
규칙의 의미는 연결된 지침, 기계적으로 해석하는 형식/범위는 이 계약을 정본으로 한다.

### C1-C5: 작업과 report 연결

| ID | 참인 조건 | 적용 및 예외 |
| --- | --- | --- |
| C1 | 이름/저장 계층이 입력 계약에 맞고 기존 경로 구성 요소가 디렉토리이며 일반 파일 충돌이 없음 | 첫 저장 전의 미생성 topic/manifest/report는 정상. 이미 등록되거나 report가 있는 작업이면 신규 첫 저장의 대상 불일치로 보고 |
| C2 | 선택 manifest H2의 작업 링크가 정확하고 stages와 reference_reports가 각각 한 번 존재함 | stages는 비어 있지 않은 중복 없는 지원 단계 문자열 목록. reference_reports는 `없음` 또는 Markdown 링크 목록. 기존 stages를 기본 5단계로 변경하지 않음 |
| C3 | 파일명이 해당 형식이고 현재 개정 이전의 report가 superseded이며 신구 형식이 섞이지 않음 | 현행 `<stage>-report.md`, `<stage>-report-rev-N.md`, 기존 `<stage>-report-N.md`. N은 001부터 최소 세 자리의 양수 십진수. 1000 이상 허용. 번호 공백만으로 실패하지 않음 |
| C4 | status/base_on이 필수 타입/허용값에 맞고 명시된 금지 필드가 없음 | status는 in_progress/in_review/awaiting_approval/completed/hold/superseded. 현행 in_review는 design에만 허용. revision/previous/once/diff 및 별도 완료 구분 필드는 금지. 그 밖의 임의 추가 필드 전체를 금지하지 않음 |
| C5 | base_on이 실제 선행 단계/report에 연결되고 경로/단계/범위/상태 조건이 맞음 | 아래 선행 계약 및 보존 예외 적용. 진행 여부나 실제 승인 내용은 판단하지 않음 |

C2의 stages는 manifest 항목의 `- stages: [...]`, reference_reports는
`- reference_reports: 없음` 또는 그 아래 링크 목록으로 읽는다.
stage 순서는 해당 목록을 사용한다. 각 단계 report가 stages에 없는 단계를 사용하면 위반이다.
알 수 없는 stage는 현재 검사기가 지원하지 않는 입력으로 보고하며 기본 목록으로 대체하지 않는다.
reference_reports는 참고자료이며 작업 식별, base_on이나 승인 근거를 대신하지 않는다.
첫 저장 전의 기존 등록 확인에도 H2 제목 링크만 사용한다.
선택 항목 본문의 링크는 C11의 대상이며 작업 식별에서 제외했다고 참조 검사까지 제외하지 않는다.

C3의 번호는 `001`처럼 세 자리로 채우고 네 자리 이상에서는 불필요한 선행 0을 허용하지 않는다.
동일 숫자를 다른 표기로 중복 사용하면 위반이다.
신구 형식 혼재는 선택 작업 전체에서 확인한다.
과거 파일의 삭제/덮어쓰기 및 생성 당시의 번호 순서는 현재 파일만으로 검사하지 않는다.

C4에서 금지한 별도 완료 구분 필드의 기계 검사 이름은 `completion_type`으로 한정한다.
다른 이름의 추가 필드가 사실상 같은 의미인지 추정하지 않는다.
기존 bundle 식별자는 `[a-z0-9][a-z0-9-]*`를 사용하며 공통 report에서는 생략한다.
현행 형식은 디렉토리로 범위를 식별하며 bundle 필드를 필수로 요구하지 않는다.

C5의 base_on은 report 위치 기준의 상대 경로 하나이며 URL/쿼리/절 및 작업 밖 경로를 허용하지 않는다.
일반 로컬 링크와 달리 URL 디코딩하지 않고 실제 파일 경로로 해석한다.
선행 없는 공통 discussion은 null이고, 단일 플로우는 stages의 직전 단계다.
현행 번들 design은 공통 design, implementation은 같은 번들의 design 또는 별도 design이 없으면 공통 design,
verification/qa는 같은 번들의 직전 단계다.
기존 묶음 design은 공통 discussion이며 나머지는 [기존 계약](legacy-records.md)을 따른다.

진행/승인 대기 report의 선행 입력은 completed여야 한다.
hold/superseded의 당시 연결은 현재 진행용 상태 조건을 소급하지 않는다.
completed 번들이 과거 superseded 공통 입력을 보존하는 경우와,
completed 번들 design/implementation이 공통 회귀 중 hold 공통 design을 참조하는 경우는 보존 예외다.
예외의 연결/상태 조건만 확인하고 유지 근거의 타당성은 검사하지 않는다.
새 진입의 명시적 base-report에는 이 예외를 적용하지 않는다.

### C6-C9: 본문과 확인 기록

- C6: 현재 report의 H2 `단계 결과`, `인계 사항`, `완료 체크리스트`, `사용자 승인`을 각각 확인한다.
  사용자 승인 아래 H3 `사용자 판단`, `보완 요청과 처리 결과`, `남은 사항과 인계 조건`을 확인한다.
  다른 단계별 상세 제목 전체를 고정 필수 목록으로 만들지 않는다.
- C7: 완료 체크리스트 안의 실제 체크 항목만 읽는다.
  completed에는 최소 한 항목이 있고 모두 `[x]` 또는 `[X]`여야 한다.
  다른 상태의 미체크 항목은 허용한다.
  체크된 각 항목의 직접 하위 목록/이어지는 설명에 비어 있지 않은 `확인 근거:`가 있어야 한다.
  `이전 확인 기록` 아래의 근거는 현재 근거로 세지 않는다.
- C8: 체크된 항목이 있으면 H3 `일괄 반영 기록`의 기록이 필요하다.
  표의 필수 열은 `묶음`, `대상 항목`, `반영 시각`이며 순서는 자유지만 중복은 금지한다.
  B 뒤에 양수를 붙인 식별자, 비어 있지 않은 대상 항목과 유효한 KST 시각을 요구한다.
  식별자는 report 전체의 반영 기록에서 중복될 수 없다.
  과거 목록형 `- B1: 대상` 아래 `- 반영 시각: 값`도 같은 규칙으로 읽는다.
  기존 항목별 `확인 완료 시각:`을 가진 체크 항목은 해당 형식을 보존하며 나머지는 묶음 기록을 요구한다.
  `이전 확인 기록`의 명시적 `반영 기록: B1`은 존재하는 묶음을 가리켜야 한다.
  자연어로 축약한 대상 이름과 체크 항목의 의미상 대응은 판정하지 않는다.
- C9: verification/qa의 사용자 승인 아래 H3 `완료 구분`을 확인한다.
  awaiting_approval/completed에는 정확히 하나, 허용 키워드 하나와 다음 줄부터 비어 있지 않은 설명이 필요하다.
  in_progress/hold는 영역/값의 미작성 또는 `미정`을 허용한다.
  값이 있으면 키워드/설명 형식을 검사하며 인라인 코드로 감싼 키워드도 허용한다.
  현행 값은 all_passed/handoff, 기존은 all_passed 및 verification의 qa_handoff 또는 QA의 next_cycle_handoff다.
  현행 단일 플로우의 마지막 QA 및 명시적으로 전체 완료를 제출하는 QA는 handoff를 사용할 수 없다.

C8의 시각은 `YYYY-MM-DD HH:mm:ss (KST)`이며 날짜와 00-23시/00-59분/00-59초 범위를 확인한다.
기존 목록/항목 시각의 문장 끝 마침표 하나는 제거하고 읽는다.
현재 시각과 비교하거나 실제 조회, 사용자 확인 및 과거 기록의 변조 여부를 판정하지 않는다.

### C10-C14: 번들, 참조, 도식, 리뷰와 보류

- C10: 기본 5단계 작업의 공통 design `단계 결과` 아래 H3 `작업 묶음표`를 검사한다.
  번들 report/디렉토리가 있거나 표 영역을 실제 작성한 경우 적용한다.
  현행/기존 필수 열은 [번들 규격](work-bundles.md#작업-묶음표의-기록-형식)과 [기존 규격](legacy-records.md)을 따른다.
  필수 열 중복/누락, 빈 셀, 묶음 이름/ID 중복과 시작한 번들의 미등록을 위반으로 판정한다.
  현행 디렉토리는 양수 순번을 최소 두 자리로 채운 뒤 `-`와 `[a-z][a-z0-9-]*`를 붙인다.
  100 이상 확장하며 불필요한 선행 0, 같은 순번 중복은 허용하지 않는다.
  `미시작`인 디렉토리/결과 셀과 아직 없는 후속 단계는 허용한다.
  결과에 실제 링크를 적었으면 같은 번들의 implementation/verification/qa여야 한다.
  번들 적용 후 루트에 현재 implementation/verification/qa를 섞으면 위반이다.
  과거 superseded 결과는 현재 표 등록을 소급 요구하지 않는다.
  필수 공통 design/정형 표가 없으면 위반이며 읽을 수 없는 옛 비정형 표는 판정 오류로 구분한다.
- C11: 선택 manifest 항목, 대상 현재 report/설계 상세, 대상 리뷰/보류 문서의 로컬 링크와 이미지를 검사한다.
  참조형 링크를 포함하며 코드/주석/인용과 HTML href/src는 검사하지 않는다.
  문서 상대 위치로 경로를 해석하고 `/` 시작은 파일시스템 절대 경로다.
  URL 경로/절은 퍼센트 인코딩을 한 번 해제하며 잘못된 인코딩/NUL은 위반이다.
  외부 URI는 미적용으로 반환하고 접근하지 않는다. 쿼리 자체의 의미는 검사하지 않는다.
  명시적 로컬 대상 부재는 위반이고 접근/읽기 불가는 오류다.
  설계 상세는 같은 위치의 `<report stem>/<그룹명>.md`에 있어야 하며 실제 링크를 통해 연결한다.
  현재 상세 파일은 검사하되 일반 코드/근거 링크를 설계 상세로 추정하지 않는다.
- C12: `text ascii-flow`로 표시한 fenced block만 검사한다.
  파서 기준의 닫는 구분자 존재, 탭/제어문자 부재를 확인한다.
  줄바꿈과 한글 설명은 허용하며 Unicode U+2500-25FF, 이름에 ARROW가 있는 비ASCII 문자,
  U+2013/U+2014와 전각 `+ - | < >`는 금지 기호로 판정한다.
  일반 코드나 표시 없는 옛 도식은 추정하여 검사하지 않는다.
  정렬, 뷰어 글꼴과 의미 일치는 검사하지 않는다.
- C13: 지정 리뷰의 이름은 `<대상 report stem>-review-N.md`이며 N은 C3의 양수 번호 형식이다.
  대상 report와 같은 디렉토리여야 하고 `검토 대상:`의 정확한 상대 경로가 지정 report와 일치해야 한다.
  검토자/모델명/버전의 값과 리뷰 템플릿의 H2 영역 존재를 확인한다.
  상단 목록의 `검토자:`, `모델명/버전:`, `검토 대상:`은 각각 한 번 읽는다.
  대상 경로는 일반 텍스트/인라인 코드 또는 Markdown 링크의 목적지로 읽고 실제 파일과 대조한다.
  모델의 `확인 불가`는 허용한다. 실제 신원/모델/검토 충분함은 판정하지 않는다.
  리뷰 파일 부재를 이유로 리뷰를 새로 만들거나 다른 리뷰를 대신 선택하지 않는다.
- C14: 현재 보류 파일은 작업 루트의 `deferred/<이름>.md`이며
  보류 템플릿의 H2 4개와 각 영역의 비어 있지 않은 본문을 확인한다.
  deferred 아래 하위 디렉토리나 Markdown이 아닌 항목은 배치 위반으로 보고하며 무시하지 않는다.
  진행 중 파일 존재 자체는 위반이 아니다.
  전체 완료 검사에서는 deferred 경로가 없어야 참이며 빈 디렉토리/일반 파일/끊어진 링크도 잔존으로 판정한다.
  경로 부재만으로 지정 목적지 보존이나 인계 해소를 증명하지 않는다.

C11의 Markdown 절은 제목 텍스트를 소문자로 바꾸고 앞뒤 공백을 제거한 뒤 ASCII 공백을 `-`로 바꾼다.
Unicode 문자/결합문자/숫자 및 `-`, `_`를 남기고 다른 문자는 제거한다.
중복 이름은 문서 순서대로 `-1`, `-2`를 붙이며 이미 사용된 식별자와 충돌하면 다음 번호를 사용한다.
주석/코드 밖의 명시적 HTML id 및 a name도 인정한다.
비Markdown 대상의 절은 판정 오류다. 이 계약은 모든 뷰어의 앵커 동작을 보증하지 않는다.

## 실행기별 검사 범위

### 첫 저장 전

`check_task_start.py`는 C1과 선택 manifest에 같은 작업 등록이 이미 있는지만 읽는다.
없어도 정상인 topic/manifest/report를 생성하지 않는다.
이미 등록된 작업이나 단계 report가 있는 경로는 신규 첫 저장 대상이 아니므로 위반을 반환한다.
실제 신규/재개 판단은 에이전트가 수행하며 검사기가 다른 실행기로 전환하지 않는다.

### 재개와 단계 진입 전

`check_stage_entry.py`는 선택 작업의 C2-C5와 지정 범위의 현재 report,
명시한 base-report 및 필요한 공통 설계의 C6-C11을 검사한다.
다른 번들은 표/등록/참조 대조에 필요한 메타데이터만 읽고 본문 전체를 검사하지 않는다.
대상 단계 report가 아직 없어도 필요한 선행 report가 있으면 검사할 수 있다.
미생성 신규 번들 디렉토리도 허용하며 이때 현행 묶음표의 `미시작` 행을 이름 유사성으로 매핑하지 않는다.
생성 후 등록 일치는 제출 검사에서 확인한다.

명시한 선행 입력은 그 범위/단계의 올바른 선행 report이며 completed여야 한다.
공통 discussion의 `none`에는 선행 파일의 존재/상태/본문 검사를 적용하지 않는다.
대상 현재 report가 in_progress/in_review/awaiting_approval이면 기록된 base_on과 같아야 한다.
hold에서 재개할 때의 새 선행 후보는 별도로 검사하고 과거 hold의 base_on을 자동 수정하지 않는다.
completed 결과를 조회/회귀 검토하는 경우에는 기존 보존 예외를 유지하되 새 진행용 선행 입력은 별도로 확인한다.
이 검사의 통과는 hold 해제, 재승인이나 단계 시작 승인이 아니다.

### 저장 후 검토 및 승인 전

`check_report_submission.py`는 지정 현재 report에 C2-C12를 적용하고,
작업 루트 deferred에 파일이 있으면 C14의 형식과 C11을 함께 검사한다.
지정 파일이 superseded 또는 같은 범위의 현재 개정이 아니면 제출 대상 위반이다.
연결된 선행 report는 메타데이터와 참조를 확인하고 해당 본문을 무조건 다시 검사하지 않는다.
공통 묶음표 및 명시한 상세의 영향 범위를 확인하며 다른 번들 전체의 본문 검사를 강제하지 않는다.
논의 중 저장된 in_progress의 미체크/미정 완료 구분은 해당 상태의 허용 조건을 유지한다.

### 리뷰 수신 후

`check_review_receipt.py`는 지정 원본과 리뷰의 위치/식별을 확인하고 리뷰에 C13/C11을 적용한다.
과거 report를 대상으로 지정한 리뷰의 수신 자체도 금지하지 않는다.
현재 결과의 근거로 사용할 수 있는지는 에이전트가 실제 검토 범위를 대조한다.
다른 리뷰와 원본 본문의 단계 완료 조건을 함께 검사하지 않는다.

### 전체 완료 전

`check_task_completion.py`는 선택 작업의 현재 report 전체에 C2-C12를 적용하고 C14의 정리 상태를 검사한다.
현재 report를 대상으로 한 실제 리뷰는 C13/C11로 확인하며 리뷰가 없는 경우는 미적용이다.
과거 superseded report의 리뷰 본문에 현재 형식을 소급 강제하지 않는다.
단일 플로우는 stages의 report가 모두 있어야 한다.
번들은 공통 discussion/design과 등록된 각 번들의 implementation/verification/qa가 있어야 하며,
별도 번들 design은 실제 존재할 때만 필수 검사에 포함한다.
미시작 번들 행은 전체 완료 시에는 미완료 범위이므로 위반이다.

qa-report는 해당 범위의 현재 QA여야 하고 hold/superseded일 수 없다.
그 QA 이외의 모든 현재 단계 report는 completed여야 한다.
마지막 QA는 제출 전 in_progress/awaiting_approval 또는 승인 후 completed를 허용한다.
완료 구분은 제출 전이라도 키워드와 설명을 요구하며 현행은 all_passed여야 한다.
기존 마지막 QA의 next_cycle_handoff는 당시 기록으로 허용하고 보류 정리 조건은 유지한다.
기존 또는 앞선 번들의 handoff 기록을 전체 테스트 통과로 해석하지 않는다.
인계의 의미상 해소, 보류 자료 보존과 전체 완료 승인은 별도 대조하며 이 도구는 정형 조건만 반환한다.

## 출력과 종료 코드

기본은 텍스트, `--json`은 표준 출력에 JSON 객체 하나를 반환한다.
두 형식의 결과와 종료 코드는 같아야 한다.
정상적인 입력 오류/검사 결과에 traceback이나 라이브러리 로그를 섞지 않는다.
Python 자체가 시작하지 못하거나 프로세스가 강제 종료된 경우 JSON 반환은 보장하지 않으며 호출자는 미실행/실행 오류로 구분한다.
실행 파일의 진입 코드가 시작된 뒤 필수 내부 모듈이나 파서 패키지를 불러오지 못한 경우는 실행 오류다.
첫 공통 모듈을 불러오는 시점도 포함하며 종료 2와 아래 결과 구조를 반환한다.
`--json`이면 traceback 대신 JSON 객체 하나를 출력하고, 읽지 않은 파일이나 확인하지 못한 버전은 추정하지 않는다.
내부 모듈 로딩 실패를 Python 자체가 시작하지 못한 경우로 취급하지 않는다.

| 종료 코드 | 의미 |
| --- | --- |
| 0 | 적용된 모든 검사가 참이고 필요한 범위에 오류가 없음 |
| 1 | 하나 이상의 검사 결과가 거짓이며 오류는 없음 |
| 2 | 입력/의존성/읽기/파싱 후 종속 검사 불가 등 오류가 있음. 이미 확인한 거짓도 함께 반환 |

### 위반과 종속 판정 오류의 구분

읽은 자료로 필수 형식이나 값의 불충족을 확정할 수 있으면 fail이다.
대상 선택, 단계 순서, 상태별 적용 조건이나 선행 연결을 해석할 필수 정보가 없어
적용할 검사를 결정하거나 수행할 수 없으면 해당 종속 항목은 error다.
상위 규칙의 fail만으로 모든 후속 항목을 일괄 error로 바꾸지 않으며,
반대로 종속 판정이 불가능한데 fail 하나만 반환하여 검사를 마친 것으로 처리하지 않는다.

| 확인한 상태 | 항목별 판정과 전체 종료 코드 |
| --- | --- |
| 작업 H2가 없거나 여러 개 | C2 등록 fail과 작업 선택 error, 종료 2 |
| stages 누락/중복/타입/목록 위반 | C2 fail과 단계 관계 판정 error, 종료 2. 미지원 단계도 error |
| reference_reports만 누락/중복/형식 위반이고 작업과 stages는 해석 가능 | C2 fail, 다른 오류가 없으면 종료 1 |
| 프론트매터 부재/파싱 불가/매핑 아님/중복 키 | C4 fail과 메타데이터 종속 판정 error, 종료 2 |
| status 누락/타입/허용값 위반 또는 base_on 누락/타입 위반 | C4 fail. 상태별 본문 또는 선행 연결을 검사해야 하면 종속 error도 반환하여 종료 2 |
| 금지 필드 또는 design 이외 현행 in_review | C4 fail. 상태와 선행 값을 해석할 수 있고 다른 오류가 없으면 종료 1 |
| 필수 본문 제목 누락/중복/잘못된 부모 | C6 fail. 해당 영역의 부재/비유일성으로 필수 내용 조건 불충족을 확정할 수 있으면 관련 내용 검사도 fail이며, 별도 판정 오류가 없으면 종료 1 |

CLI로 지정한 파일의 부재/범위 불일치는 입력 오류 2다.
문서 내부의 필수 참조 대상 부재는 해당 연결 규칙의 fail이며,
그 자료에 의존하는 별도 필수 검사까지 수행할 수 없다면 해당 error를 함께 보존한다.
리뷰의 같은 디렉토리 조건도 CLI 입력 경계와 수집된 리뷰의 C13 내용 검사에서 각각 적용한다.
전체 종료 코드는 아래 오류 우선 집계로 결정하며 한 규칙의 fail만 보고 1로 고정하지 않는다.

### 결과 구조와 집계

JSON의 필수 구조는 다음과 같다. 아래는 타입 선언이며 실제 실행 결과가 아니다.

```text
Result = {
  contract_version: 1,
  checker: string,                  # 실행기 파일 stem
  inputs: object,                   # 전달된 명시적 인자. 출력 옵션 제외
  runtime: {python: string, packages: object},
  outcome: "pass" | "fail" | "error",
  exit_code: 0 | 1 | 2,
  files_read: [string],             # 실제 읽은 파일의 절대 실경로
  items: [{
    id: string,                    # 안정적인 C번호.조건명 또는 input/runtime 오류 ID
    path: string | null,
    line: integer | null,          # 1부터 시작하는 원문 줄, 특정할 수 없으면 null
    status: "pass" | "fail" | "error" | "not_applicable",
    value: boolean | null,         # pass=true, fail=false, 나머지는 null
    reason: string                 # 해당 대상의 조건 및 실패/오류/미적용 이유
  }],
  counts: {pass: integer, fail: integer, error: integer, not_applicable: integer}
}
```

inputs는 옵션 이름의 하이픈을 밑줄로 바꾼 키와 전달받은 문자열 값을 사용한다.
runtime.packages는 패키지 이름과 설치 버전 문자열의 매핑이며 읽지 못한 버전은 null이다.
텍스트 출력도 실행기/입력/범위, 항목별 ID/위치/상태/이유, 집계와 종료 코드를 포함한다.
items는 ID, 경로, 줄, 이유 순으로 정렬한다.
문자열은 Unicode 코드 포인트 순, 줄은 숫자순이며 null은 값이 있는 항목보다 먼저 둔다.
files_read는 중복을 제거하고 경로순으로 정렬한다.
counts는 실제 items와 일치해야 한다.
미적용은 검사 대상 없음/상태별 비적용처럼 계약이 허용한 경우에만 사용한다.
적용 대상을 읽지 못하거나 해석할 수 없는 경우에는 error다.
필수 입력 오류이면 의존 검사를 중단하고 오류를 반환한다.
개별 파일 오류 이후 독립적으로 확인할 수 있는 항목은 계속 검사하되 종속 항목을 통과로 만들지 않는다.
판정 순서는 error > fail > pass이며 미적용은 통과 수에 포함하지 않는다.
설명 문구의 의미나 로그의 길이로 종료 코드를 결정하지 않는다.

## 검증 기준

다음은 계약 준수를 확인할 입력과 기대 결과다. 실제 실행 결과와 구분한다.

| 대상 | 참/정상 입력 사례 | 거짓/오류/예외 사례 |
| --- | --- | --- |
| 5개 CLI | 독립 호출, 공백/한글 경로, 다른 cwd, 텍스트/JSON 같은 판정 | 필수/중복/알 수 없는 인자, 상대 경로, 잘못된 범위, 의존성/읽기 오류 |
| 첫 저장 | 아직 없는 정상 주제 경로 | 경로 이탈, 일반 파일 충돌, 이미 report가 있는 작업. 어떤 경우에도 생성하지 않음 |
| 개정/메타데이터 | 현행/기존 각각의 정상 개정, 보존된 superseded | 신구 혼재, 중복 개정, 잘못된 YAML/타입/상태. 과거 본문은 재강제하지 않음 |
| 진입 | 유효한 명시적 선행 입력, 없는 새 단계/번들, 공통/번들 연결 | 다른 작업/번들/단계, 새 입력으로 hold/superseded. 과거 완료 보존 예외와 구별 |
| 제출 | 현재 in_progress와 승인 대기/completed 각각의 허용 형식 | 현재 근거 없이 과거 근거만 존재, 잘못된 시각/중복 묶음, 키워드만 있는 완료 구분 |
| 번들 | 미시작 행과 시작한 번들 및 같은 범위 결과 링크 | 누락 열/등록/번호 충돌/다른 번들 결과, 루트 산출물 혼재 |
| 참조/도식 | 정상 상대/절 링크, 주석/코드 예시 제외, 한글 도식 설명 | 깨진 경로/절, 접근 오류, 탭/금지 기호/닫히지 않은 표시 도식 |
| 리뷰/보류 | 정확한 원본/리뷰, 확인 불가 모델, 작성 중 보류 | 다른 원본, 잘못된 배치/필수 영역. 리뷰 부재를 필수 생성으로 처리하지 않음 |
| 전체 완료 | 마지막 QA 제출 전과 승인 후, 앞선 번들의 과거 handoff 보존 | 미완료 앞선 report, 미시작 번들, 현행 마지막 QA handoff, 빈/비어 있지 않은 deferred 잔존 |
| 비변경성과 재현성 | 같은 입력/자료/버전의 반복 판정과 정렬 일치 | 입력 파일/디렉토리/상태 변경, 로그/캐시/자동 설치 발생 금지. 전체 완료 승인을 출력하지 않음 |

각 검사는 정상 사례와 해당 조건만 바꾼 위반 사례를 대조한다.
계약으로 판정할 수 없는 의미/승인 항목을 검사에 추가하지 않는다.
계약의 충돌/누락을 발견하면 관련 지침과 근거를 대조하여 사용자와 확인하고 계약을 먼저 갱신한다.
임의의 판정 규칙을 코드에만 추가하지 않는다.
